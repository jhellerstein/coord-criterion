\section{Commitment Bases for Two-Phase Locking and Multiversion Timestamp Ordering}
\label{app:cc-bases}

This appendix gives the serializability specification of
Sections~\ref{sec:ambiguity-story} and~\ref{sec:systems} in full, and the
commitment bases of two-phase locking (2PL) and multiversion timestamp ordering
(MVTO).  Schedulers report results while transactions are still running, such
as a read result before its reader commits, so an output may leave
transactions undecided.

\paragraph{Specification.}
An input is a finite set of transactions, each listing the keys it reads and
the keys it writes; inputs are ordered by inclusion.  An output has three
parts: the committed transactions, in a serial order; the aborted
transactions; and the read results reported so far.  A read result says which
version a read of a key returned: the write of that key by some transaction, or
the initial version.  A transaction that is neither committed nor aborted is
\emph{undecided}, and its reads may already be reported.  One output \outrel
another when it extends all three parts.

An output is \emph{complete} at an input when it commits or aborts every
transaction of the input, and not both.  A complete output is permitted when
each reported read returns the initial version or a write by a transaction of
the input, and each read of a key $x$ by a committed transaction $T$ returns
the write of $x$ by the last transaction before $T$ in the serial order that
writes $x$, or the initial version if none does; reads by aborted transactions
are otherwise unconstrained.  Any output is permitted when some permitted
complete output \outrel it, that is, when it can still be completed.  The
figures of Sections~\ref{sec:ambiguity-story}--\ref{sec:systems} show only
complete outputs without aborts or read results, as serial orders.

We write an output as $(L,X,\rho)$: $X$ is the set of aborted transactions, $L$
is the serial order, a total order on the set $\mathrm{dom}\,L$ of committed
ones, and $\rho$ is the set of reported read results.  Then
\[
  \begin{aligned}
  (L,X,\rho)\OutputOrd(L',X',\rho')
  \iff{}& X\subseteq X',\ \ \mathrm{dom}\,L\subseteq\mathrm{dom}\,L',\\
         & L'|_{\mathrm{dom}\,L}=L,\ \ \rho\subseteq\rho'.
  \end{aligned}
\]
Every input has a permitted row: the one that aborts every transaction and
reports nothing.  The rows $(\{A,B\},([A,B],\varnothing,\varnothing))$ and
$(\{A,B\},([B,A],\varnothing,\varnothing))$ of
Figure~\ref{fig:ambiguity-frames}(f) have no common \outnoun, which would order
$A$ both before and after $B$, so the specification is not monotone.  The
\emph{abort-free} specification permits a row when it can be completed with
$X=\varnothing$; the same two rows show that it is not monotone either.

\paragraph{Commitments.}
Each commitment is a condition on complete outputs.  Applied at a state
$(i,R)$, it keeps the rows of $R$ that can still be completed, within $R$, by a
complete row meeting the condition, and removes the rest.  It is defined when
it keeps some row at $i$ and removes some row.
\begin{itemize}
  \item $\mathsf{order}(A,B)$, for distinct $A,B\in i$: $B$ is not committed
        before $A$, that is, not $B<_L A$.
  \item $\mathsf{commit}(A)$, for $A\in i$: $A\notin X$.\quad
        $\mathsf{abort}(A)$, for $A\in i$: $A\notin\mathrm{dom}\,L$.
  \item $\mathsf{stamp}(A)$, for $A\in i\setminus Z$, given the set $Z\subseteq
        i$ of transactions stamped before $A$: no committed transaction outside
        $Z\cup\{A\}$ precedes $A$ in $L$, and no committed transaction of $Z$
        follows $A$.
  \item $\mathsf{read}(A,x,v)$, for $A\in i$: the output reports that $A$'s
        read of $x$ returned the version $v$.
\end{itemize}
Each is a commitment (Definition~\ref{def:commitment}).  If a kept row \outrel
another row at the same input, the complete row that keeps it also
\outrel the other, which is therefore kept; so no removed row is \outrelpast by
a kept one, as Equation~\ref{eq:commitment-excludes} requires.  The first four
conditions concern only $L$ and $X$, and for them a complete row is kept
exactly when it satisfies the condition, since two permitted complete outputs
at one input, one \outrelpart the other, have the same serial order and abort
set.

The bases are
$\mathcal B_{\mathrm{2PL}}=\{\mathsf{order},\mathsf{commit},\mathsf{abort},\mathsf{read}\}$
and
$\mathcal B_{\mathrm{MVTO}}=\{\mathsf{stamp},\mathsf{commit},\mathsf{abort},\mathsf{read}\}$,
over all transactions, keys, and versions.  They share $\mathsf{commit}$,
$\mathsf{abort}$, and $\mathsf{read}$, and differ in how they order: at the
canonical state of three transactions $\{A,B,C\}$, no commitment of
$\mathcal B_{\mathrm{MVTO}}$ has the effect of $\mathsf{order}(A,B)$, and no
commitment of $\mathcal B_{\mathrm{2PL}}$ has the effect of $\mathsf{stamp}(B)$
with $Z=\varnothing$.

A scheduler applies commitments within the sequence $\gamma$ of an output
event $\Out{\gamma}{o}$ (Definition~\ref{def:system-output-event}); the
protocol steps below say which.  In every state that a run under either basis
reaches, each row has a complete \outnoun in the table at its input, and any
output between two rows of the table at one input is itself a row of the
table.  So a read is reported by applying $\mathsf{read}(A,x,v)$ and then
emitting the result, which is then exposable.

\paragraph{2PL.}
When $B$ waits for a lock that $A$ holds in a conflicting mode, the scheduler
applies $\mathsf{order}(A,B)$.  On complete rows without aborts it keeps
exactly those with $A$ before $B$ (Figure~\ref{fig:cc-commitments}(h)).  At the
canonical state of $\{A,B,C\}$ it removes $[B,A,C]$ and keeps $[A,B,C]$ and
$[C,A,B]$, so it is a choice, and it is not the choice $c_o$ of any output $o$.
When a transaction reads, the scheduler applies $\mathsf{read}$; when it
commits, $\mathsf{commit}$.

A deadlock between $A$ and $B$ means that $\mathsf{order}(A,B)$ and later
$\mathsf{order}(B,A)$ have both been applied.  Then no remaining row, at any
input, commits both $A$ and $B$, so every remaining complete row aborts one of
them, and resolving the deadlock means aborting one.  Once the scheduler
applies $\mathsf{commit}(A)$, every remaining complete row aborts $B$, and
$\mathsf{commit}(B)$ is never again defined.  Under the abort-free
specification, once $\mathsf{order}(A,B)$ is applied, $\mathsf{order}(B,A)$ is
undefined at every later state: $A$, and hence $B$, waits forever.  Whether a
deadlock can be resolved thus depends on which of the two specifications the
system implements.

\paragraph{MVTO.}
We follow Bernstein and Goodman~\cite{bernstein1981concurrency}.  An arriving
transaction $A$ receives a timestamp above all issued ones, and the scheduler
applies $\mathsf{stamp}(A)$, with $Z$ the transactions stamped before $A$.  On
complete rows without aborts, $\mathsf{stamp}(B)$ with $Z=\varnothing$ keeps
exactly those with $B$ first (Figure~\ref{fig:cc-commitments}(i)); at the
canonical state of $\{A,B,C\}$ it is a choice, and it is not the choice $c_o$
of any output.  A read of $x$ by $A$ returns the committed version of $x$ with
the largest timestamp below $A$'s, and the scheduler applies $\mathsf{read}$.
A write of $x$ by $A$ is rejected, and $A$ aborted, when a transaction stamped
after $A$ has already read a version of $x$ stamped before $A$; otherwise the
scheduler applies $\mathsf{commit}(A)$ when $A$ commits.

\emph{What a read commits to.}  Suppose $A$ writes $x$, $B$ is stamped after
$A$, and $B$'s read of $x$ returned the initial version or the write of $x$ by
a transaction stamped before $A$.  A complete row that satisfies both stamps
and commits both $A$ and $B$ places $A$ between that version and $B$, so it
does not permit the read.  Hence, after the two stamps, no row reporting the
read commits both $A$ and $B$, and once $\mathsf{read}$ has been applied, no
remaining row commits both, whether it reports the read or not.  Reporting the
read commits to this: $A$ and $B$ do not both commit.  The condition on the
version is needed.  At input $\{A,W,B\}$, stamped in that order, with $A$ and
$W$ writing $x$, the complete row that commits all three in stamp order and
reports that $B$ read $W$'s write is permitted and satisfies every stamp.

\emph{When the abort is entailed.}  Which of $A$ and $B$ aborts depends on
whether $B$ is decided.  If every remaining complete row commits $B$, for
instance after $\mathsf{commit}(B)$, then every remaining complete row aborts
$A$.  Emitting $A$'s abort, added to a row that reports the read and that every
remaining row \outrel, is then exposable: the specification entails the abort.
While $B$ is undecided, it does not.  At input $\{A,B\}$, with $A$ writing $x$,
$B$ reading it, and further transactions free to arrive, apply
$\mathsf{stamp}(A)$ and $\mathsf{stamp}(B)$, and report that $B$ read the
initial version of $x$.  Reporting the read is not exposable on its own, since
the row that commits $A$ and then $B$ cannot be completed with it; the output
event that applies $\mathsf{read}$ and then reports the read is legal under
$\mathcal B_{\mathrm{MVTO}}$.  Two completions remain: $B$ committed with $A$
aborted, and $A$ committed with $B$ aborted.  Emitting $A$'s abort is not
exposable, and $\mathsf{abort}(A)$ and $\mathsf{abort}(B)$ are both defined and
keep different completions.  After $\mathsf{commit}(B)$, $A$'s abort becomes
exposable.  MVTO's write rule aborts $A$ without waiting for $B$ to commit,
since it records reads when they execute.  That abort is the scheduler's
choice, made by $\mathsf{abort}(A)$, between two outcomes the specification
still permits.

\paragraph{Comparison.}
2PL commits relative orders, only between conflicting transactions; MVTO
commits each transaction's position against all present and future ones on
arrival.  Both report reads through $\mathsf{read}$.  Under MVTO, a later
transaction's read of an older version commits that the writer and the reader
do not both commit; the write rule settles this at once by aborting the writer,
and the specification forces that abort only after the reader commits.
