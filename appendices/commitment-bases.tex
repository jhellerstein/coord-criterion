\section{Commitment Bases for Two-Phase Locking and Multiversion Timestamp Ordering}
\label{app:cc-bases}

This appendix gives the specification of Section~\ref{sec:ambiguity-story} and
the commitment bases of 2PL and MVTO.

\paragraph{Specification.}
An input is a finite set $\mathcal T$ of transactions, ordered by inclusion.  An output
is a pair $(L,X)$ with $X$ a set of aborted transactions and $L$ a total order
(the serialization order) on a set $\mathrm{dom}\,L$ of committed ones, ordered
by
\[
  (L,X)\OutputOrd(L',X')
  \;\Longleftrightarrow\;
  X\subseteq X',\ \ \mathrm{dom}\,L\subseteq\mathrm{dom}\,L',\ \
  L'|_{\mathrm{dom}\,L}=L.
\]
A row $(\mathcal T,(L,X))$ is permitted when $X$ and $\mathrm{dom}\,L$ partition
$\mathcal T$.
The rows $(\{A,B\},([A,B],\varnothing))$ and $(\{A,B\},([B,A],\varnothing))$,
corresponding to Figure~\ref{fig:ambiguity-frames}(f), have no common \outnoun, so the
specification is not monotone.  The \emph{abort-free} specification has the
same rows with $X=\varnothing$.

\paragraph{Commitments.}
Each commitment below, applied at a state $(i,R)$, retains the rows of $R$ that
satisfy a condition, and is defined when some row of $R$ at $i$ satisfies it
and some row of $R$ fails it.
\begin{itemize}
  \item $\mathsf{order}(A,B)$, for distinct $A,B\in i$: $A\in X$, or $B\in X$,
        or $A<_L B$.
  \item $\mathsf{commit}(A)$, for $A\in i$: $A\notin X$.\quad
        $\mathsf{abort}(A)$, for $A\in i$: $A\in X$.
  \item $\mathsf{stamp}(A)$, for $A\in i\setminus Z$, given $Z\subseteq i$, the transactions stamped
        before $A$: at row $(k,(L,X))$, for every $z\in Z$, $z<_L A$ or one of
        $z,A$ is in $X$; and for every $D\in k\setminus(Z\cup\{A\})$, $A<_L D$
        or one of $A,D$ is in $X$.
\end{itemize}
Each is a commitment (Definition~\ref{def:commitment}): at a fixed input $k$,
if $(L,X)\OutputOrd(L',X')$ for permitted outputs then $X\subseteq X'$ and
$\mathrm{dom}\,L\subseteq\mathrm{dom}\,L'$ with both pairs partitioning $k$, so
$X=X'$ and $\mathrm{dom}\,L=\mathrm{dom}\,L'$, hence $L=L'|_{\mathrm{dom}\,L}=L'$.
A removed and a retained row therefore differ, so neither \outrel the other,
and Equation~\ref{eq:commitment-excludes} holds.
The bases are
$\mathcal B_{\mathrm{2PL}}=\{\mathsf{order},\mathsf{commit},\mathsf{abort}\}$
and
$\mathcal B_{\mathrm{MVTO}}=\{\mathsf{stamp},\mathsf{commit},\mathsf{abort}\}$,
ranging over all transactions.

\paragraph{2PL.}
The scheduler applies these commitments within the sequence $\gamma$ of the
output event $\Out{\gamma}{o}$ that emits the outcome
(Definition~\ref{def:system-output-event}); the protocol steps below say which
commitments $\gamma$ contains.  When $B$ waits for a lock that $A$ holds in a conflicting mode, the scheduler
applies $\mathsf{order}(A,B)$ (Figure~\ref{fig:cc-commitments}(h)); when $A$
commits, it applies $\mathsf{commit}(A)$.  A deadlock between $A$ and $B$ means
both $\mathsf{order}(A,B)$ and $\mathsf{order}(B,A)$ have been applied; the
rows left, at $i$ and every larger input, are exactly those with $A\in X$ or $B\in X$, and resolving the
deadlock is applying $\mathsf{abort}(A)$ or $\mathsf{abort}(B)$.  Under the
abort-free specification, once $\mathsf{order}(A,B)$ is applied no row at $i$
satisfies $\mathsf{order}(B,A)$, so it is undefined: $A$, and hence $B$, waits forever.
Deadlock handling thus corresponds to the choice between the two
specifications.

\paragraph{MVTO.}
On arrival $A$ receives a timestamp above all issued ones, and the scheduler
applies $\mathsf{stamp}(A)$; Figure~\ref{fig:cc-commitments}(i) is
$\mathsf{stamp}(B)$ with $Z=\varnothing$.  Reads add no commitment.  The
scheduler applies $\mathsf{abort}(A)$ when $A$ writes a version that would
directly follow a committed version $v$ already read by a transaction stamped
after $A$, and otherwise applies $\mathsf{commit}(A)$ when $A$ commits.  Because outputs record orders and
aborts but not read results, this specification does not itself require that
abort; one whose outputs include read facts, as in
Section~\ref{sec:hat-instance}, would.

\paragraph{Comparison.}
2PL commits relative orders, only between conflicting transactions; MVTO
commits each transaction's position against all present and future ones on
arrival, and pays with aborts when execution does not match it.  Only complete
outcomes $(L,X)$ are outputs here, so fixing $A$'s status or its relative
position is not itself exposable; Proposition~\ref{prop:exposability} decides
when a complete outcome is.
