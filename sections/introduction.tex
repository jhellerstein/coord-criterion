\section{Introduction}
\label{sec:intro}

Concurrent systems rely on coordination mechanisms ranging from mutexes and
atomic instructions to database locks and distributed consensus protocols.
These mechanisms prevent concurrent actions from producing undesirable
outcomes, but add significant synchronization overheads; when coordination
crosses a network partition, it can also prevent availability.  Avoiding
unnecessary coordination is therefore a central goal in distributed systems and
databases.  This paper asks what coordination mechanisms accomplish at the
specification level, and when that effect is intrinsically required.

The CALM Conjecture
proposed a crisp, bidirectional answer: consistency can be achieved without
coordination exactly when the specification is monotone
~\cite{hellerstein2010declarative}.  Ameloot et al.\ proved it in both
directions, but only for Datalog queries evaluated by relational
transducer networks~\cite{ameloot2013relational,hellerstein2020keeping}. In a related vein, the CAP
Theorem proved that an available linearizable register cannot tolerate a
network partition~\cite{brewer2000towards,gilbert2002cap}.  These results are often
invoked more broadly than the formalisms support: CALM as a general
monotonicity boundary for coordination, CAP as a general constraint on distributed
systems.  The folklore drifted from what the literature proves.

Related results reach similar conclusions from different starting points.  CRDTs
use inflationary updates over join-semilattices to guarantee coordination-free
convergence~\cite{shapiro2011crdt}.  Highly Available Transactions analyze
transaction histories to identify guarantees that remain available under
partition~\cite{bailis2013hat}.  Invariant confluence asks whether independently
reached, invariant-preserving database states can merge safely
~\cite{bailis2014coordination}.  Because these results speak different formal
languages, they do not translate directly.  Does CALM encompass CAP?  Are CRDT
join laws necessary for coordination freedom, or merely one strong sufficient
discipline?  Does convergent storage provide highly available transactions?
Do convergence and transaction availability preserve application invariants?

We develop a unified coordination criterion that spans this space,
including the translation questions above
(\S\ref{sec:cap-corollary}, \S\ref{sec:instances}).  We begin with a minimalist
specification model: a two-column relational schema pairing input values with the
corresponding outputs that are within spec.  The model is purely declarative: it
describes what can be observed about a system, without reference to any
imperative procedure.  The input domain $(I,\InputOrd)$ includes a partial order
describing how input grows; the output domain $(O,\OutputOrd)$ has its own
partial order characterizing when a later output preserves an earlier claim.
State-machine-style specifications can be compiled into this form
(\S\ref{sec:design-boundary}); the table elides operational details that are not
externally observable.  Despite its simplicity, the model captures both general
concurrency and consistency models that span applications---including
linearizability and causal consistency (\S\ref{app:registers})---and
application-specific requirements such as program invariants.  A
specification is \emph{consistent} when the executions it admits are
\emph{confluent}: states reached along different paths can still be brought to
a common state.  This unifies classical definitions of consistency: a specification
limits acceptable outcomes, while confluence asks whether those requirements
can be maintained across concurrent executions.

We begin by focusing on tables with a functional dependency from input to
output (\S\ref{sec:functional-specifications}).  These \emph{functional ordered
specifications} capture arbitrary functions
$ f:(I,\InputOrd)\to(O,\OutputOrd) $.  A function is monotone when
$i\InputOrd j$ implies $f(i)\OutputOrd f(j)$.  Concurrent executions may see
different input refinements, in different orders and batches.  Monotonicity says
that an output exposed via any execution remains valid as more input arrives.  Without
it, the system must make an irrevocable \emph{commitment} that rules out
behavior still within spec.  The framework identifies this need for commitment
as the intrinsic reason to employ operational coordination mechanisms.  For a
functional specification, commitment means sealing off inputs that could lead
to contradictory outputs.

The first result is \emph{Functional CALM}
(\S\ref{sec:functional-calm-theorem}).  It generalizes the CALM result
to arbitrary functions and partial orders, giving a common
language for coordination-freedom results over functional specifications.
This covers both relational query languages and the usual CRDT state interface.
Functional CALM proves that
Consistency is equivalent to monotonicity of the specification.

We extend this result in two independent directions.  The first adds distributed
execution without changing the specification model
(\S\ref{sec:distributed-execution}).  We place one local execution at each
participant in a Lamport history, then project away delivery and strategy
details that do not change the specification state.  \emph{Distributed
Consistency} asks whether the resulting participant states can still be brought
to the same state.

The second extension changes the specification model without requiring
distribution.  We relax the functional dependency and allow one input to have
several possible outputs, as in leader election and transaction ordering.
Standard monotonicity is no longer enough: independently chosen outputs must be
able to grow together without conflict.  We capture this requirement with
\emph{Lifted Monotonicity} (\S\ref{sec:complete-calm-criterion}).  Complete CALM
combines the two extensions, proving that Consistency, Lifted Monotonicity, and
Distributed Consistency are equivalent.  When participants can independently
prepare incompatible outputs, their preparations must be mutually excluded
before both are exposed (\S\ref{sec:complete-calm-theorem}).

Classical CALM tells us when coordination is unnecessary, but not whether a
chosen use of coordination is sufficient.  Complete CALM can answer the second
question because it represents commitments explicitly.  For example, total log
ordering and a key-value store are both non-monotone.  When they are composed
through a shared log order, however, committing that order is sufficient to make
the end-to-end specification monotone and consistent.  The store can then
execute the committed order without making further commitments.  We call this
analysis \emph{Proper Coordination} and formalize it in
Appendix~\ref{app:composition}.

Complete CALM also yields a Complete CAP Theorem
(\S\ref{sec:cap-corollary}).  For any consistency guarantee expressed as a
specification, monotonicity identifies which side of the CAP boundary it
occupies.  A monotone specification can keep its full interface available and
confluent during a partition; a non-monotone one cannot.  Classical
linearizability is one instance on the negative side.

This paper makes six contributions:
\begin{enumerate}
  \item \emph{A common specification model.} Ordered relational tables describe
        permitted input/output behavior; commitments record irrevocable choices
        among that behavior.
  \item \emph{Consistency as confluence.} One definition applies to general
        consistency models and application-specific requirements, with a
        distributed interpretation over Lamport histories.
  \item \emph{Functional CALM.} For arbitrary functions between ordered
        domains, Consistency is equivalent to monotonicity.
  \item \emph{Complete CALM and CAP.} With multiple outputs per input,
        Consistency and Distributed Consistency are equivalent to Lifted
        Monotonicity.  Complete CAP gives the corresponding availability
        boundary under partition.
  \item \emph{Composition and Proper Coordination.} Specifications compose by
        equijoin.  Committing a shared log order can make a non-monotone
        log/store composition consistent without further store commitments
        (Appendix~\ref{app:composition}).
  \item \emph{Coordination-free frontiers.} Two theorems characterize how much
        an interface can promise before coordination becomes necessary
        (Appendix~\ref{sec:frontiers}).
\end{enumerate}

Section~\ref{sec:functional-calm} introduces the framework on an election
and develops Functional CALM.  Section~\ref{sec:distributed-execution} gives
Consistency its distributed reading.  Section~\ref{sec:ambiguous-specifications}
extends the framework to output choice, and Section~\ref{sec:complete-calm}
combines the two extensions in Complete CALM and Complete CAP.
Section~\ref{sec:instances} applies the results to familiar systems, and
Section~\ref{sec:discussion} draws out the design lessons and scope limits.
Appendix~\ref{app:composition} proves the composition and Proper Coordination
results, Appendix~\ref{sec:frontiers} derives maximal coordination-free
interfaces, and Appendix~\ref{app:additional-applications} gives further
classical applications.
