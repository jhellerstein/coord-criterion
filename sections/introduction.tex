\section{Introduction}
\label{sec:intro}

Concurrent systems rely on coordination mechanisms ranging from mutexes and
atomic instructions to database locks and consensus protocols.  These
mechanisms prevent concurrent actions from producing undesirable outcomes.
They also bring costs: overhead, latency, and reduced availability in
distributed settings.  Avoiding unnecessary coordination is therefore a
central goal in distributed systems and databases.  To distinguish necessary
coordination from implementation habit, we first ask what these mechanisms
fundamentally accomplish.

In systems, as in life, possibilities narrow over time.  Some are out of our
hands: the environment moves on, and possibilities are lost.  Others are left
for us to decide.  Incidental decisions close no doors: any possibilities they
remove are carried forward by those that remain.  Fateful decisions make some
outcomes impossible: they exclude a possibility that nothing remaining can
carry forward.  Which specifications can be implemented without fateful
decisions?  We first develop a criterion that answers this question, then
relate any fateful decisions it identifies to coordination across a system's
runs.

The CALM Conjecture
proposed a crisp, bidirectional answer: consistency can be achieved without
coordination exactly when the specification is
monotone~\cite{hellerstein2010declarative}.  Ameloot et al.\ proved it in both
directions, but only for Datalog queries evaluated by relational
transducer networks~\cite{ameloot2013relational,hellerstein2020keeping}.  Gilbert and Lynch proved Brewer's CAP conjecture, but only for linearizable
registers~\cite{brewer2000towards,gilbert2002cap}.  Both results are
invoked far more broadly: CALM as a general rule that monotone programs
need no coordination, CAP as a general constraint on distributed systems.  The folklore outgrew the proofs.

Related results reach similar conclusions from different starting points.
Conflict-free Replicated Data Types (CRDTs) use inflationary updates over
join-semilattices to guarantee coordination-free
convergence~\cite{shapiro2011crdt}.  Highly Available Transactions (HATs)
identify transactional guarantees that remain available under
partition~\cite{bailis2013hat}.  Invariant confluence asks whether
independently reached, invariant-preserving database states can merge
safely~\cite{bailis2014coordination}.  Because these results speak different
formal languages, they do not translate directly.  Does CALM encompass CAP
(\S\ref{sec:complete-cap})?  Are CRDT join laws necessary, or merely one
sufficient discipline for coordination avoidance
(\S\ref{sec:crdt-instance})?  Why do some transactional guarantees
stay available under partition while others do not
(\S\ref{sec:hat-instance})?  Is invariant confluence a different test from
CALM's (\S\ref{sec:iconfluence-instance})?

We answer such questions with a single criterion.  Our foundation is a minimalist
  specification model: a \emph{table of possibilities} pairing input values
  with corresponding outputs that are within spec.  The model is purely declarative: it
describes what can be observed about a system, without fixing a language, protocol or placement.  The input domain $(I,\InputOrd)$ carries a partial order saying when one input
\inrel another; the output domain $(O,\OutputOrd)$ has a partial order:
$o\OutputOrd u$ means that $u$ \outrel $o$, carrying $o$ forward by preserving
every claim it made.
State-machine-style specifications can be compiled into this form via standard techniques
in formal verification,
eliding operational details that are not externally observable (\S\ref{sec:operational-models}).

Simplicity makes the model general: it captures
not only application invariants but also general-purpose consistency definitions
such as linearizability, causal consistency (Appendix~\ref{app:registers})
and transactional isolation levels (\S\ref{sec:hat-instance}, Appendix~\ref{app:cc-bases}).
A specification is \emph{consistent} when the executions it admits are
\emph{confluent}: states reached along different paths can be brought to
a common state.

Our first result, \emph{Functional CALM}
(\S\ref{sec:functional-calm-theorem}), covers specifications that pair each
input with one output.  It proves that consistency is equivalent to
monotonicity: \(i\InputOrd j\) implies \(f(i)\OutputOrd f(j)\), so the output at
\(j\) \outrel any output emitted at \(i\).  The mnemonic is: \emph{Whenever we
learn, our answers refine.}  If monotonicity fails, some output requires an
input exclusion, ruling out later input that could contradict it.  The result
covers relational query languages and the usual CRDT state specification.

The functional case imposes a functional dependency on the table of
possibilities, $\mathrm{in}\to\mathrm{out}$: each input permits one output.
Specifications like leader election and transaction ordering drop that
dependency, so the table may contain several rows with the same input.  Their
criterion also needs Directed Outputs: whatever outputs are chosen among rows
sharing an input must have a common \outnoun.  Together, the conditions are
\emph{Lifted Monotonicity}, with two maxims: \emph{Whenever we learn, our
answers refine; whatever we choose, our answers align.}  \emph{Complete CALM}
proves that consistency is equivalent to Lifted Monotonicity
(\S\ref{sec:complete-calm-theorem}).

Section~\ref{sec:distributed-execution} models distributed execution with participants
exchanging messages and defines consistency over their histories; this is shown
to be equivalent to consistency as defined above, so Functional and Complete
CALM apply to distributed executions unchanged.  An exclusion \emph{requires coordination} when another run could contradict it,
by accepting an input its input exclusion ruled out or emitting an output it excluded, and
\emph{distributed coordination} when that run is at another participant.

Complete CALM leads to \emph{Complete CAP} (\S\ref{sec:complete-cap}).  Given a
consistency guarantee expressed as a specification, Lifted Monotonicity says
which side of CAP it falls on.  A specification with Lifted Monotonicity can keep every output it permits
available and confluent during a partition; any other cannot. The Gilbert--Lynch theorem for linearizable
registers follows directly.

This paper makes five contributions:
\begin{enumerate}
  \item \emph{Ordered relational specifications.} Tables over ordered input and
        output domains describe permitted behavior; exclusions remove input or output possibilities.
  \item \emph{Consistency as confluence.} One definition covers general
        consistency models and application-specific requirements, and it is
        equivalent to distributed consistency.
  \item \emph{Functional CALM.} For functions between ordered domains,
        consistency is equivalent to monotonicity.
  \item \emph{Complete CALM and CAP.} In general, consistency is equivalent
        to Lifted Monotonicity, and Complete CAP gives the matching
        availability boundary under partition for any declared set of outputs
        that must stay available.
  \item \emph{Composition and Proper Coordination.} Specifications
        compose by equijoin, and we show that in a composition, upstream
        stages can free downstream stages from issuing exclusions (\S\ref{sec:composition}).
\end{enumerate}

Section~\ref{sec:functional-calm} introduces the framework on an election and
proves Functional CALM; Section~\ref{sec:complete-calm} generalizes it to
ambiguous specifications and proves Complete CALM;
Section~\ref{sec:distributed-execution} gives the distributed reading, defines
coordination, and proves Complete CAP.  Section~\ref{sec:composition}
composes specifications and characterizes proper coordination.
Section~\ref{sec:instances} recovers several earlier results as consequences
of ours and compares other approaches; Section~\ref{sec:discussion} puts
this paper into the broader context of the CALM agenda.  The appendices give the remaining proofs and further applications;
Appendix~\ref{app:notation} collects notation and defined terms.
