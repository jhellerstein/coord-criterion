\section{Introduction}
\label{sec:intro}

Concurrent systems rely on coordination mechanisms ranging from mutexes and
atomic instructions to database locks and distributed consensus protocols.
These mechanisms prevent concurrent actions from producing undesirable
outcomes, but add significant synchronization overheads; when coordination
crosses a network partition, it can also prevent availability.  Avoiding
unnecessary coordination is therefore a central goal in distributed systems and
databases.  This paper asks what coordination mechanisms accomplish at the
specification level, and when that effect is intrinsically required.

The CALM Conjecture
proposed a crisp, bidirectional answer: consistency can be achieved without
coordination exactly when the specification is
monotone~\cite{hellerstein2010declarative}.  Ameloot et al.\ proved it in both
directions, but only for Datalog queries evaluated by relational
transducer networks~\cite{ameloot2013relational,hellerstein2020keeping}. In a related vein, the CAP
Theorem proved that an available linearizable register cannot tolerate a
network partition~\cite{brewer2000towards,gilbert2002cap}.  These results are often
invoked more broadly than the formalisms support: CALM as a general
monotonicity boundary for coordination, CAP as a general constraint on distributed
systems.  The folklore outgrew what the literature proves.

Related results reach similar conclusions from different starting points.
Conflict-free Replicated Data Types (CRDTs)
use inflationary updates over join-semilattices to guarantee coordination-free
convergence~\cite{shapiro2011crdt}.  Highly Available Transactions (HATs) analyze
transaction histories to identify guarantees that remain available under
partition~\cite{bailis2013hat}.  Invariant confluence asks whether independently
reached, invariant-preserving database states can merge
safely~\cite{bailis2014coordination}.  Because these results speak different formal
languages, they do not translate directly.  Does CALM encompass CAP?  Are CRDT
join laws necessary for coordination freedom, or merely one strong sufficient
discipline?  Does convergent storage provide highly available transactions?
Do convergence and transaction availability preserve application invariants?

We develop a unified coordination criterion that spans this space,
including the translation questions above
(\S\ref{sec:cap-corollary}, \S\ref{sec:instances}).  We begin with a minimalist
specification model: a two-column relational table pairing input values with the
corresponding outputs that are within spec.  The model is purely declarative: it
describes what can be observed about a system, without reference to any
imperative procedure.  The input domain $(I,\InputOrd)$ includes a partial order
describing how input grows; the output domain $(O,\OutputOrd)$ has its own
partial order characterizing when a later output preserves an earlier claim.
State-machine-style specifications can be compiled into this form
(\S\ref{sec:design-boundary}); the table elides operational details that are not
externally observable.  Despite its simplicity, the model captures
general-purpose consistency models such as linearizability and causal
consistency (\S\ref{app:registers}) as well as application-specific
requirements such as program invariants.  A
specification is \emph{consistent} when the executions it admits are
\emph{confluent}: states reached along different paths can still be brought to
a common state.  This gives one definition that covers these models: a
specification table captures the space of acceptable outcomes, while confluence asks whether
those requirements are maintained across concurrent executions.

We begin with functional specifications, which pair each input with one output
(\S\ref{sec:functional-specifications}) and so capture arbitrary functions
\(f:(I,\InputOrd)\to(O,\OutputOrd)\).  Even then, a system may emit output
before all input has arrived, and different executions may receive input in
different orders.  A
function is monotone when \(i\InputOrd j\) implies \(f(i)\OutputOrd f(j)\): an
output emitted at \(i\) remains valid at \(j\).

Our first result is \emph{Functional CALM}
(\S\ref{sec:functional-calm-theorem}). It generalizes CALM to arbitrary
functions and partial orders, proving that consistency is equivalent to
monotonicity.  When monotonicity fails, emitting some output requires
irrevocably restricting subsequent results to those that \outrelbase it.  We call
this restriction a \emph{commitment}.  For a function, every commitment
\emph{seals} input, ruling out later input that could contradict an output, as
an election official does by closing the polls before announcing a result.
Functional CALM characterizes exactly
when a function can be computed consistently without commitment.
This captures relational query languages and the usual CRDT state specification.

We then give consistency a distributed interpretation without changing the
specification model (\S\ref{sec:distributed-execution}). We place one local
execution at each participant in a distributed history, then project away delivery
and other local details that do not change specification state.
This distributed consistency asks whether the resulting participant states can
still be brought to the same state. We prove that a specification has
distributed consistency if and only if it is consistent in the sense above.

The functional specifications above cannot capture settings like leader election
or transaction ordering, where many outputs are within spec for a given input.
There, commitments gain a second job besides sealing: \emph{choosing} among permitted outputs, as when a system
picks one leader or one serial order.  We show that at each input a commitment does one or the other: the
effect of any coordination mechanism on the specification is a combination of
input seals and output choices.  For the case of general relations we must move beyond standard
monotonicity of functions; we define a generalization called
\emph{Lifted Monotonicity}, which asks whether outputs from different executions can remain
consistent with one another as input grows. Complete CALM proves that
consistency, Lifted Monotonicity, and distributed consistency are equivalent
(\S\ref{sec:complete-calm-theorem}).  When participants could choose
differently, their commitments must rule out the same alternatives;
coordination mechanisms implement that.

Complete CALM also yields a Complete CAP Theorem
(\S\ref{sec:cap-corollary}).  For any consistency guarantee expressed as a
specification, Lifted Monotonicity identifies which side of the CAP boundary it
occupies.  A specification with Lifted Monotonicity can keep every output it permits
available and confluent during a partition; any other cannot.  A weaker form
that asks only that every operation be answered yields the Gilbert--Lynch
theorem for linearizable registers as a corollary of the same machinery
(Appendix~\ref{app:cap-response}).

This paper makes six contributions:
\begin{enumerate}
  \item \emph{A common specification model.} Ordered relational tables describe
        permitted input/output behavior; commitments record irrevocable decisions
        among that behavior, each sealing input or choosing among outputs.
  \item \emph{Consistency as confluence.} One definition applies to general
        consistency models and application-specific requirements.
        This run-level property is shown to be equivalent to distributed
        consistency over distributed histories.
  \item \emph{Functional CALM.} For arbitrary functions between ordered
        domains, consistency---and hence distributed consistency---is equivalent
        to monotonicity.
  \item \emph{Complete CALM and CAP.} With multiple outputs per input,
        consistency---and hence distributed consistency---is equivalent to
        Lifted Monotonicity.  Complete CAP gives the corresponding availability
        boundary under partition, and the same machinery recovers the
        Gilbert--Lynch theorem as a corollary.
  \item \emph{Composition and Proper Coordination.} Specifications compose by
        equijoin, and because commitments are explicit, the model can check
        whether a particular use of coordination is enough.  For example, a
        totally ordered log and a key-value store are both non-monotone, yet
        committing to a single log order makes their composition monotone and
        consistent, with no further commitments in the store
        (Appendix~\ref{app:composition}).
  \item \emph{Coordination-free frontiers.} Two theorems characterize how much
        a specification can promise before coordination becomes necessary
        (Appendix~\ref{sec:frontiers}).
\end{enumerate}

Section~\ref{sec:functional-calm} introduces the framework on an election
and develops Functional CALM.  Section~\ref{sec:distributed-execution} gives
consistency its distributed reading.  Section~\ref{sec:ambiguous-specifications}
generalizes the framework to ambiguous specifications, and
Section~\ref{sec:complete-calm} lets systems make their own commitments,
identifies coordination with commitment, and proves Complete CALM and Complete
CAP.
Section~\ref{sec:instances} applies the results to familiar systems, and
Section~\ref{sec:discussion} draws out the design lessons and scope limits.
Appendix~\ref{app:composition} proves the composition and Proper Coordination
results, Appendix~\ref{app:cap-response} develops the response form of Complete
CAP, Appendix~\ref{sec:frontiers} derives maximal coordination-free
specifications, and Appendix~\ref{app:additional-applications} gives further
classical applications.
