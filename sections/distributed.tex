\section{Distributed Execution}
\label{sec:distributed-execution}

This section gives Functional CALM and Complete CALM a distributed reading,
including a convergence guarantee for functional specs
(Corollary~\ref{cor:convergence}).  We then define systems, relate their runs to
canonical runs, and show where \commitments conflict; Complete CAP follows.

\subsection{Systems and canonical runs}
\label{sec:systems}

A spec says which behaviors are permitted, not how a system chooses among them.
We now model those choices, and show that a system's inputs and outputs always
match a canonical run's.

For example, serializability can be enforced by any of a number of concurrency
control protocols (Figure~\ref{fig:ambiguity-frames}(f), formalized in
Appendix~\ref{app:cc-bases}).  Two-phase locking (2PL) orders transactions
pairwise through lock requests: when $B$ waits for a lock $A$ holds, the 2PL \commitment $\mathsf{order}(A,B)$ fixes $A$ before $B$ and nothing else.  Multiversion
timestamp ordering (MVTO)~\cite{bernstein1981concurrency} orders them totally
through timestamp assignment: the MVTO \commitment $\mathsf{stamp}(B)$ fixes $B$ before any
transaction not yet stamped.  The
two narrow the spec differently (Figure~\ref{fig:cc-commitments}).

The registrar of Section~\ref{sec:election-story} is a similar example.  When
it emits $\bot$, it also closes the polls (Figure~\ref{fig:election-frames}(d)),
although emitting $\bot$ does not require that \commitment.  Closing the polls is the registrar's
design decision, as fixing orderings is 2PL's.

Sections~\ref{sec:functional-calm}--\ref{sec:complete-calm} used only the
canonical \commitment $x_o$ that an output requires.  Systems may commit
earlier or remove more alternatives, as these examples do, by applying other
\commitments (Definition~\ref{def:commitment}).  The ordering \commitment
$\mathsf{order}(A,B)$ is one: it removes the serial orders with $B$ before $A$,
and no surviving order with $A$ before $B$ \outrel any of them.

\begin{definition}[\Commitment event]
\label{def:commitment-event}
A \emph{\commitment event} $\mathsf{apply}(\gamma)$ applies a nonempty
sequence $\gamma=e_1\cdots e_n$ of \commitments, each defined at the state
its predecessors leave, and emits nothing.
\end{definition}

The sequence as a whole is itself a \commitment.  Each row it removes was
removed by some step, and that step left no row at the same input that \outrel
the removed one.  Every row that remains at the end also remained after that
step, so the sequence as a whole removes no row that a remaining row \outrel.
Results stated for a single \commitment therefore apply to \commitment events
as well.

A system applies its own \commitments only in \commitment events.  A \commitment event may precede an output event, which then
has less to remove.  The environment observes nothing from a \commitment event.
\Commitment events are a third kind of specification event, so a distributed
history may contain them; Definitions~\ref{def:distributed-history} and~\ref{def:participant-run} apply
unchanged.

\begin{definition}[\Commitment basis, run under a basis]
\label{def:commitment-basis}\label{def:run-under-basis}
A \emph{\commitment basis} is a set $\mathcal B$ of \commitments.  A \emph{run
under $\mathcal B$} is a finite transition sequence from a canonical state
$\sigma_P(i)$ of input, output, and \commitment events in which every
\commitment event applies only \commitments in $\mathcal B$, and every output
event of a non-legal output $o$ applies its canonical \commitment
$x_o\in\mathcal B$.
\end{definition}

A canonical run is then a run under the basis of all canonical \commitments that
contains no \commitment event.

\paragraph{Two bases on three transactions.}
We return to the concurrency protocols from the start of this subsection.
Each protocol's basis contains its ordering \commitments, $\mathsf{order}$ for
$\mathcal B_{\mathrm{2PL}}$ and $\mathsf{stamp}$ for $\mathcal B_{\mathrm{MVTO}}$,
together with \commitments for commits, aborts, and reads
(Appendix~\ref{app:cc-bases}).  Figure~\ref{fig:cc-commitments} shows each at
work on three transactions, a larger version of the ordering fiber of
Figure~\ref{fig:ambiguity-frames}(f).  2PL applies $\mathsf{order}(A,B)$ when
$B$ waits for a lock that $A$ holds, which leaves $C$'s position open
(panel~(h)).  MVTO applies $\mathsf{stamp}(B)$ when $B$ receives the first
timestamp, which places $B$ first (panel~(i)).  Both are \commitments that
leave some rows at the input.  Each is applied in a \commitment event
$\mathsf{apply}(\gamma)$, and neither is the canonical \commitment $x_o$ of
an output.

\begin{definition}[Local history]
\label{def:local-history}
A \emph{local history} of participant $p$ is a finite sequence of $p$'s
history events, including the messages it has received.
\end{definition}

\begin{definition}[Strategy]
\label{def:strategy}
A \emph{strategy} for a participant $p$ is a nondeterministic transition
function: it maps each local history $\lambda$ of $p$ to the set
$\theta_p(\lambda)$ of output, \commitment, and send events that $p$ may
perform next.  Input and receive events are not chosen by the strategy: inputs
come from the environment and receives from matching sends.
\end{definition}

\begin{definition}[System]
\label{def:system}
A \emph{system} consists of a \commitment basis $\mathcal B$ and a strategy
$\theta_p$ for each participant $p$, whose output and \commitment events apply
only \commitments from $\mathcal B$.
\end{definition}

\begin{definition}[History of a system]
\label{def:produced-history}
A distributed history is a \emph{history of} a system, or is \emph{produced} by
it, when its input events come from the environment, its receives match sends,
and its output, \commitment, and send events are chosen by the participants'
strategies.
\end{definition}

Coordination mechanisms are part of the system, not of the spec: its strategies
describe how participants use them, and its basis records the \commitments they
can enforce.  A system's strategies select the events of an actual execution;
they need not realize every run the spec permits.  Participants may behave
differently; a replicated (SPMD) system is the special case in which they share
one strategy (Appendix~\ref{app:cap-response}).

Our model places no bound on the set of participants, and a strategy has no way
to enumerate them.  In general there is no list of all participants, which
Ameloot et al.\ call the $\mathsf{All}$ relation~\cite{ameloot2013relational}.
Such a list lets a participant wait for every other participant, for example to
collect a vote from each at some step of a protocol, and know when it has them
all.  Ameloot et al.\ show that this enlarges what a system can compute.  A
spec can include this knowledge as a modeling decision, by fixing the list of
all participants as part of the input in every row.  The list is then explicit
common knowledge, available to each participant's strategy from its initial
input.

\paragraph{Observable equivalence.}
Locks, timestamps, quorums, and consensus differ in how and when they decide.
The next lemma relates runs under any basis to canonical runs.

\begin{lemma}[Observable Equivalence]
\label{lem:canonical-equivalent}
Let $\rho$ be a run of a system for a spec $\Spec$, under any \commitment
basis.  Removing the \commitment events from $\rho$ gives a canonical run of
$\Spec$ (Definition~\ref{def:run}) that is \emph{observably equivalent} to
$\rho$: the two accept the same inputs and emit the same outputs, and after each
event the canonical run keeps every row that $\rho$ keeps.
\end{lemma}

\begin{proof}[Proof sketch]
\Commitment events only remove rows, so dropping them can only keep more.  An
input or output event applied to a larger table keeps a larger table, and the
canonical run can perform it because the rows of $\rho$ are among its
own.  Full proof in
Appendix~\ref{app:bases}.
\end{proof}

To illustrate the lemma, consider 2PL on an input of three transactions $A$,
$B$, $C$ that have each issued their operations and requested commit, where $B$
waits for a lock that $A$ holds.  When $B$ begins to wait, 2PL applies
$\mathsf{order}(A,B)$ in a \commitment event, before any output, and removes
every row that places $B$ before $A$.  The canonical run drops that event and
keeps those rows for now.  Suppose 2PL later commits all three transactions,
fixes the order $A$, $C$, $B$ in a second \commitment event, and emits
$[A,C,B]$.  The canonical run emits $[A,C,B]$ directly.  Its output event
applies the canonical \commitment of $[A,C,B]$, which removes every row whose
output does not \outrelbase $[A,C,B]$.  Those include every row 2PL removed
earlier, since $[A,C,B]$ contains each order that 2PL fixed, $A$ before $B$
among them.  After the output both runs keep exactly the same rows.  So the
canonical \commitment of an output makes, all at once and at output time, the
decisions a system may have spread over earlier \commitment events.  A system
can decide earlier than its outputs require, but the \commitments those outputs
require are the same.

The converse of the lemma is not true because systems can choose to do less
than canonical runs allow (Appendix~\ref{app:bases}).  Systems may constrain their runs arbitrarily, and
their remainder tables may lack rows that their canonical runs keep.  So a spec
can be confluent while a system for it is not.  The registrar is an example:
after closing the polls at $ab\cdot$, it cannot accept the late ballot $aba$.
Under the original output order, a canonical run can emit $\bot$, accept
$aba$, and emit $a$.

The CALM and CAP criteria are about specs and
their canonical runs.  A system with no \commitment events inherits their
confluence directly, since its runs are canonical runs.  A system with
\commitments of its own keeps at most the rows of its canonical runs, and its
confluence depends on which rows those \commitments remove.

\subsection{Where \commitments conflict}
\label{sec:commitment-conflict}

The registrar shows how a system's own \commitment can block a confluence the
spec allows: once it closes the polls at $ab\cdot$, it can never reach a common
state with a canonical run that accepts $aba$ and emits $a$.  To see exactly
which rows a system gives up, we compare a run with its canonical run
(Lemma~\ref{lem:canonical-equivalent}).  An input or output event tests each
row the same way in both runs, so only the system's \commitment events remove
more.  For a run $\rho$ under a basis whose canonical run ends at
$(i,\widehat R)$, let $\Delta(\rho)$ be the rows of $\widehat R$ that a
\commitment event of $\rho$ removed.

\begin{proposition}[System confluence]
\label{prop:system-confluence}
Let $\rho_1,\ldots,\rho_n$ be runs under any \commitment bases, where $\rho_r$
ends at $(i_r,R_r)$ and its canonical run ends at $(i_r,\widehat R_r)$.
\begin{enumerate}
  \item $R_r=\widehat R_r\setminus\Delta(\rho_r)$.
  \item Let $k$ be a common \indesc of $i_1,\ldots,i_n$.  The runs are
        confluent at $k$, by continuations whose output and \commitment events
        may apply any \commitments, if and only if some row at $k$ lies in
        every $\widehat R_r$ and in no $\Delta(\rho_r)$.
\end{enumerate}
\end{proposition}

\begin{proof}[Proof sketch]
(1) A row of $\widehat R_r$ passes every input and output event of $\rho_r$,
so it can leave $R_r$ only through a \commitment event.  (2) As in the Survivor
test (Proposition~\ref{prop:confluence}), a common state at $k$ has a row at
$k$, and since rows are never added, that row lies in every $R_r$.
Conversely, if $(k,u)$ lies in every $R_r$, each run reaches the state whose
only row is $(k,u)$ by $\mathsf{input}(k)$, then $\mathsf{output}(u)$, then a
\commitment event that removes every other row.  After $\mathsf{output}(u)$,
every other row at $k$ \outrel $u$ and differs from it, so none of them is
\outrelpast by $(k,u)$ and the removal is a \commitment.  Part~(1) turns the
condition on the $R_r$ into the one stated.  Full proof in
Appendix~\ref{app:proofs-sec4}.
\end{proof}

The same test applies to a consistent cut of a history, with one run per
participant.  A continuation that adds events at each participant separately,
with no messages, brings the cut to a common state exactly when those runs
reach it (Section~\ref{sec:distributed-consistency}).

For the registrar, closing the polls at $ab\cdot$ puts in $\Delta$ every row
with a late ballot, such as $(aba,a)$ and $(abb,b)$.  Its table then has no row
at $aba$, so no family of runs that includes it is confluent at $aba$.

The continuations in Proposition~\ref{prop:system-confluence} need not be ones
the system would choose: the last \commitment event in the proof is in general
not in the system's basis.  Suppose that, from each final state, the system's
strategy can accept $k$ and then emit any output whose row at $k$ remains in
its table.  Then the test is also exact for the system's own continuations: it
holds exactly when they can bring every run to input $k$ and emit one common
output there, which \outrel everything the runs emitted.  Without that
assumption, $\Delta$ understates what the system has given up.  Consider a
server that either replies $x$ to the first request $p$ and never replies $z$,
or waits for a second $p$ and then replies $x$ and then $z$.  A run that
replied early made no \commitment, so its table keeps the row with input $pp$
and output $xz$, but its strategy never emits $z$.

Proposition~\ref{prop:system-confluence} has a simple special case: two runs,
one of which removes a row by a \commitment while the other emits that row's
output.

\begin{proposition}[Commitment conflict]
\label{prop:commitment-conflict}
Let a run under some \commitment basis from $\sigma_P(i)$ apply a \commitment
that removes the row $(k,x)$, and let a run under any \commitment basis from
$\sigma_P(i)$ issue $\mathsf{input}(k)$ followed by $\mathsf{output}(x)$.  These two runs
\emph{conflict}: they are not confluent at $k$.
\end{proposition}

\begin{proof}[Proof sketch]
A canonical run is one such second run: events only remove rows, so $(k,x)$ is
present at $\sigma_P(i)$.  After $\mathsf{output}(x)$, every row at $k$ in the
second run \outrel $x$.  The \commitment removed $(k,x)$ and left no row at $k$
that \outrel $x$ (Definition~\ref{def:commitment}), so no such row remains in
the first run's table.  No row at $k$ survives in both runs, and by
Proposition~\ref{prop:system-confluence} they are not confluent at $k$.  Full
proof in Appendix~\ref{app:proofs-sec4}.
\end{proof}

Within one participant's run, the \commitment already prevents the conflict:
once $(k,x)$ is removed, that run can no longer emit $x$ at $k$.  The conflict
matters when the other run belongs to a different participant of the same
history.  A system then has two ways to avoid it: its participants coordinate
before one of them makes the choice, or only one participant is ever allowed to
make it.

\paragraph{Deployments.}
A \emph{deployment} records the second option: it fixes, for each participant,
which outputs it may emit at which inputs.  If every participant may emit every
output, two conflicting runs can occur at participants that have not heard
from each other.  If each choice has a single owner, they cannot, and the owner
can make the choice without coordinating with anyone
(Appendix~\ref{app:deployment}).

\paragraph{Locks in a shared-nothing database.}
Consider a database partitioned by key, with each key owned and locked by one
participant~\cite{stonebraker1986sharednothing}.  Choosing an order of two
transactions on one key requires a \commitment, but only the key's owner can
make that choice, so the two possible orders can never be chosen by different
participants.  A transaction spanning two keys is different: each owner orders
its own part, and the two owners can order the same pair oppositely.  They must
agree on one order.

Two-phase commit adds no further \commitment.  Each data owner's response to a \texttt{prepare} message
from the coordinator reports the
\commitment it has already made.  The coordinator then makes the monotone
decision whether all owners prepared; it detects whether their \commitments
agree and aborts when they do not.  It does not make the owners agree.  If the
coordinator instead aborts on timeout before the last vote arrives, that abort
applies another \commitment, like closing the polls.  One coordinator can make
that choice locally.  Replicated coordinators need distributed agreement to
make it, as in Paxos Commit~\cite{gray2006consensus}.

\subsection{The Complete CAP Theorem}
\label{sec:complete-cap}

Brewer conjectured that a distributed system cannot be consistent, available,
and partition tolerant at once~\cite{brewer2000towards}; Gilbert and Lynch
proved it as an impossibility result for a linearizable register~\cite{gilbert2002cap}.
Complete CAP addresses the conjecture more broadly:
which specifications are subject to the CAP
conjecture, and which are not?

To pose the question properly, note that the outputs that each participant emits---and
needs to keep available---are not enough to judge consistency. The spec
must also model what an observer (e.g., a client) can eventually conclude by collecting
outputs from multiple participants.

Like Gilbert and Lynch, we use a replicated register as an example.
A register is a key-value store with a single key, which is enough to reason
about one object.  The register starts at $v_0$, and a read and a write race at
different participants.  Participant $p$ receives write $w(v)$ and emits its
acknowledgment; concurrently, participant $q$ receives the read $r$ and emits
$v_0$.  A client may later collect both responses.  A linearizable register
spec has a row for this situation: its input is the pair of requests, and its
output is the pair of responses.  The spec permits the row because a
linearization may place the concurrent read before the write.  No participant
emits this combined output, and availability does not need it.  Still, it
\outrel both local outputs, which shows that the two are consistent, so the
spec must contain it.  Had the write finished before the read began, no such
combined output would exist; we return to this case at the end of the section.

We therefore pair a spec with an \emph{explicit possibility relation}
$E\subseteq P$, or explicit relation for short: the rows whose outputs
participants actually emit.  Outputs in
$P\setminus E$ are not emitted by participants;
they remain permitted in $P$ to capture implicit combinations of emitted outputs.

Both availability and consistency are judged on histories in which a partition
separates the participants.

\begin{definition}[Partitioned history]
\label{def:partitioned-history}
A \emph{partitioned history} divides the participants into two or more
sides and contains no receive whose matching send lies on another
side.  Same-side messages are allowed, and participants still receive environment input
and emit outputs.
\end{definition}

\begin{definition}[Explicit possibility relation]
\label{def:explicit-relation}
An \emph{explicit possibility relation} $E\subseteq P$ is a set of rows whose
outputs participants actually emit.  Write $E(i)$ for its outputs at input
$i$.
\end{definition}

For example, consider two-phase commit (2PC).  We focus on the spec for the
voters; the coordinator is an observer of that spec.  We're interested in the
fiber at the input \textsf{prepare(tx)}: how each voter responds to that
prepare message.  Each possible explicit response is a row of $E$.  The overall
\emph{set} of responses the coordinator might observe across voters is in
$P\setminus E$.  The spec includes these as implicit outputs, representing the
possible combined outcomes that respect each voter's response.

\begin{definition}[Emitted rows]
\label{def:emitted-rows}
The \emph{emitted rows} of a run are the pairs $(i,o)$ such that the run
emits $o$ at current input $i$.  The emitted rows of a system are the
emitted rows of its participants' runs in the histories it produces.
\end{definition}

An explicit relation is declared with the spec; the emitted rows depend on
the system.  Availability for $E$ asks that every row of $E$ at a
participant's state can become an emitted row.


We consider a system whose participants each follow a strategy that depends
only on their local history, and an environment that may send any legal input
to any participant.  Availability asks that, during a partition, each
participant can still emit every explicit output its state permits.

\begin{definition}[Same-side continuation]
\label{def:local-continuation}
Consider a partitioned history that the system produces, in which participant
$p$ ends in state $(i,R)$.  A \emph{same-side continuation} for $p$ extends that
history with events the system can produce on $p$'s side alone, with no new
input and no message from another side.  Participant $p$ can emit $o$ when some same-side continuation for $p$ emits
$o$.
\end{definition}

\begin{definition}[Availability]
\label{def:partition-notions}
The system has \emph{Availability for $E$} when, in every partitioned history
it produces, each participant $p$ can emit every output in $R(i)\cap E(i)$,
where $(i,R)$ is $p$'s final state.  \emph{Availability} is shorthand for
Availability for $P$.
\end{definition}

Partition Consistency asks that, whatever participants emit on separate sides,
their states can still be brought to a common state.

\begin{definition}[Partition Consistency]
\label{def:partition-consistency}
The system has \emph{Partition Consistency} when the final cut of every
partitioned history it produces is confluent at every common \indesc of the
participants' current inputs.
\end{definition}

The \emph{canonical system for $E$} is the system whose participants follow
canonical runs and emit only outputs of $E$.

\begin{definition}[Escaping CAP]
\label{def:escapes-cap}
A spec \emph{escapes CAP} for $E$ when its canonical system for $E$ has
Availability for $E$ and Partition Consistency.
\end{definition}

The canonical system's participants never wait: each can emit any output of
$E$ that its state allows, so it always has Availability for $E$.  The
question is whether their answers stay consistent across sides.  Complete CAP
says they do exactly when outputs of $E$ emitted on different sides have a
common \outnoun in the spec at every common \indesc of their inputs.

\begin{definition}[Lifted Monotonicity for $E$]
\label{def:lm-for-A}
$\Spec$ satisfies \emph{Lifted Monotonicity for $E$} when every finite set of rows of $E$ with
a common \indesc $j$ has a common \outnoun in $\fiber{j}$.
\end{definition}

\begin{theorem}[Complete CAP]
\label{thm:complete-cap}
A spec escapes CAP for $E$ if and only if it satisfies Lifted Monotonicity for
$E$.
\end{theorem}

\begin{proof}[Proof sketch]
Suppose Lifted Monotonicity for $E$ holds, and let $j$ be a common \indesc of
the participants' current inputs.  The outputs emitted on all sides are outputs
of $E$, so they have a common \outnoun $u$ in $\fiber{j}$.  Each participant
still has the row $(j,u)$, since it makes no \commitments of its own and $u$
\outrel every output it emitted (Lemma~\ref{lem:run-residual}).  So the
participants can all continue to a common state at $j$.  Conversely, take
finitely many rows of $E$ with a common \indesc $j$, and place one participant
per row on its own side.  Availability lets each participant emit its row's
output, and Partition Consistency then gives those outputs a common \outnoun in
$\fiber{j}$.  Full proof in
Appendix~\ref{app:proofs-sec4}.
\end{proof}

\begin{corollary}
\label{cor:complete-cap-any-system}
If some system for a spec has Availability for $E$ and Partition Consistency,
then so does the spec's canonical system for $E$.
\end{corollary}

\begin{proof}[Proof sketch]
We show that if Lifted Monotonicity for $E$ fails, the system loses Partition
Consistency.  Then some rows of $E$ share a common \indesc $j$, but no output in
$\fiber{j}$ \outrel all of their outputs.  We place each row's participant on
its own side of a partition, and Availability lets each one emit its row's
output.  By Observable Equivalence, a participant keeps no more rows than its
canonical run, so each row it keeps at $j$ \outrel its own output.  A common
state at $j$ would need a row that \outrel every participant's output, and
there is none.  Full proof in Appendix~\ref{app:proofs-sec4}.
\end{proof}

A system might hope to keep more outputs available, without losing Partition
Consistency, by issuing \commitments that coordinate within each side of a
partition.  It cannot: Corollary~\ref{cor:complete-cap-any-system} holds for
every system, whether or not it issues \commitments.  For
$E=P$, a spec escapes CAP exactly when it satisfies Lifted Monotonicity, and
then the canonical system needs no \commitment at all.

We return to the voters' spec.  Each voter decides whether it can commit and emits
its vote, yes or no.  That decision is a \commitment: a voter that votes yes
rules out every set of votes in which it votes no.  But it is a single-voter
\commitment involving no communication, so the voter can make it and produce
output during a partition.  Each vote is cast by a different voter, so votes
emitted on different sides of a partition never conflict (Appendix~\ref{app:deployment} formalizes this placement as a deployment), and every
set of votes an observer may collect is consistent.

A partition does not change the intrinsic \commitments a spec needs; it prevents
separated participants from jointly enforcing them through coordination.  When Lifted
Monotonicity for $E$ fails, some output of $E$ waits for another side,
sacrificing Availability, or is emitted anyway, sacrificing Partition
Consistency.

\paragraph{Gilbert and Lynch.}
Gilbert and Lynch's theorem is a case of Complete CAP.  Linearizability
respects real-time order: if one operation finishes before another begins,
every linearization puts the first before the
second~\cite{herlihy1990linearizability}.  In the register example, suppose the
write finishes before the read begins.  Every linearization then puts the write
first, so the read must return $v$.  But each of $p$ and $q$ sees only its own
request, and Availability requires $p$ to acknowledge the write and $q$ to
answer $v_0$.  No output for the two requests together \outrel both answers, so
the spec does not satisfy Lifted Monotonicity for them.  By
Corollary~\ref{cor:complete-cap-any-system}, no system can keep both outputs
available and stay consistent across a partition, which is Gilbert and Lynch's
theorem.

In this example, the proof of Corollary~\ref{cor:complete-cap-any-system}
uses only weaker forms of its hypotheses, and these weaker forms are Gilbert
and Lynch's, which is why it yields their theorem exactly.  We place $p$ and
$q$ on separate sides.  Availability is used only to make $p$ acknowledge the
write and $q$ answer the read.  Each of their fibers holds a single output, so
requiring each to emit every permitted output is the same as requiring it to
respond, which is Gilbert and Lynch's availability.  Partition Consistency is
used only to demand a common \outnoun of the two answers.  Such an \outnoun is
a single linearization that explains both answers, which is Gilbert and Lynch's
consistency, and none exists.

In this section the real-time order of the write and the read is part of the
input.  Appendix~\ref{app:cap-response} instead takes that order from the
execution itself, extends Complete CAP to systems that choose their responses
when responses are not forced, and derives the theorem in Gilbert and Lynch's
asynchronous model.
