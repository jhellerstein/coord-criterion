\section{Distributed Execution}
\label{sec:distributed-execution}

This section gives Functional CALM and Complete CALM a distributed reading,
including a convergence guarantee for functional specs
(Corollary~\ref{cor:convergence}).  We then define systems, relate their runs to
canonical runs, and show where \commitments conflict; Complete CAP follows.

\subsection{Systems and canonical runs}
\label{sec:systems}

A spec describes which behaviors are permitted, but not how a system chooses
among them.  We now model those choices, and show that a system's inputs and
outputs always remain those of a canonical run.

For example, serializability can be enforced by any of a number of concurrency
control protocols (Figure~\ref{fig:ambiguity-frames}(f), formalized in
Appendix~\ref{app:cc-bases}).  Two-phase locking (2PL) uses locks on
operations: when $B$ waits for a lock $A$ holds, $\mathsf{order}(A,B)$
fixes $A$ before $B$.  Multiversion timestamp ordering
(MVTO)~\cite{bernstein1981concurrency} uses timestamps:
$\mathsf{stamp}(B)$ fixes $B$ before any transaction not yet stamped.  The
two narrow the spec differently.

We saw a similar example with elections.  When the registrar of
Section~\ref{sec:election-story} emits $\bot$, it also closes the polls
(Figure~\ref{fig:election-frames}(d)), although emitting $\bot$ does not
require the poll-closing \commitment.  Closing the polls is the registrar's
design decision, as fixing orderings is 2PL's.

Sections~\ref{sec:functional-calm}--\ref{sec:complete-calm} used only the
canonical \commitment $x_o$ required by an output.  Systems may commit earlier
or remove additional alternatives, as the examples above do.  We therefore
allow bespoke system \commitments.  A system dictates a spec and a basis of
\commitments its participants may issue; each participant's strategy decides
when and which to apply.

\begin{definition}[\Commitment]
\label{def:commitment}
A \emph{\commitment} is a partial function on
specification states that removes a nonempty set of rows.  No row it removes
is subsumed by a row that remains at the same input.  Thus, whenever $e(i,R)=(j,R')$, we have $R'\subsetneq R$ and
\begin{equation}
  (k,u)\in R\setminus R',\ (k,w)\in R'
  \quad\Longrightarrow\quad
  u\not\OutputOrd w.
  \label{eq:commitment-unsubsumed}
\end{equation}
It leaves the current input unchanged: $j=i$.
\end{definition}

The ordering \commitment above fits: $\mathsf{order}(A,B)$ removes the serial
orders with $B$ before $A$, each undominated by a surviving row with $A$
before $B$.  The canonical \commitments of Section~\ref{sec:lifted-output-events} satisfy this definition too.

A system draws its \commitments from a basis.

\begin{definition}[System output event]
\label{def:system-output-event}
Let $(i,R)$ be a state and $o\in R(i)$.  A system emits $o$ by the output
event $\mathsf{output}(o)$ of Section~\ref{sec:lifted-output-events}, which
ends at $(i,R[\mathrm{out}\OutputGe o])$.  When $o$ is not a legal output,
the event applies the canonical \commitment $x_o$, which must then belong to
the system's basis.
\end{definition}

\begin{definition}[\Commitment event]
\label{def:commitment-event}
A \emph{\commitment event} $\mathsf{apply}(\gamma)$ applies a nonempty
sequence $\gamma=e_1\cdots e_n$ of \commitments, each defined at the state
its predecessors leave, and emits nothing.  Since later \commitments only
remove rows, the sequence as a whole is itself a \commitment.
\end{definition}

A system applies its own \commitments only in \commitment events.  A \commitment event may precede an output event, which then
has less to remove.  The environment observes nothing from a \commitment event.
\Commitment events are a third kind of specification event, so a distributed
history may contain them; Definitions~\ref{def:distributed-history} and~\ref{def:participant-run} apply
unchanged.

\begin{definition}[Local history]
\label{def:local-history}
A \emph{local history} of participant $p$ is a finite sequence of $p$'s
history events, including the messages it has received.
\end{definition}

\begin{definition}[Strategy]
\label{def:strategy}
A \emph{strategy} for a participant $p$ is a nondeterministic transition
function: it maps each local history $\lambda$ of $p$ to a set
$\theta_p(\lambda)$ of output, \commitment, and send events of $p$, and $p$ next
performs any one of them, or waits.  Input and receive events are not chosen
by the strategy: inputs come from the environment and receives from matching
sends.
\end{definition}

A strategy says how one participant acts; a system packages one basis with
a strategy for every participant.

\begin{definition}[System]
\label{def:system}
A \emph{system} consists of a \emph{\commitment basis} $\mathcal B$, a set
of \commitments shared by all participants, and a strategy $\theta_p$ for
each participant $p$ whose output and \commitment events apply only
\commitments from $\mathcal B$.
\end{definition}

\begin{definition}[Produced history]
\label{def:produced-history}
A distributed history \emph{produced} by a system consists of input events
supplied by the environment, receives of matching sends, and output,
\commitment, and send events chosen by the participants' strategies.
\end{definition}

Coordination mechanisms live in the system: its strategies describe how
participants use them, and its basis records the \commitments they can enforce.
A system's strategies select the events of an actual execution; they need not
realize every run the spec permits.  A deployment can separately restrict which
participants may emit which rows (Appendix~\ref{app:deployment}).

Participants may behave differently; a replicated (SPMD) system is the special
case in which they share one strategy (Appendix~\ref{app:cap-response}).
Systems for different specs compose as components
(Section~\ref{sec:proper-coordination}).

We return to the concurrency protocols from the beginning of this
subsection.  Each basis contains its ordering \commitments along with
transactional-commit,
abort, and read \commitments: $\mathcal B_{\mathrm{2PL}}$ with $\mathsf{order}$,
$\mathcal B_{\mathrm{MVTO}}$ with $\mathsf{stamp}$
(Appendix~\ref{app:cc-bases}).  Figure~\ref{fig:cc-commitments} shows each

\paragraph{Observable equivalence.}
We call the runs of
Sections~\ref{sec:functional-calm}--\ref{sec:complete-calm} \emph{canonical
runs}, and a \emph{run under a basis} $\mathcal B$ is one whose output and
\commitment events apply only \commitments from $\mathcal B$
(Definition~\ref{def:run-under-basis}).  Locks, timestamps, quorums, and
consensus differ in how and when they decide.  The next lemma relates their
runs to a common canonical model.

\begin{lemma}[Observable Equivalence]
\label{lem:canonical-equivalent}
Dropping the \commitment events from a run under any \commitment basis
yields \emph{its canonical run}, which is \emph{observably equivalent} to it: it accepts
the same inputs and emits the same outputs, and after each event it keeps at
least the original's rows.
\end{lemma}

\begin{proof}[Proof sketch]
\Commitment events only remove rows, so dropping them can only keep more.  An
input or output event applied to a larger table keeps a larger table, and the
canonical run can
perform it because the original's rows are among its own.  Full proof in
Appendix~\ref{app:bases}.
\end{proof}

To illustrate the lemma, consider 2PL on an input of three transactions
$A$, $B$, $C$ that have each issued their operations and requested commit,
where $B$ waits for a lock that $A$ holds.  When $B$ begins to wait, 2PL applies
$\mathsf{order}(A,B)$ in a \commitment event, before any output, keeping only
rows that can be completed without placing $B$ before $A$.  Its canonical run
drops that event, so it keeps every row, including the one completed by
$[B,A,C]$.  Suppose 2PL later commits all three transactions and orders $A$
before $C$ before $B$ in a \commitment event, and then emits $[A,C,B]$.  Every
row whose output \outrel $[A,C,B]$ satisfies 2PL's \commitments, so 2PL
removed none of them, and after the output both runs keep exactly these rows.
The tables are equal: the lock made the $A$-before-$B$ decision
earlier than the output required.  The \commitments required by a spec's outputs
therefore do not depend on their timing or representation in a system's
\commitment basis.

Observable equivalence is one-way, and it concerns inputs and outputs, not
tables.  A system run's \commitments may remove rows that its canonical run
keeps, and the system may then lose confluence that canonical runs have.  The
registrar is an example.  After closing the polls at $ab\cdot$, it cannot
accept the late ballot $aba$, although its canonical run, which only emits
$\bot$, can.  The CALM and CAP criteria are about specs and
their canonical runs.  Showing that a particular system inherits their
confluence takes a separate argument about that system.

\paragraph{Commitments and conflict.}
The registrar's failure is one case of a general fact.  Suppose one run
applies a \commitment that removes a row, and another run emits that row's
output at its input.  Then no continuation brings the two runs to a common
state at that input.

\begin{proposition}[Commitment conflict]
\label{prop:commitment-conflict}
Let a run from $\sigma_P(i)$ apply a \commitment that removes the row
$(k,x)$, and let another run from $\sigma_P(i)$ issue
$\mathsf{input}(k)$ followed by $\mathsf{output}(x)$.  These two runs
\emph{conflict}: they are not confluent at $k$.
\end{proposition}

\begin{proof}[Proof sketch]
Events only remove rows, so $(k,x)$ is present at $\sigma_P(i)$ and the
second run exists.  By the Survivor test (Proposition~\ref{prop:confluence}),
confluence at $k$ needs a row at $k$ that survives in both runs.  Every row
that survives $\mathsf{output}(x)$ at $k$ \outrel $x$, but the \commitment left
no row at $k$ that \outrel $x$ (Definition~\ref{def:commitment}).  Full proof
in Appendix~\ref{app:proofs-sec4}.
\end{proof}

Familiar coordination mechanisms keep such runs from both occurring.

\paragraph{Placement.}
Whether a coordination mechanism must span participants depends on who can make
each choice.  A deployment records which outputs each participant may produce.
With unrestricted placement, the two conflicting runs can occur at different
participants; ownership can keep them at one.  Appendix~\ref{app:deployment}
formalizes this distinction as monotonicity across partitions.

\paragraph{Locks in a shared-nothing database.}
Consider a database partitioned by key, with each key owned and locked by one
participant~\cite{stonebraker1986sharednothing}.  Ordering two transactions on
one key makes a \commitment, but ownership keeps both choices at that owner.  A
transaction spanning two keys is different: each owner orders its own part, and
the two owners can order the same pair oppositely.  They must agree on one
order.

Two-phase commit adds no further \commitment.  Each owner's prepare reports the
\commitment it has already made.  The coordinator then makes the monotone
decision whether all owners prepared; it detects whether their \commitments
agree and aborts when they do not.  It does not make the owners agree.  If the
coordinator instead aborts on timeout before the last vote arrives, that abort
applies another \commitment, like closing the polls.  One coordinator can make
that choice locally.  Replicated coordinators instead use distributed
agreement, as in Paxos Commit~\cite{gray2006consensus}.

\subsection{The Complete CAP Theorem}
\label{sec:complete-cap}

Brewer conjectured that a distributed system cannot be consistent, available,
and partition tolerant at once~\cite{brewer2000towards}; Gilbert and Lynch
proved it for a linearizable register~\cite{gilbert2002cap}.  Their theorem
concerns one guarantee, not which guarantees can stay available and
consistent through a partition.  Complete CAP answers that broader question
for any declared guarantee.

To state the question, we must separate the outputs that participants must
keep available from the outputs that the spec permits.  A participant
acts on its local history during a partition, while consistency compares the
participants' outputs at a common \indesc of their inputs.  Their common
\outnoun need not be emitted by any participant.  It may exist only as the
client's combined observation.

Consider a register initialized to $v_0$.  During a partition, participant
$p$ receives a write $w(v)$ and emits its acknowledgment, while participant
$q$ receives a concurrent read $r$ and returns $v_0$.  A client that later
collects both observes the write acknowledgment together with the read answer
$v_0$.  The register spec permits this combined output at the input
containing both operations: a linearization may put the concurrent read before
the write.  The combined output \outrel both local outputs and provides a proof
of their consistency, although no participant need ever emit it.

We therefore encode a guarantee as an \spectype together with an
explicit relation $E\subseteq P$: the rows whose outputs must remain locally
available.  Outputs in $P\setminus E$ need only remain permitted as possible
common \outnouns.  Complete CAP says that such a guarantee can stay available
and consistent through partitions exactly when the spec satisfies
Lifted Monotonicity for $E$: outputs selected by $E$ on different sides of a
partition must have a common \outnoun in the spec at every common
\indesc of their inputs.  When $E=P$, this is Lifted Monotonicity itself.  A
partition does not change which \commitments a spec needs; it removes
the ability to make them jointly, since separated participants cannot jointly
apply a \commitment that conflicts with another participant's run.

\begin{definition}[Partitioned history]
\label{def:partitioned-history}
A \emph{partitioned history} divides the participants into two or more
blocks and contains no receive whose matching send lies in another
block; participants still receive environment input and emit outputs.
\end{definition}

We fix a system, with a strategy for each participant of every finite
participant set and every choice of initial inputs, each depending only on its
participant's local history, and an adversarial environment that may supply
any legal input event to any participant.

\begin{definition}[Local continuation]
\label{def:local-continuation}
A continuation of a partitioned history is \emph{local to} a participant $p$
when the system produces it, it adds only history events of $p$'s block and no
input events, and none of its receives takes a message sent from another
block.
\end{definition}

\begin{definition}[Explicit relation]
\label{def:explicit-relation}
An \emph{explicit relation} $E\subseteq P$ is a set of rows $(i,o)$ whose
output $o$ must stay available at input $i$; write $E(i)$ for its fiber
$\{o:(i,o)\in E\}$.
\end{definition}

\begin{definition}[Availability]
\label{def:partition-notions}
The system has \emph{Availability for $E$} when, in every partitioned history it
produces, each participant $p$, ending in state $(i,R)$, can emit each
output in $R(i)\cap E(i)$ in some continuation local to $p$.
\emph{Availability} is Availability for $P$.
\end{definition}

\begin{definition}[Partition Consistency]
\label{def:partition-consistency}
The system has \emph{Partition Consistency} when the final cut of every
partitioned history it produces is confluent at every common \indesc of the
participants' current inputs.  The continuation that confluence asks for need
not stay partitioned and need not be produced by the system.
\end{definition}

\begin{definition}[Lifted Monotonicity for $E$]
\label{def:lm-for-A}
$\Spec$ satisfies \emph{Lifted Monotonicity for $E$} when every finite set of rows of $E$ with
a common \indesc $j$ has a common \outnoun in $\fiber{j}$.
\end{definition}

With $E=P$, Lifted Monotonicity for $E$ is the common-extension condition
(Definition~\ref{def:common-expansion-condition}).  For a smaller $E$, an
available system may use output events that apply \commitments requiring
coordination under the full declared spec; the remark after
Corollary~\ref{cor:complete-cap-S} explains why restricting service to $E$ does
not erase that requirement.

\begin{theorem}[Complete CAP]
\label{thm:complete-cap}
For an \spectype $\Spec$ and an explicit relation
$E\subseteq P$, the following are equivalent:
\begin{enumerate}
  \item some system has Availability for $E$ and Partition Consistency;
  \item $\Spec$ satisfies Lifted Monotonicity for $E$.
\end{enumerate}
\end{theorem}

\begin{proof}[Proof sketch]
Consider the system whose strategies emit each output of
$E$ by the canonical output event of Section~\ref{sec:complete-calm}.  It has
Availability for $E$, and Lifted Monotonicity for $E$ gives the outputs it emits a
common \outnoun at every common \indesc of their inputs.  Conversely, given one
participant per row of $E$, each in its own block, Availability lets each
emit its row's output, and Partition Consistency then supplies the common
\outnoun.  Full proof in Appendix~\ref{app:proofs-sec4}.
\end{proof}

\begin{corollary}
\label{cor:complete-cap-S}
Some system has Availability and Partition Consistency if and only if $\Spec$
satisfies Lifted Monotonicity.  When it does, a \commitment-free system has
both: one with the empty basis, whose strategies may emit any legal output
$o$ by $\mathsf{output}(o)$, which applies no \commitment.
\end{corollary}

\begin{proof}[Proof sketch]
With $E=P$, Lifted Monotonicity for $E$ is Lifted Monotonicity itself, and the
exposure boundary makes every
output of the \commitment-free system available.  Full proof in Appendix~\ref{app:proofs-sec4}.
\end{proof}

A system might hope to keep more outputs available by issuing \commitments,
coordinating within each side of a partition.  It cannot: the impossibility
direction of the proof holds for every system, \commitment-free or not.  For
$E=P$, the system in the proof needs no \commitment at all.  For a smaller $E$,
its canonical output events may exclude rows in $P\setminus E$ and therefore
apply \commitments under the declared spec; serving only $E$ does not remove
those \commitments.  When Lifted
Monotonicity for $E$ fails, some output of $E$ waits for another block,
sacrificing Availability, or is emitted anyway, sacrificing Partition
Consistency.

\paragraph{Gilbert and Lynch.}
Their theorem is a case of Complete CAP.  Consider a register spec
whose inputs are sets of operations with their real-time precedence, and whose
outputs answer every operation of the input as some linearization
does~\cite{herlihy1990linearizability}.  Let $p$'s input contain only a write
of $v\neq v_0$, and $q$'s only a read.  The fiber at $p$'s input holds only the
write's acknowledgment; the fiber at $q$'s input, which contains no write,
holds only the answer $v_0$ to the read.  At the common \indesc where the write
precedes the read, every output in the fiber answers that same read with $v$.  That contradicts
the answer $v_0$; it is not a later read observing a newer value.  So no output
there \outrel $v_0$, and $\Spec$ does not satisfy Lifted Monotonicity.

By Complete CAP, then, no system keeps both outputs available and consistent across a partition, which is Gilbert and Lynch's theorem.  The proof needs less than the full hypotheses here, which
is why it yields Gilbert and Lynch's theorem exactly.  Place $p$ and $q$ in
separate blocks.  Availability is used only to make $p$ acknowledge the
write and $q$ answer the read; each fiber holds a single output, so any
response will do, which is Gilbert and Lynch's availability.  Partition
Consistency is used only to demand a common \outnoun of those two answers, a
single linearization that explains both, which is Gilbert and Lynch's
consistency.  No such \outnoun exists.

Appendix~\ref{app:cap-response} takes precedence from real time, extends
Complete CAP to systems that choose their responses when responses are not
forced, and derives
the theorem in Gilbert and Lynch's asynchronous model.
