\section{Functional CALM}
\label{sec:functional-calm}

This section focuses on functional specs, in which each input has a
single specified output.  We walk through the framework informally on an
election, state it precisely, and prove Functional CALM, identifying when an
output can be emitted without \commitment.

\subsection{The framework by example}
\label{sec:election-story}

We introduce the framework with a small election, illustrated in
Figure~\ref{fig:election-frames}.  Each row of the possibility table pairs
the ballots received so far with the permitted result; the column orders say how inputs \ingrow and which later outputs \outrelbase earlier ones.

Three voters $v_1,v_2,v_3$ each cast at most one immutable ballot for $a$ or
$b$.  The output is whichever candidate has two ballots, or $\bot$ while there
is no winner.  An input is a vector of the ballots received so far, one entry per voter, with a
dot for a ballot not yet received.  We write it as a string: $ab\cdot$ means
$v_1$ voted $a$, $v_2$ voted $b$, and $v_3$'s ballot has not arrived.  For brevity,
the figure shows only inputs \inrelpart $a\cdot\cdot$.

The two orders require thoughtful design.  The \emph{input order}
must record accumulated ballots: $ab\cdot$ \inrel $a\cdot\cdot$, while
$aa\cdot$ and $ab\cdot$ are incomparable.  The \emph{output order} says which
announcements are safe to build on: $\{\bot \OutputOrd a, \bot \OutputOrd b\}$.
$\bot$ claims nothing, so either winner
\outrel it, while $a$ and $b$ are incomparable.  In general, the functional table is \emph{monotone}
when
\[
  i\InputOrd j\quad\Longrightarrow\quad f(i)\OutputOrd f(j).
\]
Here, for example, the input sequence $a\cdot\cdot\InputOrd ab\cdot\InputOrd aba$
monotonically produces the output sequence $\bot\OutputOrd\bot\OutputOrd a$.

\paragraph{Input and determination.}
Each panel of Figure~\ref{fig:election-frames} shows a \emph{specification
state}: the \emph{current input} and the \emph{remainder table} of rows still
possible from it.  When $v_2$'s ballot for $b$ arrives, the input event
$\mathsf{input}(ab\cdot)$ produces panel~(b).  The table passively loses the rows
whose inputs do not extend $ab\cdot$, such as $aa\cdot$: those possibilities are
lost.  The \emph{upper fiber} (Definition~\ref{def:fiber}) is the set of outputs still possible in the
remainder table: $\{\bot,a,b\}$ in panel~(b).  If $v_2$ instead votes for $a$
(panel~(c)), the upper fiber is a singleton, $\{a\}$, and we call such
states \emph{determined}.  In this case, input alone has determined an outcome,
without \commitment.

\paragraph{Output and consistency.}
Emitting $o$ is an \emph{output event} $\mathsf{output}(o)$: it keeps only the
rows whose outputs \outrelbase $o$, since later outputs must not contradict it.
In a functional table, $o$ is a \emph{legal output} when everything in the
upper fiber already \outrel $o$, so the event removes nothing.  Thus
$\bot$ is legal in panels~(a) and~(b), and $a$ in panel~(c).  When $o$ is not
legal, the event removes the rows that conflict with $o$, ruling out their
inputs; that removal is a \commitment.

Panel~(d), by contrast, adds a decision by the \emph{system}: the implementation
that receives the ballots and announces the result.  Here
the system acts as a registrar that, when it emits $\bot$ at $ab\cdot$, also
closes the polls.  Closing the polls is a \emph{\commitment}: it removes the
still-possible rows $aba$ and $abb$, though the current input stays $ab\cdot$.
The upper fiber becomes $\{\bot\}$, so $\bot$ is the determined result.
The spec did not require this \commitment: emitting $\bot$ removes nothing by itself, since every output still possible extends $\bot$.  Closing the polls is
the registrar's own fateful decision.

Figure~\ref{fig:nonmonotone-frame} considers a variant of our example that
changes only the output order: all outputs are incomparable, including $\bot$
for no winner. Under this order (known as the \emph{equality order}), $\bot$ is
incompatible with future winners, so emitting it requires a \commitment.  That
change in the output order is Functional CALM in miniature: the spec is monotone
under the original order, so later outputs \outrelbase every earlier one; under
the equality order it is non-monotone, and some outputs can be emitted only with a \commitment.

To see why, we follow the events.  A \emph{run} is a sequence of input and output
events from a starting state, like the sequences that produce the panels of
Figure~\ref{fig:election-frames}.  Under the equality order, rows
$(ab\cdot,\bot)$ and $(aba,a)$ have the common \indesc $aba$, but no output at
$aba$ \outrel both $\bot$ and $a$.  So a run that emits $\bot$ at $ab\cdot$ and
a run that receives $aba$ and emits $a$ can never be reconciled at $aba$.
Emitting $\bot$ is safe only with the \commitment that rules out $aba$ and
$abb$; without it, the two runs would diverge for good.  This argument uses only
the table's rows and its two orders, so the need for the \commitment is a
property of the spec, not of any system that implements it.

Runs are the foundation of the consistency side of CALM.  Input and output
events form a transition system over specification states, and the runs of a
spec are \emph{consistent} when they are \emph{confluent}: runs whose inputs have a
common \indesc can always be continued to a common state there.
Section~\ref{sec:functional-calm-theorem} shows that for functional tables the
runs are consistent exactly when the spec is monotone.
Appendix~\ref{app:notation} collects the notation for reference.

\subsection{Specifications and states}
\label{sec:functional-specifications}

\begin{definition}[Functional \spectype, total]
\label{def:functional-specification}
A \emph{functional \spectype} is a tuple
\[
  \Spec=(I,\InputOrd,O,\OutputOrd,P),
\]
  where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered input and
  output types, and $P\subseteq I\times O$ is its \emph{possibility relation}:
  a typed relation with schema $(\mathrm{in},\mathrm{out})$ in which every
  input appears in at least one row ($P$ is \emph{total} on $I$) and at most one
  (a functional dependency):
\[
  (i,o)\in P\ \land\ (i,o')\in P
  \quad\Longrightarrow\quad o=o'.
\]
\end{definition}

The unique output paired with $i$ induces the function
\[f:(I,\InputOrd)\to(O,\OutputOrd)\]
with $P=\{(i,f(i)):i\in I\}.$
We call $\InputOrd$ the \emph{input order}.  Inputs are \emph{cumulative}, since an
output may depend on everything a system has received: an input
records everything received so far, not a single message, and $i\InputOrd j$
means that $j$ contains at least the input information in $i$.  We say that $j$
\emph{\inrel} $i$, or is an \emph{\indesc} of $i$; every input is an \indesc of itself. We call $\OutputOrd$ the
\emph{output order}: $o\OutputOrd u$ means that $u$ subsumes every
externally visible claim in $o$ and may add more, and we say that $u$
\emph{\outrel} $o$.  In either domain, an element above another is an extension of it.  We write $\InputGe$ and $\OutputGe$ for the converse orders.

A \emph{common \indesc} $j$ of
$i_1,\ldots,i_k$ is an input that \inrel every $i_r$, and a
\emph{common \outnoun} of $o_1,\ldots,o_k$ is an output that \outrel each $o_r$.

A row $(k,u)$ is \emph{\outrelpast} by another row $(k,w)$ at the same input
when $w$ \outrel $u$.

A functional spec is monotone when growing input only ever extends its output.

\begin{definition}[Functional monotonicity]
\label{def:functional-monotonicity}
A functional \spectype $\Spec$, with induced function $f$, is
\emph{monotone} if
\begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
\end{equation}
\end{definition}

In a monotone functional spec, if an output is emitted at some input, the
remainder table contains only rows whose input is an \indesc, and whose output
is an \outnoun.  So no output is ever contradicted at a later input.

\paragraph{Relational notation.}
For a relation $R\subseteq I\times O$, we say that a row $(k,u)$ is
\emph{at input} $k$.  To describe tables compactly, a predicate on the columns
$\mathrm{in}$ and $\mathrm{out}$ in square brackets selects rows, and commas
separate conjuncts: $R[\mathrm{in}\InputGe j,\ \mathrm{out}\OutputGe o]$ is the
table of rows whose input \inrel $j$ and whose output \outrel $o$.  As in
relational algebra, $\pi_{\mathrm{out}}(R)$ is the set of outputs in $R$.

A spec describes every permitted input/output pair.  During execution,
input arrives and outputs are emitted, so only some of those pairs remain
possible.  The changing state of the spec, illustrated by the non-gray text in
the panels of Figure~\ref{fig:election-frames}, is defined as follows.

\begin{definition}[Specification state, current input, remainder table]
\label{def:residual-state}
Given a specification $\Spec=(I,\InputOrd,O,\OutputOrd,P)$, a \emph{specification state} is a
pair $\sigma=(i,R)$, where $i\in I$ is the \emph{current input} and
$R\subseteq P$ is the \emph{remainder table}, such that:
\begin{enumerate}
  \item $R$ contains a row at $i$; and
  \item $R$ contains only rows at \indescs of $i$: every row $(k,o)\in R$ satisfies $i\InputOrd k$.
\end{enumerate}
\end{definition}

\begin{definition}[Legal input]
\label{def:legal-input}
An input $k$ is \emph{legal} at a state $\sigma=(i,R)$ when $R$ contains a row at $k$.
\end{definition}

Rows are never added during execution.  The \emph{canonical state at $i$} is
the state at $i$ with no rows removed: it keeps every row of $P$ at $i$ and its
\indescs, and it is the state of a system that has received $i$ and emitted
nothing:
\begin{equation}
  \sigma_P(i)=\bigl(i,\ P[\mathrm{in}\InputGe i]\bigr).
  \label{eq:canonical-state}
\end{equation}
An input event from a canonical state leads to another canonical state.

Two sets of outputs recur throughout: those a table permits at a given input,
and those it still permits there or once more input arrives.  In panel~(b) of
Figure~\ref{fig:election-frames}, the first is $\{\bot\}$ at $ab\cdot$, and the
second, shaded, is $\{\bot,a,b\}$.

\begin{definition}[Fiber, upper fiber]
\label{def:fiber}
Let $R$ be a table and $k$ an input.  The \emph{fiber} of $R$ at $k$ is
$R(k)=\pi_{\mathrm{out}}(R[\mathrm{in}=k])$, the outputs paired with $k$.  The
\emph{upper fiber} of $R$ at $k$ is $\pi_{\mathrm{out}}(R[\mathrm{in}\InputGe
k])$, the outputs paired with $k$ or any of its \indescs.
\end{definition}

A functional fiber has at most one value.  For a state $\sigma=(i,R)$, the
upper fiber at $i$ is $\pi_{\mathrm{out}}(R)$: every output still possible.

\subsection{Input and output events}
\label{sec:functional-events}

Two events change state: input events incorporate new information, while
output events record what the system has emitted.  Each may remove rows from
the remainder table.

\paragraph{Input events.}
Each event applies a selection predicate on one column of the remainder table.
For a state $(i,R)$ and legal input $j$ with $i\InputOrd j$, the input event is
\begin{equation}
  (i,R)\xrightarrow{\mathsf{input}(j)}
  \bigl(j,\ R' = R[\mathrm{in}\InputGe j]\bigr).
  \label{eq:input-event}
\end{equation}
It makes $j$ current and drops the rows whose input does not \inrelbase $j$,
which we call \emph{input loss}.

An input event names the cumulative input $j$: everything received so far,
including all of $i$, not just what arrived since $i$.  Thus $\mathsf{input}(j)$ then $\mathsf{input}(k)$ has the
effect of $\mathsf{input}(k)$ alone; $\mathsf{input}(i)$ at
$(i,R)$ has no effect.

\paragraph{Output events.}
Inputs arrive from the environment, but outputs are the system's to choose, and
once emitted they cannot be retracted: later outputs must \outrelbase earlier
ones.

At state $(i,R)$, the current input has a unique row $(i,o)$, so $o$ is the only
output the system may emit.

\begin{definition}[Legal output]
\label{def:exposable}
The output $o$ at $(i,R)$ is a \emph{legal output} when every output in the
upper fiber \outrel $o$.
\end{definition}

Emitting an output can require removing rows that no remaining output covers.
We call such a removal a \commitment:

\begin{definition}[\Commitment]
\label{def:commitment}
A \emph{\commitment} is a partial function $e$ on specification states that
removes a nonempty set of rows, none of which is \outrelpast by a row that
remains at the same input.  That is, whenever $e(i,R)=(j,R')$, we have
$R'\subsetneq R$ and
\begin{equation}
  (k,u)\in R\setminus R',\ (k,w)\in R'
  \quad\Longrightarrow\quad
  u\not\OutputOrd w.
  \label{eq:commitment-unsubsumed}
\end{equation}
It leaves the current input unchanged: $j=i$.
\end{definition}

In a functional spec each input has one row, so the last condition always
holds: a \commitment rules out the inputs of the rows it removes.

Since every later output must \outrelbase $o$, a system cannot simply emit a
non-legal $o$.  It must emit $o$ atomically with a \commitment that removes every
row whose output does not \outrelbase $o$.  In a functional spec each such row
is the only row at its input, so the \commitment rules out those inputs.

\begin{definition}[Output event]
\label{def:output-event}
At a state $(i,R)$ with current output $o$, the \emph{output event}
$\mathsf{output}(o)$ atomically keeps only the rows whose outputs \outrelbase $o$,
and then emits $o$:
\begin{equation}
  (i,R)\xrightarrow{\mathsf{output}(o)}\bigl(i,\ R' = R[\mathrm{out}\OutputGe o]\bigr).
  \label{eq:output-action}
\end{equation}
\end{definition}

\begin{definition}[Canonical \commitment]
\label{def:canonical-commitment-functional}
When $o$ is not legal, equivalently $R'\neq R$, some rows have outputs that do
not \outrelbase $o$, and the transition applies the \emph{canonical
\commitment} $x_o(i,R)=(i,R')$, which removes them.  In a functional table each
input has only one row, so $x_o$ rules out those rows' inputs ($x_o$ is a \commitment).
\end{definition}

Thus $o$ is legal exactly when $\mathsf{output}(o)$ applies no \commitment.  The
current row $(i,o)$ remains, since $o$ \outrel itself, so the event always ends
at a specification state with current input $i$.  A \commitment removes rows that input alone would
keep; after the canonical \commitment, the inputs of the removed rows are no
longer legal.  This section uses only canonical \commitments.  Systems
may issue more \commitments than an output requires, as the registrar does in
Figure~\ref{fig:election-frames}(d), but such extra \commitments are a
system's choice, not the spec's (Section~\ref{sec:systems}).

\paragraph{Determination.}
A spec with multiple distinct outputs can have undetermined states, as in panel~(b) of
Figure~\ref{fig:election-frames}.
A state is \emph{determined} when its upper fiber has one element: one result
remains, whatever legal input still arrives.  This is a property of the state
alone.  \emph{Determination} is the process of reaching a determined state.
An input event can achieve determination through input loss, as in panel~(c), and a
\commitment can do so by ruling out inputs that would otherwise remain possible,
as in panel~(d).
An event from a determined state always leads to another determined state with the same output:
events only remove rows, and a row at the current input always remains.

\subsection{Executions and consistency}
\label{sec:executions}

Input and output events move a spec from state to state.  We now consider
sequences of them, which we call runs, and ask when runs that took different
paths can still be brought to a common state.  The answer turns on the
existence of one row: some row at a common \indesc must survive in every run.

\begin{definition}[Specification event]
\label{def:specification-event}
Input and output events are \emph{specification events}: they change the
specification state.  We call them simply \emph{events} when unambiguous.
\end{definition}

\begin{definition}[Transition system]
\label{def:transition-system}
The \emph{transition system} consists of specification states and
specification events.
\end{definition}

\begin{definition}[Canonical run]
\label{def:run}
A \emph{canonical run}, or just \emph{run}, is any finite transition sequence of the transition system from the
canonical state $\sigma_P(i)$ at some input $i$.
\end{definition}

Runs range over every behavior the spec permits, not only the behaviors a
particular system happens to produce.  A system that never uses some of the
spec's latitude is better described by a narrower spec.  For the spec as
written, we assume that any permitted behavior may occur.

A run is \emph{\commitment-free} when none of its output events applies a
\commitment.  A state is \emph{reachable without \commitment} when
some \commitment-free run reaches it.

Input and output events are both relational selections, and selections
commute, so a run's remainder table depends only on its last input and the
outputs it emitted:

\begin{lemma}[Rows remaining after a run]
\label{lem:run-residual}
If a run ends at current input $i$ after emitting
$o_1,\ldots,o_m$, its remainder table is
\begin{equation}
  P[\mathrm{in}\InputGe i,\ \mathrm{out}\OutputGe o_1,\ \ldots,\
    \mathrm{out}\OutputGe o_m],
  \label{eq:run-residual}
\end{equation}
the rows whose input \inrel $i$ and whose output \outrel each $o_r$.
\end{lemma}

\begin{proof}
See Appendix~\ref{app:proofs-sec2}.
\end{proof}

For example, in the equality-order variant of
Figure~\ref{fig:nonmonotone-frame}, a run that emits $\bot$ at $ab\cdot$ keeps
$P[\mathrm{in}\InputGe ab\cdot,\ \mathrm{out}\OutputGe\bot]$: the single row
$(ab\cdot,\bot)$, as the figure shows.

To compare runs that end at different inputs, we consider a common \indesc
of those inputs.

\begin{definition}[Confluence at an input]
\label{def:confluence}
A finite family of runs ending at states $(i_1,R_1),\ldots,(i_k,R_k)$ is \emph{confluent at} $j$, a common \indesc of their current inputs, when each can be continued to a common state with current input $j$.
\end{definition}

\begin{definition}[Consistency]
\label{def:consistency}
The runs of an \spectype are \emph{consistent} when every finite family of
them is confluent at every common \indesc of their current inputs.
\end{definition}

Consistency requires confluence at every common \indesc of the runs' current
inputs, not just at some larger common \indesc that arrives later.  Otherwise
the runs could emit conflicting outputs before that larger input arrives.
In the equality-order election, $f(ab\cdot)=\bot$ and $f(aba)=a$ are
incomparable.  One run can emit $\bot$ at $ab\cdot$, while another accepts
$aba$ and can emit $a$.  The two runs are not confluent at their common \indesc $aba$, and waiting cannot
retract either output from the environment.  More generally, even when later
input could bring the runs to a common state, the environment may already have
acted on the outputs through channels the system does not see, as in Lamport's
``anomalous behavior''~\cite{lamport1978time}. And even when such a larger input exists, it might
never arrive.

We can now state the condition promised above: some row at the common
\indesc must survive in every run.

\begin{proposition}[Survivor test]
\label{prop:confluence}
Runs ending at states $(i_r,R_r)$, $r=1,\ldots,k$, are confluent at a common
\indesc $j$ of their current inputs if and only if some row $(j,u)$ is in every
$R_r$.  For any such $u$, $\mathsf{input}(j)$ followed by $\mathsf{output}(u)$
brings every run to the same state,
$\bigl(j,\ P[\mathrm{in}\InputGe j,\ \mathrm{out}\OutputGe u]\bigr)$.
\end{proposition}

\begin{proof}[Proof sketch]
Rows are never added, so a row of a common state at $j$ was already in every
$R_r$.  Conversely, the two events above reach a common state.  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

In a functional spec the only row at $j$ is $(j,f(j))$, so the test
asks whether $(j,f(j))$ survives in every run.

Consistency thus ensures that runs never diverge irreparably: there is no
``split brain.''  Whatever events a finite collection of runs contains, at any
common \indesc of their current inputs, some state is reachable by every run
and contradicts none of their outputs; Proposition~\ref{prop:confluence}
identifies it.  Consistency is a safety property of the spec's runs: it guarantees that a common
state exists, not that a system reaches it
(Section~\ref{sec:commitment-conflict}).  Reaching it takes an algorithm,
message delivery, and a termination argument, which belong to the operational
model in which a spec is realized.

Whether runs are consistent depends on the outputs they emit.  Confluence
fails exactly when some run can emit an output that is not legal:

\begin{lemma}[Confluence and legality]
\label{lem:confluence-legality}
The runs of an \spectype are consistent if and only if every output that a
run can emit is legal at the state where it is emitted.
\end{lemma}

\begin{proof}[Proof sketch]
If a run can emit an output $o$ that is not legal, $\mathsf{output}(o)$
removes some row $(k,x)$ such that no row at $k$ \outrel both $x$ and $o$.  One
continuation of the run emits $o$; another takes $\mathsf{input}(k)$ and then
emits $x$.  The two share no row at $k$, so by the Survivor test they are not
confluent at $k$.  Conversely, suppose every output is legal, and take a family of runs and
a common \indesc $j$.  Pick for each run a row $(i_r,u_r)$ remaining at its
current input; $u_r$ \outrel everything that run emitted
(Lemma~\ref{lem:run-residual}).  Each $u_r$ is legal at $\sigma_P(i_r)$, the
canonical state of its input, so every output at an \indesc of $i_r$ has an
\outnoun there that also \outrel $u_r$.  Taking the runs one at a time gives
$u\in P(j)$ that \outrel every $u_r$.  The row $(j,u)$ remains in every run,
and the Survivor test gives confluence.  Full proof in
Appendix~\ref{app:proofs-sec2}.
\end{proof}

\subsection{The Functional CALM theorem}
\label{sec:functional-calm-theorem}

Monotonicity is defined by a spec's table and orders alone, consistency by its
runs.  Functional CALM shows that one holds exactly when the other does.  By
Lemma~\ref{lem:confluence-legality}, the question is when every output a run
can emit is legal.  In the functional case, monotonicity has a strong
consequence: emitting outputs never changes the state, which depends only on
the input.

\begin{corollary}[State is fixed by input]
\label{cor:state-by-input}
In a monotone functional specification, every run ending at current
input $i$ is in the canonical state $\sigma_P(i)$, whatever outputs it emitted
along the way.
\end{corollary}

\begin{proof}[Proof sketch]
By monotonicity, the outputs a run emits remove no row at an \indesc
of $i$ (Lemma~\ref{lem:run-residual}).  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

To be confluent at a common \indesc $j$, each run therefore needs only the
single event $\mathsf{input}(j)$, which takes it to $\sigma_P(j)$, the state of a
run that starts with all of the input.  Knowing the input is enough to know the state, and with it the one
output $f(j)$.

Monotonicity also governs legality:

\begin{proposition}[No-\commitment test]
\label{prop:functional-exposure-boundary}
A functional \spectype is monotone if and only if every output at
every state reachable without \commitment is legal.
\end{proposition}

\begin{proof}[Proof sketch]
By Corollary~\ref{cor:state-by-input}, monotone $f$ reaches only canonical
states. At $\sigma_P(i)$, which input alone reaches, $f(i)$ is legal exactly
when $f$ is monotone at $i$.  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

A monotone spec can thus emit every current output without \commitment. If a
spec is non-monotone, then for some $i\InputOrd k$,
$f(i)\not\OutputOrd f(k)$, so at $\sigma_P(i)$ the event
$\mathsf{output}(f(i))$ applies $x_{f(i)}$ and rules out input $k$.

\begin{theorem}[Functional CALM]
\label{thm:functional-calm}
The runs of a functional \spectype are consistent if and only if the spec is
monotone.
\end{theorem}

\begin{proof}[Proof sketch]
By Lemma~\ref{lem:confluence-legality}, the runs are consistent exactly when
every output a run can emit is legal.  If every output at every state reachable
without \commitment is legal, every run is reachable without \commitment, so
this is the condition of Proposition~\ref{prop:functional-exposure-boundary},
which holds exactly when the spec is monotone.  Full proof in
Appendix~\ref{app:proofs-sec2}.
\end{proof}

Functional CALM restates the familiar CALM dichotomy at the level of the spec
rather than inside a particular programming language.
Classical CALM fits, with inputs $J$ as sets of facts ordered by
inclusion and output views $Q(J)$ ordered by inclusion.  Functional
monotonicity becomes
        \begin{equation}
  J\subseteq J'
  \quad\Longrightarrow\quad
  Q(J)\subseteq Q(J'),
  \label{eq:query-monotonicity}
        \end{equation}
the standard definition of a monotone query~\cite{abiteboul1995foundations};
positive Datalog satisfies it, and negation may not.  Functional CALM
generalizes the statement to arbitrary input and
output orders, whatever formalism expresses the spec.  CRDT state specs have the same functional shape, with received payloads ordered by inclusion and states by the semilattice order~\cite{shapiro2011crdt} (Sections~\ref{sec:query-instance}
and~\ref{sec:crdt-instance}).
