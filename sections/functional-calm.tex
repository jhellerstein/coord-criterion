\section{Functional CALM}
\label{sec:functional-calm}

The CALM Theorem was proved for queries in a logic programming language,
evaluated by relational transducers, and its applicability outside that
setting was never made precise.  Here we use a simpler model that applies to
any specification expressible as an input/output relation over ordered domains.  A
specification describes allowed input/output
behavior without committing to a language, placement, protocol, or message
schedule.  This section addresses the case that prior work on both CALM and
CRDTs shared: specifications that are functions, in which each
input has a single specified output.  Section~\ref{sec:election-story} walks
through the framework informally on an election.
Section~\ref{sec:functional-specifications} defines specifications, states, and
commitment bases; Section~\ref{sec:functional-events} defines input and output
events; Section~\ref{sec:determination} assembles executions and Consistency;
Section~\ref{sec:functional-calm-theorem} proves Functional CALM; and
Section~\ref{sec:canonical-transition-system} identifies when an output can be
emitted without commitment.

Before the full formalism, we explain the framework by example. We consider a small election,
illustrated in Figure~\ref{fig:election-frames}.  Each row of the specification table pairs
the ballots received so far with the permitted result; orders on the columns
describe how inputs grow and which later outputs preserve earlier ones.  This
section considers tables in which each input has exactly one output;
Section~\ref{sec:ambiguous-specifications} later removes that functional
dependency.

Three voters $v_1,v_2,v_3$ each cast at most one immutable ballot for $x$ or
$y$.  The output is whichever candidate has two ballots, or $\bot$ while there
is no winner.  An input is the ballots received so far, written as a
three-character string with a dot for a ballot not yet received.  For brevity,
the figure shows only inputs extending $x\cdot\cdot$.

The two orders express different interface decisions.  The \emph{input order}
records accumulated ballots: $xy\cdot$ refines $x\cdot\cdot$, while
$xx\cdot$ and $xy\cdot$ are incomparable.  The \emph{output order} records
preservation of visible claims: $\bot$ lies below either winner, while $x$ and
$y$ are incomparable.  In general, the functional table is \emph{monotone}
when
\[
  i\InputOrd j\quad\Longrightarrow\quad f(i)\OutputOrd f(j).
\]
Here, for example, the input sequence $x\cdot\cdot\InputOrd xy\cdot\InputOrd xyx$
monotonically produces the output sequence $\bot\OutputOrd\bot\OutputOrd x$.

\paragraph{Input and determination.}
Each panel captures the state of the system: a pair of a \emph{current input}
and a \emph{remainder table} of rows
still possible from that input.  When $v_2$'s ballot for $y$ arrives, the event
$\mathsf{input}(xy\cdot)$ produces panel~(b), retiring rows whose inputs no
longer extend the ballots received.  The \emph{upper fiber} is the set of
outputs in the remaining current and refining rows; in panel~(b) it is
$\{\bot,x,y\}$.

If $v_2$ instead votes for $x$, as in panel~(c), the upper fiber is $\{x\}$.  The state
is \emph{determined}: input has resolved the ambiguity alone, without commitment.  In
panel~(d), by contrast, a registrar closes the polls at $xy\cdot$, removing
the still-valid $xyx$ and $xyy$ rows but leaving the current input unchanged.
This is an irrevocable \emph{seal commitment}, which determines $\bot$.  Commitments belong
to a system's declared \emph{commitment basis} $\mathcal B$, not to the
specification itself; a system whose polls cannot close does not have this commitment in its basis.

\paragraph{Output and consistency.}
An output $o$ is \emph{exposable} when every output still possible at the
current input or a valid refinement can preserve it.  Hence $\bot$ is exposable
in panels~(a) and~(b), and $x$ in panel~(c).  The atomic
$\mathsf{output}(o)$ action has three parts: apply any required commitments,
retire rows superseded by $o$, and emit $o$.  They occur in one transition.  The
emission remains explicit in the history because the uncontrolled environment
may use it when choosing later input.

Figure~\ref{fig:nonmonotone-frame} considers a variant of our example that
changes only the output order: all outputs are incomparable, including $\bot$
for no winner.  At $x\cdot\cdot$, $\bot$ is then incompatible with future
winners.  Emitting it requires sealing those winner-producing refinements; the
figure shows the stronger, optional action of closing the polls and sealing all
refinements, including $xy\cdot$, which also outputs $\bot$.  This isolates the
Functional CALM boundary: under the original monotone order, outputs remain
valid as input grows; under the equality order, some outputs require commitment
before they can be emitted.

Input and output actions form a transition system between system states.  A
specification is \emph{consistent} when paths with compatible inputs can still
converge after any way of extending all of those inputs.  Functional CALM proves
that a functional specification is consistent exactly when it is monotone.

The rest of this section formalizes these notions; Figure~\ref{fig:formalism-summary}
serves as a reference.

\subsection{Specifications, states, and commitments}
\label{sec:functional-specifications}

We begin by defining the core structures of our framework: specifications and commitment bases.
\begin{definition}[Functional ordered specification]
\label{def:functional-specification}
A \emph{functional ordered specification} is a tuple
\[
  \Spec=(I,\InputOrd,O,\OutputOrd,S),
\]
where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered input and
output types, and $S\subseteq I\times O$ is a typed relation that is total on
$I$ and satisfies the functional dependency from input to output: every input
appears in at least one row, and
\[
  (i,o)\in S\ \land\ (i,o')\in S
  \quad\Longrightarrow\quad o=o'.
\]
\end{definition}

The unique output paired with $i$ induces the function
\[f:(I,\InputOrd)\to(O,\OutputOrd)\] 
with $S=\{(i,f(i)):i\in I\}.$
We call
$\InputOrd$ the \emph{input-refinement order}: $i\InputOrd j$ means that $j$
contains at least the input information in $i$.  We call $\OutputOrd$ the
\emph{output-refinement order}: $o\OutputOrd u$ means that $u$ preserves every
externally visible claim in $o$ and may add more.

The two orders are independent: the input order compares inputs; the output
order compares outputs.  Either may be the \emph{equality order}, under which an
element refines only itself.

\begin{definition}[Monotonicity]
\label{def:functional-monotonicity}
A functional ordered specification $\Spec$, with induced function $f$, is
\emph{monotone} if
\begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
\end{equation}
\end{definition}

Thus an output emitted from partial input remains valid as more input arrives.
For $i,k\in I$, write $i\prec_I k$ when $i\InputOrd k$ and $i\neq k$, and
write
\[
  \mathord\uparrow_I i=\{k\in I:i\InputOrd k\}.
\]

A specification describes every permitted input/output pair.  During execution,
input arrives and choices become binding, so only some of those pairs remain
possible.  The evolving state of the specification is defined as follows.

\begin{definition}[Specification state]
\label{def:residual-state}
Given a specification $\Spec=(I,\InputOrd,O,\OutputOrd,S)$, a \emph{specification state} is a
pair $\sigma=(i,R)$, where $i\in I$ is the \emph{current input} and
$R\subseteq S$ is the \emph{remainder table}, such that:
\begin{enumerate}
  \item $R$ contains a row at $i$; and
  \item every row $(k,o)\in R$ satisfies $i\InputOrd k$.
\end{enumerate}
An input $k$ is \emph{valid} in $\sigma$ when $R$ contains a row at $k$, and
otherwise \emph{invalid}.
\end{definition}

Rows are never added during execution.  For each input $i$, the \emph{canonical
state at $i$} retains all rows at $i$ and its refinements:
\begin{equation}
  \sigma_S(i)=\bigl(i,\ \{(k,o)\in S:\ i\InputOrd k\}\bigr).
  \label{eq:canonical-state}
\end{equation}

The specification and its states say which behaviors are possible, but not
which possibilities the system is authorized to rule out.  That authority is a
separate part of the model, as follows.

\begin{definition}[Commitment basis]
\label{def:commitment-basis}
A \emph{commitment} is a partial function on specification states that preserves
the current input and strictly reduces the remainder table: whenever
$c(i,R)=(i,R')$, we have $R'\subsetneq R$.  A \emph{commitment basis}
$\mathcal B$ is a set of commitments available to a system.  In a functional
specification, removing a row invalidates its input; we call such an action a
\emph{seal commitment}.
\end{definition}

Note that commitments are partial functions:  a system may be designed to
authorize a commitment only at states satisfying an application-specific
precondition.  For example, in Figure~\ref{fig:election-frames}(d), we defined the
poll-closing commitment at every state; a different system might authorize it
only after some candidate has a majority.

A commitment basis therefore describes the authority of a particular system.
To characterize the behaviors permitted by the specification independent of
any particular system, we derive a canonical basis from $S$.  It supports every
permitted output and, when an output requires a commitment, removes only the
rows incompatible with that output's promise.


\begin{definition}[Canonical seal commitment, canonical basis]
\label{def:canonical-commitment-basis}
For a state $(i,R)$ and its current row $(i,o)$, retaining the promise made by
$o$ permits exactly the rows
\begin{equation}
  R_o=R\mathbin{\upharpoonright_O}o
      =\{(k,u)\in R:o\OutputOrd u\}.
  \label{eq:residual-refining-fibers}
\end{equation}
If $R_o\neq R$, reaching $R_o$ removes the sole row at one or more inputs and
therefore requires a seal commitment.  
The \emph{canonical seal commitment}
for $(i,R)$ and $o$ is the partial function defined at that state by
\begin{equation}
  s_{(i,R),o}(i,R)=(i,R_o),
  \label{eq:canonical-seal-commitment}
\end{equation}
when $R_o\neq R$.  The \emph{canonical commitment basis}
$\mathcal B_S^{\mathrm{can}}$ contains every such commitment.  It supplies the
least restrictive commitment needed to retain the promise made by each
permitted current output.
\end{definition}

\subsection{Input and output events}
\label{sec:functional-events}

With the definitions of our core objects now in hand, we are
ready to define the events that change state and emit results.

\paragraph{Input events.}
For a state $(i,R)$ and valid input $j$ with $i\InputOrd j$, the input event is
\begin{equation}
  (i,R)\xrightarrow{\mathsf{input}(j)}
  \bigl(j,\ R\mathbin{\upharpoonright_I}j\bigr),
  \qquad
  R\mathbin{\upharpoonright_I}j=\{(k,u)\in R:\ j\InputOrd k\}.
  \label{eq:input-event}
\end{equation}
It makes $j$ current and \emph{retires} every row whose input does not refine $j$.

An input event records a new cumulative input $j$, not how $j$ was assembled.
The accumulation of inputs is handled outside the scope of our discussion.
Our framework does not require cumulative inputs to come from a least common
refinement or a lattice, only that they grow according to $\InputOrd$.  For example,
interleavings of two sequences (e.g., schedules from two independent transactions sharing
no variables) form a partial order, but not a lattice---they have many incomparable
refinements, rather than one distinguished least common refinement. This poses no
difficulty in our framework.

Because inputs are cumulative, applying
$\mathsf{input}(j)$ and then $\mathsf{input}(k)$ has the same effect as applying
$\mathsf{input}(k)$ directly; $\mathsf{input}(i)$ at $(i,R)$ has no effect.

\paragraph{Output events.}
At state $(i,R)$, an output event $\mathsf{output}(o)$ may apply a finite,
possibly empty sequence of commitments from the system's basis and then emit
$o$.  If the commitments reach $(i,R')$, the event is valid when
\begin{equation}
  (i,o)\in R'\subseteq R_o.
  \label{eq:supported-output-action}
\end{equation}
Thus every output left possible after the event preserves $o$.  A noncanonical
basis may remove more rows than this promise requires.

Under the canonical basis, the event applies $s_{(i,R),o}$ when $R_o\neq R$
and no commitment when $R_o=R$.  In either case its target is exactly $R_o$:
\begin{equation}
  (i,R)\xrightarrow{\mathsf{output}(o)}(i,R_o).
  \label{eq:output-action}
\end{equation}
The event and its row removals are atomic, and the execution records the
commitments it applies.  Section~\ref{sec:safe-exposure} extends output events
with output retirement when the functional dependency is removed.

With states, authority, and events defined, we can assemble executions and ask
whether paths through the specification can be reconciled.

\subsection{Executions and consistency}
\label{sec:determination}

\begin{definition}[Transition system and run]
\label{def:io-transition-system}
\label{def:transition-system}
The \emph{transition system} consists of specification states and the input and
output events above.  A \emph{run} is any finite transition sequence from the canonical state
$\sigma_S(i)$ at some input $i$.  Unless stated otherwise, runs use the
canonical commitment basis.
\label{def:run}
\end{definition}

A specification state is \emph{run-generated} when it is reachable by a run.
This is a provenance condition, not another local invariant on a remainder
table.

\begin{lemma}[Rows remaining after a run]
\label{lem:run-residual}
A run starts at the canonical state $\sigma_S(i_0)$, ends at $(i,R)$, and contains output events
emitting $o_1,\ldots,o_m$.  Its final state is
\begin{equation}
  \left(i,\ \left\{(k,x)\in S:
    \begin{array}{l}
      i\InputOrd k,\ \text{and}\\
      o_\ell\OutputOrd x\ \text{for every }\ell
    \end{array}
  \right\}\right).
  \label{eq:run-residual}
\end{equation}
\end{lemma}

\begin{proof}
Each input event intersects $R$ with $\{(k,x):j\InputOrd k\}$ and each
canonical output event with $\{(k,x):o\OutputOrd x\}$.  These intersections
commute, and the input restrictions compose to the restriction at the final
input $i$.
\end{proof}

A \emph{common refinement} of inputs $i_1,\ldots,i_k$ is an input $j$ with
$i_r\InputOrd j$ for every $r$.

\begin{definition}[Consistency]
\label{def:consistency}
A functional ordered specification is \emph{consistent} when every finite
family of runs under its canonical commitment basis is confluent: if the runs
end at states $(i_1,R_1),\ldots,(i_k,R_k)$ and $j$ is a common refinement of
their current inputs, one state with current input $j$ is reachable by input and
output events from each endpoint.  The runs are then \emph{confluent at} $j$.
\end{definition}

Consistency quantifies over run-generated endpoints, not arbitrary specification
states or commitments.  The canonical basis exercises every output permitted by
the specification; a weaker basis could hide non-monotonicity by disabling a
conflicting output.

\begin{proposition}[Confluence at a common refinement]
\label{prop:confluence}
Runs ending at states $(i_1,R_1),\ldots,(i_k,R_k)$ are confluent at $j$ if and
only if some row at $j$ survives in every final state,
\begin{equation}
  (j,u)\in R_r\quad\text{for every }r,\ \text{for some }u\in O.
  \label{eq:reconciliation}
\end{equation}
For any such $u$, $\mathsf{input}(j)$ followed by $\mathsf{output}(u)$ takes
every endpoint to the state
$\bigl(j,\{(k,x)\in S:j\InputOrd k,\ u\OutputOrd x\}\bigr)$.
\end{proposition}

\begin{proof}
A common state with current input $j$ has a row at $j$, and that row belongs to
every $R_r$.  Conversely, let $(j,u)$ belong to every $R_r$.  Then
$\mathsf{input}(j)$ is defined at every $(i_r,R_r)$.  By
Lemma~\ref{lem:run-residual}, $(j,u)\in R_r$ says that $u$ refines every output
emitted on run $r$.  After $\mathsf{input}(j)$ and $\mathsf{output}(u)$, the
same lemma leaves exactly the rows of $S$ above $j$ and $u$, independent of the
starting run.
\end{proof}

A single run can witness inconsistency: an output event for one permitted output
may remove every row at a refinement of its current input.  Consistency describes
no protocol and promises no delivery or termination; Section~\ref{sec:discussion}
returns to this.

\subsection{The Functional CALM theorem}
\label{sec:functional-calm-theorem}

\begin{theorem}[Functional CALM]
\label{thm:functional-calm}
A functional ordered specification is consistent if and only if it is
monotone.
\end{theorem}

\begin{proof}
Every input has one row.  By Lemma~\ref{lem:run-residual}, a run ending at
input $i$ retains $(k,f(k))$ at $k\succeq_I i$ exactly when every output
$f(i_\ell)$ emitted on the run satisfies $f(i_\ell)\OutputOrd f(k)$.  By
Proposition~\ref{prop:confluence}, a finite family of runs is confluent at a
common refinement $k$ exactly when every output emitted on any run lies below
$f(k)$.  If $f$ is monotone this holds because each emitted $f(i_\ell)$ has
$i_\ell\InputOrd k$.  If $f$ is not monotone, some $i\prec_I k$ has
$f(i)\not\OutputOrd f(k)$; the run that starts at $\sigma_S(i)$ and emits
$f(i)$ has no row at $k$ and cannot advance to its own refinement $k$.
\end{proof}

This is the familiar CALM dichotomy stated at the specification interface
rather than inside a particular programming language.  Classical CALM fits the
pattern with inputs $J$ ordered by fact inclusion and outputs $Q(J)$ ordered by
answer inclusion.  Functional monotonicity becomes
        \begin{equation}
  J\subseteq J'
  \quad\Longrightarrow\quad
  Q(J)\subseteq Q(J'),
  \label{eq:query-monotonicity}
        \end{equation}
the standard definition of a monotone query~\cite{abiteboul1995foundations},
which positive Datalog satisfies and negation may not.  Functional CALM
extends the statement from fact sets under inclusion to arbitrary input and
output refinement orders.  The usual CRDT state interface has the same
functional shape, with received payloads ordered by inclusion and states by
the semilattice order~\cite{shapiro2011crdt};
Sections~\ref{sec:query-instance} and~\ref{sec:crdt-instance} take up both
instances.

\subsection{Output actions and exposability}
\label{sec:canonical-transition-system}

The canonical commitment basis exists to exercise every output the specification
permits, not to claim that every implementation supports every output action.
An implementation supplies its own basis; it can take an output action only
when commitments in that basis, together with permitted retirements, produce
the required effect.  The following definitions identify when no commitment is
required.

For $R\subseteq S$, the \emph{upper fiber} at $i$ collects outputs at $i$ and
its still-valid refinements:
        \begin{equation}
  R^\uparrow(i)=\{o\in O:\exists j\in I,\ i\InputOrd j\text{ and }(j,o)\in R\}.
  \label{eq:upper-fiber}
        \end{equation}
A state is \emph{determined} when $|R^\uparrow(i)|=1$, regardless of how it was
reached.  \emph{Determination} is movement toward or arrival at that condition.
A commitment may advance determination by excluding an alternative that
otherwise remains possible; an input event may instead resolve ambiguity by
retiring histories that no longer extend the input received.  We call the
resulting outcomes \emph{commitment-resolved} and \emph{input-resolved},
respectively.

\begin{definition}[Exposable output, functional case]
\label{def:exposable}
For a functional specification, $(i,o)\in R$ is \emph{exposable} at $(i,R)$
when its output action requires no commitment.  Equivalently, the output action
removes no row: $o\OutputOrd f(j)$ at every valid $j\succeq_I i$.
\end{definition}

A state is \emph{sealed} when no strict refinement of its current input remains
valid.  A sealed functional state is determined.  Commitments that produce such
a state make it commitment-resolved, although determination need not seal every
strict refinement at once.

A system's \emph{strategy} chooses input and output actions, including which
commitments from its basis an output action applies, using the specification
and any additional strategy state.  Strategy state is not part of the
specification state and affects the remainder table only through the selected
transitions.

\begin{proposition}[Functional exposure boundary]
\label{prop:functional-exposure-boundary}
A functional ordered specification is monotone if and only if every output at
every state reachable without commitment is exposable.
\end{proposition}

\begin{proof}
If $f$ is monotone, a commitment-free state has lost rows only to input events,
since its output actions use no commitments and retire no rows.  If
its current input is $i$, then the only output paired with $i$ is $f(i)$, and
every valid $j\succeq_I i$ has $f(i)\OutputOrd f(j)$, so $f(i)$ is exposable.
Conversely, suppose every output at every commitment-free reachable state is
exposable.  At $\sigma_S(i)$, exposability of $f(i)$ preserves the row
$(j,f(j))$ for each $j\succeq_I i$, so $f(i)\OutputOrd f(j)$ and $f$ is
monotone.
\end{proof}

Functional CALM and this proposition give the operational boundary.  A
monotone functional specification can emit every current output without a
commitment.  If monotonicity fails at $i\prec_I k$, the canonical output action
for $f(i)$ includes a commitment that removes the conflicting row at $k$.

Historically, CALM stands for \emph{Consistency As Logical Monotonicity}, and
its C has been read both as consistency and as confluence;
Definition~\ref{def:consistency} is both.  Functional CALM states the result
for any functional specification, regardless of the formalism used to express
it.  Before dropping the functional dependency, we give this consistency
condition a distributed interpretation.  Section~\ref{sec:distributed-execution}
realizes runs as participant runs; the construction will apply unchanged when
Section~\ref{sec:ambiguous-specifications} introduces output choice.
