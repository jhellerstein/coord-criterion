\section{Functional CALM}
\label{sec:functional-calm}

The CALM Theorem was proved for queries in a logic programming language,
evaluated by relational transducers, and its applicability outside that
setting was never made precise.  Here we use a simpler model that applies to
any specification expressible as an input/output relation over ordered domains.  A
specification describes allowed input/output
behavior without committing to a language, placement, protocol, or message
schedule.  This section addresses the case that prior work on both CALM and
CRDTs shared: specifications that are functions, in which each
input has a single specified output.  Section~\ref{sec:election-story} walks
through the framework informally on an election.
Section~\ref{sec:functional-specifications} defines functional specifications
and monotonicity, Section~\ref{sec:determination} defines the transition system
and Consistency, Section~\ref{sec:functional-calm-theorem} proves Functional
CALM, and Section~\ref{sec:canonical-transition-system} identifies when an
output can be prepared without commitment.

\subsection{The framework on an election}
\label{sec:election-story}

We begin with an informal, example-driven treatment.
Terms introduced in italics are defined formally in the rest of this section
and in Sections~\ref{sec:distributed-execution}--\ref{sec:complete-calm};
italics also mark the occasional
standard term borrowed from database theory.  Nothing here is needed for the
proofs, but every notion the Functional CALM theorem rests on---specification
states, input events, retirement, commitments, upper fibers, determination,
preparation, exposure, runs, and consistency---is exercised on the example.

The framework begins with an \emph{ordered specification}
$\Spec=(I,\InputOrd,O,\OutputOrd,S)$: a table $S\subseteq I\times O$ that
captures exactly which outputs are within spec at each input, with a partial
order on each column.  In this section, input functionally determines output:
every input is paired with exactly one output.
Section~\ref{sec:ambiguous-specifications} later drops this functional
dependency.

\paragraph{A specification is a table.}
A specification table lists the output paired with each input.  It need not be finite. Squaring, for example,
has rows $(2,4)$, $(3,9)$, $(4,16),\ldots$.  Everything that follows is a
matter of removing rows from an initial specification.

Figure~\ref{fig:election-frames}(a) shows a set of rows taken from the specification of a small election.
Three voters $v_1,v_2,v_3$ each cast at most one immutable ballot for $x$ or
$y$; the result is whichever candidate has two ballots, and $\bot$ (no result
yet) until one does.  An input represents the
ballots seen so far, written as a three-letter string whose $k$th position holds
$v_k$'s ballot or a dot if it has not arrived; only rows above $x\cdot\cdot$,
where $v_1$ has voted $x$, are shown.  The first row says that with $v_1$'s
ballot alone the result is $\bot$; row $xx\cdot$ says that once $v_2$ also votes
$x$ the result is $x$; row $xyy$ says that if $v_2$ and $v_3$ both vote $y$ the
result is $y$.

The rows are only part of the specification.  Each column also carries a
partial order, and both orders are design decisions.  The \emph{input order}
says what counts as more input: here, more ballots, so $xy\cdot$ \emph{refines}
$x\cdot\cdot$, while $xx\cdot$ and $xy\cdot$ are incomparable.  The \emph{output
order} says when a later output keeps every promise an earlier one made: here
$\bot$ lies below both $x$ and $y$, so ``no result yet'' can eventually refine
to a winner, but $x$ and $y$ are incomparable, so neither winner refines the
other.  (A
different design could make all outputs incomparable, so that every result is
final; we return to that choice below.)  Given these orders, one can follow any input
upward through its refinements, say $x\cdot\cdot$ to $xy\cdot$ to $xyx$: the
output climbs too, from $\bot$ to $x$, and never steps down or sideways.  That
is what it means for the \emph{specification} to be \emph{monotone}, a property
of the rows together with the orders. Viewing the specification as a function $f:I \times O$,
it is always that case that $i \InputOrd j \implies f(i) \OutputOrd f(j)$.

\paragraph{Input arrives.}
Now $v_2$'s ballot arrives, for $y$; panel (b) shows the result.  The
\emph{current input}, the ballots seen so far, has advanced from $x\cdot\cdot$
to $xy\cdot$, shown in bold.  One rule governs what an input event does to the specification:
only the rows at the current input and its refinements remain; every other row is
\emph{retired}---removed from the resulting remainder table.  Each state pairs the current input
with the rows that remain: it records what
is still possible and how far input has come.  Each panel shows one such state,
with its remainder table and current input in bold.  The inputs that still have rows are the \emph{valid} ones.
Note that the environment supplies new input; the system passively retires the dominated rows.
Here $v_2$'s ballot
extends the cumulative input from $x\cdot\cdot$ to $xy\cdot$, and the system
records that change as $\mathsf{input}(xy\cdot)$.
The state depends only on the input reached, not on the order or
grouping in which the ballots arrived.  In panel (b) the input has grown
from $x\cdot\cdot$ to $xy\cdot$, so the row at $x\cdot\cdot$ is retired; the
rows at $xx\cdot$, $xxx$, and $xxy$ are retired because no input refines both
$xx\cdot$ and $xy\cdot$.  The retired output $\bot$ at $x\cdot\cdot$ is
refined by the $\bot$ at $xy\cdot$, so growing the input lost nothing the
smaller input's output claimed; this is a consequence of the monotonicity
observed above.

\paragraph{What could still happen.}
While input may still grow, what matters is not only the current row but what
any input that could still arrive might require.  The future of the election
is its current input together with its valid input refinements, and the outputs of
those rows form the current input's \emph{upper fiber}.  In
panel (b) those rows are the current row and the two refinements $xyx$ and
$xyy$ in which $v_3$ votes, so the upper fiber, shaded, is $\{\bot,x,y\}$:
either candidate could still win.

Panel (c) shows the alternative in which $v_2$ voted $x$.  The rows at or
above $xx\cdot$ all say $x$, so the upper fiber is the singleton $\{x\}$ and
the current input is \emph{determined}: it fixes the output regardless of what
ballot $v_3$ could cast.  Narrowing the upper fiber until a single output
remains is what we call \emph{determination}.  Here input arrival determined the
state on its own; below we meet the case where the system must act.

\paragraph{Commitments.}
Return to panel (b).  Consider a registrar who prepares $\bot$ for exposure by closing
the polls, so any later ballot from $v_3$ will not count.  Panel (d) removes the rows at $xyx$ and $xyy$ while
leaving the current input $xy\cdot$ unchanged.  The system has thereby made
those input refinements invalid.  This irrevocable act is a \emph{commitment},
specifically a \emph{seal commitment}: the system, rather than new input from
the environment, has ruled out behavior that was within spec. 
% CALM asks whether progress can avoid that act.

The specification itself does not authorize closing the polls.  That authority
comes from an additional component: the system's \emph{commitment basis} $\mathcal B$, which contains
all the commitments it may perform.  A system whose polls can close includes
this commitment in its basis; one whose polls cannot close does not.  After
this preparation, no refinement of $xy\cdot$ remains valid, its upper fiber is
$\{\bot\}$, and the state is determined.

Because a functional specification has one row per input, any commitment that
removes a row makes that input invalid.  This is a seal commitment; it may
invalidate one future input or many.  Section~\ref{sec:ambiguous-specifications}
adds output-prepare commitments, which remove conflicting outputs while leaving
their input valid.

\paragraph{Preparing and exposing outputs.}
Output handling has two actions.  First, $\mathsf{prepare}(o)$ makes any
commitments needed to remove conflicting alternatives that no remaining row
preserves; this prepares the promise that the eventual result will refine $o$.
Then $\mathsf{expose}(o)$
reveals the prepared result to a client and retires rows whose claims are
preserved by remaining rows.  Keeping exposure explicit matters because what a
client learns may influence later input.

In a functional specification, $o$ is \emph{exposable} exactly when preparation
requires no commitment: every possible future output---the values in the upper
fiber---refines $o$.  If this test fails, an authorized commitment in the
preparation expansion can remove the conflicting rows and thereby enable
exposure of $o$; the preparation itself is still a coordinating act.  In Figure~\ref{fig:election-frames}, $\bot$ is exposable in every
panel because every shaded output refines it, and $x$ is exposable in panel (c).

\paragraph{When monotonicity fails.}
Now change one thing in our example: make all outputs incomparable, dropping
$\bot\OutputOrd x,y$, so that an output refines only itself; this is the
\emph{equality order}.  The rows are the same, but in panels (a) and (b)
nothing is exposable: $\bot$ no longer lies below the $x$ and $y$ in the upper
fiber.  To expose anything, the registrar's preparation expansion must include
a seal commitment.
Figure~\ref{fig:nonmonotone-frame} shows the result of closing the polls at
$x\cdot\cdot$: every refinement is removed by commitment, the upper fiber
collapses to $\{\bot\}$, and exposure of $\bot$ is now enabled---but only
because preparation coordinated.  That contrast is
Functional CALM (Section~\ref{sec:functional-calm}): a monotone functional
specification can prepare and expose outputs without commitment; a non-monotone
one requires commitment in some preparation expansion.

\paragraph{A transition system.}
We now have the ingredients for a state transition model.  A state consists of
two things: the current input and the rows of the specification that remain.
Each panel above depicts one such state, and each action moves from one state to
another.  An input event grows the current input and retires rows that are no longer
reachable.  Preparation keeps the input fixed and makes the commitments needed
to remove conflicting alternatives that no remaining row preserves.  Exposure
reveals the prepared output and retires dominated rows.  Input events come from
the environment;
preparation and exposure come from the system.  Panels (b) through (e) are
reached from panel (a) by input or preparation actions.  The formal development
uses this one transition system throughout.

\paragraph{Consistency.}
Our goal is \emph{confluence}: any finite collection of input/output paths
through the transition system can be brought to one common state, whatever
further input arrives.  We call a specification \emph{consistent} when all
such paths are confluent.

Our framework can encode either a general consistency model that spans many
applications or an application-specific requirement such as an invariant.  In
the election, the table and its orders license the application's legal
behaviors: which results it permits and which later results preserve earlier
ones.  Consistency then asks whether paths through those behaviors can still
meet.  Appendix~\ref{app:registers} instead instantiates the framework with
linearizability and causal consistency, two application-independent consistency
models that license different register behaviors and therefore yield different
confluence results; Section~\ref{sec:consistency-as-confluence} develops this
distinction generally.  Specifications can also be composed: joining component
tables on their shared interface yields an end-to-end specification
(Appendix~\ref{app:composition}).

Monotonicity gives a condition directly on the specification table: whenever
input grows from $i$ to $k$, the output at $k$ refines the output at $i$.
Functional CALM proves that this condition is equivalent to confluence: a
functional specification is consistent exactly when it is monotone.

The rest of this section states these notions formally.
Figure~\ref{fig:formalism-summary} collects the formal objects of Functional
CALM; Figure~\ref{fig:complete-formalism-summary} will collect the additions
for Complete CALM.

\subsection{Functional specifications and monotonicity}
\label{sec:functional-specifications}

\begin{definition}[Functional ordered specification]
\label{def:functional-specification}
A \emph{functional ordered specification} is a function
        \begin{equation}
  f:(I,\InputOrd)\longrightarrow(O,\OutputOrd),
  \label{eq:functional-specification}
        \end{equation}
where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered sets.  We call
$\InputOrd$ the \emph{input-refinement order}: $i\InputOrd j$ means that $j$
contains at least the input information in $i$.  We call $\OutputOrd$ the
\emph{output-refinement order}: $o\OutputOrd u$ means that $u$ preserves every
externally visible claim in $o$ and may add more.
\end{definition}

These are two separate partial orders.  The input order compares inputs; the
output order compares outputs.  Neither orders executions or rows in a table.
Either may be the \emph{equality order}, under which an element refines only
itself; on outputs this is the case in which no output can be extended, only
replaced.

\begin{definition}[Monotonicity]
\label{def:functional-monotonicity}
A functional ordered specification $f$ is \emph{monotone} if
        \begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
        \end{equation}
\end{definition}

This is the standard mathematical definition of a monotone function.  In
systems terms, an output exposed from partial input remains valid as more input
arrives.

\subsection{The transition system}
\label{sec:determination}

Section~\ref{sec:election-story} previewed one transition model with input,
commitment, and output handling.  We now define it.  Output handling has two
stages.  First, $\mathsf{prepare}(o)$ atomically makes any commitments needed
to remove undominated conflicts with $o$.  Then $\mathsf{expose}(o)$ reveals
$o$ to the environment and retires dominated rows.  The complete sequence
retains exactly the rows whose outputs refine $o$.  Keeping exposure explicit
matters: the environment may learn from $o$ and choose subsequent input
accordingly.

The CALM proofs use a canonical commitment basis that can prepare every output
the specification permits.  This is the right basis for testing the full
specification: a weaker basis could hide non-monotonicity merely by making a
problematic output unavailable.  Its commitments are nevertheless
output-directed or seal future inputs; the normal-form lemma below shows that
arbitrary additional removal only narrows the specification.

\paragraph{The specification and remainder tables.}
The graph $S\subseteq I\times O$ is the \emph{specification table}; its rows
are the pairs $(i,f(i))$, one at each input.  During a run, $R\subseteq S$ is
the \emph{remainder table}; it records the rows not yet removed.  No action
adds a row.

Inputs are \emph{cumulative}: an input is everything seen so far, and
$i\InputOrd j$ means that $j$ contains at least the information in $i$.  The
specification sees inputs only through the domain, its order, and the outputs
it allows for each; corrections, retractions, or conflicting ballots are
accommodated by designing the input domain to record them.  Write
$k\prec_I i$ when $k\InputOrd i$ and $k\neq i$, and
$\mathord\uparrow_I i=\{j\in I:i\InputOrd j\}$ for the refinements of $i$.

\paragraph{States.}
A state pairs the current input with a remainder table.  Every panel of
Figure~\ref{fig:election-frames} is such a state.

\begin{definition}[Specification state]
\label{def:residual-state}
A \emph{specification state} is a pair $\sigma=(i,R)$ such that
\begin{enumerate}
  \item $i\in I$ is the \emph{current input};
  \item $R\subseteq S$;
  \item $R$ has a row at the current input:
        \begin{equation}
          (i,o)\in R\ \text{for some }o;
          \label{eq:current-input-validity}
        \end{equation}
  \item only refinements of the current input have rows in $R$:
        \begin{equation}
          (k,o)\in R
          \quad\Longrightarrow\quad i\InputOrd k.
          \label{eq:retired-input-absence}
        \end{equation}
\end{enumerate}
An input $k$ is \emph{valid} when $R$ has a row at $k$, and otherwise
\emph{invalid}.
\end{definition}

A \emph{execution state} is $\gamma=(\sigma,q)$, where $\sigma=(i,R)$
is a specification state and $q\in O\cup\{\mathsf{none}\}$ records the output
pending exposure.  An execution state is \emph{stable} when
$q=\mathsf{none}$.  Input and preparation events are enabled only in stable
execution states; an exposure event is enabled only when $q$ contains its matching
output.

Valid inputs other than the current one are possible futures: refinements of
$i$ whose rows have not been removed.  For an input $i$, the \emph{canonical initial specification state} is
        \begin{equation}
  \sigma_0(i)=\bigl(i,\ \{(k,o)\in S:\ i\InputOrd k\}\bigr),
  \label{eq:canonical-initial-state}
        \end{equation}
the specification table restricted to $i$ and its refinements.  The canonical
initial execution state is
$\gamma_0(i)=(\sigma_0(i),\mathsf{none})$.
Figure~\ref{fig:election-frames}(a) shows $\sigma_0(x\cdot\cdot)$.

\paragraph{Input events.}
For $j\in I$ with $i\InputOrd j$, an input event makes $j$ current and removes
every row whose input does not refine $j$:
        \begin{equation}
  (i,R)\xrightarrow{\mathsf{input}(j)}
  \bigl(j,\ R\mathbin{\upharpoonright_I}j\bigr),
  \qquad
  R\mathbin{\upharpoonright_I}j=\{(k,u)\in R:\ j\InputOrd k\},
  \label{eq:input-event}
        \end{equation}
defined when $R$ has a row at $j$.  Every row this event removes is an
\emph{input retirement}: its input does not refine the new current input $j$.

An input event records the new cumulative input, not the value that caused it.
The system model supplies a partial function
        \begin{equation}
  \mathsf{advance}:I\times I\rightharpoonup I,
  \qquad
  \mathsf{advance}(i,a)=j
  \ \Longrightarrow\
  \begin{cases}
    i\InputOrd j,\\
    a\InputOrd j,
  \end{cases}
  \label{eq:cumulative-advance}
        \end{equation}
where $i$ is current and $a$ is arriving cumulative input.  We require
$\mathsf{advance}(i,a)=a$ whenever $i\InputOrd a$, so an already cumulative
arrival is recorded directly.  The computation is not an event; the resulting
$\mathsf{input}(j)$ is.  For set-valued inputs, advance may be union; for a
join-semilattice, it may be join.  Neither structure is assumed.  In particular,
two inputs may have no common refinement, or several incomparable common
refinements, and the framework requires neither a least common refinement nor a
lattice.  The function is partial because advance need not be defined for every
pair; where several results are possible, it records the one chosen by the
system model.

Input events compose: $\mathsf{input}(j)$ followed by $\mathsf{input}(k)$ has
the same effect as $\mathsf{input}(k)$ alone, and $\mathsf{input}(i)$ at
$(i,R)$ is the identity.  Thus input order, batching, and repeated delivery do
not affect the state reached by input events alone.

\paragraph{Commitments and output handling.}
For any remainder table, write
\[
  R(k)=\{u\in O:(k,u)\in R\}.
\]
For $(i,o)\in R$, the final table needed to honor exposure of $o$ is
\begin{equation}
  R_o=R\mathbin{\upharpoonright_O}o
      =\{(k,u)\in R:o\OutputOrd u\}.
  \label{eq:residual-refining-fibers}
\end{equation}
The rows in $R\setminus R_o$ fall into three classes.  First, let
\begin{align}
  K_o&=\{k:R(k)\neq\varnothing\text{ and }R_o(k)=\varnothing\},
      \label{eq:seal-inputs}\\
  D_o&=\{(k,x)\in R\setminus R_o:
          \exists u\in R_o(k).\ x\OutputOrd u\},
      \label{eq:output-retirements}\\
  P_o&=(R\setminus R_o)
       \setminus\bigl(D_o\cup\{(k,x):k\in K_o\}\bigr).
      \label{eq:prepare-removals}
\end{align}
Rows at inputs in $K_o$ must all disappear, making those inputs invalid.  Rows
in $D_o$ are dominated by rows that remain at the same input, so they can be
retired without losing their claims.  Rows in $P_o$ are the remaining,
undominated conflicts with $o$.

A \emph{commitment basis} $\mathcal B$ is a set of partial functions on
specification states.  Each commitment keeps the current input fixed and
strictly decreases the remainder table.  It may remove one canonical set of
rows or bundle several canonical sets atomically.  A \emph{seal commitment}
removes every row at one or more valid noncurrent inputs, making those inputs
invalid.  An \emph{output-prepare commitment for $o$} removes undominated rows
that conflict with $o$, such as the rows in $P_o$.  These are the only two
canonical forms of commitment.

The canonical commitments for preparing $o$ at $(i,R)$ are concrete partial
functions.  Let
\[
  C_o^{\mathrm{seal}}=\{(k,x)\in R:k\in K_o\},
  \qquad R_o^{\mathrm{seal}}=R\setminus C_o^{\mathrm{seal}}.
\]
When $K_o\neq\varnothing$, the canonical seal commitment is
\begin{equation}
  s_{(i,R),o}(i,R)=(i,R_o^{\mathrm{seal}}).
  \label{eq:canonical-seal-commitment}
\end{equation}
When $P_o\neq\varnothing$, the canonical output-prepare commitment is
\begin{equation}
  p_{(i,R),o}\bigl(i,R_o^{\mathrm{seal}}\bigr)
    =\bigl(i,R_o^{\mathrm{seal}}\setminus P_o\bigr).
  \label{eq:canonical-output-prepare-commitment}
\end{equation}
Identity cases are omitted.  The \emph{canonical commitment basis}
$\mathcal B_S^{\mathrm{can}}$ contains these commitments for every specification
state and every $(i,o)\in R$.

The macro $\mathsf{prepare}(o)$ atomically applies the corresponding seal and
output-prepare commitments, in that order, to a stable execution state.  This
finite sequence is its \emph{preparation expansion}; no cut or participant
action occurs inside it.  It then sets the pending output to $q=o$.
Preparation does not retire $D_o$ and does not reveal $o$.  Under another basis,
a preparation for $o$ is \emph{legal} when it retains $(i,o)$ and, after its
commitments, every remaining row excluded by $o$ is dominated at the same input
by a retained row that refines $o$.  The matching exposure can then retire all
such excluded rows, leaving a subset of $R_o$.  A basis supports an exposure
sequence when it provides a legal preparation for it.

The matching event $\mathsf{expose}(o)$ is enabled when $q=o$.  It reveals $o$
to the environment, retires every remaining row excluded by $o$, and clears $q$
to $\mathsf{none}$.  For the canonical preparation, those rows are exactly
$D_o$, so the canonical \emph{exposure sequence}
\begin{equation}
  \mathsf{prepare}(o);\mathsf{expose}(o)
  \label{eq:output-stage}
\end{equation}
takes the stable execution state $((i,R),\mathsf{none})$ to
$((i,R_o),\mathsf{none})$.  A finite history may have a cut at the intermediate
execution state with $q=o$, but no participant action other than the matching
exposure is enabled there.  Exposure remains explicit because what the
environment learns may influence later input.

The canonical basis supports every output permitted by the specification.  This
completeness is essential for CALM: a weaker basis could hide non-monotonicity
merely by making a conflicting output unavailable.  Other bases may omit
canonical commitments or package several into one atomic bundle.  A basis
\emph{covers} the canonical preparation for $o$ when one of its bundles, or an
atomic sequence of its commitments, removes exactly the canonical seal and
output-prepare rows.  Coverage is sufficient for legal preparation; a legal
preparation may remove additional rows.

\begin{lemma}[Canonical commitment normal form]
\label{lem:canonical-commitment-normal-form}
The canonical basis can legally prepare every permitted output.  Every legal
preparation for $o$ removes the canonical seal and output-prepare rows for $o$.
The canonical exposure sequence therefore exposes the same $o$ while retaining
every row not required to honor that exposure.  At this state, any additional
row removal only narrows the resulting remainder table.
\end{lemma}

\begin{proof}
Every row at an input in $K_o$ conflicts with $o$, so a preparation that leaves
that input valid cannot expose $o$; those fibers must be sealed.  At every
remaining input, each row in $P_o$ conflicts with $o$ and is not dominated by a
row in $R_o$, so it cannot be retired and must be removed by commitment.  The rows in
$D_o$ are dominated by retained rows and are retired by the canonical exposure.
These three sets partition $R\setminus R_o$, so the canonical exposure sequence
ends at exactly $R_o$.  Any completed exposure sequence whose preparation
removes more rows ends at a subset of $R_o$ and therefore exposes no output
unavailable to the canonical basis; it
only excludes additional behavior at this state.  Treating that exclusion as a
permanent interface rule amounts to declaring a narrower specification
$S'\subsetneq S$; history-dependent extra removal remains an implementation
choice, not another canonical form of commitment.
\end{proof}

\begin{definition}[Transition system and run]
\label{def:io-transition-system}
\label{def:transition-system}
The \emph{transition system} has execution states as its states, with
input events as in Equation~\ref{eq:input-event}, atomic preparations supported
by its commitment basis, and exposure events with their output retirements.  A
\emph{run} is any finite transition sequence from a canonical initial
execution state $\gamma_0(i)$ to a stable execution state.  A \emph{run prefix} may
additionally end with a pending output.  Unless stated otherwise, runs use the
canonical commitment basis.
\label{def:run}
\end{definition}

A specification state is \emph{run-generated} when it is reachable via a run.
This is a provenance condition, not another local invariant on a remainder
table.  It excludes structurally valid states whose missing rows cannot be
explained by input retirements, canonical commitments, and output retirements.

\begin{lemma}[Rows remaining after a run]
\label{lem:run-residual}
A run starts at $\gamma_0(i_0)$, ends with stable execution state
$((i,R),\mathsf{none})$, and completes exposure sequences for outputs
$o_1,\ldots,o_m$.  Its final specification state is
        \begin{equation}
  \left(i,\ \left\{(k,x)\in S:
    \begin{array}{l}
      i\InputOrd k,\ \text{and}\\
      o_\ell\OutputOrd x\ \text{for every }\ell
    \end{array}
  \right\}\right).
  \label{eq:run-residual}
        \end{equation}
\end{lemma}

\begin{proof}
Each input event intersects $R$ with $\{(k,x):j\InputOrd k\}$ and each complete
exposure sequence with $\{(k,x):o\OutputOrd x\}$.  Its preparation commitments
remove the canonical seal and output-prepare rows, and its exposure retires the
dominated rows, giving exactly this aggregate effect.  These intersections
commute, and the input restrictions compose to the restriction at the final
input $i$.
\end{proof}

A \emph{common refinement} of inputs $i_1,\ldots,i_k$ is an input $j$ with
$i_r\InputOrd j$ for every $r$.

\begin{definition}[Consistency]
\label{def:consistency}
An ordered specification is \emph{consistent} when every finite family of runs
under its canonical commitment basis is confluent: if the runs end at
$(i_1,R_1),\ldots,(i_k,R_k)$ and $j$ is a common refinement of their current
inputs, a single state with current input $j$ is reachable by input events and
complete exposure sequences from each $(i_r,R_r)$.  The runs are then
\emph{confluent at} $j$.
\end{definition}

Equivalently, Consistency quantifies over every finite family of run-generated
endpoints.  This covers every run-generated starting state, since any path from
one extends the run that generated it.  It does not quantify over arbitrary
specification states or arbitrary commitments.  The canonical commitment basis
includes exactly the output-directed commitments needed to exercise every
output permitted by the specification; a weaker basis could make a
non-monotone specification appear consistent by disabling its conflicting
outputs.  A coordinating component's exported interface is tested separately
as a specification in Appendix~\ref{app:composition}.

\begin{proposition}[Confluence at a common refinement]
\label{prop:confluence}
Runs ending at $(i_1,R_1),\ldots,(i_k,R_k)$ are confluent at $j$ if and only
if some row at $j$ survives in every final state,
        \begin{equation}
  (j,u)\in R_r\quad\text{for every }r,\ \text{for some }u\in O.
  \label{eq:reconciliation}
        \end{equation}
For any such $u$, $\mathsf{input}(j)$ followed by the exposure sequence for
$u$ takes every final state to
$\bigl(j,\{(k,x)\in S:j\InputOrd k,\ u\OutputOrd x\}\bigr)$.
\end{proposition}

\begin{proof}
A common state with current input $j$ has a row at $j$, and that row belongs to
every $R_r$.  Conversely, let $(j,u)$ belong to every $R_r$.  Then
$\mathsf{input}(j)$ is defined at every $(i_r,R_r)$.  By
Lemma~\ref{lem:run-residual}, $(j,u)\in R_r$ says that $u$ refines every output
exposed on run $r$.  After $\mathsf{input}(j)$ and the exposure sequence for
$u$, the same lemma leaves exactly the rows of $S$ above $j$ and $u$, independent
of the starting run.
\end{proof}

A single run can witness inconsistency: completing an exposure sequence for one
permitted output may remove every row at a refinement of its current input.
Consistency describes
no protocol and promises no delivery or termination;
Section~\ref{sec:discussion} returns to this.

\subsection{The Functional CALM theorem}
\label{sec:functional-calm-theorem}

\begin{theorem}[Functional CALM]
\label{thm:functional-calm}
A functional ordered specification is consistent if and only if it is
monotone.
\end{theorem}

\begin{proof}
Every input has one row.  By Lemma~\ref{lem:run-residual}, a run ending at
input $i$ retains $(k,f(k))$ at $k\succeq_I i$ exactly when every output
$f(i_\ell)$ exposed on the run satisfies $f(i_\ell)\OutputOrd f(k)$.  By
Proposition~\ref{prop:confluence}, a finite family of runs is confluent at a
common refinement $k$ exactly when every output exposed on any run lies below
$f(k)$.  If $f$ is monotone this holds because each exposed $f(i_\ell)$ has
$i_\ell\InputOrd k$.  If $f$ is not monotone, some $i\prec_I k$ has
$f(i)\not\OutputOrd f(k)$; the run that starts at $\gamma_0(i)$ and completes
the exposure sequence for $f(i)$ has no row at $k$ and cannot advance to its own
refinement $k$.
\end{proof}

This is the familiar CALM dichotomy stated at the specification interface
rather than inside a particular programming language.  Classical CALM fits the
pattern with inputs $J$ ordered by fact inclusion and outputs $Q(J)$ ordered by
answer inclusion.  Functional monotonicity becomes
        \begin{equation}
  J\subseteq J'
  \quad\Longrightarrow\quad
  Q(J)\subseteq Q(J'),
  \label{eq:query-monotonicity}
        \end{equation}
the standard definition of a monotone query~\cite{abiteboul1995foundations},
which positive Datalog satisfies and negation may not.  Functional CALM
extends the statement from fact sets under inclusion to arbitrary input and
output refinement orders.  The usual CRDT state interface has the same
functional shape, with received payloads ordered by inclusion and states by
the semilattice order~\cite{shapiro2011crdt};
Sections~\ref{sec:query-instance} and~\ref{sec:crdt-instance} take up both
instances.

\subsection{Preparing and exposing outputs}
\label{sec:canonical-transition-system}

The canonical commitment basis exists to exercise every output the specification
permits, not to claim that every implementation supports every preparation.
An implementation supplies its own basis; it can realize an exposure sequence
only when that basis supports a preparation expansion with the required
aggregate effect.  The following definitions identify when no commitment is
required.

For $R\subseteq S$, the \emph{upper fiber} at $i$ collects outputs at $i$ and
its still-valid refinements:
        \begin{equation}
  R^\uparrow(i)=\{o\in O:\exists j\in I,\ i\InputOrd j\text{ and }(j,o)\in R\}.
  \label{eq:upper-fiber}
        \end{equation}
The current input is \emph{determined} when $|R^\uparrow(i)|=1$, and a state
is determined when its current input is.

\begin{definition}[Exposable output, functional case]
\label{def:exposable}
For a functional specification, $(i,o)\in R$ is \emph{exposable} at $(i,R)$
when $\mathsf{prepare}(o)$ requires no commitment.  Equivalently, the exposure
sequence removes no row: $o\OutputOrd f(j)$ at every valid
$j\succeq_I i$.
\end{definition}

A state is \emph{sealed} when no strict refinement of its current input remains
valid.  A sealed functional state is determined, but a seal commitment need not
seal every strict refinement at once.

A system's \emph{strategy} chooses input events and exposure sequences, and
chooses a valid preparation expansion from its basis, using the specification
and any additional strategy state.  Strategy state is not part of the
specification state and affects the remainder table only through the selected
transitions.

\begin{proposition}[Functional exposure boundary]
\label{prop:functional-exposure-boundary}
A functional ordered specification is monotone if and only if every output at
every state reachable without commitment is exposable.
\end{proposition}

\begin{proof}
If $f$ is monotone, a commitment-free state has lost rows only to input events
and output retirements, since its preparations are the identity.  If
its current input is $i$, then the only output paired with $i$ is $f(i)$, and
every valid $j\succeq_I i$ has $f(i)\OutputOrd f(j)$, so $f(i)$ is exposable.
Conversely, suppose every output at every commitment-free reachable state is
exposable.  At $\sigma_0(i)$, exposability of $f(i)$ preserves the row
$(j,f(j))$ for each $j\succeq_I i$, so $f(i)\OutputOrd f(j)$ and $f$ is
monotone.
\end{proof}

Functional CALM and this proposition give the operational boundary.  A
monotone functional specification can prepare and expose every current output
without a commitment.  If monotonicity fails at $i\prec_I k$, preparing
$f(i)$ invokes the canonical commitment that removes the conflicting row at
$k$ before $\mathsf{expose}(f(i))$ occurs.

Historically, CALM stands for \emph{Consistency As Logical Monotonicity}, and
its C has been read both as consistency and as confluence;
Definition~\ref{def:consistency} is both.  Functional CALM states the result
for any functional specification, regardless of the formalism used to express
it.  Before dropping the functional dependency, we give this consistency
condition a distributed interpretation.  Section~\ref{sec:distributed-execution}
realizes runs as participant runs; the construction will apply unchanged when
Section~\ref{sec:ambiguous-specifications} introduces output choice.
