\section{Functional CALM}
\label{sec:functional-calm}

This section focuses on functional specs, in which each input has a
single specified output.  We walk through the framework informally on an
election, make it precise, and prove Functional CALM, identifying along the
way when an output can be emitted without \commitment.

We introduce the framework with a small election, illustrated in
Figure~\ref{fig:election-frames}.  Each row of the possibility table pairs
the ballots received so far with the permitted result; the column orders say how inputs \ingrow and which later outputs \outrelbase earlier ones.

Three voters $v_1,v_2,v_3$ each cast at most one immutable ballot for $a$ or
$b$.  The output is whichever candidate has two ballots, or $\bot$ while there
is no winner.  An input is the ballots received so far, written as a
three-character string with a dot for a ballot not yet received.  For brevity,
the figure shows only inputs \inrelpart $a\cdot\cdot$.

The two orders require thoughtful design.  The \emph{input order}
must record accumulated ballots, one per voter: $ab\cdot$ \inrel $a\cdot\cdot$, while
$aa\cdot$ and $ab\cdot$ are incomparable.  The \emph{output order} says which
announcements are safe to build on: $\{\bot \OutputOrd a, \bot \OutputOrd b\}$.
$\bot$ claims nothing, so either winner
\outrel it, while $a$ and $b$ are incomparable.  In general, the functional table is \emph{monotone}
when
\[
  i\InputOrd j\quad\Longrightarrow\quad f(i)\OutputOrd f(j).
\]
Here, for example, the input sequence $a\cdot\cdot\InputOrd ab\cdot\InputOrd aba$
monotonically produces the output sequence $\bot\OutputOrd\bot\OutputOrd a$.

\paragraph{Input and determination.}
Each panel of Figure~\ref{fig:election-frames} shows a \emph{specification
state}: the \emph{current input} and the \emph{remainder table} of rows still
possible from it.  When $v_2$'s ballot for $b$ arrives, the input event
$\mathsf{input}(ab\cdot)$ produces panel~(b).  The table passively loses the rows
whose inputs do not extend $ab\cdot$, such as $aa\cdot$: those possibilities are
lost.  The \emph{future-output set} is the set of outputs still possible in the
remainder table: $\{\bot,a,b\}$ in panel~(b).  If $v_2$ instead votes for $a$
(panel~(c)), the future-output set is a singleton, $\{a\}$, and we call such
states \emph{determined}.  In this case, input alone has determined an outcome,
without \commitment.

Panel~(d), by contrast, adds a decision by the \emph{system}: the implementation
that receives the ballots and announces the result (Section~\ref{sec:systems}).  Here
the system acts as a registrar that, when it emits $\bot$ at $ab\cdot$, also
closes the polls.  Closing the polls is a \emph{\commitment}: it removes the
still-possible rows $aba$ and $abb$, though the current input stays $ab\cdot$.
The future-output set becomes $\{\bot\}$, so $\bot$ is the determined result.
The spec did not require this \commitment: emitting $\bot$ alone would remove
nothing, since every output still possible extends $\bot$.  Closing the polls is
the registrar's own fateful decision.

\paragraph{Output and consistency.}
In a functional table, an output is a \emph{legal output} when every output in
the future-output set \outrel it.  Hence $\bot$ is legal
in panels~(a) and~(b), and $a$ in panel~(c).
The output event $\mathsf{output}(o)$ emits $o$ and keeps only the rows whose
outputs extend $o$, since later outputs must not contradict it.  When $o$ is
legal, every remaining row qualifies and nothing is lost.  When it is not, the
event removes the rows that conflict with $o$, ruling out their inputs; that
removal is a \commitment.

Figure~\ref{fig:nonmonotone-frame} considers a variant of our example that
changes only the output order: all outputs are incomparable, including $\bot$
for no winner (the \emph{equality order}, under which each element is related only
to itself).  Then $\bot$ is incompatible with future winners, so emitting it
requires a \commitment.  That change in the output order is Functional CALM in
miniature: the original order is monotone, so later outputs \outrelbase every
earlier one; under the equality order, some outputs can be emitted
only with a \commitment.

The need to issue a \commitment is a property solely of the table and its orders.  Rows $(ab\cdot,\bot)$ and
$(aba,a)$ have the common input \indesc $aba$, but under the equality
order no output at $aba$ \outrel both outputs $\bot$ and $a$.  A run that emits
$\bot$ at $ab\cdot$ and one that receives $aba$ cannot be reconciled at $aba$.

Input and output events form a transition system, and the spec is
consistent when its runs are confluent.  For functional tables this corresponds exactly to monotonicity (Section~\ref{sec:functional-calm-theorem}).
Appendix~\ref{app:notation} collects the notation for reference.

\subsection{Specifications and states}
\label{sec:functional-specifications}

\begin{definition}[Functional \spectype, total]
\label{def:functional-specification}
A \emph{functional \spectype} is a tuple
\[
  \Spec=(I,\InputOrd,O,\OutputOrd,P),
\]
  where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered input and
  output types, and $P\subseteq I\times O$ is its \emph{possibility relation}:
  a typed relation with schema $(\mathrm{in},\mathrm{out})$ in which every
  input appears in at least one row ($P$ is \emph{total} on $I$) and at most one
  (a functional dependency):
\[
  (i,o)\in P\ \land\ (i,o')\in P
  \quad\Longrightarrow\quad o=o'.
\]
\end{definition}

The unique output paired with $i$ induces the function
\[f:(I,\InputOrd)\to(O,\OutputOrd)\]
with $P=\{(i,f(i)):i\in I\}.$
We call
$\InputOrd$ the \emph{input order}.  Because an output may depend on everything
a system has received, we model inputs as \emph{cumulative}: an input
records everything received so far, not a single message, and $i\InputOrd j$
means that $j$ contains at least the input information in $i$.  We say that $j$
\emph{\inrel} $i$, or is an \emph{\indesc} of $i$; every input is an \indesc of itself. We call $\OutputOrd$ the
\emph{output order}: $o\OutputOrd u$ means that $u$ subsumes every
externally visible claim in $o$ and may add more, and we say that $u$
\emph{\outrel} $o$.  In either domain, we call the element above another
an extension.  We write $\InputGe$ and $\OutputGe$ for the converse orders.

A \emph{common \indesc} $j$ of
$i_1,\ldots,i_k$ is an input that \inrel every $i_r$, and a
\emph{common \outnoun} of $o_1,\ldots,o_k$ is an output that \outrel each $o_r$.
Neither need be unique or least: for example, two independent transactions $u$ and $v$, with schedules ordered by subsequence, have two incomparable minimal common \indescs, $uv$ and $vu$.
A row $(k,u)$ is \emph{\outrelpast} by another row $(k,w)$ at the same input
when $w$ \outrel $u$.

\begin{definition}[Functional monotonicity]
\label{def:functional-monotonicity}
A functional \spectype $\Spec$, with induced function $f$, is
\emph{monotone} if
\begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
\end{equation}
\end{definition}

Thus an output emitted on partial input is \outrelpast by the output at every \indesc.

\paragraph{Relational notation.}
For a relation $R\subseteq I\times O$, a predicate on the columns
$\mathrm{in}$ and $\mathrm{out}$ in square brackets selects rows, and commas
separate conjuncts: $R[\mathrm{in}\InputGe j,\ \mathrm{out}\OutputGe o]$ is the
table of rows whose input \inrel $j$ and whose output \outrel $o$.  We say that a row
$(k,u)$ is \emph{at} $k$, and $\mathrm{out}(R)$ is the set of outputs that
appear in $R$.

A spec describes every permitted input/output pair.  During execution,
input arrives and outputs are emitted, so only some of those pairs remain
possible.  The changing state of the spec, illustrated by the non-gray text in
the panels of Figure~\ref{fig:election-frames}, is defined as follows.

\begin{definition}[Specification state, current input, remainder table]
\label{def:residual-state}
Given a specification $\Spec=(I,\InputOrd,O,\OutputOrd,P)$, a \emph{specification state} is a
pair $\sigma=(i,R)$, where $i\in I$ is the \emph{current input} and
$R\subseteq P$ is the \emph{remainder table}, such that:
\begin{enumerate}
  \item $R$ contains a row at $i$; and
  \item $R$ contains only rows at \indescs of $i$: every row $(k,o)\in R$ satisfies $i\InputOrd k$.
\end{enumerate}
\end{definition}

\begin{definition}[Legal input]
\label{def:legal-input}
An input $k$ is \emph{legal} at a state $\sigma=(i,R)$ when $R$ contains a row at $k$.
\end{definition}

Rows are never added during execution.  The \emph{canonical state at $i$} is
the state at $i$ with no rows removed: it keeps every row of $P$ at $i$ and its
\indescs, and it is the state of a system that has received $i$ and emitted
nothing:
\begin{equation}
  \sigma_P(i)=\bigl(i,\ P[\mathrm{in}\InputGe i]\bigr).
  \label{eq:canonical-state}
\end{equation}
An input event from a canonical state leads to another canonical state, and
runs start at one.

The \emph{fiber} of a table $R$ at input $k$ is the set of outputs paired
with $k$: $R(k)=\mathrm{out}(R[\mathrm{in}=k])$.  A functional fiber has at
most one value.
The \emph{future-output set} at $k$, $\mathrm{out}(R[\mathrm{in}\InputGe k])$,
collects the outputs in the fibers at $k$ and its \indescs.
For a state $\sigma=(i, R)$ the future-output set at $i$ is $\mathrm{out}(R)$---the
outputs still possible.

\subsection{Input and output events}
\label{sec:functional-events}

Two events change state: input events incorporate new information, while
output events record what the system has emitted.  Each may remove rows from
the remainder table.

\paragraph{Input events.}
For a state $(i,R)$ and legal input $j$ with $i\InputOrd j$, the input event is
\begin{equation}
  (i,R)\xrightarrow{\mathsf{input}(j)}
  \bigl(j,\ R' = R[\mathrm{in}\InputGe j]\bigr).
  \label{eq:input-event}
\end{equation}
It makes $j$ current and causes the remainder table to lose the rows whose
input does not \inrelbase $j$.  We call this \emph{input loss}.

An input event names the cumulative input $j$: everything received so far,
including all of $i$, not just what arrived since $i$.  Thus $\mathsf{input}(j)$ then $\mathsf{input}(k)$ has the
effect of $\mathsf{input}(k)$ alone; $\mathsf{input}(i)$ at
$(i,R)$ has no effect.

\paragraph{Output events.}
A system controls what it tells the world.  Later outputs must \outrelbase
earlier ones.

At state $(i,R)$, the current input has a unique row $(i,o)$, so $o$ is the only
output the system may emit.

\begin{definition}[Legal output]
\label{def:exposable}
The output $o$ at $(i,R)$ is a \emph{legal output} when every output in the
future-output set \outrel $o$.
\end{definition}

Equivalently, as the only row at a legal input $j$ is $(j,f(j))$, $o$ is legal
exactly when $f(j)$ \outrel $o$ for every legal $j$.

Since every later output must \outrelbase $o$, emitting a non-legal $o$ requires
a \commitment that removes every legal input whose output does not \outrelbase
it.

\begin{definition}[Output event]
\label{def:output-event}
At a state $(i,R)$ with current output $o$, the \emph{output event}
$\mathsf{output}(o)$ performs two steps atomically: it keeps exactly the rows
whose outputs \outrelbase $o$, and emits $o$ to the environment:
\begin{equation}
  (i,R)\xrightarrow{\mathsf{output}(o)}\bigl(i,\ R' = R[\mathrm{out}\OutputGe o]\bigr).
  \label{eq:output-action}
\end{equation}
\end{definition}

\begin{definition}[Canonical \commitment]
\label{def:canonical-commitment-functional}
When $o$ is not legal, equivalently $R'\neq R$, the transition applies the
\emph{canonical \commitment} $x_o(i,R)=(i,R')$.  For every row it removes, no
row remains at the same input.  It is a \commitment.
\end{definition}

Thus $o$ is legal exactly when $\mathsf{output}(o)$ applies no \commitment.  The
current row $(i,o)$ remains, since $o$ \outrel itself, so the event always ends
at a state. A \commitment removes rows that input alone would preserve; after
the canonical \commitment above, their inputs are no longer legal.  Canonical
\commitments of this form are the only \commitments this section uses.  Systems
may issue more \commitments than an output requires, as the registrar does in
Figure~\ref{fig:election-frames}(d), but such extra \commitments are a
system's choice, not the spec's (Section~\ref{sec:systems}).

\paragraph{Determination.}
A state is \emph{determined} when its future-output set has one element: one result
remains, whatever legal input still arrives.  This is a property of the state
alone.  Under the functional dependency each input determines its own
output; a determined state goes further, since its current input determines
the output of every input that may still arrive.  A functional spec
can therefore have undetermined states, as in panel~(b) of
Figure~\ref{fig:election-frames}.  \emph{Determination} is the process of
reaching a determined state.  An input event may do so through input loss,
while a \commitment may do so by emptying fibers that would otherwise
remain possible, as in panels (c) and (d), respectively.
An event from a determined state always leads to another determined state:
events only remove rows, and a row at the current input always remains.

\subsection{Executions and consistency}
\label{sec:executions}

When runs take different paths through the spec, can they still be
brought to a common state?  The answer reduces to a check on a single row.

\begin{definition}[Specification event]
\label{def:specification-event}
Input and output events are \emph{specification events}: they change the
specification state.  We call them simply \emph{events} when unambiguous.
\end{definition}

\begin{definition}[Transition system]
\label{def:transition-system}
The \emph{transition system} consists of specification states and
specification events.
\end{definition}

\begin{definition}[Run]
\label{def:run}
A \emph{run} is any finite transition sequence of the transition system from the
canonical state $\sigma_P(i)$ at some input $i$.
\end{definition}

We compare a system's choices with every behavior the declared spec permits,
not only the behaviors that system happens to produce.

A run is \emph{\commitment-free} when none of its output events applies a
\commitment.  A state is \emph{reachable without \commitment} when
some \commitment-free run reaches it.

A run's state has a simple description.  Input events keep only rows whose
input \inrel the current one, and output events keep only rows whose outputs
\outrelbase what has been emitted.  Both steps are relational selections, and selections commute; since inputs only \ingrow during a run, the last input's selection
subsumes the earlier ones.

\begin{lemma}[Rows remaining after a run]
\label{lem:run-residual}
If a run ends at current input $i$ after emitting
$o_1,\ldots,o_m$, its remainder table is
\begin{equation}
  P[\mathrm{in}\InputGe i,\ \mathrm{out}\OutputGe o_1,\ \ldots,\
    \mathrm{out}\OutputGe o_m],
  \label{eq:run-residual}
\end{equation}
the rows whose input \inrel $i$ and whose output \outrel each $o_r$.
\end{lemma}

\begin{proof}
See Appendix~\ref{app:proofs-sec2}.
\end{proof}

For example, in the equality-order variant of
Figure~\ref{fig:nonmonotone-frame}, a run that emits $\bot$ at $ab\cdot$ keeps
$P[\mathrm{in}\InputGe ab\cdot,\ \mathrm{out}\OutputGe\bot]$: the single row
$(ab\cdot,\bot)$, as the figure shows.

To compare runs that end at different inputs, we consider a common \indesc
of those inputs.

\begin{definition}[Confluence at an input]
\label{def:confluence}
A finite family of runs ending at states $(i_1,R_1),\ldots,(i_k,R_k)$ is \emph{confluent at} $j$, a common \indesc of their current inputs, when each can be continued to a common state with current input $j$.
\end{definition}

\begin{definition}[Consistency]
\label{def:consistency}
An \spectype is \emph{consistent} when every finite family of
runs is confluent at every common \indesc of their current inputs.
\end{definition}

Consistency requires confluence at every common \indesc, not merely at some
later one.  Otherwise conflicting outputs can escape before reconciliation.
In the equality-order election, $f(ab\cdot)=\bot$ and $f(aba)=a$ are
incomparable.  One run can emit $\bot$ at $ab\cdot$, while another accepts
$aba$ and can emit $a$.  The runs cannot reconcile at their common \indesc
$aba$, and waiting cannot retract either output from the environment.  More
generally, even when later input could reconcile the internal states, the
environment may already have acted on their outputs through channels the system
does not see, as in Lamport's ``anomalous behavior''~\cite{lamport1978time};
the reconciling input may never arrive.

Confluence has a simple test: some row at the common \indesc must survive
in every run.

\begin{proposition}[Survivor test]
\label{prop:confluence}
Runs ending at states $(i_r,R_r)$, $r=1,\ldots,k$, are confluent
at $j$ if and only if some row at $j$ survives in every final state:
\begin{equation}
  (j,u)\in R_r\quad\text{for every }r,\ \text{for some }u\in\fiber{j}.
  \label{eq:reconciliation}
\end{equation}
For any such $u$, $\mathsf{input}(j)$ followed by $\mathsf{output}(u)$ takes
every final state to the state
$\bigl(j,\ P[\mathrm{in}\InputGe j,\ \mathrm{out}\OutputGe u]\bigr)$.
\end{proposition}

\begin{proof}[Proof sketch]
Rows are never added, so the row of a common state at $j$ was there
in every run.  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

In a functional spec the only row at $j$ is $(j,f(j))$, so the test
asks whether $(j,f(j))$ survives in every run.

Consistency guarantees runs never diverge irreparably: no ``split brain''.  Whatever input
and output events a finite collection of runs has taken, any input \inrelpart all
of theirs leaves a single state that every run can reach: one that honors all
of their emitted outputs and accepts all of that input.
Proposition~\ref{prop:confluence} identifies that state.  Consistency is a
property of the spec, not of a protocol (Section~\ref{sec:scope}).

\subsection{The Functional CALM theorem}
\label{sec:functional-calm-theorem}

Consistency is defined by a spec's executions, monotonicity by its
table and orders alone.  Functional CALM shows that these coincide.

\begin{theorem}[Functional CALM]
\label{thm:functional-calm}
A functional \spectype is consistent if and only if it is
monotone.
\end{theorem}

\begin{proof}[Proof sketch]
A monotone $f$ only emits outputs that all of its future outputs \outrelbase,
so the row $(j,f(j))$ at a common \indesc $j$ survives in every run.
If $f$ is not monotone, a run that emits $f(i)$ and a run that accepts an
\indesc $k$ of $i$ with $f(i)\not\OutputOrd f(k)$ can never be reconciled at $k$.  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

In the functional case, consistency has a strong consequence: emitting outputs
never changes the state, which depends only on the input.

\begin{corollary}[State is fixed by input]
\label{cor:state-by-input}
In a consistent functional specification, every run ending at current
input $i$ is in the canonical state $\sigma_P(i)$, whatever outputs it emitted
along the way.
\end{corollary}

\begin{proof}[Proof sketch]
By monotonicity, the outputs a run emits remove no row at an \indesc
of $i$.  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

To be confluent at a common \indesc $j$, each run therefore needs only the
single event $\mathsf{input}(j)$, which takes it to $\sigma_P(j)$, the state of a
run that starts with all of the input.  Knowing the input is enough to know the state, and with it the one
output $f(j)$.

Monotonicity also governs legality:

\begin{proposition}[Output-legality boundary]
\label{prop:functional-exposure-boundary}
A functional \spectype is monotone if and only if every output at
every state reachable without \commitment is legal.
\end{proposition}

\begin{proof}[Proof sketch]
By Corollary~\ref{cor:state-by-input}, monotone $f$ reaches only canonical
states. At $\sigma_P(i)$, which input alone reaches, $f(i)$ is legal exactly
when $f$ is monotone at $i$.  Full proof in Appendix~\ref{app:proofs-sec2}.
\end{proof}

A monotone spec can thus emit every current output without \commitment. If a
spec is non-monotone, then for some $i\InputOrd k$,
$f(i)\not\OutputOrd f(k)$, so at $\sigma_P(i)$ the event
$\mathsf{output}(f(i))$ applies $x_{f(i)}$ and excludes input $k$.

Functional CALM is the familiar CALM dichotomy stated at the level of the spec
rather than inside a particular programming language.
Classical CALM fits, with inputs $J$ as sets of facts ordered by
inclusion and output views $Q(J)$ ordered by inclusion.  Functional
monotonicity becomes
        \begin{equation}
  J\subseteq J'
  \quad\Longrightarrow\quad
  Q(J)\subseteq Q(J'),
  \label{eq:query-monotonicity}
        \end{equation}
the standard definition of a monotone query~\cite{abiteboul1995foundations};
positive Datalog satisfies it, and negation may not.  Functional CALM
generalizes the statement to arbitrary input and
output orders, whatever formalism expresses the spec.  CRDT state specs have the same functional shape, with received payloads ordered by inclusion and states by the semilattice order~\cite{shapiro2011crdt}; Sections~\ref{sec:query-instance}
and~\ref{sec:crdt-instance} treat both.
