\section{Instances Across the Literature}
\label{sec:instances}

Complete CALM provides a unified lens for many results across literatures.
Each setting below declares an input, an output, and their orders before
applying either theorem.  Changing the specification changes
whether monotonicity or Directed Outputs holds.

\subsection{Query monotonicity}
\label{sec:query-instance}

As previously discussed (\S\ref{sec:functional-calm}),
the CALM Theorem of Ameloot et al.\ proves an operational result for
relational languages on transducer networks: coordination-free evaluation is possible
iff a program is monotone,
under its data-placement and execution assumptions~\cite{ameloot2013relational,ameloot2015weaker}.
Functional CALM does not replace the details of that theorem.  It abstracts
the result to a property that can be compared with specifications outside
Datalog.

Subsequent refinements of that CALM Theorem are all instances of our Functional CALM
Theorem: \jmh{fill in brief explanations of Zinn, Baccaert, etc.}

\subsection{CRDTs: monotone queries over convergent state}
\label{sec:crdt-instance}

A CRDT guarantees that replicas receiving the same updates converge to
equivalent states, whatever the order of delivery and merge.  But the Strong
Eventual Consistency property it offers provides no guarantee on what the environment
may observe, and is subject to Lamport's ``anomalous
behavior''~\cite{lamport1978time} (\S\ref{sec:coordination}).
Laddad et al.\ proposed monotonicity as the right test for safe
observation from CRDT state~\cite{laddad2022keep}.  Their example is a two-phase set, whose state
$(\mathit{Add},\mathit{Del})$ merges by componentwise union.  The query
$\mathit{Add}\setminus\mathit{Del}$ can report a Ferrari in a shopping cart
before a delayed removal arrives, and an application that treats that answer as
final ships the car.  We make the proposed test precise with Functional CALM.

Let $(D,\sqsubseteq,\sqcup)$ be the state join-semilattice.  The input is the
finite set $U$ of immutable payloads received so far, ordered by inclusion, and
the replica's state is $s(U)=s_0\sqcup\bigsqcup U$.  Then $U\subseteq V$
implies $s(U)\sqsubseteq s(V)$, and $s(U_1)\sqcup s(U_2)=s(U_1\cup U_2)$ is the
least state \outrelpart both~\cite{shapiro2011crdt}.  A client observation
$q:D\to(Y,\preceq_Y)$ gives the client-visible specification $q\circ s$.  By
Functional CALM, $q\circ s$ is consistent exactly when $U\subseteq V$ implies
$q(s(U))\preceq_Y q(s(V))$.  Monotonicity of $q$ on all of $D$ suffices, but
$q$ need only be monotone between reachable states.  The two-phase query fails
the test: a removal payload grows $U$ and shrinks the answer.
Operation-based CRDTs fit too, with the causally closed set of
delivered operations as
input~\cite{shapiro2011crdt,burckhardt2014replicated,baquero2014operation,hellerstein2025turtles}.

CRDT states form a join-semilattice.  Observations $q$ need less:
Complete CALM requires only \emph{some} common \outnoun of query outputs
(Section~\ref{sec:lifted-monotonicity}), not a least one.

\subsection{Highly available transactions}
\label{sec:hat-instance}

For a transactional specification, an input is the set of begin, read, write, and
commit requests received so far, ordered by inclusion.  An output is a growing
set of public facts such as $\mathsf{read}(T,x,v)$,
$\mathsf{commit}(T)$, and session-order facts, also ordered by inclusion.  The
isolation level (which reads and commits concurrent transactions may expose) or
session guarantee (per-client ordering, such as reading one's own writes)
determines which fact sets are permitted.  HAT's ingredients then
separate~\cite{bailis2013hat,terry1994session}: the isolation level fixes the
specification, the rule that transactions commit rather than suffer
system-initiated aborts is the response obligation
(Appendix~\ref{app:cap-response}), and sticky availability, in which each
client keeps contacting replicas that hold its session's earlier operations,
is a deployment (Proposition~\ref{thm:complete-cap-deployment}).

\paragraph{Accumulating facts.}
Suppose two replicas execute transactions on disjoint keys.  One exposes
$\mathsf{read}(T_1,x,0)$ and $\mathsf{commit}(T_1)$; the other exposes
$\mathsf{read}(T_2,y,0)$ and $\mathsf{commit}(T_2)$.  If each read observes a
committed version at its replica, the union contains no dirty read.  Under the stated read-committed specification (a transaction reads only committed
versions), later delivery keeps all four facts.  This is the positive accumulation pattern behind HAT results;
it is not a claim that every combination of session guarantees is available.

\paragraph{Serializability and transaction ordering.}
Serializability requires the exposed facts to be explained by some serial order
of committed transactions.  This becomes a distributed obstruction when exposed reads force
opposite serialization orders.  Initially $x=y=0$.  On one side, $T_1$ reads
$x=0$, writes $y=1$, and commits.
On the other, $T_2$ reads $y=0$, writes $x=1$, and commits.  Preserving $T_1$'s
read requires $T_1$ before $T_2$ in any serial explanation; preserving $T_2$'s
read requires $T_2$ before $T_1$.  The serialization graph contains a cycle, so
no serial order of $T_1$ and $T_2$ explains both sets of
facts~\cite{adya2000generalized}.

\paragraph{Snapshot isolation.}
Let overlapping transactions $T_1$ and $T_2$ read the same snapshot and both
write $x$.  Separate replicas could each expose its local commit.  Snapshot
isolation's first-committer-wins rule (of two concurrent writers of $x$, only the first to
commit may commit) allows no output containing both commit
facts~\cite{berenson1995critique,bailis2013hat}.  Eventual storage convergence
may choose a final state; it cannot retract a commit already exposed to a
client.

The examples show where the boundary falls.  A guarantee whose permitted fact sets
are closed under union, as read committed's are here, has a common \outnoun for
whatever separated replicas expose, so it stays available
(Corollary~\ref{cor:complete-cap-S}).  One that orders or excludes concurrent
transactions, as serializability and first-committer-wins do, rules out
combinations that separated replicas can each expose; emitting either side
requires a choice (Proposition~\ref{thm:commitments-require-coordination}), and
a partition prevents making it jointly.  Storage convergence constrains states
after delivery; the facts already exposed are outputs, and output events never
remove them.  We do not re-derive HAT's classification.

\subsection{Invariant confluence}
\label{sec:iconfluence-instance}

An invariant is a predicate that every state must satisfy.  We follow the model
of Bailis et al.~\cite{bailis2014coordination}.  A database state is a set of
versions, and replicas merge states by union.  Each transaction $t\in T$ runs
on the state of the replica that executes it and adds the versions it writes,
so $t(s)\supseteq s$.  An initial state $s_0$ satisfies the invariant
$\mathcal I$.  A state is \emph{reachable} when it can be derived from $s_0$ by
applying transactions and merging states, with every state along the way
satisfying $\mathcal I$.  Every reachable state descends from $s_0$, so $T$ is
\emph{invariant confluent} exactly when $\mathcal I(s_1\cup s_2)$ for all
reachable $s_1$ and $s_2$.

From an instance $(s_0,T,\mathcal I)$ of their model we construct a
specification $S_{\mathcal I}$ in ours as follows (Appendix~\ref{app:iconfluence}).
Inputs are \emph{transaction histories}: partial orders of
        events, each labeled by a transaction in $T$, where one event precedes
        another when the replica running the second saw the first.  A history
        \inrel each of its downward-closed sub-orders.  We keep the
        \emph{locally valid} histories, in which every transaction step
        preserves $\mathcal I$ on its replica's state.
Outputs are database states, ordered by inclusion.
The specification table permits, at input $h$, the state of any downward-closed
        sub-history of $h$ that is \emph{valid}: every merge of what it
        contains satisfies $\mathcal I$.
A replica may thus hold transactions back, but whatever it exposes must be
valid together with everything it contains.

\begin{proposition}[Invariant confluence and Lifted Monotonicity]
\label{prop:iconfluence-lm}
$T$ is invariant confluent if and only if $S_{\mathcal I}$ satisfies Lifted
Monotonicity.
\end{proposition}

\begin{proof}
See Appendix~\ref{app:iconfluence}.
\end{proof}

Invariant confluence is therefore not a separate boundary: for the
specification that exposes database states, it is Lifted Monotonicity, and by
Complete CALM it is consistency.  The
uniqueness constraint of Bailis et al.'s payroll example shows the failure
directly.  Two replicas each create an employee and assign ID~7, which each
sees is unused.  The history in which neither creation saw the other is
locally valid and \inrel both one-creation histories, but its state has two
employees with ID~7, so no state it permits \outrel both.  The system must
reserve IDs, reject one creation, or weaken the invariant.  Concurrency,
not the transactions alone, decides the outcome: a transaction that is harmless
after another can, when it runs without seeing it, produce a state whose merge
with the other's is invalid.

Invariant preservation and transaction availability are different
specifications: $S_{\mathcal I}$ constrains exposed database states, while an
isolation level constrains exposed read and commit facts.

We close with the resulting design lessons and scope limits.
