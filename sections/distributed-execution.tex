\section{Distributed Execution}
\label{sec:distributed-execution}

Consistency already compares independent runs.  This
section shows that those runs are exactly what the participants of a
distributed history execute, once sends and receives are set aside.  Keeping only
each participant's input and output events reduces a snapshot of the history
to one specification state per participant, while retaining the output events
that the environment can observe.  The payoff is that consistency results read
directly as statements about distributed executions, including a convergence
guarantee that can be derived from the specification (Corollary~\ref{cor:convergence}).

\subsection{Distributed histories}
\label{sec:histories}

A distributed execution adds one complication to the transition system of
Section~\ref{sec:determination}: participants may learn the same input through
different message paths and at different times.

\paragraph{Participants and messages.}
A finite set $P$ of \emph{participants} each holds a specification state,
starting at a canonical state $\sigma_S(i_p)$.  A participant changes its
state only by its own input and output events.  It learns input in two ways:
directly from the environment, or in a message from another participant.
Participants exchange messages by $\mathsf{send}(m)$ and $\mathsf{receive}(m)$
events.  A \emph{message} is a pair $m=(j,d)$ of a cumulative input $j$, or
$\varnothing$ if it carries none, and arbitrary other data $d$.  A receive
does not change the specification state.  A participant at $(i,R)$ that
receives $(j,d)$ with $j\neq\varnothing$ incorporates $j$ by its own
$\mathsf{input}(k)$ for a legal common \indesc $k$ of $i$ and $j$.  A message
thus affects specification state only through that input event.

\begin{definition}[Distributed history, consistent cut]
\label{def:distributed-history}
Fix an ordered specification, participants $P$, and an initial input $i_p$
for each.  A \emph{distributed history} $H$ is a finite set of events with:
\begin{enumerate}
  \item a participant assignment and total local order for each participant;
  \item labels $\mathsf{input}(j)$, $\mathsf{output}(o)$
        (Definition~\ref{def:output-event}), $\mathsf{send}(m)$, or
        $\mathsf{receive}(m)$; and
  \item for each receive, a matching send at another participant.
\end{enumerate}
\emph{Happens-before} is the transitive closure of the local orders and of
each send preceding its matching receive; events it does not order are
concurrent.  A \emph{consistent cut} $C$ is a subset of events closed under
happens-before~\cite{lamport1978time,chandy1985distributed}.
\end{definition}

The standard term ``consistent cut'' is unrelated to our notion of
consistency.  The events at any consistent cut project to one run per
participant (Definition~\ref{def:semantic-projection}).

The figure shows why we need a transition projection.  A distributed history
records sends and receives even when they make no difference
to the specification state.  The projection filters each participant's history
to the transitions that determine that state.

\begin{definition}[Transition projection, state endpoint]
\label{def:semantic-projection}
For a consistent cut $C$ and participant $p$, list the events of $C$ assigned
to $p$ in local order.  Its \emph{transition projection} $\pi_p(C)$ keeps input
and output events in that order and deletes sends and receives.  We consider only pairs $(H,C)$ for
which each $\pi_p(C)$ is a defined transition sequence from $\sigma_S(i_p)$;
each recorded $\mathsf{input}(j)$ must itself be legal at the state where it
occurs.  Write $\sigma_p(C)$ for the final specification state of
$\pi_p(C)$.  The \emph{state endpoint} of the cut is the vector
        \begin{equation}
  \operatorname{end}(H,C)=(\sigma_p(C))_{p\in P}.
  \label{eq:semantic-endpoint}
        \end{equation}
Because input and output events are atomic transitions, every transition
projection is a run (Definition~\ref{def:run}).
\end{definition}

At both cuts in Figure~\ref{fig:history-projection}, each local projection is
$\mathsf{input}(xy\cdot)$, so every participant has specification state
$\sigma_1$ and
$\operatorname{end}(H_d,C_d)=\operatorname{end}(H_f,C_f)
=(\sigma_1,\sigma_1)$.  Projection erases the delivery path while retaining
its effect on the participant states.

Equal endpoints need not determine the same future history: participants and
the environment may have observed different outputs, and those observations may
influence later inputs or choices.

\paragraph{Confluence of a history.}
At a consistent cut $C$, the participants may hold different specification
states $(\sigma_p(C))_{p\in P}$.  Confluence asks whether their local paths can
be brought to the same later specification state at every input that combines
their current inputs.  Formally, let $j$ be a common \indesc of the
participant inputs at $C$.  The history $H$ is \emph{confluent at $C$ and $j$}
when the sub-history consisting of the events of $C$ has a further \emph{continuation}---additional events after those of
$C$---in which every participant reaches the same
specification state $\sigma_j=(j,R)$; equivalently, the new cut has state
endpoint $(\sigma_j)_{p\in P}$.  This is an existence
claim about transitions, not a claim that a protocol delivers $j$,
communicates, or terminates.

\subsection{Distributed consistency}
\label{sec:distributed-consistency}

Confluence is a property at one cut and common \indesc.  Distributed
consistency requires it at every cut of every history.

\begin{definition}[Distributed consistency]
\label{def:distributed-consistency}
An ordered specification has \emph{distributed consistency} when, for every
finite participant set, history $H$, and consistent cut $C$, $H$ is
confluent at $C$ and every common \indesc of the participants' current
inputs.
\end{definition}

Distributed consistency is the history-level reading of consistency.
Histories add participants, messages, and cuts, but do not by themselves
assert communication, delivery, or termination.  The next proposition shows
that nothing is lost or gained; its short proof is also why the run
formulation remains useful.

\begin{proposition}[Consistency and distributed consistency]
\label{prop:distributed-consistency}
An ordered specification is consistent if and only if it has distributed
consistency.
\end{proposition}

\begin{proof}
At any cut of a history, the projections are a finite set of runs, so
consistency implies their confluence from those endpoints.  Conversely, place
any finite set of runs in a message-free history,
one per participant; every input event in a run is already a cumulative
$\mathsf{input}(j)$ event.  Distributed consistency at the final cut gives
their confluence.
\end{proof}

Combining Proposition~\ref{prop:distributed-consistency} with Functional CALM,
a functional specification has distributed consistency exactly when it is
monotone.  Corollary~\ref{cor:state-by-input} then gives convergence in every
history:

\begin{corollary}[Convergence]
\label{cor:convergence}
In any history of a consistent functional specification, every
participant whose current input at a consistent cut is $j$ is in state
$\sigma_S(j)$.  Participants that have received the same input therefore agree,
regardless of message paths, arrival order, or the outputs they emitted.
\end{corollary}

\begin{proof}
Each participant's transition projection is a run; apply
Corollary~\ref{cor:state-by-input}.
\end{proof}

This is the convergence that strong eventual
consistency~\cite{shapiro2011crdt} asks of replicated state---replicas that
have received the same updates are in equivalent states---derived here from the specification rather than from a merge operator.
With several outputs per input, this uniqueness fails, as
Section~\ref{sec:complete-calm} discusses.  The distributed reading itself does
not depend on how many outputs an input permits: its proof uses only runs, so
Proposition~\ref{prop:distributed-consistency} holds unchanged for the
specifications of Section~\ref{sec:ambiguous-specifications}, to which we turn
next.
