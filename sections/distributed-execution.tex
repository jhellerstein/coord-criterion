\section{Distributed Execution}
\label{sec:distributed-execution}

Functional CALM defines Consistency as confluence of finite sets of runs under
the canonical commitment basis.  We now add participants, messages, and cuts.
Transition projection reduces a cut to one specification state per participant,
while retaining the output events that the environment can observe.

\subsection{Lamport histories}
\label{sec:histories}

A distributed execution adds one complication to the transition system of
Section~\ref{sec:determination}: participants may learn the same input through
different message paths and at different times.  We retain those paths in a
Lamport history.  Each participant's events are totally ordered; a send precedes
its matching receive; events not ordered by these constraints are concurrent.
Their transitive closure is the familiar \emph{happens-before} relation.

A \emph{consistent cut} is a snapshot of this history that never includes a
receive without the events that causally precede it.  Because the input and
output actions of Section~\ref{sec:determination} are atomic, the events at any
such cut project to one ordinary run for each participant.  Messages explain
how a participant learned something; its projected run records only how that
information changed the specification state.

\begin{definition}[Lamport history of the transition system]
\label{def:distributed-history}
Fix an ordered specification, a finite participant set $P$, initial input $i_p$
for each participant, a commitment basis, and a message set
$M\subseteq(I\cup\{\mathsf{none}\})\times(D\cup\{\mathsf{none}\})$, where $D$
is arbitrary strategy data.  A \emph{distributed history} $H$ consists of a
finite set of events with:
\begin{enumerate}
  \item a participant assignment and total local order for each participant;
  \item labels $\mathsf{input}(j)$, $\mathsf{output}(o)$,
        $\mathsf{send}(m)$, or $\mathsf{receive}(m)$;
  \item for each output event, the finite sequence of basis commitments it
        applies, possibly empty; and
  \item for each receive, a matching send at another participant.
\end{enumerate}
An output event atomically applies its commitments and retirements and emits its
label.  A \emph{consistent cut} $C$ is a subset of events closed under
happens-before~\cite{chandy1985distributed}.  (This standard use of
``consistent'' is unrelated to consistency as confluence.)
\end{definition}

Sends, receives, and strategy data preserve delivery causality without
complicating the specification state.  The next subsection shows how transition
projection removes those details.

The figure shows why we need a transition projection.  A Lamport history
records sends, receives, and strategy state even when they make no difference
to the specification state.  The projection filters each participant's history
to the transitions that determine that state.

\begin{definition}[Transition projection and state endpoint]
\label{def:semantic-projection}
For a consistent cut $C$ and participant $p$, list the events of $C$ assigned
to $p$ in local order.  Its \emph{transition projection} $\pi_p(C)$ keeps input
and output events in that order and deletes sends and receives.  A receive may
update strategy state and influence a later input event, but it does not
directly change the specification state.  We consider only pairs $(H,C)$ for
which each $\pi_p(C)$ is a defined transition sequence from $\sigma_0(i_p)$;
each recorded $\mathsf{input}(j)$ must itself be enabled at the state where it
occurs.  Write $\sigma_p(C)$ for the final specification state of
$\pi_p(C)$.  The \emph{state endpoint} of the cut is the vector
        \begin{equation}
  \operatorname{end}(H,C)=(\sigma_p(C))_{p\in P}.
  \label{eq:semantic-endpoint}
        \end{equation}
Because input and output events are atomic transitions, every transition
projection is a run under the history's commitment basis.
\end{definition}

At both cuts in Figure~\ref{fig:history-projection}, each local projection is
$\mathsf{input}(xy\cdot)$, so every participant has specification state
$\sigma_1$ and
$\operatorname{end}(H_d,C_d)=\operatorname{end}(H_f,C_f)
=(\sigma_1,\sigma_1)$.  Projection erases the delivery path while retaining
its effect on the participant states.

State endpoints determine which state transformations are enabled next.  Equal
endpoints have the same applicable transformations and effects because each is
a partial function of the specification state.  They need not determine the
same future history: participants and the environment may have observed
different outputs, and those observations may influence later inputs or
strategy choices.

\paragraph{Confluence of a history.}
At a consistent cut $C$, the participants may hold different specification
states $(\sigma_p(C))_{p\in P}$.  Confluence asks whether their local paths can
be brought to the same later specification state at every input that combines
their current inputs.  Formally, let $j$ be a common refinement of the
participant inputs at $C$.  The history $H$ is \emph{confluent at $C$ and $j$}
when it has a further extension using input and output events in which every
participant reaches the same specification state $\sigma_j=(j,R)$;
equivalently, the new cut has state endpoint $(\sigma_j)_{p\in P}$.  This is
an existence claim about transitions, not a claim that a protocol delivers
$j$, communicates, or terminates.

\subsection{Distributed Consistency}
\label{sec:distributed-consistency}

Confluence is a property at one cut and common input refinement.  Distributed
Consistency requires it at every cut of every history under the canonical
commitment basis.

\begin{definition}[Distributed Consistency]
\label{def:distributed-consistency}
An ordered specification has \emph{Distributed Consistency} when, for every
finite participant set, history $H$ under the canonical commitment basis, and
consistent cut $C$, $H$ is
confluent at $C$ and every common refinement of
the participants' current inputs.
\end{definition}

Distributed Consistency is the history-level reading of consistency.  It is a
representation theorem: histories add participants, messages, and cuts, but do
not by themselves assert communication, delivery, or termination.  The next
proposition states the exact relationship; its short proof is also why the run
formulation remains useful.

\begin{proposition}[Consistency and Distributed Consistency]
\label{prop:distributed-consistency}
An ordered specification is consistent if and only if it has Distributed
Consistency.
\end{proposition}

\begin{proof}
At any cut, the projections are a finite set of runs under the canonical
commitment basis, so Consistency implies their confluence from those endpoints.
Conversely, place any finite set of such runs in a message-free history, one per
participant; every input action in a run is already a cumulative
$\mathsf{input}(j)$ event.  Distributed Consistency at the final cut gives run
confluence.
\end{proof}

Combining Proposition~\ref{prop:distributed-consistency} with Functional CALM,
a functional specification has Distributed Consistency exactly when it is
monotone.  This distributed reading does not depend on output choice.  We next
make that orthogonal extension to ambiguous specifications.
