\section{Conclusion}
\label{sec:conclusion}

A specification abstracts execution details away, and the results here reduce
to a single question: can a participant act on what it knows without being
contradicted by what it learns later?  Mutexes, locks, atomic instructions, and
agreement protocols prevent such contradictions by making commitments.
Functional CALM answers the question for functions: a functional specification
stays confluent as input arrives exactly when it is monotone, and then no
output needs a seal.  This generalizes the classic result from logical fact
sets to arbitrary input and output orders.

Complete CALM extends the answer to specifications that offer several outputs
for one input.  The test is Lifted Monotonicity, which combines Relational
Monotonicity with Directed Outputs.  When it fails, some reachable output
requires a commitment, and every commitment does one of two jobs: it seals
input or it chooses among outputs.  Because commitments are explicit, the model
can also check whether a use of coordination is proper
(Appendix~\ref{app:composition}).  For example, a totally ordered log and a
key-value store are both non-monotone at their ordinary specifications, yet
once they are composed through a shared order, committing the log order alone
makes the composition consistent.  Multi-Paxos is one way to distribute those
commitments.

Complete CAP is the partition form of the same equivalence, and it makes
Brewer's conjecture precise for any declared guarantee.  A system can keep
every permitted output available and consistent through partitions exactly
when the specification satisfies Lifted Monotonicity.  If only some outputs
must stay available, it can do so exactly when those outputs have a common
\outnoun wherever their inputs meet.  The Gilbert--Lynch theorem follows
directly: a replica's only permitted response is invalidated by a write it
cannot see.  The guarantee, which of its outputs must stay available, and who
serves which operations thus become separate design choices, and query
monotonicity, CRDT merge, transactional availability, and invariant confluence
can be compared on one table without being identified with one another.

Several directions build on these results.  The first moves from criterion to
complexity: not only whether a specification needs commitments, but how many.
The second is determination provenance: which inputs determine an output that
needs no commitment.  The third is general-purpose static analysis of CALM and
of proper coordination in a real programming framework.
