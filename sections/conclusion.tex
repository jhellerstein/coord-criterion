\section{Conclusion}
\label{sec:conclusion}

A specification abstracts execution details away.  Functional CALM asks when
a functional specification remains confluent as input arrives: it does exactly
when it is monotone, and then no output event needs a seal commitment.  This
generalizes the classic result from logical fact sets to arbitrary input and
output refinement orders.

Complete CALM extends the model to specifications that offer several outputs
for one input.  Lifting output events to retire subsumed rows and make output
choices leaves the event contract, and with it the whole argument, intact:
Consistency is again the common-\extension condition, now read as Lifted
Monotonicity, which combines Relational Monotonicity with Directed Outputs.
When Lifted Monotonicity fails, some reachable output requires a commitment and
hence coordination, whether implemented by a mutex, lock, atomic ordering
mechanism, or distributed agreement.  Whatever the mechanism, its effect is
contained in two jobs: sealing input, which Functional CALM already
characterizes, and choosing among permitted outputs, which Complete CALM adds.
Unlike classical CALM, the model can then verify
whether that coordination is proper.  Sequential and independently
parameterized composition are equijoins of specification tables; commitments
restrict the joined table.  At their ordinary interfaces, total log ordering
and a register or key-value store are both non-monotone.  Once composed through
a shared order, committing that log order alone makes the end-to-end
specification satisfy Lifted Monotonicity and hence consistent.  Multi-Paxos
distributes those log commitments.  Distributed histories and Complete CAP
specialize the same boundary to participants and partitions.

The Complete CAP Theorem is the partition form of the same equivalence.  It
makes Brewer's conjecture precise for any declared guarantee: a specification
keeps its whole interface available and consistent through partitions exactly
when it satisfies Lifted Monotonicity, and a response form characterizes when
every operation can at least be answered.  The Gilbert--Lynch register is the
special case in which a replica's only permitted answer is invalidated by a
write it cannot see.  The guarantee, what counts as an answer, and who serves
which operations become separate design choices.  Query
monotonicity, CRDT merge, transactional availability, and invariant confluence
then become directly comparable without being identified with one another.
