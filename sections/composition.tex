\section{Composition and Proper Coordination}
\label{sec:composition}

A replicated key-value store poses a puzzle.  With mutable values, it is
non-monotone and inconsistent~\cite{alvaro2011bloom}. The pragmatic solution is
to impose a consensus-driven log upstream of the replicas, \`a la
Multi-Paxos~\cite{lamport2001paxos}, so all replicas execute the same commands
in the same order. But consensus is itself non-monotone: when two commands
arrive concurrently, either may be appended next, and the two alternative orders
have no common \outnoun.  In essence, the standard solution to non-monotonicity
is more non-monotonicity! Why does it work?

That puzzle is explained by our framework.  As we'll see, two specs compose by equijoin,
and the composition of two monotone specs is also monotone. Moreover, for non-monotone specs,
as in our puzzle, we
can reason about which component actually makes \commitments under composition.  When the
upstream component makes every \commitment the composition needs, and the
downstream needs none on the inputs the upstream offers, we say the pipeline's
coordination is \emph{proper}
(\S\ref{sec:proper-coordination}).  Proofs are in
Appendix~\ref{app:composition}.
\label{sec:sequential-composition}

Formally, consider two \spectype[s]
${\Spec_1=(I,\InputOrd,M,\preceq_M,P_1)}$ and
${\Spec_2=(M,\preceq_M,O,\OutputOrd,P_2)}$
in which the output domain of $\Spec_1$ is the input domain of $\Spec_2$.  Their
\emph{sequential composition} is the \spectype from $I$ to $O$ with table
\begin{equation}
\begin{split}
  P_2\circ P_1
  &=\pi_{I,O}(P_1\Join_M P_2)\\
  &=\{(i,o):\exists m.\ (i,m)\in P_1\land(m,o)\in P_2\}
\end{split}
  \label{eq:spec-composition}
\end{equation}
where $\pi$ and $\Join$ are relational projection and equijoin.  Every $i\in I$
has a nonempty fiber in $P_2\circ P_1$, since $P_1$ is total on $I$ and $P_2$ is
total on $M$ (it has a row at every $m\in M$).  When the two specs run as a
pipeline, $\Spec_2$ takes the outputs of $\Spec_1$ as its inputs, and
we say that $\Spec_1$ \emph{guards} $\Spec_2$.
Appendix~\ref{sec:parameterized-composition} gives each spec an input of its
own as well, as when a store serves reads that bypass the log
(Example~\ref{ex:bare-reads}).

\begin{lemma}[Composition]
\label{lem:composition}
If $\Spec_1$ and $\Spec_2$ satisfy Lifted Monotonicity, then so does the \spectype with table $P_2\circ P_1$.
\end{lemma}

\begin{proof}[Proof sketch]
By Proposition~\ref{prop:common-expansion-form}, it suffices to check the
common-extension condition.  Let finitely many rows $(i_r,o_r)$ of
$P_2\circ P_1$ have a common \indesc $j$.  Each row comes from an intermediate
value $m_r$ with $(i_r,m_r)\in P_1$ and $(m_r,o_r)\in P_2$.  The condition for
$\Spec_1$ gives some $m\in P_1(j)$ that \outrel every $m_r$.  So $m$ is a
common \indesc of the inputs $m_r$ of $\Spec_2$, and the condition for
$\Spec_2$ gives some $o\in P_2(m)$ that \outrel every $o_r$.  Then $(j,o)$ is a
row of $P_2\circ P_1$, and $o$ is the common \outnoun.  Full proof
in Appendix~\ref{app:composition}.
\end{proof}

By associativity the lemma extends to finite pipelines.  For a function $f$,
its table $\{(i,f(i))\}$ satisfies Lifted Monotonicity exactly when $f$ is
monotone (\S\ref{sec:lifted-monotonicity}).

\subsection{Proper Coordination}
\label{sec:proper-coordination}

We return to the replicated store of the opening.  The key-value store is not
monotone on its own, but it is monotone on what the log offers: a log fixes
the order of commands, and a longer log only extends the responses.  The log
issues a \commitment to offer only such inputs, freeing the store from making any
\commitments.

More generally, let $\Spec_1$, which guards $\Spec_2$, be run by a system with any basis, and
let $\Spec_2$ run under a system of its own.  Write $\Spec_2|_{\Spec_1}$ for $\Spec_2$ restricted to the outputs of
$\Spec_1$.  We say that $P_2$ satisfies Lifted Monotonicity \emph{on} a set
$D\subseteq M$ when its restriction to inputs in $D$ does.

\begin{definition}[Proper Coordination]
\label{def:proper-coordination}
A pipeline in which $\Spec_1$ guards $\Spec_2$ is \emph{proper} when
$\Spec_2|_{\Spec_1}$ needs no \commitment: every output at every state it
reaches without \commitment is legal.
\end{definition}

\begin{theorem}[Proper Coordination]
\label{thm:proper-coordination}
Let $\Spec_1$ guard $\Spec_2$ in a pipeline.
\begin{enumerate}
  \item The pipeline is proper exactly when $\Spec_2$ satisfies Lifted
        Monotonicity on the outputs of $\Spec_1$.
  \item Suppose the pipeline is proper, and fix any system for $\Spec_1$.
        Then $\Spec_2|_{\Spec_1}$ can take each output of a run $\rho$ of that
        system as its next input and answer it without \commitment.  Replacing
        each output of $\rho$ by these answers, and dropping the \commitment
        events of $\rho$, gives a canonical run of $P_2\circ P_1$.  Such runs are
        confluent whenever the runs of the system are.
  \item If the pipeline is proper and $P_2\circ P_1$ does not satisfy Lifted
        Monotonicity, some output of $\Spec_1$ needs a \commitment.
\end{enumerate}
\end{theorem}

\begin{proof}[Proof sketch]
(1) is Complete CALM and the no-\commitment test
(Theorem~\ref{thm:complete-calm}, Proposition~\ref{prop:exposure-boundary})
applied to $\Spec_2|_{\Spec_1}$.  (2) The outputs of a run of $\Spec_1$ form a
chain, since each output event keeps only rows above its output.  They are
therefore a valid input sequence for $\Spec_2|_{\Spec_1}$, which by (1) answers
each without \commitment.  The pipeline's run is a run of $P_2\circ P_1$: joining
each answer with the row of $\Spec_1$ it answers gives a row of the composite.
For confluence, confluent runs of $\Spec_1$ share a row above every input the
downstream runs have taken, and Lifted Monotonicity of $\Spec_2$ at that row
gives a common answer.  (3) The no-\commitment test
of the composite fails at a canonical state, which is the image of a canonical
state of $\Spec_1$.  Full proof in Appendix~\ref{app:composition}.
\end{proof}

A proper pipeline is itself a guard for a further stage (Corollary~\ref{cor:pipelines}).  Locks in
the key-value store would be pure overhead: by (1), the store restricted to
logs needs no \commitment.

Theorem~\ref{thm:proper-coordination} follows a pipeline event by event,
with one system per stage.  Stages can also be viewed from outside, so that
stages with different specs and participants compose without one shared
history.  We call a system for one spec, seen only
through its boundary, a \emph{component}.  A component may run as one process
or as a replicated cluster.  The stages around it observe only its
\emph{admitted runs}, each pairing an input with an emitted output that its
spec permits.  Components with different specs form \emph{typed pipelines}
(Appendix~\ref{app:components}).  A typed pipeline hides the intermediate
value and both components' runs, and every input--output pair it shows is a
row of $P_2\circ P_1$.  Properness then has two forms.  A typed pipeline is
\emph{contract-proper} when the pipeline of its specs is proper
(Definition~\ref{def:proper-coordination}), which concerns the specs alone.
\emph{Implementation properness} also depends on the runs that the chosen
downstream component admits: it holds when no downstream run that follows
an upstream output applies a \commitment.  A contract-proper downstream component may still take
locks, or admit too few runs to follow its upstream.  The maximally
permissive empty-basis component for $\Spec_2|_{\Spec_1}$, which admits every
run under the empty basis, does neither.

\subsection{Composite CALM}
\label{sec:composite-calm}

Proper coordination answers our opening puzzle by showing how an upstream
component can discharge a pipeline's \commitment obligations.
\emph{Composite CALM} asks a stronger question: when does a pipeline need no
\commitment at any stage?  If every stage is monotone, the answer is immediate:
by Lemma~\ref{lem:composition} the composite is monotone too, and no stage needs
a \commitment.  The interesting case has a non-monotone stage, and it raises a
simpler puzzle than our opening one.

Consider the spec for an incrementing counter that is capped at $9$, and
compose it with a downstream spec for a double-digit threshold test, which
outputs \textsf{false} for values up through $9$ and \textsf{true} from $10$ on.
Under the usual boolean order, as in LVars~\cite{kuper2013lvars}, \textsf{false}
is only a lower bound, and the test is monotone.  Suppose instead that every
answer must be final.  Then the output order is equality, and the test cannot
emit \textsf{false} without a \commitment, since a later count of $10$ would
contradict it.  Yet when composed after the capped counter, the pair of
components needs no \commitment.  When do composed specs erase the need for
\commitment entirely?

The composite is itself an \spectype.  By Complete CALM, it is consistent
exactly when it satisfies Lifted Monotonicity, and then no output needs a
\commitment (Theorem~\ref{thm:complete-calm},
Proposition~\ref{prop:exposure-boundary}).  The orders on $I$ and $O$ are part
of the composite's contract with its environment.  The order on $M$ is not:
the composite's table never mentions it, and some order on $M$ may make both
stages monotone.  A composite can be jointly monotone, with no stage needing a
\commitment, in three ways.

First, every stage is monotone, as noted above
(Corollary~\ref{cor:pipelines}).  The CRDT observations of Section~\ref{sec:crdt-instance} have this shape.  A
client query $q$ over the replica state $s$ is the composition $q\circ s$, and
compositions of monotone functions are monotone
(Corollary~\ref{cor:functional-composition}), so monotonicity of $q$ on the
whole state domain suffices.

Second, the upstream can filter out the inputs on which the downstream is not
monotone.  In the example above, the test fails monotonicity only when the
count passes from single to double digits, and the capped counter never does
so.  Restricted to the counts it does produce, the test always answers
\textsf{false}; it is constant, and so monotone under any output order,
including equality.  By Theorem~\ref{thm:proper-coordination}(1), the pipeline
is proper, and since the capped counter is itself monotone, neither stage needs
a \commitment (Proposition~\ref{prop:joint-monotone}(2)).  This is proper
coordination in which the upstream itself needs no \commitment.

Third, a different order on $M$ can make two non-monotone stages monotone.
We order the booleans with false below true for $I$, $O$, and $M$.  In a
double toggle, two stages that each negate a boolean compose to the identity.
Neither stage is monotone, but under the reversed order on $M$, both are
(Appendix~\ref{app:composition}).

\begin{proposition}[Jointly monotone composites]
\label{prop:joint-monotone}
The composite $P_2\circ P_1$ satisfies Lifted Monotonicity, and so is
consistent and needs no \commitment, in each of the following cases.
\begin{enumerate}
  \item $\Spec_1$ and $\Spec_2$ satisfy Lifted Monotonicity.
  \item $\Spec_1$ satisfies Lifted Monotonicity; $\Spec_2$ satisfies it on
        $\Spec_1$'s outputs.
  \item $\Spec_1$ and $\Spec_2$ satisfy Lifted Monotonicity via a different order
        on $M$.
\end{enumerate}
\end{proposition}

\begin{proof}[Proof sketch]
(1) is Lemma~\ref{lem:composition}.  (2) The proof of the lemma uses only
intermediate values in fibers of $\Spec_1$.  (3) The composite joins the two
tables on the intermediate value and never compares two of them, so its table
is the same under a different order.  The lemma then applies under that order.  Full
proof in Appendix~\ref{app:composition}.
\end{proof}

The three cases do not cover every monotone composite
(Appendix~\ref{app:composition}).  When no case applies, some stage may have to issue a \commitment even though the composite is monotone.

Sequential composition, products of independent stages, and glue stages that
copy, merge, or route outputs build arbitrary acyclic graphs.  A graph
satisfies Lifted Monotonicity when every node does on the outputs offered to
it, checked node by node much as types are
(Appendix~\ref{app:dataflow-graphs}).

\subsection{Intersection}
\label{sec:intersection}

Sequential composition feeds the outputs of one spec to the inputs of the
next.  Specs can also be combined on a shared interface.  An application spec,
such as a replicated store that answers reads by a fixed rule, may promise
nothing about isolation, while a consistency property, such as an isolation
level, constrains the same reads.  A system that meets both may produce only
the rows that both permit.

\begin{definition}[Intersection]
\label{def:intersection}
Let $\Spec_1=(I,\InputOrd,O,\OutputOrd,P_1)$ and
$\Spec_2=(I,\InputOrd,O,\OutputOrd,P_2)$ share their ordered domains.  Their
\emph{intersection} $\Spec_1\cap\Spec_2$ has table $P_1\cap P_2$.  It is an
\spectype when $P_1\cap P_2$ is total on $I$: every input has an output that
both permit.
\end{definition}

The shared domains matter.  For example, isolation levels are defined on
histories of reads, writes, and commits, so an application spec must describe
its inputs and outputs in those terms before it can be intersected with one.

Intersection does not preserve Lifted Monotonicity.  Let $a$ and $b$ be
incomparable outputs, each below both $c$ and $d$, with $c$ and $d$
incomparable, and let both specs have a single input.  The fiber $\{a,b,c\}$ is
directed, since $c$ \outrel each of its members, and so is $\{a,b,d\}$.  The
intersection of the two fibers, $\{a,b\}$, is not: no output in it \outrel
both $a$ and $b$.  Two specs that need no \commitment can thus have an
intersection that does.  A
monotone bound rules this out.

\begin{proposition}[Intersection under a monotone bound]
\label{prop:intersection-bound}
Let $g:I\to O$ be monotone.  Suppose that every output $\Spec_1$ permits at an
input $j$ lies below $g(j)$, and that $\Spec_1$ and $\Spec_2$ both permit $g(j)$
at every $j$.  Then $\Spec_1\cap\Spec_2$ is an \spectype and satisfies Lifted
Monotonicity.
\end{proposition}

\begin{proof}[Proof sketch]
The intersection permits $g(j)$ at every $j$, so it is total.  An output it
permits at $i\InputOrd j$ lies below $g(i)$, and $g(i)\OutputOrd g(j)$, so
$g(j)$ \outrel every output it permits at inputs below $j$.  Full proof in
Appendix~\ref{app:intersection}.
\end{proof}

A store whose answers follow a monotone rule therefore stays monotone when
intersected with any property that permits the rule's answers.
Section~\ref{sec:hat-instance} uses this construction for isolation levels and
a key-value store.
