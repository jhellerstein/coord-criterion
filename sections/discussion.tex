\section{Discussion}
\label{sec:discussion}

The CALM agenda is to separate what a specification intrinsically requires
from properties of one implementation, deployment, or execution.  The model's
small vocabulary makes several distinctions explicit.

\subsection{Did executions differ, or were multiple answers allowed?}

A functional specification assigns one output to each input, yet executions
may emit different outputs because input arrives incompletely, in different
orders, or in different batches.  This is execution ambiguity.  Semantic
ambiguity is different: the specification permits several outputs at the same
input.  Classical CALM addresses the first setting; Complete CALM adds the
second.

The distinction locates the intrinsic question.  A particular schedule explains
why one execution emitted an output, but cannot establish that the output is
safe under every admitted schedule.  Ordinary monotonicity answers that question
for functions.  Lifted Monotonicity answers it when the interface itself offers
output choice.

\subsection{Was an alternative discovered impossible, or made impossible?}

Both input and commitment can advance determination, but they exercise different
authority.  An input event may make an alternative unreachable: the execution
has learned which cumulative history occurred.  A commitment instead excludes
an alternative that the available input still permits.  Receiving a decisive
ballot and closing the polls can both leave one result, but only the latter is a
binding system choice.

Output retirement is a third case.  It removes a row only when a surviving row
preserves that row's output.  Input retirement, output retirement, and commitment
therefore all narrow a remainder table, but only commitment removes an otherwise
live claim without preserving it.  This semantic effect is the intrinsic source
of coordination in the model.

\subsection{Did replicas converge, or did they preserve what they reported?}

Convergence concerns replicas after they incorporate the same updates.  Output
refinement concerns whether later observations preserve claims already emitted.
Neither implies the other without an interface connecting internal state to
observations.  A last-writer-wins object can converge while replacing a value
previously shown to a client; this is the observable equivalent of retraction.
Conversely, a safe lower-bound observation may remain valid even while replicas
have different internal states.

Join-semilattices are consequently a strong sufficient discipline, not an
intrinsic requirement of consistency.  They provide a uniform least merge for
states.  Complete CALM asks only for an allowed common refinement of the outputs
that the declared interface promises to preserve; Section~\ref{sec:crdt-instance}
shows why the observation function and output order matter.

\subsection{Was a coordination mechanism used, or was a commitment made?}

Locks, validators, timestamp services, mutexes, and agreement protocols are
mechanisms.  They coordinate in this model exactly when they implement a
commitment.  An uncontended lock may exclude no behavior, while a single local
controller may make a binding commitment without communicating.  Mechanism names
therefore do not determine the intrinsic coordination requirement; their effect
on the remainder table does.

This separation also supports Proper Coordination.  A mechanism may be
sufficient without being necessary or unique.  By representing the commitments
it produces, we can test the resulting end-to-end specification for
monotonicity.  In Appendix~\ref{app:composition}, committing the shared log order
makes the composed log/store interface monotone, showing that the chosen
coordination is sufficient.

\subsection{Does a common answer exist, or can the deployed system reach it?}

A common output refinement proves semantic compatibility.  It does not supply
an algorithm to compute that output, authority for every participant to emit it,
messages across a partition, or termination.  Those properties belong to a
deployment and operational model.  Appendix~\ref{app:deployment}, for example,
distinguishes abstract partition compatibility from reconciliation through
deployment-authorized output actions.

The Complete CAP theorem makes one particular operational requirement explicit:
interface-wide Availability requires every permitted output action to avoid both
commitment and a cross-component wait.  Its deployment-relative variant instead
allows commitments made wholly within a component's existing authority.  These
are semantic nonblocking conditions, not full liveness models; protocol results
must separately state fairness, failure, delivery, and cost assumptions.

\subsection{What behavior is promised, and can concurrent executions preserve it?}
\label{sec:consistency-as-confluence}

Linearizability, causal consistency, isolation levels, and application
invariants promise different behaviors.  The framework does not identify these
guarantees with one another.  It represents each as an ordered specification,
then asks one common question: can independently reached states continue to a
common state without invalidating emitted outputs?  Consistency as confluence is
this test, not another protocol or consistency model.

The answer depends on the declared interface.  A CRDT state and an exact read
make different promises; permitting a transaction to abort gives a different
specification from requiring both transactions to commit.  Changing the output
order, adding an allowed common-refining output, narrowing the table, or changing
the deployment can move the boundary.  Each changes the contract or system
design rather than evading the criterion.

\subsection{How does the declarative model connect to execution?}
\label{sec:design-boundary}

The two-column relation is deliberately smaller than a programming or protocol
model.  It can represent an implementation-independent property, such as an
invariant, as readily as a protocol-level consistency guarantee.  Its input
order records how observations accumulate, its output order records which
visible claims persist, and equijoin composes typed component interfaces.  These
choices make the model language-independent without limiting it to protocol
specifications.

Operational models still determine which executions occur.  At the finest
grain, a state machine induces a table whose inputs are environment-event
histories and whose rows pair each history with its possible observable outputs.
When machine state is a sufficient summary of history, those states can instead
serve as inputs.  The abstraction is sound only when histories represented by
the same input have the same relevant continuations; choosing the input domain
is therefore part of specification design.

Lamport histories ground this abstraction without choosing a particular
protocol language.  They retain participant order, message causality, and
observable output events.  Transition projection removes delivery and strategy
details that do not change the specification state, and the equivalence of
Consistency with Distributed Consistency shows that this projection preserves
the confluence question.  It does not preserve or establish every operational
property: implementation, liveness, and complexity remain separate obligations.
