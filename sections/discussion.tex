\section{Discussion}
\label{sec:discussion}

The formal development isolates a small semantic core beneath several familiar
systems models.  This section collects the payoff.  For readers who followed the
theorems, it explains what their distinctions buy; for readers who skipped
ahead, it gives a practical guide to applying the criterion.  The recurring
method is diagnostic: before asking which coordination mechanism to use, first
ask what varies, why an alternative disappears, and what the interface promises
to preserve.

\subsection{Did executions differ, or were multiple answers allowed?}

Two traces can emit different outputs for two fundamentally different reasons.
A functional specification fixes one output for each input, but input may arrive
incompletely, in different orders, or in different batches.  This is execution
ambiguity.  A relational specification adds semantic ambiguity: even at the
same input, several outputs are permitted.

The distinction determines which test applies.  Ordinary monotonicity asks
whether varying functional executions can safely emit results as input grows.
Lifted Monotonicity must additionally account for choices that the interface
itself permits.  Adding nondeterminism to an implementation does not model this
second case; the alternatives must appear as rows in the specification.

Both forms of ambiguity can narrow toward determination, but useful output need
not wait for that process to finish.  The election can emit $\bot$ while either
candidate may still win, and traceroute can emit one observed route while larger
route sets remain possible.  Determination reduces the possibilities that
remain; output reports information that all surviving possibilities can
preserve.  These are separate forms of progress.

\subsection{Was an alternative discovered impossible, or made impossible?}

Whenever a remainder table shrinks, the reason matters.  An input event removes
histories that no longer extend the input received.  An output retirement
removes a row whose output is preserved by a surviving refinement.  Neither
makes a binding choice among otherwise live alternatives.  A commitment does:
it excludes an alternative that input still permits and no surviving output
preserves.

The distinction is visible even when the endpoint looks the same.  Receiving a
decisive ballot and closing the polls can both leave one election result.  The
first learns which input occurred; the second exercises authority over inputs
that could still occur.  Only the second is intrinsically a commitment.  This
classification by semantic effect, rather than by the operation's name, is what
lets one criterion apply across different system models.

\subsection{Did replicas converge, or did they preserve what they reported?}

A convergent object eventually gives equivalent state to replicas that have
incorporated the same updates.  That says nothing by itself about an observation
already returned to a client.  A last-writer-wins object can converge while
replacing an earlier visible value---the observable equivalent of retraction.
Conversely, a lower-bound observation can remain valid while replicas still
hold different internal states.

The output order makes the missing contract explicit: it says which later
observations preserve earlier ones.  A join-semilattice is one strong way to
supply convergence and a uniform least merge, but neither is intrinsically
required by Complete CALM.  The criterion requires an allowed common refinement
only for the outputs the interface promises to preserve.  Consequently a CRDT
state, a point read on that state, and an application query over it can lie on
different sides of the coordination boundary
(Section~\ref{sec:crdt-instance}).

\subsection{Was a coordination mechanism used, or was a commitment made?}

Locks, mutexes, validators, timestamp services, and agreement protocols are
mechanisms.  Their use is not itself the intrinsic event of interest.  An
uncontended lock may exclude no behavior, while one local controller may make a
binding choice without communicating.  In this model an execution coordinates
exactly when it makes a commitment, regardless of the mechanism that realizes
it.

This separation supports a question that the usual CALM test does not ask.  A
mechanism may be sufficient without being necessary or unique.  \emph{Proper
Coordination} tests the specification produced by its commitments.  In
Appendix~\ref{app:composition}, committing the shared log order makes the
composed log/store interface monotone.  The result validates what the mechanism
accomplished without claiming that this mechanism is the only way to accomplish
it.

\subsection{Does a common answer exist, or can the deployed system reach it?}

An allowed common refinement proves that independently emitted outputs are
semantically compatible.  It does not give every participant authority to emit
that refinement, an algorithm to compute it, messages across a partition, or a
termination argument.  Appendix~\ref{app:deployment} exposes this gap directly:
partition compatibility can hold even when the declared deployment cannot carry
out reconciliation through its authorized output events.

Complete CAP adds one particular operational requirement.  Its interface-wide
Availability condition requires every permitted output event to avoid both
commitment and a cross-component wait.  The deployment-relative variant instead
allows commitments made wholly within a component's existing authority.  These
conditions identify semantic nonblocking boundaries; a protocol result must
still state its delivery, fairness, failure, and cost assumptions.

\subsection{What behavior is promised, and can concurrent executions preserve it?}
\label{sec:consistency-as-confluence}
\label{sec:design-boundary}

Linearizability, causal consistency, isolation levels, and application
invariants make different promises.  Consistency as confluence does not replace
or equate them.  Each becomes a specification of permitted observations, and
confluence asks the same question of each: can independently reached states
continue together without invalidating what they emitted?  The promise comes
from the specification; confluence is the common test.

This separation is a source of generality.  The two-column relation can encode a
property such as an invariant as readily as a protocol-level consistency model.
Its input order says how observations accumulate, and its output order says what
later results preserve.  Changing either order changes the interface being
tested.  Because specifications remain typed relations, equijoin also composes
component properties into an end-to-end contract.  The model can therefore ask
whether a local coordination decision is sufficient after composition, rather
than examining components in isolation.

There is a useful historical turn here.  \emph{The Declarative Imperative}
proposed that declarative database languages could provide a foundation for
distributed programming, and stated CALM in terms of expressibility in monotonic
Datalog~\cite{hellerstein2010declarative}.  That formulation still left the
coordination question entangled with a program: its rules, language extensions,
time and location constructs, and operational semantics.  Our specification
table is declarative at a lower layer.  It says only which input/output behaviors
are permitted and which observations refine others.  Monotonic Datalog remains
one way to realize such a specification, but is no longer the object that defines
the intrinsic boundary.  In retrospect, the durable part of the original thesis
was not that the right distributed programs must be written in one declarative
language; it was that the coordination boundary should be stated on a monotone
declarative object.  Here that object is the specification table.

The simplicity does not detach the model from execution.  A state machine
induces a table by pairing environment histories with their observable outputs.
If machine state is a sufficient summary of history---equal states have the same
relevant continuations---those states can serve as the inputs instead.  Choosing this summary is part of specification design: the table may
forget operational detail only when that detail cannot change its future
obligations.

Distributed histories provide the corresponding grounding.  They retain
participant order, message causality, and observable output events; transition
projection discards delivery and strategy details that do not change the
specification state.  The equivalence of Consistency and Distributed
Consistency shows that this projection preserves the confluence question.  It
does not claim that the projection preserves every implementation property or
supply a language, protocol, liveness proof, or complexity bound.  Those remain
the work of the operational model in which the specification is realized.
