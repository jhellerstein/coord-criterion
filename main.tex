\begin{abstract}
When does a distributed system inherently require coordination?  CALM, CAP,
CRDTs, Highly Available Transactions, and invariant confluence give related
answers in different mathematical languages.  This fragmentation has allowed
conventional wisdom to drift away from what the literature actually proves.
It also makes intuitive questions spanning these results hard even to state.

We show how to express these results in one small, common model.  A
specification is simply a relation from inputs to allowed outputs, together
with orders saying when one input contains more information than another and
when one output can safely extend another without contradiction.  Complete
CALM says that participants can expose outputs without coordination exactly
when the specification is monotone with respect to these orders.  Applying the
same test only to collections of choices that a deployment can separate across
a network partition yields Complete CAP: consistency, availability, and
partition tolerance coexist exactly when the specification is monotone across
partitions.  The shared monotonicity test also clarifies questions spanning
these previously separate areas; we illustrate it with examples covering
various pairings.
\end{abstract}

\section{Introduction}
\label{sec:intro}

CALM and CAP are among the best-known guides to coordination in distributed
systems.  CRDTs, Highly Available Transactions (HATs), and invariant confluence
address closely related questions.  Yet these results are difficult to compare
directly.  CALM is proved using monotone logic and relational transducers; CAP
uses executions of replicated registers; CRDTs use semilattices; HATs classify
transactional guarantees; invariant confluence reasons about application-valid
database states
~\cite{ameloot2013relational,gilbert2002cap,shapiro2011crdt,bailis2013hat,bailis2014coordination}.
Each formalism provides machinery suited to its purpose, but the machinery
hides the simple semantic boundary the results share.

This separation has practical and conceptual costs.  It leaves basic
cross-cutting questions surprisingly awkward to state.  Does CALM encompass
the CAP tradeoff?  Are associative, commutative, and idempotent CRDT joins
necessary for coordination freedom, or are they one strong implementation
discipline?  Does convergent CRDT storage automatically provide highly
available transactions?  If storage converges and transactions remain
available, do application invariants follow?  Today these questions cross
several vocabularies.  We show that they can all be asked using one test.

The test begins with an observation that the individual literatures sometimes
make in different ways: \emph{different answers can still fit together}.  Two
set replicas may hold different elements and later take their union.  Two log
shards may show different local sequences and later interleave them.  Two
readers of a causally consistent register may even return different concurrent
writes, while one later explanation keeps both.  In each case the answers
differ, yet some later answer keeps them all, so no coordination is needed.

Coordination is forced only when answers \emph{cannot} fit together.  Two sites
that independently elect different leaders have given answers that no single
later leader keeps.  Transactions whose reads imply opposite orders have no
single order that keeps both.  Once answers like these are public, it is too
late to patch things up: at least one site had to wait before it answered.
This is the operational question behind all five traditions:
\begin{quote}
\emph{When do independently allowed answers all fit together---when does some
later allowed answer keep them all?}
\end{quote}

We answer with the simplest model we know that still states the question
correctly: an ordered table of input/output pairs.  A row says an output is
allowed at an input.  One order tracks learning more input; another tracks
extending an answer without taking anything back.  A table is monotone when two
things hold.  First, more input always leaves room for an answer that keeps what
was already shown.  Second, when several answers are allowed at once, some
allowed answer keeps all of them.  The first is ordinary query monotonicity.
The second is what matters when a system genuinely has a choice to make.

At this level, Complete CALM is almost immediate: participants can make the
choices the interface allows, on their own and without coordinating, exactly
when the table is monotone.  ``Complete'' means the test works both ways---it is
necessary as well as sufficient.  A semilattice is one strong way to guarantee
that answers fit together, but the test only asks that some later answer keep
them all, not that there be a single canonical one.

Complete CAP is the same result restricted by a \emph{deployment}: a record of
which participant is allowed to give which answer.  CALM looks at every
independent choice.  CAP looks only at the choices a partition can push onto
opposite sides of the cut.  The restriction matters.  Two answers to one read
may fail to fit together, but if only that read's owner can pick between them, a
network cut never splits the choice.  In this precise sense, \emph{CAP is CALM
restricted by a deployment}.

This paper makes four contributions:
\begin{enumerate}
  \item a common model for coordination results: an input/output relation with
        separate orders for input growth and output growth;
  \item a clear account of what forces coordination---not that answers differ,
        and not even that they are unrelated, but that they cannot fit
        together---and the matching split between safely exposing an answer and
        committing to one;
  \item Complete CALM, and Complete CAP as its restriction to the choices a
        deployment can split across a partition; and
  \item a walk through query monotonicity, CRDTs, registers, HATs, and invariant
        confluence, with concrete successes and failures that show both their
        shared structure and their different guarantees.
\end{enumerate}

The small model does not replace relational transducers, semilattices,
transaction protocols, or application-level analysis.  Those give us languages,
algorithms, and proof techniques.  They are just not needed to state the shared
question.  The proof is short because the model points right at what forces
coordination; connecting a real system to the model can still take real work.

Section~\ref{sec:choices} builds up exposure and commitment through voting and
leader election.  Section~\ref{sec:model} writes down the ordered table, and
Section~\ref{sec:calm} states Complete CALM.  A register execution sets up the
deployment-relative Complete CAP in Sections~\ref{sec:registers}
and~\ref{sec:cap}.  Section~\ref{sec:instances} revisits the surrounding
literature in the common vocabulary, and the discussion and related work
follow.  Throughout, the criterion is about safety---whether answers can be
kept together---not about building a live or efficient system.

\section{Why Systems Have to Wait}
\label{sec:choices}

We start with two small applications.  They separate input that can safely
accumulate from choices that cannot be made independently.

\subsection{Voting: accumulate evidence}

Consider a fixed population of three voters.  Each voter casts at most one
immutable ballot for $a$ or $b$.  A site may know only some ballots, but its
knowledge grows as ballots arrive.  Table~\ref{tab:voting} shows the facts it
can safely publish.

\begin{table}[h]
  \centering
  \small
  \caption{A three-voter election.  More ballots may certify a result, but
  never revoke one.}
  \label{tab:voting}
  \begin{tabular}{@{}ll@{}}
    \toprule
    Ballots known & Safe output \\
    \midrule
    $\{v_1\!:\!a\}$ & $\varnothing$ \\
    $\{v_1\!:\!a,v_2\!:\!a\}$ & $\{\mathsf{winner}(a)\}$ \\
    $\{v_1\!:\!a,v_2\!:\!b\}$ & $\varnothing$ \\
    $\{v_1\!:\!a,v_2\!:\!b,v_3\!:\!b\}$
      & $\{\mathsf{winner}(b)\}$ \\
    \bottomrule
  \end{tabular}
\end{table}

The empty set is always a safe answer: it claims nothing.  Once two immutable
ballots certify a winner, no valid third ballot can reverse that result.  Sites
can therefore reveal what they know without first agreeing on an arrival
order.  They are accumulating evidence, not choosing among futures.

\subsection{Leader election: choose one future}

Now suppose two candidates, $c_1$ and $c_2$, are eligible to lead.  Either is an
acceptable outcome, but clients require one leader.  Reporting $c_1$ does more
than reveal a fact: it rules out the still-acceptable outcome $c_2$.  If another
site can independently report $c_2$, the system has given two answers that no
single later leader keeps.  Agreement has to happen before those answers get
out.

Three small output shapes capture the difference:
\begin{equation}
\begin{gathered}
  \bot\OutputOrd a\OutputOrd b \qquad \text{(a chain)},\\
  a\OutputOrd t\;\land\;b\OutputOrd t \qquad \text{(a joined fork)},\\
  a\qquad b \qquad \text{(an unjoined fork)}.
\end{gathered}
\label{eq:three-shapes}
\end{equation}
The chain is ordinary accumulation.  In the joined fork, $a$ and $b$ differ and
neither contains the other, yet $t$ keeps both---they fit together.  Only the
unjoined fork fails to fit together, because nothing keeps both $a$ and $b$.  So
two answers being unrelated is not enough to force coordination; coordination is
forced only when no later answer keeps both.

\subsection{Exposure is not commitment}
\label{sec:exposure}

Public output cannot be taken back.  After a system reports $o$, it may add
more information later, but it cannot switch to an answer that contradicts $o$.
Every later answer has to extend $o$.

Still, reporting $o$ need not throw away a meaningful alternative.  In the
joined fork above, reporting $a$ rules out the literal answer $b$, but $b$'s
content survives in $t$, which extends both.  We call $o$ \emph{safe to expose}
when reporting it leaves some later answer for every outcome that was possible
beforehand.  Reporting such an answer is just that---sharing information---and
needs no agreement with anyone.

Choosing $c_1$ in the leader example is different.  It rules out $c_2$ and
leaves no answer that preserves it.  This is a \emph{commitment}: the point
where the system picks one future and gives up another.  Commitments are not
bad; real systems make them all the time.  But if two participants might each
make a commitment and those commitments cannot both hold, they have to
coordinate first---wait for enough information or agreement that their choices
line up.

A little notation makes the distinction precise without modeling a whole
protocol.  Let $R(i)$ be the answers still possible at the current input $i$.
Once $o$ is public, the ones that survive are those that extend it:
\begin{equation}
  R(i)\mathbin{\upharpoonright}o
    = \{u\in R(i):o\OutputOrd u\}.
  \label{eq:residual}
\end{equation}
Reporting $o$ is safe to expose when every still-possible answer $x$ has a
survivor $u$ that extends both $x$ and $o$.  If some $x$ has no such survivor,
reporting $o$ destroys content: it is a commitment.

\begin{table}[h]
  \centering
  \small
  \caption{Four things a participant can do, and what each one costs.}
  \label{tab:exposure}
  \begin{tabular}{@{}p{.20\columnwidth}p{.69\columnwidth}@{}}
    \toprule
    Action & What it means \\
    \midrule
    Receive input & Learn more; receiving a request chooses no answer by
      itself. \\
    Expose $o$ & Report an answer while keeping some future for every
      still-possible outcome. \\
    Commit to $o$ & Rule out a still-possible outcome that nothing left can
      recover. \\
    Coordinate & Wait for information or agreement before a commitment that
      might not fit with someone else's. \\
    \bottomrule
  \end{tabular}
\end{table}

This corrects a tempting but wrong shortcut.  Reporting $o$ does not simply drop
the answers below $o$ and leave unrelated answers alone.  An unrelated answer
survives only if some allowed result extends both it and $o$.  The test is
whether two answers can be kept together, not whether one sits above the
other.

\section{A Small Model of System Behavior}
\label{sec:model}

The examples above already contain the whole model.  We now name its parts so
we can apply the same test to queries, registers, transactions, and replicated
state.

A deterministic API maps each input to one output.  An API with choices is a
table $S$ of input/output rows: a row $(i,o)$ says that $o$ is an acceptable
answer at $i$.  Leader election needs a table rather than a function because
either candidate is acceptable until someone picks one.

The table also records how things change over time.  Write $i\InputOrd j$ when
$j$ holds at least the input information in $i$---more has been learned.  Write
$o\OutputOrd u$ when $u$ keeps everything $o$ has already shown and perhaps adds
more.  For ballots and query facts, both orders are usually set inclusion.  For
registers, a later answer extends an earlier explanation of what happened.  For
a CRDT, the output order is the state lattice.

Putting the parts together, a specification is
\begin{equation}
  \Spec=(I,\InputOrd,O,\OutputOrd,S),
  \qquad S\subseteq I\times O.
  \label{eq:ordered-spec}
\end{equation}
We write $\fiber{i}=\{o:(i,o)\in S\}$ for the answers allowed at $i$.

\subsection{The test: do answers fit together?}

Imagine several participants working from partial but compatible information.
Participant $r$ has seen input $i_r$ and reports an allowed answer $o_r$.  Later
the system reaches an input $j$ that contains every $i_r$.  Can it still give an
allowed answer that keeps every earlier report?  This is the paper's one central
definition.

\begin{definition}[Monotonicity]
\label{def:monotone}
The specification is \emph{monotone} when the following holds.  Take any
nonempty finite set of allowed rows
$(i_1,o_1),\ldots,(i_k,o_k)$ and any input $j$ that extends all the $i_r$.
There is an allowed output $u\in\fiber{j}$ that extends every selected output:
\begin{equation}
  o_r\OutputOrd u \qquad\text{for all }r.
  \label{eq:monotonicity}
\end{equation}
\end{definition}

In plain terms: if the inputs can hold together, the answers must fit together
too---some allowed answer at $j$ keeps them all.  We check finite groups, not
just pairs, because answers can be pairwise fine yet have no single answer that
keeps the whole group.

The definition bundles two familiar checks:
\begin{description}
  \item[Growth with new input.] If $i\InputOrd j$ and $o$ is allowed at $i$,
        some answer allowed at $j$ keeps $o$.
  \item[Coherent choices.] If several answers are allowed at the same input,
        some answer allowed there keeps all of them.
\end{description}
The first check is what voting and ordinary query monotonicity need.  The second
asks whether the allowed choices are compatible freedom or competing
commitments.

The two checks together are exactly Definition~\ref{def:monotone}.  One
direction is immediate: a single row gives growth, and several rows at one input
give coherent choices.  For the other direction, first grow each reported answer
out to the combined input $j$, then use coherence at $j$ to find one answer that
keeps them all.

A deterministic API has no competing choices at one input, so only growth is
left.  The test becomes ordinary order preservation:
\begin{equation}
  i\InputOrd j\quad\Longrightarrow\quad f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
\end{equation}
Once an API allows real choices, coherence is a genuine second requirement.  A
test that looks only within one input's answers catches that case but misses
plain growth as new input arrives---which is why both orders are needed.

\section{The Coordination Boundary}
\label{sec:calm}

We can now answer the question from the introduction.  Picture the participants
in a system each reporting answers from the table as they learn more input, and
ask whether they can do this on their own or must sometimes wait for one
another.

One caveat makes the question precise.  We treat each row in the table as a
behavior a participant is actually allowed to produce, not just an option an
implementation may quietly skip.  If an implementation only ever produces a
smaller set of answers, that smaller table is its real interface, and that is
the table to test.

Call a set of independent reports consistent when, once their inputs come
together, some allowed later answer keeps all of them.  The reports need not be
identical: a set replica may grow, a log may gain records, a causal history may
gain events.  What matters is that no answer already shown gets taken back.

\begin{theorem}[Complete CALM]
\label{thm:calm}
At a declared input/output interface, participants can make the choices the
interface allows without ever waiting to avoid a conflict if and only if the
specification is monotone.
\end{theorem}

\begin{proof}
If the table is monotone, Equation~\ref{eq:monotonicity} hands us an allowed
answer that keeps every finite group of independent reports once their inputs
come together.  This holds no matter what order the messages arrive in, so no
participant has to wait just to keep the reports from conflicting.

If the table is not monotone, the failed test is itself a concrete execution: a
finite group of allowed answers and a combined input where nothing keeps them
all.  The system can only wait before one of the choices, let the conflicting
answers stand, or refuse an answer the interface allowed.  These give up
coordination freedom, consistency, or the interface, respectively.
\end{proof}

The proof is short because the model points straight at the obstruction.
Relational transducers, semilattices, transaction protocols, and other models
still do real work: they give us languages to write programs in, algorithms to
run, and ways to check that an implementation matches a table.  They are simply
not needed to say why two independent answers conflict.

``Complete'' means the test runs both ways at this interface.  A semilattice is
one strong way to guarantee a common answer, but not the only way.  And when the
test fails, it names the exact choices that force agreement.  Change the rows,
the growth orders, or who is allowed to pick which answer, and you change the
interface---possibly moving the boundary.

The theorem is about safety, not progress.  Knowing a common answer exists does
not tell a replica how to compute it, guarantee that every request finishes, or
bound how long reconciliation takes.  Those stay the job of a protocol.

\section{Registers: Different Answers Can Be Safe}
\label{sec:registers}

We now return to a familiar execution.  It shows why CAP has to know not just
which answers are possible, but which participant is allowed to give each one.

A register is replicated at processes $p$ and $q$.  Starting from no value, $p$
writes \dog{} while $q$ concurrently writes \catv.  Each process later learns
the other's write and then serves a local read.  Both writes finish before
either read begins.

\begin{table}[h]
  \centering
  \small
  \caption{Two processes observe both concurrent writes and answer local reads.}
  \label{tab:register}
  \begin{tabular}{@{}p{.43\columnwidth}p{.43\columnwidth}@{}}
    \toprule
    Process $p$ & Process $q$ \\
    \midrule
    $w_p(x,\dog)$ & $w_q(x,\catv)$ \\
    receive $w_q$ & receive $w_p$ \\
    $r_p(x)\mapsto\catv$ & $r_q(x)\mapsto\dog$ \\
    \bottomrule
  \end{tabular}
\end{table}

To place this execution in our table, let the input be a causal history; more
input adds events along with everything that causally came before them.  An
output is an \emph{explanation}: an ordering of the operations plus, for each
completed read, which write supplied its value.  A later explanation may add
events, ordering, and read answers, but it may not flip an ordering it already
committed to or change a read it already answered.

\subsection{A total order cannot explain both answers}

Linearizability needs one total order of the operations that respects real
time~\cite{herlihy1990linearizability}.  For $p$ to return \catv, its
explanation puts the \dog{} write before the \catv{} write.  For $q$ to return
\dog, its explanation needs the opposite order.  Each is fine on its own, but no
single total order extends both.  If the two sides are each allowed to answer
their read, they have to agree on the write order first.  This is the conflict
behind the classic linearizable-register CAP result; the full impossibility
proof also pins down the exact timing of operations and failures
~\cite{gilbert2002cap}.

\subsection{A causal order can explain both answers}

Causal consistency leaves the concurrent writes unordered.  Either one may
explain a read~\cite{lamport1978time,ahamad1995causal}.  So a single larger
explanation can keep both read results at once: it answers $p$'s read with
\catv{} and $q$'s read with \dog{} while leaving the two writes concurrent.  The
answers differ, but they do not conflict.

There is a subtlety worth drawing out.  The two possible values for the
\emph{same} read cannot both stand; once a read is answered, that answer is
fixed.  So if we imagined every participant free to answer every read, the
causal-register table would not be monotone.  Real deployments do not work that
way.  Only $p$ answers $p$'s read, so its two possible answers are never chosen
on opposite sides of a partition, and that local choice needs no cross-partition
agreement.  This is exactly where the deployment enters the picture.

\section{Partitions Restrict the Test}
\label{sec:cap}

Complete CALM asks whether every independent choice can coexist.  CAP asks a
narrower question: which of those choices can a network cut push apart?
Processes on the same side of a partition can still talk to each other, pick a
local leader, or settle a local choice.  What availability forbids is waiting
for a message that has to cross the cut.

To make this precise we add one ingredient: who is allowed to answer what.  A
\emph{deployment} $\Delta$ gives each participant $p$ a set $\Delta_p$ of table
rows it may produce.  A partition $\Pi$ splits the participants into two or more
sides.  A finite group of rows is \emph{separable} under $\Pi$ when its rows can
be handed to participants on at least two different sides.  Those are the
choices that can race ahead of each other while the partition lasts.

The deployment is \emph{monotone across $\Pi$} when every such separable group
still passes the common-answer test once their inputs come together:
\begin{equation}
  \exists u\in\fiber{j}\;\;\forall r:\;o_r\OutputOrd u.
  \label{eq:partition-monotonicity}
\end{equation}
Notice what this does not test.  If two conflicting answers are controlled by
one process, or by processes that stay on the same side of the cut, they can be
settled locally.  CAP only cares about agreement that would have to cross the
cut.

Two words need pinning down here.  \emph{availability} means a working side can
produce the answers it is allowed to produce without waiting across the cut.
\emph{consistency} means the answers produced on different sides have an allowed
answer in common once their inputs meet.  This is consistency in the sense of
keeping every answer, not in the sense of linearizability or identical replica
state.

\begin{theorem}[Complete CAP under a deployment]
\label{thm:cap}
For a fixed deployment and set of relevant network partitions, available
choices can always be reconciled after a partition if and only if the
specification is monotone across those partitions.
\end{theorem}

\begin{proof}
If the restricted test holds, gather the answers produced on the different
sides.  Equation~\ref{eq:partition-monotonicity} gives an allowed answer that
keeps them all once communication resumes.  Conflicts within one side can be
settled locally, so no choice has to wait across the cut just to stay
consistent.

If the test fails, its witness hands conflicting answers to participants on
different sides.  While the partition lasts, neither side can see the other's
choice.  Waiting across the cut gives up availability; answering anyway gives up
consistency; dropping one of the rows means offering a narrower interface.
\end{proof}

The three ways out are worth stating plainly:
\begin{center}
\begin{tabular}{@{}ll@{}}
wait across the cut & give up availability; \\
answer anyway & give up consistency; \\
drop a choice & offer a narrower interface.
\end{tabular}
\end{center}

This is why the one-line summary holds up: \emph{CAP is CALM restricted by a
deployment.}  CALM tests every independent group of choices; CAP tests only the
groups a deployment can push onto different sides of a cut.  If any participant
could produce any row, the two tests are the same.  Otherwise, conflicts that
stay on one side do not stand in the way of staying available during a
partition.

Back to the register.  The two opposing total orders can be produced by the two
replicas and fail the restricted test.  The causal explanations for $p$'s and
$q$'s different reads have an answer in common.  The one conflict that
remains---two possible values for a single read---stays with that read's owner and
cannot be split across the cut.  That is why a causal register can keep
answering during a partition even though, in the abstract, its table contains
conflicting local choices.

\section{The Same Test in Familiar Systems}
\label{sec:instances}

A small model earns its keep by letting us set results from different traditions
side by side---without pretending they offer the same guarantees.
Table~\ref{tab:instances} lists the input, output, and preservation order for
five of them.  The subsections then walk through where the test passes and where
it fails.

\subsection{CALM becomes ordinary query monotonicity}

A site evaluating a query $Q$ has seen a finite set of facts $J$.  More input
means more facts, and the one allowed answer is $Q(J)$.  Output grows by set
inclusion too.  The test becomes the textbook definition of a monotone query
~\cite{abiteboul1995foundations}:
\begin{equation}
  J\subseteq J'\quad\Longrightarrow\quad Q(J)\subseteq Q(J').
  \label{eq:query-monotonicity}
\end{equation}
If two sites know $J_1$ and $J_2$, then $Q(J_1\cup J_2)$ keeps both partial
answers when the query is monotone.  A non-monotone query may have to take back
a fact once the missing input shows up.

Ameloot et al. tie this property to coordination-free execution for a network of
relational transducers~\cite{ameloot2013relational,ameloot2015weaker}.  Their
model supplies a language, a story for how computation is distributed, and an
operational theorem.  The table here pulls out the property that theorem relies
on, so we can ask the same question of interfaces that are not Datalog
programs.

\subsection{CRDT joins are sufficient, not necessary}

For a state-based CRDT, let the input be the state deltas (or the upward-moving
replica states) received so far.  The output is the accumulated state, ordered
by the CRDT's state lattice.  Merge is the lattice join
~\cite{shapiro2011crdt}, and for delta sets $U_1$ and $U_2$,
\begin{equation}
  s(U_1)\sqcup s(U_2)=s(U_1\cup U_2).
  \label{eq:crdt-join}
\end{equation}
The join is an allowed common answer.  Because it is associative, commutative,
and idempotent, the result does not depend on how the deltas are grouped,
ordered, or duplicated.

This is more than Complete CALM asks for.  A semilattice hands you a single
\emph{least} common answer for every pair.  The test only needs \emph{some}
allowed common answer for each finite group---it need not be the least one, and
it need not come from one global operator.

A sharded log shows the gap.  Shard $A$ exposes $[a_1,a_2]$ and shard $B$
exposes $[b_1,b_2]$.  Any combined sequence has to keep each shard's own order.
Both
\begin{equation}
  [a_1,a_2,b_1,b_2]
  \quad\text{and}\quad
  [b_1,b_2,a_1,a_2]
  \label{eq:log-interleavings}
\end{equation}
are smallest common extensions, and neither sits below the other, so there is no
single least interleaving.  Either one is still a fine reconciliation.  As long
as each shard only publishes its own local sequence, the cross-shard choices fit
together without any global join.  (The full set of finished global
interleavings would not be monotone, so this is a deployment-relative example.)

One boundary is worth stating.  This argument is about the state or append
interface, not about exact reads.  ``The current value is $v$'' can stop being
true after the next update, whereas ``the count is at least 10'' stays true.
Convergent state does not settle read or transaction semantics
~\cite{burckhardt2014principles,laddad2022keep}.

\subsection{Convergent storage does not make every transaction available}

A transactional input holds the begin, read, write, and commit requests seen so
far.  The output holds facts such as $\mathsf{read}(T,x,v)$ and
$\mathsf{commit}(T)$, plus session facts, all growing by inclusion.  The
isolation level decides which combinations of facts are allowed, and the
deployment decides which replica may act for each transaction.  As in the HAT
work, whether a level stays available depends on these contact, failure, and
session assumptions~\cite{bailis2013hat,terry1994session}.

The positive case looks unremarkable, which is the point.  Two sites run
transactions on different keys.  One reports that $T_1$ read the committed value
$x=0$ and committed; the other reports the matching facts for $T_2$ and $y=0$.
Together these facts contain no dirty read and no write conflict, so under read
committed a later delivery can keep all four.  This is the accumulating-facts
pattern behind the positive HAT results---not a claim that every mix of session
guarantees is available.

Serializability gives a clean negative case.  Start with $x=y=0$.  On one side,
$T_1$ reads $x=0$, writes $y=1$, and commits.  On the other, $T_2$ reads $y=0$,
writes $x=1$, and commits.  Keeping $T_1$'s read puts it before $T_2$ in a
serial order; keeping $T_2$'s read needs the reverse.  The dependency graph has
a cycle, so no serial history keeps both sets of facts
~\cite{adya2000generalized}.

Snapshot isolation fails for a different reason.  Let $T_1$ and $T_2$ overlap,
read the same snapshot, and both write $x$.  If two replicas each report their
own commit, snapshot isolation's first-committer-wins rule allows no outcome
holding both commits~\cite{berenson1995critique,bailis2013hat}.  Storage can
still converge on a final value; it just cannot un-tell a client about a commit
it already reported.

These executions settle a question that comes up often.  A CRDT under a
transaction processor can make the stored state converge once updates arrive.
It does not automatically keep the reads and commits reported before then.  The
transactional interface has to pass its own common-answer test.

\subsection{Invariant confluence tests application correctness}

Invariant confluence asks yet another question: if transactions run on their
own from a shared valid state, is the merged state still valid for the
application~\cite{bailis2014coordination}?  Here the input is the set of applied
transactions, and we take each transaction to map a valid state to a valid
state---the standard assumption, and the one that makes the question about
merging rather than about any single transaction.  The output is a reachable,
valid database state.  One state extends another when the application's merge
can get there while keeping the earlier effects.

Two things have to hold for this to be the same test as before.  Growth: adding
a transaction keeps the state valid, which is exactly the assumption above, so
an answer at the smaller input still has an answer at the larger one.  Coherent
choice: merging two valid reachable states leaves a valid state---this is
invariant confluence itself.  With merge associative, merged states still
reachable, and the valid states closed under merge, the pairwise check extends
to a whole finite group by merging over and over.  So invariant confluence is
the growth-plus-coherent-choice test applied to valid states, and dropping the
single-transaction assumption would make it fail for a trivial reason---one bad
transaction---rather than for the merge conflict it is meant to catch.

A uniqueness constraint shows the failure.  Two replicas both see that the
username \texttt{sam} is free and hand it to different accounts.  Each database
is valid on its own.  No state that keeps both assignments is valid.  The system
has to reserve names up front, reject one assignment, or relax the rule.

None of this folds three properties into one.  Convergence asks whether replicas
settle on the same state.  HAT availability asks which reads and commits can
finish.  Invariant confluence asks whether effects that each keep the invariant
still keep it once merged.  All three share the shape of the test but run it
over different outputs, so a system can pass one and fail another.

\section{What the Criterion Does---and Does Not---Say}
\label{sec:discussion}

\subsection{The model is a lens, not an implementation language}

Relational transducers, semilattices, concurrency-control protocols, and
consistency models are not being retired.  They tell us how programs run, how
state is stored, how replicas learn things, and how to check a property.  The
ordered table does less: it says what the interface is allowed to produce and
when two answers can be kept together.  Doing less is exactly what lets it
compare results across these traditions.

Read the short Complete CALM proof in that light.  Once the table lists every
allowed answer and the output order says what ``keep'' means, there is nowhere
for a conflict to hide.  The hard engineering is usually elsewhere: writing down
the table, implementing its choices, and computing a reconciliation fast enough.

\subsection{Specification design moves the boundary}

Monotonicity is not a label stuck permanently on ``register,'' ``transaction,''
or ``shopping cart.''  It depends on what the interface actually exposes.  A
linearizable register promises something different from a causal one.  A CRDT
state interface promises something different from exact reads.  A system allowed
to abort one writer has a different table from one that must commit both.

A designer can remove a conflict by narrowing the allowed answers, or by adding
a new answer that safely stands for both branches.  They can also move authority
so that one side owns a local choice.  Each of these changes what clients see,
or how the system is deployed.  The point is that the criterion puts that
tradeoff in the open, instead of letting the implementation mechanism quietly
decide what consistency means.

\subsection{Compatibility is weaker than convergence}

Monotonicity asks for \emph{some} allowed common answer, not a unique or least
one.  The sharded log had several smallest interleavings.  Strong eventual
consistency promises more: replicas that have seen the same information reach
the same state.  A semilattice join is a tidy way to get that.  Going the other
way, a last-writer-wins register converges by throwing one concurrent value
away---fine for convergence, but it breaks an interface that promised to keep
both.  Converging and keeping every answer are different goals.

\subsection{Safety is not liveness}

The common-answer test is about safety.  It does not promise message delivery,
force a replica to answer, or show that the common answer can actually be
computed.  Complete CAP's availability assumption already rules out the trivial
system that never answers: a working side has to make progress without waiting
across the cut.  A full protocol theorem still has to add termination, fairness,
failure detection, and cost, as the system demands.

\section{Related Work}
\label{sec:related}

CALM connects logical monotonicity to coordination freedom
~\cite{hellerstein2010declarative,hellerstein2020keeping}.  Ameloot et al. prove
the connection for Datalog queries running as relational transducers and study
how network knowledge affects coordination
~\cite{ameloot2013relational,ameloot2015weaker}.  We retain their semantic
intuition while separating the general interface test from a particular
programming language and machine model.

Brewer's conjecture and the Gilbert--Lynch theorem focus on availability during
partitions~\cite{brewer2000towards,gilbert2002cap}.  Our deployment-relative
formulation keeps the consistency contract explicit and tests only choices that
a cut can separate.  This recovers the total-order register conflict while
also explaining why incompatible local alternatives need not require
cross-partition agreement.

CRDTs provide practical state and operation algebras for strong eventual
consistency~\cite{shapiro2011crdt}.  Our distinction is between their uniform
least merge and the weaker semantic requirement that some allowed common future
exist.  Prior work on consistency semantics likewise separates visibility,
ordering, availability, and convergence
~\cite{burckhardt2014principles,mahajan2011consistency}.

HATs classify transactional semantics under explicit availability and
client-contact assumptions~\cite{bailis2013hat}.  Invariant confluence asks
when application invariants survive independent execution and merge
~\cite{bailis2014coordination}.  The two operate on different things:
transaction observations in one case and valid database states in the other.
Both fail, however, when independently acceptable choices have no acceptable
combined result.

\section{Conclusion}
\label{sec:conclusion}

Distributed systems do not need coordination just because replicas give
different answers.  They need it when the answers participants are allowed to
give on their own have no answer in common that keeps them all.  An ordered
table of input/output pairs is enough to say when that happens.  Input growth
stands for information arriving; output growth stands for answers that cannot be
taken back.  Monotonicity says the answers can always grow together.

The picture is simple.  Complete CALM tests every independent group of choices.
Complete CAP tests the groups a deployment can push onto opposite sides of a
cut.  Query monotonicity, CRDT merge, available transactions, and invariant
confluence work on different objects and promise different things, but each one
comes down to asking whether the visible answers still have an answer in common.

The small model helps precisely because it does not compete with richer systems
machinery.  It gives a designer one plain question to ask before reaching for
that machinery: \emph{can the answers we give out on our own still be true
together?}  If yes, no coordination is needed for safety.  If no, somebody has
to wait, some promise has to weaken, or some choice has to go.
