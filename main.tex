\begin{abstract}
When does a distributed system inherently require coordination?  CALM, CAP,
CRDTs, Highly Available Transactions, and invariant confluence give related
answers in different mathematical languages.  This fragmentation has allowed
conventional wisdom to drift away from what the literature actually proves.
It also makes intuitive questions spanning these results hard even to state.

We show how to express these results in one small, common model.  A
specification is a relation from inputs to allowed outputs, equipped with
refinement orders on both inputs and outputs.  Complete CALM says that
participants can act without coordination exactly when input growth permits
output growth and independently allowed outputs have an admitted common
refinement.  Applying the same test only to choices that a deployment can
separate across a network partition yields Complete CAP.  The common model
clarifies how CALM, CAP, CRDTs, transactional availability, and invariant
confluence relate without replacing the languages, implementation disciplines,
or proof techniques developed for each setting.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Coordination occurs when one participant must wait for information or agreement
from another before making a choice.  The wait adds latency and can destroy
availability when the needed communication crosses a network partition.
Avoiding unnecessary coordination is therefore a central goal in distributed
systems and databases.  This paper asks about the intrinsic need for
coordination: which specifications permit independent action, and which force
participants to agree?

CALM proposed a crisp answer: consistency can be achieved without coordination
exactly when the computation is monotone~\cite{hellerstein2010declarative}.
Ameloot et al. proved this connection for Datalog queries evaluated by networks
of relational transducers~\cite{ameloot2013relational}.  Their theorem gives an
operational result for a particular language and machine model.  The broader
systems principle has since been applied well beyond that setting
~\cite{hellerstein2020keeping}.

CAP followed a similar path.  Brewer stated a broad systems observation
~\cite{brewer2000towards}; Gilbert and Lynch proved an impossibility result for
linearizable registers~\cite{gilbert2002cap}.  Other traditions developed
related answers in different terms.  CRDTs obtain convergent replicated state
from join-semilattices and inflationary updates~\cite{shapiro2011crdt}.  Highly
Available Transactions (HATs) classify transaction guarantees that survive
partitions~\cite{bailis2013hat}.  Invariant confluence identifies when
independently executed transactions can merge without breaking an application
invariant~\cite{bailis2014coordination}.

These results clearly share an idea, but their different formalisms make
cross-cutting questions hard to answer.  Does CALM encompass the CAP tradeoff?
Are CRDT join laws necessary for coordination freedom, or one strong sufficient
discipline?  Does convergent storage automatically provide highly available
transactions?  Do convergence and transaction availability preserve application
invariants?  Section~\ref{sec:cap} answers the first question.  The CRDT, HAT,
and invariant-confluence parts of Section~\ref{sec:instances} answer the next
three.  The point is not that these properties are identical.  The point is
that one semantic model lets us state their boundaries in the same terms.

The common intuition is simple.  Different outputs need not cause trouble.  Two
set replicas can hold different elements and later take their union; two log
shards can expose different local sequences and later interleave them.  In each
case, some later output preserves both earlier outputs.  By contrast, two sites
that independently elect different leaders have made choices that no later
single-leader result can preserve.  Before we introduce notation, we will say
that the first pair of outputs \emph{fits together} and the second does not.
After Section~\ref{sec:ordered-specs} defines output refinement, we use the
formal terms \emph{compatible} and \emph{incompatible}.

We strip the semantic question down to an ordered table of input/output pairs.
A row says that an output is allowed at an input.  One order says when input
information grows; the other says when an output preserves an earlier output.
For a functional specification, the criterion is ordinary order preservation.
For a relational specification, the alternatives allowed at one input must
also be coherent: every finite collection must have an admitted common
refinement.  These are two distinct conditions.  We call their conjunction
monotonicity for an ordered relational specification.

This paper makes four contributions:
\begin{enumerate}
  \item We give a common semantic model for coordination results: an
        input/output relation with independent input and output refinement
        orders.  We define its monotonicity and prove that it decomposes into
        ordinary growth and coherent ambiguity.
  \item We distinguish \emph{exposure}, which preserves every remaining
        possibility, from \emph{commitment}, which excludes one.  Coordination
        is required before independently authorized participants make
        incompatible commitments.
  \item We state Complete CALM at this interface and derive Complete CAP by
        restricting the same criterion to choices that a deployment can
        separate across a partition.
  \item We instantiate the model for query monotonicity, CRDTs, HATs, and
        invariant confluence, giving a construction or a concrete failure for
        each case.
\end{enumerate}

``Complete'' describes the scope of the unification: the model captures the
common semantic issue across these coordination results.  It does not suggest
that prior formalisms are obsolete.  Relational transducers provide a language
and an operational theorem; semilattices provide an implementation discipline
and a canonical merge; transaction and invariant analyses expose their own
system assumptions.  Our criterion is a semantic safety result, not a protocol
or a liveness theorem.

Section~\ref{sec:examples} begins with voting and leader election.
Sections~\ref{sec:ordered-specs}--\ref{sec:calm} form the technical core: they
define ordered specifications, exposure, commitment, coordination, and Complete
CALM.  Section~\ref{sec:registers} uses registers to motivate the
deployment-relative Complete CAP of Section~\ref{sec:cap}.
Section~\ref{sec:instances} maps the surrounding literature into the common
model.  We close with scope, related work, and the resulting view of the
coordination boundary.

\section{Two Small Examples}
\label{sec:examples}

Two examples introduce the two parts of the criterion.  Fixed-population voting
shows safe growth as more input arrives.  Leader election shows that several
outputs allowed at one input may fail to fit together.

\subsection{Voting: input growth}

Suppose three named voters each cast at most one immutable ballot for $a$ or
$b$.  A site may know only some ballots, but its knowledge grows as ballots
arrive.  Before two matching ballots arrive, the only safe output is $\bot$,
meaning that no winner is yet certified.  A certified winner can never be
reversed by another valid ballot.

\begin{table}[h]
  \centering
  \small
  \caption{A fixed-population election.  More ballots may certify a result but
  never revoke one.}
  \label{tab:voting}
  \begin{tabular}{@{}ll@{}}
    \toprule
    Ballots known & Output \\
    \midrule
    $\{v_1\!:\!a\}$ & $\bot$ \\
    $\{v_1\!:\!a,v_2\!:\!a\}$ & $a$ \\
    $\{v_1\!:\!a,v_2\!:\!b\}$ & $\bot$ \\
    $\{v_1\!:\!a,v_2\!:\!b,v_3\!:\!b\}$ & $b$ \\
    \bottomrule
  \end{tabular}
\end{table}

The output order places $\bot$ below either certified result.  The input order
adds ballots.  Moving upward in the input order never forces the output to move
downward or switch between certified winners.  This is ordinary monotone
growth.

\subsection{Leader election: allowed choice}

Now suppose the input lists two eligible candidates, $c_1$ and $c_2$, and the
specification permits either one to be elected.  If the interface promises one
leader, reporting $c_1$ rules out $c_2$, and reporting $c_2$ rules out $c_1$.
No allowed output preserves both choices.  If different participants may elect
a leader independently, they must agree before either choice becomes public.

Figure~\ref{fig:orders} separates three cases that are often conflated.  An
output may extend another; two outputs may be unrelated but have a common
extension; or two outputs may have no common extension.  Only the third case
fails to fit together.

\begin{figure}[h]
  \centering
  \begin{tabular}{@{}c@{\qquad}c@{\qquad}c@{}}
    $\bot\ \longrightarrow\ a\ \longrightarrow\ b$
      & $\begin{array}{c}t\\[-2pt]\nearrow\!\!\!\!\nwarrow\\[-4pt]a\qquad b\end{array}$
      & $a\qquad b$ \\
    chain & common extension & no common extension
  \end{tabular}
  \caption{Difference and incomparability do not by themselves force
  coordination.  The obstruction is the absence of a common extension.}
  \label{fig:orders}
\end{figure}

These examples are deliberately informal.  We now define exactly what inputs,
outputs, extension, and compatibility mean.

\section{Ordered Input/Output Specifications}
\label{sec:ordered-specs}

A deterministic specification is a function from inputs to outputs.  A
specification that permits several outputs is a relation.  Distributed systems
need one additional ingredient: orders that describe how inputs and outputs may
be refined.

\begin{definition}[Ordered relational specification]
\label{def:specification}
An \emph{ordered relational specification} is
\begin{equation}
  \Spec=(I,\InputOrd,O,\OutputOrd,S),
  \qquad S\subseteq I\times O,
  \label{eq:specification}
\end{equation}
where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered sets.  A row
$(i,o)\in S$ says that output $o$ is admissible at input $i$.  The \emph{fiber}
at $i$ is
\begin{equation}
  \fiber{i}=\{o\in O:(i,o)\in S\}.
  \label{eq:fiber}
\end{equation}
We assume every input under discussion has a nonempty fiber.
\end{definition}

We read $i\InputOrd j$ as ``$j$ refines $i$ with more input information.''  We
read $o\OutputOrd u$ as ``$u$ preserves and extends every externally visible
claim in $o$.''  Both orders are part of the specification.  They do not rank
outputs by quality, and they need not be set inclusion.  For a query they often
are inclusion; for a register they extend an explanation of operations; for a
CRDT the output order may be a lattice order.

\begin{definition}[Compatibility]
\label{def:compatibility}
Outputs $o_1,\ldots,o_k$ are \emph{compatible at input $j$} if there is an
admissible common refinement $u\in\fiber{j}$ such that
$o_r\OutputOrd u$ for every $r$.  Otherwise they are \emph{incompatible at
$j$}.
\end{definition}

Compatibility is not comparability.  The middle order in
Figure~\ref{fig:orders} has incomparable outputs $a$ and $b$, but they are
compatible because $t$ refines both.  The leader outputs are incompatible
because the specification admits no output that refines both.

\subsection{The functional case}
\label{sec:functional}

Let $S$ be the graph of a function $f:I\to O$, so that
$\fiber{i}=\{f(i)\}$.  The familiar condition is order preservation:
\begin{equation}
  i\InputOrd j \quad\Longrightarrow\quad f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
\end{equation}
This is the usual meaning of a monotone function.  The voting specification is
functional: adding ballots can refine $\bot$ to a certified winner, but cannot
invalidate a certified winner.  Query monotonicity in
Section~\ref{sec:query-instance} is another direct instance.

A relation adds genuine choice.  Order preservation must then say what happens
to \emph{every} output admitted at the earlier input, not merely choose one
convenient trajectory.

\begin{definition}[Growth]
\label{def:growth}
The specification has \emph{growth} if, whenever $i\InputOrd j$ and
$o\in\fiber{i}$, there is an $o'\in\fiber{j}$ with $o\OutputOrd o'$.
\end{definition}

Growth is relational order preservation.  It reduces to
Equation~\ref{eq:functional-monotonicity} when every fiber is a singleton.  It
does not constrain two different outputs admitted at the same input.  That is a
second condition.

\begin{definition}[Coherence]
\label{def:coherence}
The specification has \emph{coherence} if every nonempty finite collection
$o_1,\ldots,o_k\in\fiber{i}$ is compatible at $i$.  Equivalently, every fiber
is finitely directed under $\OutputOrd$.
\end{definition}

The order-theoretic term is directedness; we use \emph{coherence} for the
semantic reading.  Growth concerns refinement between inputs.  Coherence
concerns the choices admitted at one input.  Functional specifications have
coherence automatically.  The leader-election specification does not.

\subsection{Monotonicity for a relation}

The single condition used in the rest of the paper combines growth and
coherence across any finite collection of rows.

\begin{definition}[Monotonicity]
\label{def:monotonicity}
An ordered relational specification $\Spec$ is \emph{monotone} if, for every
nonempty finite family of rows
\begin{equation*}
  (i_1,o_1),\ldots,(i_k,o_k)\in S
\end{equation*}
and every common input refinement $j$ satisfying $i_r\InputOrd j$ for all $r$,
the outputs $o_1,\ldots,o_k$ are compatible at $j$.  Equivalently, there is a
$u\in\fiber{j}$ such that
\begin{equation}
  o_r\OutputOrd u
  \qquad\text{for every }r\in\{1,\ldots,k\}.
  \label{eq:monotonicity}
\end{equation}
\end{definition}

The universal quantifier over $j$ is important.  The environment may choose
which common refinement occurs; the implementation cannot rely on a more
convenient one.  If the inputs have no common refinement, the definition imposes
no condition.  We require finite families because pairwise compatibility need
not imply compatibility of a larger family.

\begin{proposition}[Decomposition]
\label{prop:decomposition}
An ordered relational specification is monotone if and only if it has growth
and coherence.
\end{proposition}

\begin{proof}
Assume $\Spec$ is monotone.  Given $i\InputOrd j$ and $o\in\fiber{i}$, apply
Definition~\ref{def:monotonicity} to the one-row family $(i,o)$ and common input
refinement $j$.  The resulting $o'\in\fiber{j}$ establishes growth.  Given a
finite collection $o_1,\ldots,o_k\in\fiber{i}$, apply the definition to the rows
$(i,o_1),\ldots,(i,o_k)$ with common input refinement $i$.  The resulting
common output refinement establishes coherence.

Conversely, assume growth and coherence.  Consider rows
$(i_1,o_1),\ldots,(i_k,o_k)$ and a common input refinement $j$.  Growth gives,
for every $r$, an output $o'_r\in\fiber{j}$ with
$o_r\OutputOrd o'_r$.  Coherence of the literal fiber $\fiber{j}$ gives a
$u\in\fiber{j}$ with $o'_r\OutputOrd u$ for every $r$.  Transitivity yields
$o_r\OutputOrd u$ for every $r$, which is
Equation~\ref{eq:monotonicity}.
\end{proof}

\begin{proposition}[Functional specifications]
\label{prop:functional}
If $S$ is the graph of a function $f:I\to O$, then $\Spec$ is monotone if and
only if $f$ is order-preserving as in
Equation~\ref{eq:functional-monotonicity}.
\end{proposition}

\begin{proof}
Every singleton fiber is coherent.  Proposition~\ref{prop:decomposition}
therefore reduces monotonicity to growth, which for a function is exactly
Equation~\ref{eq:functional-monotonicity}.
\end{proof}

This proposition shows precisely how the relational definition extends
ordinary monotonicity.  It does not rename directedness as monotonicity:
monotonicity of a relational specification is the conjunction of relational
growth and directed fibers.  The second condition becomes visible only when a
specification admits more than one output.

\section{Exposure, Commitment, and Coordination}
\label{sec:exposure}

The output order describes irrevocable public information.  Once $o$ is
exposed, every later output must refine $o$.  We model only the resulting
restriction on the specification; no protocol state is needed.

Let $R\subseteq S$ be the rows still possible in the current execution.  For a
selected row $(i,o)\in R$, define
\begin{equation}
  R\mathbin{\upharpoonright}(i,o)
  = R\setminus
    \{(j,x)\in R:i\InputOrd j\ \land\ o\not\OutputOrd x\}.
  \label{eq:residual}
\end{equation}
The restriction removes each row at a refinement of $i$ whose output does not
itself refine $o$.  Rows at inputs unrelated to $i$ are unchanged.

\begin{definition}[Exposure and commitment]
\label{def:exposure}
An output $o$ is \emph{exposure-ready} in residual $R$ at input $i$ if, for
every $(j,x)\in R$ with $i\InputOrd j$, there is a row $(j,u)$ retained in
$R\mathbin{\upharpoonright}(i,o)$ such that
\begin{equation}
  x\OutputOrd u.
  \label{eq:exposure-ready}
\end{equation}
Because $(j,u)$ is retained, $o\OutputOrd u$ also holds.  Selecting an
exposure-ready output is an \emph{exposure}: every removed possibility has a
retained refinement.  Selecting an output that is not exposure-ready is a
\emph{commitment}: some removed possibility has no retained refinement.
\end{definition}

Literal rows may disappear during exposure without changing the specified
possibilities.  In the middle order of Figure~\ref{fig:orders}, exposing $a$
removes the row $b$, but retains $t$, which refines both.  In leader election,
selecting $c_1$ removes $c_2$ and retains no refinement of it, so the selection
is a commitment.

A residual is \emph{exposure-reachable} if it is obtained from $S$ by a finite
sequence of exposures.  This accounts for outputs that have already been made
public.

\begin{definition}[Exposure at will]
\label{def:exposure-at-will}
A specification permits \emph{exposure at will} if, in every
exposure-reachable residual $R$, every row $(i,o)\in R$ is exposure-ready.
\end{definition}

\begin{definition}[Coordination]
\label{def:coordination}
\emph{Coordination} is agreement required before a participant makes a
commitment that could exclude a choice independently authorized to another
participant.  A declared interface is \emph{coordination-free} if it permits
exposure at will: every output the interface offers may be selected without
prior agreement and without excluding any remaining specified possibility.
\end{definition}

Communication that does not delay a commitment is not coordination in this
sense.  Participants may exchange inputs, gossip state, and propagate output
refinements asynchronously.  Coordination occurs when one participant must
learn or constrain another participant's choice before making its own.

The qualifier ``declared interface'' matters.  Every row in $S$ is a behavior
that the interface offers.  An implementation that always suppresses some rows
implements a narrower relation; the criterion applies to that relation instead.

\section{Complete CALM}
\label{sec:calm}

We can now state the coordination boundary.  Consistency here means
\emph{refinement consistency}: exposed outputs need not be equal, but no later
selection may contradict one, and independently exposed outputs must retain an
admitted common refinement when their inputs are combined.

\begin{theorem}[Complete CALM]
\label{thm:calm}
An ordered relational specification permits exposure at will---and hence is
coordination-free at its declared interface---if and only if it is monotone.
\end{theorem}

\begin{proof}
First suppose $\Spec$ is monotone.  Let $R$ be the residual after exposures
$(i_1,o_1),\ldots,(i_m,o_m)$, and consider any $(i,o)\in R$.  To show that $o$
is exposure-ready, choose any $(j,x)\in R$ with $i\InputOrd j$.  Apply
Definition~\ref{def:monotonicity} to $(i,o)$, $(j,x)$, and every earlier
exposure $(i_h,o_h)$ with $i_h\InputOrd j$.  It gives $u\in\fiber{j}$ refining
$o$, $x$, and every such $o_h$.  The last condition means $(j,u)$ survived all
previous restrictions; $o\OutputOrd u$ means it also survives the new one.
Thus every removed $x$ has a retained refinement $u$, so $o$ is exposure-ready.
Every available selection is therefore an exposure.

Conversely, suppose exposure at will holds.  Growth follows immediately.  If
$i\InputOrd j$ and $o\in\fiber{i}$, choose any $x\in\fiber{j}$.  Since $o$ is
exposure-ready in the initial residual, some retained $u\in\fiber{j}$ refines
$x$ and $o$; hence $o$ has a refinement at $j$.

It remains to prove coherence.  Assume for contradiction that a fiber contains
a finite incompatible family, and choose one of least cardinality,
$o_1,\ldots,o_k$.  We have $k\geq2$.  If $k=2$, then $o_1$ is not
exposure-ready because $o_2$ has no common refinement with it.

Suppose $k>2$.  By minimality, the proper subfamilies
$\{o_1,\ldots,o_{k-1}\}$ and
$\{o_1,\ldots,o_{k-2},o_k\}$ have common refinements $v$ and $w$ in the
fiber.  Both $v$ and $w$ refine $o_1$, so both remain after exposing $o_1$.
They are incompatible: a common refinement of $v$ and $w$ would refine all
$o_1,\ldots,o_k$.  Hence $v$ is not exposure-ready in the resulting residual,
contradicting exposure at will.  Every fiber is coherent.  Growth and coherence
imply monotonicity by Proposition~\ref{prop:decomposition}.
\end{proof}

The proof is short because the model isolates the exact obstruction: a finite
family of admissible outputs with no admitted common refinement.  The name
``Complete CALM'' refers to the breadth of the unification across coordination
results, not to the mere presence of a biconditional.

The theorem is a semantic safety result.  It does not compute a common
refinement or guarantee termination, message delivery, or a response-time
bound.  A language or protocol must still show that its participants can
compute the required outputs under its execution and failure assumptions.

\section{Registers: Difference Versus Incompatibility}
\label{sec:registers}

Registers connect the criterion to familiar consistency models and expose a
subtle distinction between global and deployment-relative monotonicity.

Let an input $h$ be a finite, causally closed operation history.  We write
$h\InputOrd h'$ when $h$ is a downward-closed induced subhistory of $h'$:
$h'$ adds operations with all of their causal predecessors and preserves the
causal order among operations already in $h$.  An output is an explanation
$(L,\rho)$.  Here $L$ is an operation order admitted by the consistency model,
and $\rho$ maps each completed read to the write that supplied its response.
An explanation $(L',\rho')$ refines $(L,\rho)$ when $L'$ extends $L$ without
reversing an existing order and $\rho'$ extends $\rho$ without changing an
answered read.

Consider two replicas of a register initially holding no value.  Process $p$
completes a write of \dog{} while $q$ concurrently completes a write of
\catv.  Each process learns both writes and then serves a local read; both
writes complete before either read begins.

\begin{table}[h]
  \centering
  \small
  \caption{Two reads following concurrent writes.}
  \label{tab:register}
  \begin{tabular}{@{}p{.43\columnwidth}p{.43\columnwidth}@{}}
    \toprule
    Process $p$ & Process $q$ \\
    \midrule
    $w_p(x,\dog)$ & $w_q(x,\catv)$ \\
    receive $w_q$ & receive $w_p$ \\
    $r_p(x)\mapsto\catv$ & $r_q(x)\mapsto\dog$ \\
    \bottomrule
  \end{tabular}
\end{table}

\subsection{Total-order explanations}

For a linearizable register, $L$ is a total order that extends real-time order,
and each read returns the latest preceding write in $L$
~\cite{herlihy1990linearizability}.  Because both writes precede both reads,
$r_p=\catv$ requires
\begin{equation}
  w_p(x,\dog)<_L w_q(x,\catv),
  \label{eq:dog-before-cat}
\end{equation}
whereas $r_q=\dog$ requires
\begin{equation}
  w_q(x,\catv)<_L w_p(x,\dog).
  \label{eq:cat-before-dog}
\end{equation}
Each explanation is admissible alone.  No total order can satisfy both
constraints, so the explanations are incompatible.  If opposite replicas are
authorized to expose these read responses independently, they must agree on a
write order first.  This is the obstruction used in the classical
linearizable-register CAP result~\cite{gilbert2002cap}.

\subsection{Causal explanations}

For causal consistency, $L$ is the happens-before relation and a read may return
an admitted causally visible write not superseded by a later causal write
~\cite{lamport1978time,ahamad1995causal}.  The two writes above remain
concurrent.  One explanation can therefore preserve both responses by assigning
$r_p$ to the \catv{} write and $r_q$ to the \dog{} write.  The read outputs are
different but compatible.

The causal specification is not necessarily monotone under universal authority.
The two possible responses \dog{} and \catv{} for the \emph{same} read are
incompatible because refinement cannot change an existing read assignment.  In
the actual deployment, however, only the owner of a read chooses its response.
That local choice cannot be separated across a network partition.  This
distinction motivates the deployment-relative criterion.

\section{Complete CAP Under a Deployment}
\label{sec:cap}

Complete CALM tests every family of independently authorized rows.  CAP tests
only families that a deployment can select on opposite sides of a network cut.
Participants within one connected component may coordinate; availability
forbids waiting for information from another component.

\begin{definition}[Deployment and separability]
\label{def:deployment}
A \emph{deployment} $\Delta$ assigns each participant $p$ an authority set
$\Delta_p\subseteq S$ of rows that $p$ may select.  A partition $\Pi$ divides
the participants into two or more connected components.  A finite family of
rows is \emph{separable under $\Pi$} if there is a partitioned execution in
which those rows can be selected jointly by authorized participants, with at
least two components making a selection.  Participants within each component
may coordinate before making their component's selections.
\end{definition}

Joint selectability is essential.  Two mutually exclusive alternatives owned
by one participant do not become separable merely because an unrelated row is
selected in another component.  Separability describes a realizable partitioned
execution, not just membership in authority sets.

\begin{definition}[Monotonicity across a partition]
\label{def:partition-monotonicity}
A deployed specification is \emph{monotone across $\Pi$} if, for every
$\Pi$-separable family
$(i_1,o_1),\ldots,(i_k,o_k)$ and every common input refinement $j$, there is a
$u\in\fiber{j}$ such that
\begin{equation}
  o_r\OutputOrd u
  \qquad\text{for every }r.
  \label{eq:partition-monotonicity}
\end{equation}
It is \emph{monotone across the relevant partitions} if this holds for every
cut in the declared failure model.
\end{definition}

At this interface, \emph{cross-partition availability} means that each
nonfailed component may make every locally feasible selection without waiting
for a message across the cut.  \emph{Consistency} again means refinement
consistency: jointly selected rows have an admitted common output refinement
when their inputs are combined.  We assume each component can resolve its own
choices correctly using internal coordination.  Partition tolerance quantifies
these requirements over every relevant partition and schedule.

\begin{theorem}[Complete CAP under a deployment]
\label{thm:cap}
For a fixed deployment and set of relevant partitions, cross-partition
availability and refinement consistency coexist at the declared selection
interface if and only if the specification is monotone across those partitions.
\end{theorem}

\begin{proof}
Assume partition monotonicity.  Consider any finite family selected in a
partitioned execution and any common input refinement.  By
Equation~\ref{eq:partition-monotonicity}, an admitted output refines every
selection.  Thus selections made without a cross-partition wait remain
refinement-consistent when the partition heals.

Conversely, suppose partition monotonicity fails.  Its witness is a jointly
selectable family, a relevant cut, and a common input refinement with no
admitted common output refinement.  Cross-partition availability permits the
authorized components to make the witness selections while communication
across the cut is delayed.  The system must then either wait across the cut,
retain selections with no consistent refinement, or suppress a selection
permitted by the interface.  These respectively lose availability, consistency,
or the declared specification.
\end{proof}

This is a semantic safety result at the declared selection interface.  It does
not construct a resolver, guarantee that internal coordination terminates, or
bound healing time.

The relationship to CALM is direct.  CALM tests all independently authorized
families.  CAP tests the jointly selectable families a deployment can separate.
Under universal authority and realizability, every family can be separated and
the conditions coincide.  Under a restricted deployment, an incompatibility
controlled by one participant or one component does not obstruct partition
availability.  In this precise sense, \emph{CAP is CALM restricted by a
deployment}.

The register example illustrates both cases.  Opposing total-order explanations
are jointly selectable across the two replicas and have no common refinement.
The causal explanations for different reads are compatible.  The incompatible
answers for one literal read remain under that read owner's authority and are
not jointly selectable.

\subsection{CALM and query monotonicity}
\label{sec:query-instance}

Fix a query $Q$.  An input $J$ is a finite database fact set, ordered by
inclusion.  The specification is functional:
\begin{equation}
  \fiber{J}=\{Q(J)\},
  \label{eq:query-fiber}
\end{equation}
and outputs are ordered by fact inclusion.  By
Proposition~\ref{prop:functional}, monotonicity is exactly
\begin{equation}
  J\subseteq J' \quad\Longrightarrow\quad Q(J)\subseteq Q(J'),
  \label{eq:query-monotonicity}
\end{equation}
the standard definition of a monotone query
~\cite{abiteboul1995foundations}.  If two sites know $J_1$ and $J_2$, then
$Q(J_1\cup J_2)$ refines both partial answers.  A nonmonotone query may instead
need to retract a fact exposed before missing input arrived.

The relational-transducer CALM theorem proves the corresponding operational
result for its language~\cite{ameloot2013relational,ameloot2015weaker}.  The
ordered table does not replace that language or its analysis.  It isolates the
semantic property that the transducer theorem realizes and that the following
systems share.

\subsection{CRDTs: sufficient structure versus the criterion}
\label{sec:crdt-instance}

For a state-based CRDT, take the input to be the set of joinable state deltas
(or upward-moving replica states) received so far, ordered by inclusion.  Let
$s(U)$ be their accumulated state.  The specification is functional, and
outputs use the CRDT's lattice order.  Under the usual state-based CRDT
conditions, local states move upward and merge is join
~\cite{shapiro2011crdt}.  Thus
\begin{equation}
  s(U_1)\sqcup s(U_2)=s(U_1\cup U_2)
  \label{eq:crdt-join}
\end{equation}
is a least common refinement.

A join-semilattice gives more structure than Definition~\ref{def:monotonicity}
requires.  It provides a uniform least common refinement for every pair in the
output domain.  Monotonicity asks only for some admitted common refinement of
each relevant finite family.  The refinement need not be least or computed by
one global binary operator.  Semilattices are therefore a powerful sufficient
discipline, not a necessary condition for coordination freedom.

\paragraph{A sharded log.}
Let shard $A$ expose the local sequence $[a_1,a_2]$ and shard $B$ expose
$[b_1,b_2]$.  Sequence refinement is order-preserving subsequence.  At the
combined input, the specification admits any interleaving that preserves each
shard's local order.  For example,
\begin{equation}
  [a_1,a_2,b_1,b_2]
  \qquad\text{and}\qquad
  [b_1,b_2,a_1,a_2]
  \label{eq:log-interleavings}
\end{equation}
are two minimal common refinements.  Neither refines the other, so no least
common refinement exists.  Under a deployment that authorizes each shard to
expose only its local sequence, every cross-shard family nevertheless has an
admitted interleaving.  A global join is unnecessary for that interface.

This conclusion is deployment-relative.  A specification that exposes
completed global interleavings would admit incompatible outputs and require a
separate reconciliation rule.  Similarly, convergence of replicated state says
nothing by itself about exact reads or transactional observations.  Those
outputs require their own monotonicity tests
~\cite{burckhardt2014principles,laddad2022keep}.

\subsection{Highly available transactions}
\label{sec:hat-instance}

For a transactional interface, an input is the set of begin, read, write, and
commit requests received so far, ordered by inclusion.  An output is a growing
set of public facts such as $\mathsf{read}(T,x,v)$,
$\mathsf{commit}(T)$, and session-order facts, also ordered by inclusion.  The
isolation or session guarantee determines which fact sets are admissible.  The
deployment assigns transactions and requests to replicas.  Complete CAP then
tests the families those authorities can select across a partition.  As in HAT
work, the result depends on the declared contact, failure, and session
assumptions~\cite{bailis2013hat,terry1994session}.

\paragraph{Accumulating facts.}
Suppose two available replicas execute transactions on disjoint keys.  One
exposes $\mathsf{read}(T_1,x,0)$ and $\mathsf{commit}(T_1)$; the other exposes
$\mathsf{read}(T_2,y,0)$ and $\mathsf{commit}(T_2)$.  If each read observes a
committed version at its replica, the union contains no dirty read or write
conflict.  Under the stated read-committed interface, later delivery preserves
all four facts.  This is the positive accumulation pattern behind HAT results;
it is not a claim that every combination of session guarantees is available.

\paragraph{Serializability.}
Initially $x=y=0$.  On one side, $T_1$ reads $x=0$, writes $y=1$, and commits.
On the other, $T_2$ reads $y=0$, writes $x=1$, and commits.  Preserving $T_1$'s
read requires $T_1$ before $T_2$ in any serial explanation; preserving $T_2$'s
read requires $T_2$ before $T_1$.  The serialization graph contains a cycle, so
no serial history refines both sets of read and commit facts
~\cite{adya2000generalized}.

\paragraph{Snapshot isolation.}
Let overlapping transactions $T_1$ and $T_2$ read the same snapshot and both
write $x$.  Separate replicas could each expose its local commit.  Snapshot
isolation's first-committer-wins rule admits no output containing both commit
facts~\cite{berenson1995critique,bailis2013hat}.  Eventual storage convergence
may choose a final state; it cannot retract a commit already exposed to a
client.

These examples answer the question posed in the introduction.  Convergent
storage does not automatically provide a highly available transactional
interface.  Storage convergence constrains states after update delivery;
isolation constrains irreversible reads and commits before then.

\subsection{Invariant confluence}
\label{sec:iconfluence-instance}

Let the input be a set of applied transactions, ordered by inclusion.  Each
transaction is assumed to map an invariant-valid state to another
invariant-valid state; without this assumption, one transaction could violate
the invariant before any merge occurred.  Outputs are reachable,
invariant-valid database states.  Output refinement is induced by the
application's prescribed reconciliation: $s\OutputOrd s'$ when merging $s$ with
admissible additional effects can produce $s'$ while preserving the effects in
$s$.

Invariant confluence asks whether independently reachable valid states merge to
a valid state~\cite{bailis2014coordination}.  The two parts of
Proposition~\ref{prop:decomposition} are explicit here.  Individual transaction
preservation gives growth.  Invariant confluence gives coherence under merge.
If merge is associative and merged states remain reachable, the pairwise test
extends inductively to finite families; the iterated merge is the required
common refinement.

A uniqueness constraint supplies the standard counterexample.  Two replicas
each observe that username \texttt{sam} is free and independently allocate it
to different accounts.  Each local state satisfies uniqueness, but no
invariant-valid common refinement preserves both allocations.  The system must
reserve names, reject one allocation, or weaken the invariant.

State convergence, transaction availability, and invariant preservation thus
test three different specifications.  A convergent merge may produce an invalid
state; an available transaction may expose facts that later violate an
invariant; an invariant-confluent application need not provide a particular
isolation level.  The common criterion applies to each output domain without
collapsing the properties into one.

\section{Discussion}
\label{sec:discussion}

\subsection{A semantic criterion, not an implementation discipline}

The ordered table deliberately omits internal computation.  This is useful for
stating a common boundary and insufficient for building a system.  Relational
transducers provide a language and operational network semantics; semilattices
provide a local algebra and deterministic merge; transaction protocols provide
scheduling, validation, and recovery.  Complete CALM identifies a semantic
obstruction at the declared interface.  It does not say how to represent $S$,
decide its orders, compute a common refinement, or do so efficiently.

A short semantic proof and a model-specific operational proof answer different
questions.  Once admissible outputs and preservation are explicit, the core
necessity and sufficiency argument is direct.  Connecting a real programming
model to those definitions may still require substantial arguments about
knowledge, expressiveness, and computability.

\subsection{Specification design determines the boundary}

Monotonicity is not a permanent label on ``register,'' ``transaction,'' or
``shopping cart.''  It is a property of
$(I,\InputOrd,O,\OutputOrd,S)$ under a deployment.  A linearizable register and
a causal register admit different explanations.  A CRDT state and an exact
read expose different promises.  A database permitted to abort one transaction
implements a different relation from one required to commit both.

Narrowing $S$ may eliminate an incompatibility.  Broadening $O$ with a new
output that refines two alternatives may also eliminate it.  Changing authority
may keep an incompatibility within one component.  Each option changes the
client-visible specification or the deployment; none is a loophole in the
criterion.

\subsection{Monotonicity is not convergence}

Monotonicity requires an admitted common refinement, not a unique result and not
a least one.  The sharded log has several minimal interleavings.  Strong
eventual consistency adds run insensitivity: replicas that receive the same
information reach equivalent state.  A semilattice join supplies this stronger
property elegantly.  Conversely, last-writer-wins can converge by discarding
one concurrent value, but it does not preserve an interface that promised both
values.  Convergence and semantic preservation are distinct requirements.

\subsection{Safety is not liveness}

The theorems identify when independent selections remain refinement-consistent.
They do not force a participant to expose an output, guarantee message delivery,
bound reconciliation time, or prove that a common refinement is computable.
Complete CAP's availability premise requires authorized selections to proceed
without a cross-partition wait; it therefore excludes an implementation that
never responds.  Full protocol results must add appropriate termination,
fairness, and failure assumptions.

\section{Related Work}
\label{sec:related}

The CALM conjecture connected logical monotonicity with coordination freedom
~\cite{hellerstein2010declarative,hellerstein2020keeping}.  Ameloot et al.
established the theorem using relational transducers and studied how system
knowledge changes coordination requirements
~\cite{ameloot2013relational,ameloot2015weaker}.  We do not replace that
operational result; we isolate the ordered relational property that it realizes.

Brewer's conjecture and the Gilbert--Lynch theorem focus attention on
availability during partitions~\cite{brewer2000towards,gilbert2002cap}.
Complete CAP keeps the consistency contract and deployment authority explicit,
then restricts monotonicity to choices a network cut can separate.  This
recovers the linearizable-register obstruction while explaining why a local
choice need not require cross-partition agreement.

CRDTs derive strong eventual consistency from carefully designed state or
operation algebras~\cite{shapiro2011crdt}.  The distinction here is between a
uniform least merge and the weaker existence of some admitted common
refinement.  Work on consistency semantics similarly distinguishes visibility,
ordering, availability, and convergence
~\cite{burckhardt2014principles,mahajan2011consistency}.

HATs classify transactional guarantees realizable without cross-partition
coordination under stated client and failure assumptions~\cite{bailis2013hat}.
Invariant confluence characterizes when independently valid transactional
states preserve an application invariant on merge
~\cite{bailis2014coordination}.  The ordered specification exposes their common
refinement structure while preserving their distinct output domains.

\section{Conclusion}
\label{sec:conclusion}

CALM, CAP, CRDTs, HATs, and invariant confluence use different formalisms, but
they encounter the same semantic obstruction: independently admissible outputs
with no admitted common refinement.  An ordered input/output relation is enough
to state that obstruction.  Its monotonicity has two explicit parts: growth
along input refinement and coherence of the outputs admitted at one input.

Complete CALM tests all independently authorized families.  Complete CAP tests
the families a deployment can separate across a network partition.  Query
monotonicity, semilattice merge, transactional availability, and invariant
confluence then become directly comparable without being identified with one
another.

The model is useful because it does not compete with richer implementation and
verification machinery.  It provides a common semantic boundary for choosing
and evaluating that machinery: coordination is required precisely when an
independently authorized commitment would exclude an admissible possibility
with no common refinement.
