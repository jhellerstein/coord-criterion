\title{Complete CALM: A Unified Criterion for Coordination}

\author{Joseph M. Hellerstein}
\affiliation{%
  \institution{UC Berkeley \& Amazon Web Services}
  \city{Berkeley, CA}
  \country{USA}
}

\begin{abstract}
When does a concurrent system inherently require coordination?  CAP, CALM,
CRDTs, Highly Available Transactions, and Invariant Confluence each draw a
coordination boundary in a different formal model, and conventional
wisdom has drifted from what the literature proves.  We give one framework for
all of them: a specification is a table that says exactly which outputs are
within spec at each input, with separate partial orders for input growth and for
output refinement.  A computation state is simply a pair of the current input with
the specification rows that remain.

At the specification level, the inherent reason for coordination is an
irrevocable \emph{commitment} that rules out behavior still within spec; locks,
atomics, and distributed agreement are mechanisms for establishing such
commitments.  \emph{Functional CALM} generalizes the original CALM Theorem from
Datalog queries to arbitrary functions between ordered input and output
domains.  It defines consistency as confluence of executions and proves that a
functional specification supports consistency without commitment exactly when
it is monotone, independent of programming language or execution model.

\emph{Complete CALM} extends this equivalence to \emph{ambiguous}
specifications that allow several outputs for one input.  Its criterion is
\emph{Lifted Monotonicity}, monotonicity under an order lifted from outputs to
sets of outputs.  Lifted Monotonicity holds exactly when consistency requires
no commitment.  Classical CALM does not represent commitments; Complete CALM does, so it
can verify \emph{Proper Coordination}: whether coordination removes enough
alternatives to leave a monotone interface for the rest of the system.
Counterintuitively, non-monotone commitments can resolve a non-monotone
specification into a monotone interface whose downstream execution is
coordination-free.  We prove that Lifted Monotonicity is preserved by sequential
and independently parameterized composition.  A log authority followed by
commitment-free register or key-value-store evaluation is the canonical
example; MultiConsensus implements the same interface with distributed
authority.  Complete CALM also yields a Complete CAP dichotomy under arbitrary
partitions.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Concurrent systems rely on coordination mechanisms ranging from mutexes and
atomic instructions to database locks and distributed agreement protocols.
These mechanisms prevent concurrent actions from producing incompatible
outcomes, but add synchronization, blocking, or aborts; when coordination
crosses a network partition, it can also destroy availability.  Avoiding
unnecessary coordination is therefore a central goal in concurrent systems and
databases.  This paper asks what coordination mechanisms accomplish at the
specification level, and when that effect is intrinsically required.

The CALM Conjecture proposed a crisp, bidirectional answer: consistency can be
achieved without coordination exactly when the computation is
monotone~\cite{hellerstein2010declarative}.  Ameloot et al.\ proved it, in
both directions, for Datalog queries evaluated by networks of relational
transducers~\cite{ameloot2013relational,hellerstein2020keeping}.  That CALM
Theorem is therefore tied to one formalism, while its intuition is often
invoked much more broadly.  This has left a gap between folklore and formal
results.

Several other traditions draw closely related boundaries, each in its own
formalism.  The CAP Theorem proves an impossibility for available linearizable registers
under partition~\cite{brewer2000towards,gilbert2002cap}.  CRDTs give
a strong sufficient discipline for coordination-free convergence using
join-semilattices and inflationary updates~\cite{shapiro2011crdt}.  Highly
Available Transactions (HATs) classify transaction guarantees that survive
partitions~\cite{bailis2013hat}.  Invariant confluence gives a necessary and
sufficient condition for independently executed transactions to merge without
breaking an application invariant~\cite{bailis2014coordination}.

The results plainly share an idea, but their mathematical frameworks do not
compose: logic programs and transducers, register executions, semilattices,
transaction histories, and invariant-preserving database states rest on
different objects and assumptions.  This makes simple cross-cutting questions
awkward.  Does CALM encompass CAP?  Are CRDT join laws necessary for
coordination freedom, or one strong sufficient discipline?  Does convergent
storage provide highly available transactions?  Do convergence and transaction
availability preserve application invariants?  Section~\ref{sec:cap-corollary}
answers the first question; the CRDT, HAT, and invariant-confluence parts of
Section~\ref{sec:instances} answer the others.

We develop a unified criterion from a simple specification model: a
conceptual relational table whose rows pair each input with the outputs that
are within spec.  The model is purely declarative: it states what results are
allowed while setting aside the imperative procedure that produces them.  One
partial order describes how input grows; another says when a later output
preserves an earlier claim.  State-machine-style specifications can be compiled
into this form (Section~\ref{sec:design-boundary}); the table keeps only what
the specification can ask about.  The table can express a classical consistency
model, such as
linearizability or causal consistency, or an application-specific requirement,
such as an invariant.  We call any such specification \emph{consistent} when
its executions are \emph{confluent}: states reached along different paths can
still be brought to a common state.  The declared model determines which
outputs are within spec; confluence asks whether those requirements can be
maintained across concurrent executions.

We begin with tables having a functional dependency from input to output
(\S\ref{sec:functional-specifications}).  These \emph{functional ordered
specifications} capture arbitrary functions
\(f:(I,\InputOrd)\to(O,\OutputOrd)\) between separately ordered input and
output domains.  Such a function is monotone when \(i\InputOrd j\) implies
\(f(i)\OutputOrd f(j)\).  Concurrent
executions make input arrival uncertain: different paths may see different
input refinements, in different orders and batches.  Monotonicity says that an
output exposed on any path remains valid as more input arrives.  Without it,
the system must make an irrevocable \emph{commitment} that rules out behavior
still within spec.  The framework identifies this need for commitment as the
underlying reason to employ operational coordination mechanisms.  For a functional
specification, commitment means sealing off inputs that could contradict the
output.

The first result is \emph{Functional CALM}
(\S\ref{sec:functional-calm-theorem}).  It generalizes the CALM result from
relational logic languages and fact inclusion
to these arbitrary functions and refinement partial orders, giving a common
language for coordination-freedom results over functional specifications,
including query evaluation and the usual CRDT state interface.  It proves that
Consistency is equivalent to monotonicity.  ``Functional'' means only that each
input has one specified output; execution may be as nondeterministic as it
likes.

We then develop two orthogonal extensions.  First, we give Consistency its
distributed reading (Section~\ref{sec:distributed-execution}).  Lamport
histories place one local execution at each participant; transition projection removes
delivery and strategy details, and Distributed Consistency asks whether the
resulting participant states can still be brought to the same state.  This step applies to functional
specifications and the extensions that follow.

Second, we drop the functional dependency from input to output.  The resulting
\emph{ambiguous} specifications allow several distinguishable outputs for one
input, as in leader election and transaction ordering.  Multiple outputs
require extending standard monotonicity to sets of outputs, a condition we call
\emph{Lifted Monotonicity} (\S\ref{sec:complete-calm-criterion}).  Complete CALM
equates this condition with Consistency.  Ambiguity adds another form of
commitment: progress may require ruling out an alternative output.  In a
distributed execution, if participants must retain independently selectable
incompatible alternatives, the alternatives must be mutually excluded before
either is committed
(\S\ref{sec:complete-calm-theorem}).

The acronym Complete CALM reads \emph{Consistency As Lifted Monotonicity}, and
the original CALM Theorem is its functional case over relations and queries.
Classical CALM classifies which specifications are consistent without
coordination.  Because its model contains no commitments, it cannot ask whether
a coordination mechanism properly resolves a non-monotone specification.
Complete CALM can: a commitment is itself non-monotone---it removes rows---but
may leave a monotone remainder whose downstream execution needs no further
commitment.  Appendix~\ref{app:composition} proves composition lemmas that make
this \emph{Proper Coordination} analysis modular.  A single authority that
commits to a log and feeds a deterministic register or key-value store gives
the basic construction; MultiConsensus provides distributed authority with the
same exported interface.

Complete CALM also yields a Complete CAP Theorem
(\S\ref{sec:cap-corollary}).  Classical CAP gives an impossibility for
linearizable registers under partition.  Complete CAP turns that one negative
result into a dichotomy for any consistency model expressed by a specification:
it identifies both specifications that face a CAP tradeoff and those that do
not.  Linearizability is one instance on the tradeoff side.

This paper makes six contributions:
\begin{enumerate}
  \item A framework for concurrent computation: specifications as
        relations with ordered inputs and outputs, specification states
        recording what remains possible, and three transitions: input events,
        output events, and \emph{commitments}.
  \item A general definition of Consistency as confluence, applicable whether
        the specification expresses a classical consistency model or an
        application-specific requirement.  Transition projections give this
        definition a distributed reading over Lamport histories, and
        Section~\ref{sec:instances} applies it to CRDTs, highly available
        transactions, and invariant confluence.
  \item Functional CALM generalizes and proves the CALM Conjecture in the context of
        arbitrary functions, represented as ordered input/output specifications
        with separate input- and output-refinement partial orders.
  \item Complete CALM extends the model to output choice and identifies
        coordination with commitment.  It proves that Consistency as confluence
        is equivalent to Lifted Monotonicity; through transition projection,
        both are equivalent to Distributed Consistency over Lamport histories.  A monotone specification therefore
        needs no coordination, since
        exposing outputs alone keeps its histories confluent; where monotonicity
        fails, progress requires a commitment and therefore coordination.
          When participants must retain independently selectable conflicting
          alternatives, those courses are shown to require mutual exclusion.
          Distributed agreement is one mechanism; static authority is another.
          In partition form
        this is the Complete CAP Theorem,
        which extends the classical impossibility to a bidirectional dichotomy
        parameterized by the declared specification and the
        deployment.
  \item Composition and Proper Coordination
        (Appendix~\ref{app:composition}).  Sequential and independently
        parameterized composition preserve Lifted Monotonicity.  Consequently,
        a commitment may restrict a non-monotone specification to a monotone
        remainder that composes consistently with downstream components without
        further commitment.  A single log authority illustrates the result;
        MultiConsensus implements the same committed-log interface with
        distributed authority.
  \item Two frontier theorems (Appendix~\ref{sec:frontiers}) characterize how
        far an interface can be strengthened before coordination becomes
        unavoidable: which earlier outputs a monotone interface must preserve,
        and when constraints across independently acting participants create a
        CAP tradeoff.
\end{enumerate}

Section~\ref{sec:functional-calm} introduces the framework on an election
and develops Functional CALM.  Section~\ref{sec:distributed-execution} gives
Consistency its distributed reading.  Section~\ref{sec:ambiguous-specifications}
extends the framework to output choice, and Section~\ref{sec:complete-calm}
combines the two extensions in Complete CALM and Complete CAP.
Section~\ref{sec:instances} applies the results to familiar systems, and
Section~\ref{sec:discussion} draws out the design lessons and scope limits.
Appendix~\ref{app:composition} proves the composition and Proper Coordination
results, Appendix~\ref{sec:frontiers} derives maximal coordination-free
interfaces, and Appendix~\ref{app:additional-applications} gives further
classical applications.

\section{Functional CALM}
\label{sec:functional-calm}

The CALM Theorem was proved for queries in a logic programming language,
evaluated by relational transducers, and its applicability outside that
setting was never made precise.  Here we use a simpler model that applies to
any specification expressible as an ordered input/output relation.  A
specification describes allowed input/output
behavior without committing to a language, placement, protocol, or message
schedule.  This section addresses the case that prior work on both CALM and
CRDTs shared: specifications that are functions, in which each
input has a single specified output.  Section~\ref{sec:election-story} walks
through the framework informally on an election.
Section~\ref{sec:functional-specifications} defines functional specifications
and monotonicity, Section~\ref{sec:determination} defines the I/O transition
system and Consistency, Section~\ref{sec:functional-calm-theorem} proves
Functional CALM, and Section~\ref{sec:canonical-transition-system} factors
unrestricted output into commitment and exposable output events.

\subsection{The framework on an election}
\label{sec:election-story}

We begin with an informal, example-driven treatment.
Terms introduced in italics are defined formally in the rest of this section
and in Sections~\ref{sec:distributed-execution}--\ref{sec:complete-calm};
italics also mark the occasional
standard term borrowed from database theory.  Nothing here is needed for the
proofs, but every notion the Functional CALM theorem rests on---specification
states, input events, retirement, commitments, upper fibers, determination,
output events, runs, and consistency---is exercised on the example.

The framework begins with an \emph{ordered specification}
$\Spec=(I,\InputOrd,O,\OutputOrd,S)$: a table $S\subseteq I\times O$ that
captures exactly which outputs are within spec at each input, with a partial
order on each column.  In this section, input functionally determines output:
every input is paired with exactly one output.
Section~\ref{sec:ambiguous-specifications} later drops this functional
dependency.

\paragraph{A specification is a table.}
A specification table lists the output paired with each input.  Squaring, for example,
has rows $(2,4)$, $(3,9)$, $(4,16),\ldots$.  Everything that follows is a
matter of removing rows from a specification.

Figure~\ref{fig:election-frames}(a) shows a set of rows taken from the specification of a small election.
Three voters $v_1,v_2,v_3$ each cast at most one immutable ballot for $x$ or
$y$; the result is whichever candidate has two ballots, and $\bot$ (no result
yet) until one does.  An input represents the
ballots seen so far, written as a three-letter string whose $k$th position holds
$v_k$'s ballot or a dot if it has not arrived; only rows above $x\cdot\cdot$,
where $v_1$ has voted $x$, are shown.  The first row says that with $v_1$'s
ballot alone the result is $\bot$; row $xx\cdot$ says that once $v_2$ also votes
$x$ the result is $x$; row $xyy$ says that if $v_2$ and $v_3$ both vote $y$ the
result is $y$.

The rows are only part of the specification.  Each column also carries a
partial order, and both orders are design decisions.  The \emph{input order}
says what counts as more input: here, more ballots, so $xy\cdot$ \emph{refines}
$x\cdot\cdot$, while $xx\cdot$ and $xy\cdot$ are incomparable.  The \emph{output
order} says when a later output keeps every promise an earlier one made: here
$\bot$ lies below both $x$ and $y$, so ``no result yet'' can eventually refine
to a winner, but $x$ and $y$ are incomparable, so neither winner refines the
other.  A
different design could make all outputs incomparable, so that every result is
final; we return to that choice below.  Given these orders, one can follow any input
upward through its refinements, say $x\cdot\cdot$ to $xy\cdot$ to $xyx$: the
output climbs too, from $\bot$ to $x$, and never steps down or sideways.  That
is what it means for the \emph{specification} to be \emph{monotone}, a property
of the rows together with the orders.

\paragraph{Input arrives.}
Now $v_2$'s ballot arrives, for $y$; panel (b) shows the result.  The
\emph{current input}, the ballots seen so far, has advanced from $x\cdot\cdot$
to $xy\cdot$, shown in bold.  What an input event does to the specification
is governed by one rule: only the rows at the current input and its
refinements remain, and every other row is \emph{retired}.  Each state pairs the current input with the rows that remain: it records what
is still possible and how far input has come.  Each panel shows one such state,
with its remainder table and current input in bold.  The inputs that still have rows are the \emph{valid} ones.
The environment, not the system, supplies new input.  Here $v_2$'s ballot
extends the cumulative input from $x\cdot\cdot$ to $xy\cdot$, and the system
records that change as $\mathsf{input}(xy\cdot)$ whether the ballot arrived
directly or in a message.
The state depends only on the input reached, not on the order or
grouping in which the ballots arrived.  In panel (b) the input has grown
from $x\cdot\cdot$ to $xy\cdot$, so the row at $x\cdot\cdot$ is retired; the
rows at $xx\cdot$, $xxx$, and $xxy$ are retired because no input refines both
$xx\cdot$ and $xy\cdot$.  The retired output $\bot$ at $x\cdot\cdot$ is
refined by the $\bot$ at $xy\cdot$, so growing the input lost nothing the
smaller input's output claimed; this is a consequence of the monotonicity
observed above.

\paragraph{What could still happen.}
While input may still grow, what matters is not only the current row but what
any input that could still arrive might require.  The future of the election
is its current input together with its valid input refinements, and the outputs of
those rows form the current input's \emph{upper fiber}.  In
panel (b) those rows are the current row and the two refinements $xyx$ and
$xyy$ in which $v_3$ votes, so the upper fiber, shaded, is $\{\bot,x,y\}$:
either candidate could still win.

Panel (c) shows the alternative in which $v_2$ voted $x$.  The rows at or
above $xx\cdot$ all say $x$, so the upper fiber is the singleton $\{x\}$ and
the current input is \emph{determined}: it fixes the output regardless of what
ballot $v_3$ could cast.  Narrowing the upper fiber until a single output
remains is what we call \emph{determination}.  Here input arrival determined the state on its own; below we meet the case where the system must act.

\paragraph{Commitments.}
Return to panel (b).  The registrar now closes the polls, so any later ballot
from $v_3$ will not count.  Panel (d) removes the rows at $xyx$ and $xyy$ while
leaving the current input $xy\cdot$ unchanged.  The system has thereby made
those input refinements invalid.  This irrevocable act is a \emph{commitment},
specifically an \emph{input-sealing commitment}: the system, rather than new
input from the environment, has ruled out behavior that was within spec.

The specification itself does not authorize closing the polls.  That authority
comes from the system's \emph{commitment basis} $\mathcal B$, which contains
all the commitments it may perform.  A system whose polls can close includes
this commitment in its basis; one whose polls cannot close does not.  After the
commitment, no refinement of $xy\cdot$ remains valid, its upper fiber is
$\{\bot\}$, and the state is determined.

Because a functional specification has one row per input, any commitment that
removes a row from the remainder table makes that input invalid.  We call such
a commitment \emph{input-sealing}; it need not invalidate every possible future
input.  Section~\ref{sec:ambiguous-specifications} adds choice commitments for
specifications with several outputs at one input.

\paragraph{Output events.}
Up to this point we have not discussed how outputs are represented in our model.
An \emph{output event} \emph{exposes} a result $o$ to a client; this is a
distinct act from input events and commitments.  In a functional specification,
$o$ is \emph{exposable} exactly when every possible future output---the values
in the upper fiber---refines $o$.  If this test fails, an authorized commitment
can remove the conflicting rows and thereby make $o$ exposable.  In
Figure~\ref{fig:election-frames}, $\bot$ is exposable in every panel because
every shaded output refines it, and $x$ is exposable in panel (c).

\paragraph{When monotonicity fails.}
Now change one thing in our example: make all outputs incomparable, dropping
$\bot\OutputOrd x,y$, so that an output refines only itself; this is the
\emph{equality order}.  The rows are the same, but in panels (a) and (b)
nothing is exposable: $\bot$ no longer lies below the $x$ and $y$ in the upper
fiber.  To expose anything, the registrar must first make an input-sealing
commitment.
Figure~\ref{fig:nonmonotone-frame} shows the result of closing the polls at
$x\cdot\cdot$: every refinement is removed by commitment, the upper fiber
collapses to $\{\bot\}$, and only now is $\bot$ exposable.  That contrast is
Functional CALM (Section~\ref{sec:functional-calm}): a monotone functional
specification can expose outputs as input arrives; a non-monotone one must
first make a commitment.

\paragraph{A transition system.}
We now have the ingredients for a state transition model.  A state consists of
two things: the current input and the rows of the specification that remain.
Each panel above depicts one such state, and each action moves from one state to
another.  An input event grows the current input and retires rows that are no longer
reachable.  An output event keeps the input fixed and exposes an exposable
result.  A commitment also
keeps the input fixed, but removes alternatives authorized by the commitment
basis.  Input events come from the environment; output events and commitments
come from the system.  Panels (b) through (e) are reached from panel (a) by one
or two transitions.  For the confluence test, the formal development first lets
an I/O transition system select any current output; it then separates
commitments from exposable output events in the canonical transition system.

\paragraph{Consistency.}
Our goal is \emph{confluence}: any finite collection of input/output paths
through the I/O transition system can be brought to one common state, whatever
further input arrives.  We call a specification \emph{consistent} when all
such paths are confluent.

Our framework can encode either a general consistency model that spans many
applications or an application-specific requirement such as an invariant.  In
the election, the table and its orders license the application's legal
behaviors: which results it permits and which later results preserve earlier
ones.  Consistency then asks whether paths through those behaviors can still
meet.  Appendix~\ref{app:registers} instead instantiates the framework with
linearizability and causal consistency, two application-independent consistency
models that license different register behaviors and therefore yield different
confluence results; Section~\ref{sec:consistency-as-confluence} develops this
distinction generally.  Specifications can also be composed: joining component
tables on their shared interface yields an end-to-end specification
(Appendix~\ref{app:composition}).

Monotonicity gives a condition directly on the specification table: whenever
input grows from $i$ to $k$, the output at $k$ refines the output at $i$.
Functional CALM proves that this condition is equivalent to confluence: a
functional specification is consistent exactly when it is monotone.

The rest of this section states these notions formally.
Figure~\ref{fig:formalism-summary} collects the formal objects of Functional
CALM; Figure~\ref{fig:complete-formalism-summary} will collect the additions
for Complete CALM.

\subsection{Functional specifications and monotonicity}
\label{sec:functional-specifications}

\begin{definition}[Functional ordered specification]
\label{def:functional-specification}
A \emph{functional ordered specification} is a function
        \begin{equation}
  f:(I,\InputOrd)\longrightarrow(O,\OutputOrd),
  \label{eq:functional-specification}
        \end{equation}
where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered sets.  We call
$\InputOrd$ the \emph{input-refinement order}: $i\InputOrd j$ means that $j$
contains at least the input information in $i$.  We call $\OutputOrd$ the
\emph{output-refinement order}: $o\OutputOrd u$ means that $u$ preserves every
externally visible claim in $o$ and may add more.
\end{definition}

These are two separate partial orders.  The input order compares inputs; the
output order compares outputs.  Neither orders executions or rows in a table.
Either may be the \emph{equality order}, under which an element refines only
itself; on outputs this is the case in which no output can be extended, only
replaced.

\begin{definition}[Monotonicity]
\label{def:functional-monotonicity}
A functional ordered specification $f$ is \emph{monotone} if
        \begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  f(i)\OutputOrd f(j).
  \label{eq:functional-monotonicity}
        \end{equation}
\end{definition}

This is the standard mathematical definition of a monotone function.  In
systems terms, an output exposed from partial input remains valid as more input
arrives.

\subsection{The I/O transition system}
\label{sec:determination}

Section~\ref{sec:election-story} previewed the full transition model: input
events, output events, and system actions that remove alternatives.  We called
the last kind \emph{commitments} informally; their formal definition comes in
Section~\ref{sec:canonical-transition-system}.  We now step back and begin
with a simpler model containing only input and output events.  Its output events
are unrestricted: they may select any output at the current input and remove
the rows that do not refine it.  This intentionally combines exposure with any
restriction needed to honor the exposed output.  That conflation is deliberate:
it lets non-monotonicity appear as a failure of confluence.  Section~\ref{sec:election-story}
used \emph{exposable} informally for an output that needs no restriction of the
remaining rows.  If this model allowed only such outputs, monotonicity would be
enforced by its transition rule rather than studied, and the CALM equivalence
would be built into the model.  Section~\ref{sec:canonical-transition-system}
will define exposability formally.  The simpler model instead asks whether all
input/output paths are confluent without yet classifying the restrictions they
make.

This subsection defines that I/O transition system, its runs, and Consistency.
Section~\ref{sec:canonical-transition-system} then returns to the model
previewed in Section~\ref{sec:election-story}, formally defining commitments
and factoring each unrestricted output event into any required commitments
followed by an exposable output event.

\paragraph{The specification and remainder tables.}
The graph $S\subseteq I\times O$ is the \emph{specification table}; its rows
are the pairs $(i,f(i))$, one at each input.  During a run, $R\subseteq S$ is
the \emph{remainder table}; it records the rows not yet removed.  Neither kind
of event adds a row.

Inputs are \emph{cumulative}: an input is everything seen so far, and
$i\InputOrd j$ means that $j$ contains at least the information in $i$.  The
specification sees inputs only through the domain, its order, and the outputs
it allows for each; corrections, retractions, or conflicting ballots are
accommodated by designing the input domain to record them.  Write
$k\prec_I i$ when $k\InputOrd i$ and $k\neq i$, and
$\mathord\uparrow_I i=\{j\in I:i\InputOrd j\}$ for the refinements of $i$.

\paragraph{States.}
A state pairs the current input with a remainder table.  Every panel of
Figure~\ref{fig:election-frames} is such a state.

\begin{definition}[Specification state]
\label{def:residual-state}
A \emph{specification state} is a pair $\sigma=(i,R)$ such that
\begin{enumerate}
  \item $i\in I$ is the \emph{current input};
  \item $R\subseteq S$;
  \item $R$ has a row at the current input:
        \begin{equation}
          (i,o)\in R\ \text{for some }o;
          \label{eq:current-input-validity}
        \end{equation}
  \item only refinements of the current input have rows in $R$:
        \begin{equation}
          (k,o)\in R
          \quad\Longrightarrow\quad i\InputOrd k.
          \label{eq:retired-input-absence}
        \end{equation}
\end{enumerate}
An input $k$ is \emph{valid} when $R$ has a row at $k$, and otherwise
\emph{invalid}.
\end{definition}

Valid inputs other than the current one are possible futures: refinements of
$i$ whose rows have not been removed.  For an input $i$, the \emph{canonical
initial state} is
        \begin{equation}
  \sigma_0(i)=\bigl(i,\ \{(k,o)\in S:\ i\InputOrd k\}\bigr),
  \label{eq:canonical-initial-state}
        \end{equation}
the specification table restricted to $i$ and its refinements.
Figure~\ref{fig:election-frames}(a) is $\sigma_0(x\cdot\cdot)$.

\begin{definition}[I/O transition system]
\label{def:io-transition-system}
The \emph{I/O transition system} has specification states as its states and
partial functions of two kinds as its transitions.  Each transition is defined
only when its result is a specification state.
\begin{enumerate}
  \item \emph{Input event.}  For $j\in I$ with $i\InputOrd j$,
        $\mathsf{input}(j)$ makes $j$ current and removes every row whose input
        does not refine $j$:
        \begin{equation}
          (i,R)\xrightarrow{\mathsf{input}(j)}
          \bigl(j,\ R\mathbin{\upharpoonright_I}j\bigr),
          \qquad
          R\mathbin{\upharpoonright_I}j=\{(k,u)\in R:\ j\InputOrd k\},
          \label{eq:input-event}
        \end{equation}
        defined when $R$ has a row at $j$.
  \item \emph{Unrestricted output event.}  For $(i,o)\in R$,
        $\mathsf{output}(o)$ exposes $o$ and removes every row whose output does
        not refine it:
        \begin{equation}
          (i,R)\xrightarrow{\mathsf{output}(o)}
          \bigl(i,\ R\mathbin{\upharpoonright_O}o\bigr),
          \qquad
          R\mathbin{\upharpoonright_O}o=\{(k,u)\in R:\ o\OutputOrd u\}.
          \label{eq:residual-refining-fibers}
        \end{equation}
        This event is always defined because $(i,o)$ remains.
\end{enumerate}
\end{definition}

The output event is \emph{unrestricted} because it may select any output paired
with the current input.  As motivated above, it treats exposure and the row
restriction needed to honor that exposure as one action so confluence can test
whether the restriction was necessary.  The canonical transition system will
separate them.

\paragraph{Input events.}
An input event records the new cumulative input, not the value that caused it.
The system model supplies a partial function
        \begin{equation}
  \mathsf{advance}:I\times I\rightharpoonup I,
  \qquad
  \mathsf{advance}(i,a)=j
  \ \Longrightarrow\
  \begin{cases}
    i\InputOrd j,\\
    a\InputOrd j,
  \end{cases}
  \label{eq:cumulative-advance}
        \end{equation}
where $i$ is current and $a$ is arriving cumulative input.  We require
$\mathsf{advance}(i,a)=a$ whenever $i\InputOrd a$, so an already cumulative
arrival is recorded directly.  The computation is not an event; the resulting
$\mathsf{input}(j)$ is.  For set-valued inputs, advance may be union; for a
join-semilattice, it may be join.  Neither structure is assumed.  In particular,
two inputs may have no common refinement, or several incomparable common
refinements, and the framework requires neither a least common refinement nor a
lattice.  The function is partial because advance need not be defined for every
pair; where several results are possible, it records the one chosen by the
system model.

Input events compose: $\mathsf{input}(j)$ followed by $\mathsf{input}(k)$ has
the same effect as $\mathsf{input}(k)$ alone, and $\mathsf{input}(i)$ at
$(i,R)$ is the identity.  Thus input order, batching, and repeated delivery do
not affect the state reached by input events alone.

\begin{definition}[I/O run and I/O-generated state]
\label{def:run}
An \emph{I/O run} is a finite sequence of input and unrestricted output events
from a canonical initial state.  A specification state is \emph{I/O-generated}
when it is reachable via an I/O run.
\end{definition}

Thus I/O-generated is a provenance condition, not another local invariant on a
remainder table.  It excludes structurally valid states whose missing rows
cannot be explained by input or unrestricted output events.

\begin{lemma}[Rows remaining after an I/O run]
\label{lem:run-residual}
An I/O run starts at $\sigma_0(i_0)$, ends with current input $i$, and exposes
outputs $o_1,\ldots,o_m$.  Its final state is
        \begin{equation}
  \left(i,\ \left\{(k,x)\in S:
    \begin{array}{l}
      i\InputOrd k,\ \text{and}\\
      o_\ell\OutputOrd x\ \text{for every }\ell
    \end{array}
  \right\}\right).
  \label{eq:run-residual}
        \end{equation}
\end{lemma}

\begin{proof}
Each input event intersects $R$ with $\{(k,x):j\InputOrd k\}$ and each output
event with $\{(k,x):o\OutputOrd x\}$.  Intersections commute, and the input
restrictions compose to the restriction at the final input $i$.
\end{proof}

A \emph{common refinement} of inputs $i_1,\ldots,i_k$ is an input $j$ with
$i_r\InputOrd j$ for every $r$.

\begin{definition}[Consistency]
\label{def:consistency}
An ordered specification is \emph{consistent} when every finite family of I/O
runs is confluent: if the runs end at
$(i_1,R_1),\ldots,(i_k,R_k)$ and $j$ is a common refinement of their current
inputs, a single state with current input $j$ is reachable by I/O events from
each $(i_r,R_r)$.  The runs are then \emph{confluent at} $j$.
\end{definition}

Equivalently, Consistency quantifies over every finite family of I/O-generated
endpoints.  This covers every I/O-generated starting state, since any path from
one extends the run that generated it.  It does not quantify over arbitrary
specification states: their remainder tables may encode row removals that no
I/O event produced.  An interface obtained after such additional row removal
is tested separately as a specification in Appendix~\ref{app:composition}.

\begin{proposition}[Confluence at a common refinement]
\label{prop:confluence}
I/O runs ending at $(i_1,R_1),\ldots,(i_k,R_k)$ are confluent at $j$ if and
only if some row at $j$ survives in every final state,
        \begin{equation}
  (j,u)\in R_r\quad\text{for every }r,\ \text{for some }u\in O.
  \label{eq:reconciliation}
        \end{equation}
For any such $u$, $\mathsf{input}(j)$ followed by $\mathsf{output}(u)$ takes
every final state to
$\bigl(j,\{(k,x)\in S:j\InputOrd k,\ u\OutputOrd x\}\bigr)$.
\end{proposition}

\begin{proof}
A common state with current input $j$ has a row at $j$, and that row belongs to
every $R_r$.  Conversely, let $(j,u)$ belong to every $R_r$.  Then
$\mathsf{input}(j)$ is defined at every $(i_r,R_r)$.  By
Lemma~\ref{lem:run-residual}, $(j,u)\in R_r$ says that $u$ refines every output
exposed on run $r$.  After $\mathsf{input}(j)$ and $\mathsf{output}(u)$, the
same lemma leaves exactly the rows of $S$ above $j$ and $u$, independent of the
starting run.
\end{proof}

A single I/O run can witness inconsistency: an unrestricted output event may
remove every row at a refinement of its current input.  Consistency describes
no protocol and promises no delivery or termination;
Section~\ref{sec:discussion} returns to this.

\subsection{The Functional CALM theorem}
\label{sec:functional-calm-theorem}

\begin{theorem}[Functional CALM]
\label{thm:functional-calm}
A functional ordered specification is consistent if and only if it is
monotone.
\end{theorem}

\begin{proof}
Every input has one row.  By Lemma~\ref{lem:run-residual}, an I/O run ending at
input $i$ retains $(k,f(k))$ at $k\succeq_I i$ exactly when every output
$f(i_\ell)$ exposed on the run satisfies $f(i_\ell)\OutputOrd f(k)$.  By
Proposition~\ref{prop:confluence}, a finite family of I/O runs is confluent at
a common refinement $k$ exactly when every output exposed on any run lies below
$f(k)$.  If $f$ is monotone this holds because each exposed $f(i_\ell)$ has
$i_\ell\InputOrd k$.  If $f$ is not monotone, some $i\prec_I k$ has
$f(i)\not\OutputOrd f(k)$; the I/O run that starts at $\sigma_0(i)$ and exposes
$f(i)$ has no row at $k$ and cannot advance to its own refinement $k$.
\end{proof}

This is the familiar CALM dichotomy stated at the specification interface
rather than inside a particular programming language.  Classical CALM fits the
pattern with inputs $J$ ordered by fact inclusion and outputs $Q(J)$ ordered by
answer inclusion.  Functional monotonicity becomes
        \begin{equation}
  J\subseteq J'
  \quad\Longrightarrow\quad
  Q(J)\subseteq Q(J'),
  \label{eq:query-monotonicity}
        \end{equation}
the standard definition of a monotone query~\cite{abiteboul1995foundations},
which positive Datalog satisfies and negation may not.  Functional CALM
extends the statement from fact sets under inclusion to arbitrary input and
output refinement orders.  The usual CRDT state interface has the same
functional shape, with received payloads ordered by inclusion and states by
the semilattice order~\cite{shapiro2011crdt};
Sections~\ref{sec:query-instance} and~\ref{sec:crdt-instance} take up both
instances.

\subsection{The canonical transition system}
\label{sec:canonical-transition-system}

The I/O transition system deliberately bundles two effects into an unrestricted
output event: restricting the table to honor an output and exposing that
output.  The \emph{canonical transition system} separates restriction from
exposure.  Input events reflect information supplied by the environment; the
system actions informally called commitments above explicitly rule out
behavior and are defined below; output events expose only outputs that require
no such action.

For $R\subseteq S$, the \emph{upper fiber} at $i$ collects outputs at $i$ and
its still-valid refinements:
        \begin{equation}
  R^\uparrow(i)=\{o\in O:\exists j\in I,\ i\InputOrd j\text{ and }(j,o)\in R\}.
  \label{eq:upper-fiber}
        \end{equation}
The current input is \emph{determined} when $|R^\uparrow(i)|=1$, and a state
is determined when its current input is.

\begin{definition}[Exposable output, functional case]
\label{def:exposable}
For a functional specification, $(i,o)\in R$ is \emph{exposable} at $(i,R)$
when the unrestricted event $\mathsf{output}(o)$ removes no row.  Equivalently,
$o\OutputOrd f(j)$ at every valid $j\succeq_I i$.
\end{definition}

A \emph{commitment basis} $\mathcal B$ is the set of commitments a system is
authorized to apply.  A commitment $c\in\mathcal B$ is a partial function on
specification states with $c(i,R)=(i,R')$, where $R'\subsetneq R$, that removes
at least one row $(k,x)$ for which no retained output at $k$ refines $x$.

\begin{definition}[Canonical transition system]
\label{def:transition-system}
The \emph{canonical transition system} has specification states as its states
and exactly three kinds of transition:
\begin{enumerate}
  \item input events, as in Equation~\ref{eq:input-event};
  \item commitments from the system's commitment basis; and
  \item output events $\mathsf{output}(o)$, as in
        Equation~\ref{eq:residual-refining-fibers}, defined only when $o$ is
        exposable.
\end{enumerate}
A state is \emph{reachable in the canonical system} when it is obtained from a
canonical initial state by these transitions.
\end{definition}

The same notation $\mathsf{output}(o)$ is intentional.  In the I/O system it is
an unrestricted output event that may hide a restriction of the table.  In the
canonical system the output is already exposable, so the event performs no
hidden commitment.  If an output is not exposable, a system must first apply
commitments from its basis until the output becomes exposable; an appropriate
commitment need not exist in every basis.

\begin{definition}[Retirement]
\label{def:retirement}
Let a transition take $(i,R)$ to $(i',R')$ and remove $(k,x)$.  The removal is
an \emph{input retirement} if $k$ does not refine $i'$.  For a canonical
transition of a functional specification, every other removal is \emph{removed
by commitment}.
\end{definition}

An \emph{input-sealing commitment} makes at least one valid input invalid.  A
\emph{choice commitment} keeps every valid input valid but removes some rows at
a valid input.  These cases are exhaustive.  Every commitment in a functional
specification is input-sealing because each input has one row; choice
commitments arise after Section~\ref{sec:ambiguous-specifications} drops the
functional dependency.  A state is \emph{sealed} when no strict refinement of
its current input remains valid.  A sealed functional state is determined, but
an input-sealing commitment need not seal the state.

A system's \emph{strategy} chooses which canonical output event or commitment
to make, using the specification state and any additional strategy state.
Strategy state is not part of the specification state and affects the remainder
table only through the selected transition.

\begin{proposition}[Functional exposure boundary]
\label{prop:functional-exposure-boundary}
A functional ordered specification is monotone if and only if every output at
every state reachable without commitment in the canonical system is exposable.
\end{proposition}

\begin{proof}
If $f$ is monotone, a commitment-free canonical state has lost rows only to
input events, since its output events remove none.  If its current input is $i$,
then the only output paired with $i$ is $f(i)$, and every valid
$j\succeq_I i$ has $f(i)\OutputOrd f(j)$, so $f(i)$ is exposable.  Conversely,
suppose every output at every commitment-free state reachable in the canonical
system is exposable.  At $\sigma_0(i)$, exposability of
$f(i)$ preserves the row $(j,f(j))$ for each $j\succeq_I i$, so
$f(i)\OutputOrd f(j)$ and $f$ is monotone.
\end{proof}

Functional CALM and this proposition give the operational boundary.  A
monotone functional specification can expose every current output without a
commitment.  If monotonicity fails at $i\prec_I k$, exposing $f(i)$ requires a
commitment that removes the conflicting row at $k$ before the canonical output
event can occur.

Historically, CALM stands for \emph{Consistency As Logical Monotonicity}, and
its C has been read both as consistency and as confluence;
Definition~\ref{def:consistency} is both.  Functional CALM states the result
for any functional specification, regardless of the formalism used to express
it.  Before dropping the functional dependency, we give this consistency
condition a distributed interpretation.  Section~\ref{sec:distributed-execution}
realizes I/O runs as participant runs; the construction will apply unchanged
when Section~\ref{sec:ambiguous-specifications} introduces output choice.

\section{Distributed Execution}
\label{sec:distributed-execution}

Functional CALM defines Consistency as confluence of finite sets of I/O runs.
We now add a distributed setting for both transition systems.  Lamport histories
add participants, messages, and cuts; transition projection reduces a cut to one
specification state per participant.  A commitment-free canonical projection is
also an I/O run, so the same confluence test applies.

\subsection{Lamport histories}
\label{sec:histories}

A Lamport history can label participant actions from either transition system.
I/O histories use only I/O-system events and support the confluence test;
canonical histories additionally record explicit commitments and restrict
output events to exposable outputs.  This subsection adds messages and
consistent cuts; the next projects each cut to specification states.

\paragraph{Participants and local execution.}
A participant holds one specification state, changed only by its own input
events, output events, and commitments.  Participants may receive different
inputs and expose different outputs.  In an I/O history, each participant's
local transition sequence is an I/O run.  Consistency compares these runs
whenever their current inputs have a common refinement, covering sharded
systems as well as replicas.  Because input events
compose, delivery order and batching do not affect a state reached by input
events alone.

\paragraph{Histories and consistent cuts.}
A Lamport history records local events and the message edges between them.  A
message $m=(i_m,s_m)$ has an optional cumulative-input component and arbitrary
strategy data.  After a receive, the strategy may use $\mathsf{advance}$ to
compute a later input event; neither the calculation nor the receive is that
input event.  The external environment has no timeline in $H$: when it supplies
$a$, the strategy computes
$\mathsf{advance}(i,a)=j$ and the participant records
$\mathsf{input}(j)$.
\begin{definition}[Lamport history of the transition system]
\label{def:distributed-history}
Fix an ordered specification, a finite participant set $P$, a message set
$M\subseteq(I\cup\{\mathsf{none}\})\times(D\cup\{\mathsf{none}\})$ for some set $D$
of strategy data, an
initial input $i_p$ for each $p\in P$, a cumulative-advance function
(Equation~\ref{eq:cumulative-advance}), and a commitment basis.  A
\emph{distributed history} $H$ consists of a finite set of events, together
with:
\begin{enumerate}
  \item an assignment of each event to a participant $p\in P$, and a total
        local order on the events assigned to each participant;
  \item a label on each event: an input event $\mathsf{input}(j)$, an output
        event $\mathsf{output}(o)$, a commitment from the basis, a send
        $\mathsf{send}(m)$, or a receive $\mathsf{receive}(m)$; and
  \item for each $\mathsf{receive}(m)$, a matching $\mathsf{send}(m)$ at
        another participant.
\end{enumerate}
A history is an \emph{I/O history} when its participant transitions are input
and unrestricted output events of the I/O system and an \emph{canonical
history} when they are transitions of the canonical system.  The
\emph{happens-before} order is the transitive closure of the local orders
and the edges from sends to their matching receives.  A
\emph{consistent cut} $C$ is a subset of events closed under happens-before
~\cite{chandy1985distributed}.  (This textbook use of ``consistent'' is
unrelated to consistency as confluence, which is a property of
specifications.)
\end{definition}

Histories retain delivery and strategy details that the specification does not
need.  We next project those details away and ask whether the resulting
participant states can still be brought to the same state.

\subsection{Transition projection and confluence}
\label{sec:projection-confluence}

The projection is easiest to see by comparing two histories with the same
effect on their participants.

\paragraph{Example: direct and forwarded input.}
In Figure~\ref{fig:history-projection}, $p$ and $q$ start at
$\sigma_0=(x\cdot\cdot,R_0)$ and receive cumulative input $xy\cdot$ directly
from the environment or through a forwarded message.  The histories differ,
but both participants reach $\sigma_1=(xy\cdot,R_1)$.

\begin{figure}[t]

The figure shows why we need a transition projection.  A Lamport history
records sends, receives, and strategy state even when they make no difference
to the specification state.  The projection filters each participant's history
to the transitions that determine that state.

\begin{definition}[Transition projection and state endpoint]
\label{def:semantic-projection}
For a consistent cut $C$ and participant $p$, list the events of $C$ assigned
to $p$ in local order.  Its \emph{transition projection} $\pi_p(C)$ keeps the
input events, output events, and commitments in that order, and deletes sends
and receives.  A receive may update strategy state and lead the strategy to
compute a later input event, but it does not directly change the specification state.
We consider only pairs $(H,C)$ for which each $\pi_p(C)$ is a defined
transition sequence from $\sigma_0(i_p)$ and every input event caused by an
arrival or receive has the target computed by $\mathsf{advance}$.  Write
$\sigma_p(C)$ for the final specification state of $\pi_p(C)$.  The
\emph{state endpoint} of the cut is the vector
        \begin{equation}
  \operatorname{end}(H,C)=(\sigma_p(C))_{p\in P}.
  \label{eq:semantic-endpoint}
        \end{equation}
In an I/O history, every transition projection is an I/O run.  In a canonical
history, it is a canonical transition sequence and may include commitments.
\end{definition}

At both cuts in Figure~\ref{fig:history-projection}, each local projection is
$\mathsf{input}(xy\cdot)$, so
$\operatorname{end}(H_d,C_d)=\operatorname{end}(H_f,C_f)
=(\sigma_1,\sigma_1)$.  Projection erases the delivery path while retaining
its effect on the participant states.

State endpoints determine what can happen next.  Equal endpoints have the
same applicable transitions and effects at corresponding participants because
each transition is a partial function of the current specification state.  Strategies
may still choose different events.

\paragraph{Confluence of a history.}
At a consistent cut $C$, the participants may hold different specification states
$(\sigma_p(C))_{p\in P}$.  Confluence asks whether their local paths can be
brought to the same later state at every input that combines their current
inputs.
Formally, let $j$ be such a common refinement.  The history $H$ is
\emph{confluent at $C$ and $j$} when it has an extension using I/O-system input
and unrestricted output events in which every participant reaches the same
specification state
$\sigma_j=(j,R)$; equivalently, the new cut has state endpoint
$(\sigma_j)_{p\in P}$.  This is an existence claim about transitions, not a
claim that a protocol delivers $j$, communicates, or terminates.

\subsection{Distributed Consistency}
\label{sec:distributed-consistency}

Confluence is a property at one cut and common input refinement.  Distributed
Consistency requires it at every cut of every I/O history.

\begin{definition}[Distributed Consistency]
\label{def:distributed-consistency}
An ordered specification has \emph{Distributed Consistency} when, for every
finite participant set, I/O history $H$, and consistent cut $C$, $H$ is
confluent at $C$ and every common refinement of
the participants' current inputs.
\end{definition}

Distributed Consistency is the history-level reading of consistency.  The
next proposition states their exact relationship; its short proof is also why
the I/O-run formulation remains useful.

\begin{proposition}[Consistency and Distributed Consistency]
\label{prop:distributed-consistency}
An ordered specification is consistent if and only if it has Distributed
Consistency.
\end{proposition}

\begin{proof}
At any cut, the participants' transition projections are one finite set of
I/O runs, so Consistency implies their confluence.  Conversely, place any finite
set of I/O runs in a message-free history, one per participant, supplying each
input target $j$ as the cumulative arrival $a=j$.
Equation~\ref{eq:cumulative-advance} records each such step.  Distributed
Consistency at the final cut gives I/O-run confluence.
\end{proof}

Combining Proposition~\ref{prop:distributed-consistency} with Functional CALM,
a functional specification has Distributed Consistency exactly when it is
monotone.  This distributed reading does not depend on output choice.  We next
make that orthogonal extension to ambiguous specifications.

\section{Ambiguous Specifications and Lifted Monotonicity}
\label{sec:ambiguous-specifications}

A functional specification fixes one output at each input.  We now allow a
fiber to contain several outputs and ask when they can be preserved together
as input grows.  Two examples introduce the issue; the formal development then
extends the specification, monotonicity condition, and transition system from
Section~\ref{sec:functional-calm}.

\label{sec:ambiguity-story}

example-driven treatment.  Terms introduced in italics are defined formally
below, and nothing here is needed for the proofs.  Section~\ref{sec:election-story}
exercised the shared transition system; these examples exercise the additions
for ambiguous specifications: directedness, choice commitments, output
retirement, and Lifted Monotonicity.

\paragraph{Output events under choice.}
As in the functional case, $\mathsf{output}(o)$ exposes output $o$ and promises
that the final result will refine it.  The event removes every row whose output
does not refine $o$.  With several rows at one input, however, removing a row
need not lose an alternative: a retained row at the same input may refine both
$o$ and the removed output.  We call this an \emph{output retirement}.  Output
$o$ is \emph{exposable} when every row its event removes is an output
retirement.  Thus, unlike in a functional specification, an exposable output
event may remove rows while preserving what they said.

\paragraph{Ambiguity.}
Figure~\ref{fig:ambiguity-frames}(f) allows either serial order of concurrent
transactions $A$ and $B$.  No output refines both orders, so exposing one first
requires a \emph{choice commitment} that removes the other.  In the traceroute
of panel (g), by contrast, outputs are prefix-closed route sets and their
unions are within spec.  Exposing $\{s{\to}\texttt{s1}\}$ removes rows whose
outputs do not refine it, but a retained union refines each removed output;
nothing is lost, so the output is exposable.

The distinction is \emph{directedness}: every finite set of outputs in a fiber
must have a common refinement in that fiber.  A directed fiber allows any output
to be exposed without losing an alternative; a nondirected fiber may require
a choice commitment.  Lifted Monotonicity combines this requirement with the
requirement from Functional CALM that more input not invalidate an output:
every finite set of outputs within spec at $i$ must have a common refinement
within spec at every $j\succeq_I i$.

\paragraph{The commitment basis.}
The specification does not dictate which alternatives a commitment removes;
the system's commitment basis does.  In Figure~\ref{fig:cc-commitments},
two-phase locking commits only $A$ before $B$, whereas multiversion timestamp
ordering commits $B$ to first place.  Appendix~\ref{app:cc-bases} gives both
bases, including their abort commitments, and
Section~\ref{sec:design-boundary} returns to this design choice.

\subsection{Relational specifications and Lifted Monotonicity}
\label{sec:relational-specifications}

The examples pose the specification-level question: when can every finite set
of possible outputs survive together as input grows?  We first define the two
ways this can fail, then combine them in Lifted Monotonicity.

\begin{definition}[Ordered relational specification]
\label{def:relational-specification}
An \emph{ordered relational specification} is
        \begin{equation}
  \Spec=(I,\InputOrd,O,\OutputOrd,S),
  \qquad S\subseteq I\times O,
  \label{eq:relational-specification}
        \end{equation}
where $(I,\InputOrd)$ and $(O,\OutputOrd)$ are partially ordered sets.  A row
$(i,o)\in S$ says that output $o$ is within spec at input $i$.  The
\emph{fiber} of $S$, or of any $R\subseteq S$, at $i$ is the set of outputs
paired with $i$,
        \begin{equation}
  R(i)=\{o\in O:(i,o)\in R\},
  \label{eq:fiber}
        \end{equation}
and may now contain several outputs; the upper fiber of
Section~\ref{sec:canonical-transition-system} is the union of the fibers at $i$ and its
valid refinements.  The original specification has a nonempty fiber at every
input under discussion.  A functional specification is the special case
$\fiber{i}=\{f(i)\}$.
\end{definition}

The specification-state and I/O-system definitions of
Section~\ref{sec:determination} were stated for a table $S$ and apply unchanged
to relational tables.  So do Lemma~\ref{lem:run-residual}, Consistency, and
Proposition~\ref{prop:confluence}; an unrestricted output event may now select
any row in the current fiber.

The output-refinement order lifts from individual outputs to nonempty sets of
outputs.  For nonempty $A,B\subseteq O$, define
        \begin{equation}
  A\LiftedOutputOrd B
  \quad\Longleftrightarrow\quad
  \forall a\in A\;\exists b\in B:\;a\OutputOrd b.
  \label{eq:lifted-output-order}
        \end{equation}
This relation is often called the Hoare preorder.  It compares sets
pointwise: $A\LiftedOutputOrd B$ means that every output in $A$ is
refined by some output in $B$.

\begin{definition}[Relational Monotonicity]
\label{def:relational-monotonicity}
An ordered relational specification satisfies \emph{Relational Monotonicity}
when the mapping $i\mapsto\fiber{i}$ is monotone
under the pointwise lift:
        \begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  \fiber{i}\LiftedOutputOrd\fiber{j}.
  \label{eq:relational-monotonicity}
        \end{equation}
\end{definition}

For singleton fibers this is functional monotonicity,
Equation~\ref{eq:functional-monotonicity}.  In general it says that each output within spec before more input arrives has
some refinement afterward.  It does not say whether several outputs within
spec at one input can be preserved
together; Directed Outputs addresses that question.

\begin{definition}[Compatibility]
\label{def:compatibility}
Let $F\subseteq O$ be a set of outputs.  Outputs $o_1,\ldots,o_k$ are
\emph{compatible in $F$} if some $u\in F$ refines all of them,
$o_r\OutputOrd u$ for every $r$, and \emph{incompatible in $F$} otherwise.
They are \emph{compatible at input $i$} when they are compatible in the fiber
$\fiber{i}$.
\end{definition}

\begin{definition}[Directed fiber; Directed Outputs]
\label{def:fiber-directedness}
A fiber $F\subseteq O$ is \emph{directed} when every nonempty finite
$X\subseteq F$ is compatible in $F$.  An ordered relational specification has
\emph{Directed Outputs} when every fiber $\fiber{i}$ is directed.
\end{definition}

A singleton fiber is directed, and closure under a join is sufficient but not
necessary.  Directedness requires some upper bound within the fiber for each finite
set, not a least one or a fixed merge operator, so it is weaker than a
join-semilattice.  Compatibility likewise does not require comparability: two
incomparable outputs may have a third output in the fiber above both.  Thus the
traceroute fiber is directed by union, whereas the two transaction orders in
Figure~\ref{fig:ambiguity-frames}(f) are incompatible.

\paragraph{Lifted Monotonicity.}
\label{sec:complete-calm-criterion}

Relational Monotonicity preserves each output across input refinement;
Directed Outputs preserves finite choices within a fiber.  The joint lift
expresses both.  For nonempty $A,B\subseteq O$, define
        \begin{equation}
  A\JointOutputOrd B
  \;\Longleftrightarrow\;
  \text{every nonempty finite }X\subseteq A\text{ is compatible in }B,
  \label{eq:joint-output-order}
        \end{equation}
the \emph{joint lift} of $\OutputOrd$.  Unlike the Hoare preorder, it
preserves finite sets of outputs together rather than each output separately.
It is transitive, and $A\JointOutputOrd A$ holds exactly when $A$ is directed.

\begin{definition}[Lifted Monotonicity; monotone specification]
\label{def:lifted-monotonicity}
An ordered relational specification satisfies \emph{Lifted Monotonicity}, and
is called \emph{monotone}, when the mapping $i\mapsto\fiber{i}$ is monotone
under the joint lift:
        \begin{equation}
  i\InputOrd j
  \quad\Longrightarrow\quad
  \fiber{i}\JointOutputOrd\fiber{j}.
  \label{eq:lifted-monotonicity}
        \end{equation}
\end{definition}

The next proposition supplies two forms used later: form~(2) separates the
across-input and within-fiber requirements, and form~(3) matches confluence by
allowing outputs from several inputs.

\begin{proposition}[Equivalent forms of Lifted Monotonicity]
\label{prop:lifted-monotonicity-decomposition}
For an ordered relational specification, the following are equivalent:
\begin{enumerate}
  \item Lifted Monotonicity: $i\InputOrd j$ implies
        $\fiber{i}\JointOutputOrd\fiber{j}$;
  \item Relational Monotonicity and Directed Outputs;
  \item for every finite set of rows $(i_1,o_1),\ldots,(i_k,o_k)$ of $S$, at
        inputs that need not be comparable, the outputs $o_1,\ldots,o_k$ are
        compatible at every common refinement of $i_1,\ldots,i_k$.
\end{enumerate}
\end{proposition}

\begin{proof}
(1) implies (2).  Taking $j=i$, $\fiber{i}\JointOutputOrd\fiber{i}$ says that
$\fiber{i}$ is directed.  Taking $X=\{o\}$ for $o\in\fiber{i}$ and
$i\InputOrd j$ gives $u\in\fiber{j}$ with $o\OutputOrd u$, which is Relational
Monotonicity.

(2) implies (3).  Let rows $(i_r,o_r)$ have common refinement $j$.  Since
$i_r\InputOrd j$, Relational Monotonicity gives, for each $r$, a
$u_r\in\fiber{j}$ with $o_r\OutputOrd u_r$.  The $u_r$ now all lie in the one
fiber $\fiber{j}$, which is directed, so some $u\in\fiber{j}$ refines every
$u_r$, hence every $o_r$.

(3) implies (1).  Let $i\InputOrd j$ and $X\subseteq\fiber{i}$ be nonempty and
finite.  The rows $\{(i,x):x\in X\}$ have common refinement $j$, so some
$u\in\fiber{j}$ refines all of $X$; that is $\fiber{i}\JointOutputOrd\fiber{j}$.
\end{proof}

For singleton fibers this is functional monotonicity.  Form~(3) quantifies over
all finite sizes because pairwise compatibility is insufficient
(Appendix~\ref{app:additional-applications}), and over incomparable inputs
because different I/O runs meet only at a common refinement.

\subsection{The canonical system under output choice}
\label{sec:safe-exposure}

The I/O transition system needs no change: unrestricted output events already
allow any row in the current fiber, and Complete CALM will study confluence of
those I/O runs.  What changes under output choice is the canonical
factorization.  With several rows at one input, an output event may
remove covered rows without losing their claims.  We call those removals output
retirements; only uncovered removals require commitment.

\begin{definition}[Output retirement]
\label{def:output-retirement}
Let a transition from $(i,R)$ to $(i',R')$ remove $(k,x)$, where
$i'\InputOrd k$.  The removal is an \emph{output retirement} if some retained
$u\in R'(k)$ covers it, $x\OutputOrd u$.  Every removal that is neither an
input retirement nor an output retirement is removed by commitment.
\end{definition}

\begin{definition}[Exposable, under output choice]
\label{def:exposable-relational}
An output $o\in R(i)$ is \emph{exposable} at $(i,R)$ when every row that
$\mathsf{output}(o)$ removes is an output retirement.
\end{definition}

For singleton fibers no removed row is covered, so this reduces to
Definition~\ref{def:exposable}.

\begin{proposition}[Exposability]
\label{prop:exposability}
An output $o\in R(i)$ is exposable at $(i,R)$ if and only if, for every valid
$j\succeq_I i$ and $x\in R(j)$, some $u\in R(j)$ refines both:
\begin{equation}
  o\OutputOrd u
  \qquad\text{and}\qquad
  x\OutputOrd u.
  \label{eq:safe-exposure}
\end{equation}
When $o$ is exposable, $\mathsf{output}(o)$ leaves every valid input valid.
\end{proposition}

\begin{proof}
At a valid $j$, the event retains
$R'(j)=\{u\in R(j):o\OutputOrd u\}$.  A removed $x$ is retired exactly when
some $u\in R'(j)$ refines it, which is the stated test; the same witness makes
$R'(j)$ nonempty.
\end{proof}

This test marks the canonical boundary: if it fails, the system must first
use a basis commitment to remove the conflicting rows.  Section~\ref{sec:complete-calm}
combines this boundary with the distributed execution model.

\section{Complete CALM and Complete CAP}
\label{sec:complete-calm}

The previous two sections developed orthogonal extensions of Functional CALM:
Lamport histories give Consistency a distributed reading, while relational
specifications add output choice.  We now combine them.  First we identify
coordination with commitment and state when conflicting commitment courses
cannot coexist; then Complete CALM equates Consistency, Lifted Monotonicity, and
Distributed Consistency, and Complete CAP states the resulting partition
boundary.

\subsection{Coordination}
\label{sec:coordination}

Consistency is confluence: independently evolving states can still meet.
Coordination is its operational counterpart: the system makes a binding choice
that removes some otherwise possible behavior.  In our transition system, that
act is exactly a commitment.  A mutex, lock, atomic ordering mechanism, or
agreement protocol is in scope when it serves this role.  Computation or
communication that removes no such alternative is not coordination merely
because it uses one of these mechanisms.

\begin{definition}[Coordination]
\label{def:coordination}
A system execution \emph{coordinates} when it applies a commitment: it
irrevocably removes a row by commitment from the remainder table.  It is
\emph{coordination-free} when it uses only input events and exposable output
events.
\end{definition}

Hereafter, \emph{reachable} means reachable without commitment in the
canonical system.  A system
\emph{selects} an output by exposing it when exposable, and otherwise by first
applying a commitment that, at the current input and its refinements, retains
exactly the outputs refining the selected output.

In a shared-memory system, a mutex or atomic instruction can establish a
commitment by fixing an order or choice.  In a distributed system, a commitment
that conflicts with an alternative that must remain independently selectable
requires mutual exclusion before it is applied; agreement is one way to
establish that exclusion.

\begin{theorem}[Conflicting commitment courses cannot coexist]
\label{thm:commitments-require-coordination}
Suppose one participant can apply a commitment $c$ at a reachable state
$\sigma=(i,R)$, producing $(i,R')=c(\sigma)$ and removing some $x\in R(i)$ by
commitment: no output in $R'(i)$ refines $x$.  Suppose a second participant can
independently select $x$ after receiving the same input events, obtaining a
state $t$ whose fiber at $i$ contains only refinements of $x$.  Then $c(\sigma)$
and $t$ cannot be brought to a common state with current input $i$.
\end{theorem}

\begin{proof}
By hypothesis, the second participant can reach $t$, whose fiber at $i$ is
contained in $\{u\in\fiber{i}:x\OutputOrd u\}$.  The first participant's fiber
$R'(i)$ contains no such $u$.  Their fibers at $i$ are therefore disjoint, so the two states cannot be brought
to a common state whose current input is $i$.  Output events cannot restore a
removed row, and an input event cannot return to $i$.
\end{proof}

If both courses must remain independently available, a system must mutually
exclude them before either participant commits; distributed agreement is one
way to do so.  Static authority or a predetermined strategy can instead make
one course unavailable, in which case no runtime agreement follows from the
theorem.

\subsection{The Complete CALM theorem}
\label{sec:complete-calm-theorem}

Complete CALM turns the coordination boundary into a property of the
specification.  It equates Consistency---confluence of I/O runs---with Lifted
Monotonicity.  The distributed execution model supplies the equivalent third
view, Distributed Consistency.

\begin{theorem}[Complete CALM]
\label{thm:complete-calm}
For an ordered relational specification, the following are equivalent:
\begin{enumerate}
  \item Consistency;
  \item Lifted Monotonicity;
  \item Distributed Consistency.
\end{enumerate}
\end{theorem}

\begin{proof}
Items~(1) and~(3) are equivalent by
Proposition~\ref{prop:distributed-consistency}.  It remains to prove the
substantive equivalence of items~(1) and~(2).

Proposition~\ref{prop:confluence} says that Consistency means: for every
finite set of I/O runs ending at $(i_r,R_r)$ and every common refinement
$j$ of the $i_r$, some output $u\in\fiber{j}$ survives in every I/O run,
$u\in\bigcap_rR_r(j)$.  By Lemma~\ref{lem:run-residual}, this holds exactly
when $u$ refines every output exposed on those I/O runs; each such output $o$ was
exposed at some $i_o\InputOrd j$ with $o\in\fiber{i_o}$.

\emph{(2) $\Rightarrow$ (1): Lifted Monotonicity implies Consistency.}
Assume Lifted Monotonicity.  The finitely many rows $(i_o,o)$ exposed on the
I/O runs have common refinement $j$, so
Proposition~\ref{prop:lifted-monotonicity-decomposition}(3) supplies
$u\in\fiber{j}$ refining them all.  Thus $u$ survives every I/O run.

\emph{(1) $\Rightarrow$ (2): Consistency implies Lifted Monotonicity.}
Let rows $(i_1,o_1),\ldots,(i_k,o_k)$ have a common refinement $j$.  For each
$r$, start an I/O run at $\sigma_0(i_r)$ and expose $o_r$; then
$R_r(j)=\{u\in\fiber{j}:o_r\OutputOrd u\}$.  Consistency supplies an output
$u$ that survives every I/O run, so it refines every $o_r$.  This is form~(3) of
Proposition~\ref{prop:lifted-monotonicity-decomposition}, hence Lifted
Monotonicity.

\end{proof}



The theorem gives a specification-level test for history confluence and closes
the operational loop.  Exposability follows rather than being assumed.  In a
consistent specification, every $o\in R(i)$ is exposable at every reachable
$(i,R)$: for
valid $j\succeq_I i$ and $x\in R(j)$, confluence of the I/O run extended by
$\mathsf{output}(o)$ with the I/O run extended by $\mathsf{input}(j)$ and
$\mathsf{output}(x)$ supplies $u\in R(j)$ above both outputs; then
Proposition~\ref{prop:exposability} applies.  Thus Lifted Monotonicity makes all
reachable outputs exposable, so progress needs no commitment and is
coordination-free.  Its failure exhibits a finite family without a common
refinement, so selecting an offending output requires a commitment and hence
coordination.  When different participants must retain independently
selectable conflicting alternatives,
Theorem~\ref{thm:commitments-require-coordination} shows that their courses
must be mutually excluded; distributed agreement is one mechanism for doing so.

\subsection{The Complete CAP Theorem}
\label{sec:cap-corollary}

The coordination boundary becomes an availability boundary during a
partition: participants in different components cannot establish a new shared
commitment.  A \emph{partitioned history} divides participants into two or more
components and has no cross-component message receive while the partition
lasts, though participants may still receive environment input and expose
outputs.  At a cut, \emph{Availability} means that every output in a
participant's current fiber is exposable without a cross-component wait.  The
history has \emph{Partition Consistency} when its commitment-free participant
projections, viewed as I/O runs, are confluent at every common refinement of
their current inputs.

\begin{theorem}[Complete CAP]
\label{thm:complete-cap}
For an ordered relational specification $\Spec$, the following are equivalent:
\begin{enumerate}
  \item every consistent cut of every commitment-free canonical partitioned
        history has Availability and Partition Consistency;
  \item $\Spec$ satisfies Lifted Monotonicity.
\end{enumerate}
\end{theorem}

\begin{proof}
Suppose first that $\Spec$ satisfies Lifted Monotonicity.  Every output at every
commitment-free canonical state is exposable by the consequence of Complete
CALM above, giving Availability.  Each participant projection is also an I/O
run, so Complete CALM gives their confluence and hence Partition Consistency.

Conversely, let any finite rows $(i_r,o_r)$ have a common refinement $j$.
Place their participants in separate partition components.  If there is only
one row, add a second participant initialized at $j$ and make no selection
there.  Availability lets each original participant expose $o_r$ from
$\sigma_0(i_r)$ without a commitment.  Partition Consistency then supplies a
row $(j,u)$ surviving in every remainder table, so
$o_r\OutputOrd u$ for every $r$.  Form~(3) of
Proposition~\ref{prop:lifted-monotonicity-decomposition} gives Lifted
Monotonicity.
\end{proof}

Partition Consistency requires outputs from different components to be jointly
refinable, not identical or totally ordered; this is why the characterization
is bidirectional.  When Lifted Monotonicity fails, some permitted output either
cannot be exposed without first establishing a commitment, sacrificing
Availability, or can be selected through the unrestricted I/O view only at the
cost of Partition Consistency.

A linearizable register is the classical instance of the tradeoff side: two
reads of concurrent writes may be explained by opposite serial orders, no
total order refines both, and the theorem withholds availability under
partition.  Whether a commitment requires agreement across a partition also
depends on which participant may hold which input and make which choice;
Appendix~\ref{app:deployment} refines the theorem by such a \emph{deployment}
and shows that a causal register, though it fails Lifted Monotonicity without
deployment restrictions, needs no coordination
when each participant answers only its own reads.  With the central results
in place, we now compare their consequences across the surrounding
literature.

\subsection{Query monotonicity}
\label{sec:query-instance}

Section~\ref{sec:functional-calm} gave the functional encoding
$J\mapsto Q(J)$.  Relational-transducer CALM proves the operational result for
that language: monotone queries allow coordination-free evaluation under its
data-placement and execution assumptions
~\cite{ameloot2013relational,ameloot2015weaker}.  Functional CALM does not replace
that theorem.  It isolates the order-preservation property so that it
can be compared with interfaces outside Datalog.

Why did earlier CALM results not state Directed Outputs separately?  Their
query specification is functional: each input $J$ has one result
$Q(J)$, so each output fiber is a singleton and directed automatically.
CRDTs also present a functional state for a fixed set of incorporated
updates; semilattice join additionally provides least common refinements across
partial inputs.  Complete CALM makes multiple outputs at one input explicit,
so directedness can no longer be assumed.

\subsection{CRDTs: from convergent state to safe observations}
\label{sec:crdt-instance}

  A CRDT answers one important question: if replicas receive the same updates,
will they converge to equivalent states despite differences in update delivery
and merge order?  Applications immediately ask a second question: what may a
client safely conclude from one replica's current state?  The CRDT merge theorem does not answer this second
question.  Keep CALM and CRDT On called out this gap and proposed monotonicity as
the test for safe queries~\cite{laddad2022keep}.  Functional CALM makes that
test precise for the whole client-visible interface.

Let $(D,\sqsubseteq,\sqcup)$ be the state join-semilattice, and let the input
be the finite set $U$ of immutable, joinable payloads received so far, ordered
by inclusion.  The replica's state is
        \begin{equation}
  s(U)=s_0\sqcup\bigsqcup U,
  \label{eq:crdt-state-function}
        \end{equation}
so $U\subseteq V$ implies $s(U)\sqsubseteq s(V)$, and
$s(U_1)\sqcup s(U_2)=s(U_1\cup U_2)$: the state interface is monotone, and
join is the least state refining both inputs~\cite{shapiro2011crdt}.  A
client observation $q:(D,\sqsubseteq)\to(R,\preceq_R)$ replaces the state
output with a new promise, and by Functional CALM the client-visible interface
$q\circ s$ is consistent exactly when
        \begin{equation}
  U\subseteq V \quad\Longrightarrow\quad q(s(U))\preceq_R q(s(V)).
  \label{eq:crdt-query-monotonicity}
        \end{equation}
Monotonicity of $q$ on all of $D$ is sufficient but not required; $q$ need
only preserve refinements between reachable states.  Operation-based CRDTs have the same form.  Their payloads
are operations delivered in causal order, and the set of operations a replica
has received, closed under causal predecessors, grows by union; the causal
order, once made explicit in the payload, is the state lattice, and the
replica's state is a function of that set.  This is the emulation of
operation-based by state-based CRDTs in the original CRDT
paper~\cite{shapiro2011crdt}, the operation-context semantics of replicated
data types~\cite{burckhardt2014replicated}, and the partially ordered log of
pure operation-based CRDTs~\cite{baquero2014operation}; see
also~\cite{hellerstein2025turtles}.

\paragraph{A safe merge can have an unsafe observation.}
Consider a two-phase set with state $(A,R)$: $A$ records additions and $R$
records removals.  Both components grow by union, so replica state merges
perfectly well.  Its user-facing query is
        \begin{equation}
  q_{\mathrm{2P}}(A,R)=A\setminus R,
  \qquad F_{\mathrm{2P}}=q_{\mathrm{2P}}\circ s.
  \label{eq:crdt-2p-query}
        \end{equation}
Suppose the payload set $U_0$ yields
\[
  s(U_0)=(\{\mathsf{potato},\mathsf{Ferrari}\},\varnothing),
  \qquad
  (q_{\mathrm{2P}}\circ s)(U_0)
    =\{\mathsf{potato},\mathsf{Ferrari}\}.
\]
If the application treats membership in this result as a lasting claim, it may
ship the Ferrari.  Now let $U_1$ add a delayed payload removing the Ferrari.
Then $U_0\subseteq U_1$, but
\[
  s(U_1)=(\{\mathsf{potato},\mathsf{Ferrari}\},\{\mathsf{Ferrari}\}),
  \qquad
  (q_{\mathrm{2P}}\circ s)(U_1)=\{\mathsf{potato}\}.
\]
The internal state advanced, but the client-visible claim did not.  An ordinary
point-in-time read may merely expose its chosen local cut.  The bug appears when
the program interprets that answer as complete, stable, or sufficient to justify
an irreversible action.  Such a promise needs a seal on the relevant updates.
State convergence does not establish monotonicity of an application query.

\paragraph{Threshold queries.}
Kuper and Newton's LVars introduced \emph{threshold queries}: Boolean-valued
application queries that become true when a lattice state crosses a threshold
~\cite{kuper2013lvars}.  Order the Boolean codomain by
$\mathsf{false}\preceq_B\mathsf{true}$.  For example, let a grow-only set $d$
record distinct failed login attempts and define
        \begin{equation}
  q_{100}(d)=[\,|d|\geq100\,],
  \qquad Q_{100}=q_{100}\circ s.
  \label{eq:crdt-thresholds}
        \end{equation}
Once $Q_{100}(U)=\mathsf{true}$, every refinement $V\supseteq U$ still
contains at least 100 attempts, so $Q_{100}(V)=\mathsf{true}$, and before the
threshold $\mathsf{false}$ is exposable because it may refine to
$\mathsf{true}$.  The query is monotone, so Functional CALM says that it
extracts a stable fact from an incomplete replica state without claiming that
the state itself is complete.

\paragraph{Beyond least merges.}
A join-semilattice provides a uniform \emph{least} refinement and a fixed merge
operator.  Complete CALM asks only for \emph{some} common refinement of
each relevant finite family.  For example, suppose two shards expose
$[a_1,a_2]$ and $[b_1,b_2]$, and the output fiber contains every order-preserving
interleaving.  Both
        \begin{equation}
  [a_1,a_2,b_1,b_2]\qquad\text{and}\qquad[b_1,b_2,a_1,a_2]
  \label{eq:log-interleavings}
        \end{equation}
are minimal common refinements, and neither refines the other.  Consequently,
the pair has no least common refinement, so this output order is not a
join-semilattice.  It is nevertheless directed: any finite family of sequences
has an order-preserving interleaving in the fiber.  A join-semilattice is
therefore a sufficient discipline, not a requirement of Lifted
Monotonicity; strong eventual consistency, which it provides, is a stronger
promise than consistency in our sense, and last-writer-wins shows that
convergence can also be weaker, discarding one concurrent value that an
interface promised to preserve.

\subsection{Highly available transactions}
\label{sec:hat-instance}

For a transactional interface, an input is the set of begin, read, write, and
commit requests received so far, ordered by inclusion.  An output is a growing
set of public facts such as $\mathsf{read}(T,x,v)$,
$\mathsf{commit}(T)$, and session-order facts, also ordered by inclusion.  The
isolation or session guarantee determines which fact sets are within spec.
A deployment assigns transactions and requests to replicas.  The Complete
CAP Theorem tests the combinations those replicas can select across a partition,
under the contact, failure, and session assumptions of the interface
~\cite{bailis2013hat,terry1994session}.

\paragraph{Accumulating facts.}
Suppose two replicas execute transactions on disjoint keys.  One exposes
$\mathsf{read}(T_1,x,0)$ and $\mathsf{commit}(T_1)$; the other exposes
$\mathsf{read}(T_2,y,0)$ and $\mathsf{commit}(T_2)$.  If each read observes a
committed version at its replica, the union contains no dirty read or write
conflict.  Under the stated read-committed interface, later delivery preserves
all four facts.  This is the positive accumulation pattern behind HAT results;
it is not a claim that every combination of session guarantees is available.

\paragraph{Serializability and transaction ordering.}
The ordering issue becomes a distributed obstruction when exposed reads force
opposite serialization orders.  Initially $x=y=0$.  On one side, $T_1$ reads
$x=0$, writes $y=1$, and commits.
On the other, $T_2$ reads $y=0$, writes $x=1$, and commits.  Preserving $T_1$'s
read requires $T_1$ before $T_2$ in any serial explanation; preserving $T_2$'s
read requires $T_2$ before $T_1$.  The serialization graph contains a cycle, so
no serial history refines both sets of facts~\cite{adya2000generalized}.

\paragraph{Snapshot isolation.}
Let overlapping transactions $T_1$ and $T_2$ read the same snapshot and both
write $x$.  Separate replicas could each expose its local commit.  Snapshot
isolation's first-committer-wins rule allows no output containing both commit
facts~\cite{berenson1995critique,bailis2013hat}.  Eventual storage convergence
may choose a final state; it cannot retract a commit already exposed to a
client.

Convergent storage does not automatically provide a highly available
transactional interface.  Storage convergence constrains states after update delivery;
isolation constrains reads and commits exposed before then.

\subsection{Invariant confluence}
\label{sec:iconfluence-instance}

Let the input be a set of applied transactions, ordered by inclusion.  We use
the standard invariant-confluence assumptions: each transaction remains
applicable where the specification allows it and maps an invariant-valid state
to another invariant-valid state; independently reached states share the
required ancestor; the prescribed merge is associative and preserves all
included effects; and merged states remain reachable.  Outputs are reachable,
invariant-valid states.  We order outputs by merge refinement: $s\OutputOrd s'$
when $s'$ is a merge within spec that preserves every effect in $s$ (quotienting
states with identical effects if necessary to obtain a partial order).

Invariant confluence asks whether independently reachable valid states merge to
a valid state~\cite{bailis2014coordination}.  Under the assumptions above,
individual transaction preservation supplies Relational Monotonicity, while
invariant confluence supplies common refinements for independently reached
states at the combined transaction input.  Associativity and reachability let
the pairwise merge argument extend inductively to finite families.  Thus the
prescribed merge witnesses Lifted Monotonicity, in the form of
Proposition~\ref{prop:lifted-monotonicity-decomposition}(3), for the deployed
transaction families.

A uniqueness constraint supplies the standard counterexample.  Two replicas
each observe that username \texttt{sam} is free and allocate it to different
accounts.  Each local state satisfies uniqueness, but no invariant-valid common
refinement preserves both allocations.  The system must reserve names, reject
one allocation, or weaken the invariant.

State convergence, transaction availability, and invariant preservation test
three different specifications.  A convergent merge may produce an invalid
state; an available transaction may expose facts that later violate an
invariant; an invariant-confluent application need not provide a particular
isolation level.  The shared model makes these distinctions explicit rather
than collapsing the properties.  We close by drawing out the resulting design
lessons and scope limits.

\section{Discussion}
\label{sec:discussion}

\subsection{Output choice versus operational nondeterminism}

Output choice in Complete CALM concerns the declared interface, not whether
executions are deterministic.  CALM and CRDTs already account for operational nondeterminism in message delivery, batching, retries, and
merge order.  Their usual declared outputs are fixed for a given input.  Complete CALM
adds specifications whose declared interface itself offers several outputs and
models the commitments that resolve them.

\subsection{A criterion on specifications, not an implementation discipline}

Coordination names a specification-level effect, not a particular mechanism.
A lock, mutex, transaction protocol, or agreement protocol coordinates here
only when it applies a commitment; synchronization that removes no row does
not.  The input/output relation and its two refinement orders omit internal
computation.  This is useful for stating a common boundary and insufficient for
building a system.  Relational transducers provide a language and operational
network semantics; semilattices provide a local algebra and deterministic
merge; transaction protocols provide scheduling, validation, and recovery.
Neither Functional CALM nor Complete CALM says how to represent $S$, choose the
refinement orders, compute a common refinement, or do so efficiently.  Those
questions belong to the programming language, protocol, and verification
method used to realize the specification.

\subsection{Specification design determines the boundary}
\label{sec:design-boundary}

Lifted Monotonicity is a property of the declared specification, not a
permanent label on ``register,'' ``transaction,'' or ``shopping cart.''
The deployment determines whether a commitment requires agreement between
participants.
A linearizable register and a causal register allow different explanations.  A
CRDT state and an exact read expose different promises.  A database permitted
to abort one transaction implements a different relation from one required to
commit both.

Narrowing $S$ may eliminate an incompatibility.  Broadening $O$ with a new
output that refines two alternatives may also eliminate it.  Changing the
deployment may keep an incompatibility under one participant's authority.  Each option
changes the interface or system design; none is a loophole in the criterion.

The transition projection is also a design criterion.  Choosing the input
domain and its order decides which histories the specification treats as the
same: two cuts yield one specification state exactly when they reach the same input and
have removed the same rows.  A finer input order forgets less of the execution
and obliges the specification to say more; a coarser one forgets more.  The
specification then states its possible outcomes over specification states without
re-encoding the history it was built to forget.

A reader who thinks in state machines can compile one into this form.  At the
finest grain, an input is the sequence of environment events the machine has
consumed, ordered by extension, and a row $(i,o)$ is within spec when some run
of the machine on $i$ produces $o$; the register example of
Appendix~\ref{app:deployment} is of this kind.  If the machine's state
summarizes its past, so that two event sequences reaching the same state have
the same futures, the states themselves may serve as inputs, ordered by
reachability, provided that order is antisymmetric.  That is the coarsening the
proposition licenses, and the election of Section~\ref{sec:election-story} is the
result for a vote-counting machine whose state is the set of ballots received.

\subsection{Consistency as confluence}
\label{sec:consistency-as-confluence}

The word consistency names two levels in the literature, and the framework
connects them.  A consistency model---linearizability, causal consistency,
snapshot isolation, read committed---is encoded as a specification: it says
which outputs are allowed for a given history of operations.  Consistency in
our cross-cutting sense is confluence of that specification's executions.  The
same definition also applies when the table instead captures an
application-specific requirement, such as an invariant.  Written as a table
with orders, each declared model or requirement therefore falls on one side of
the confluence boundary.  Linearizability and serializability
allow total orders that cannot refine two concurrent explanations, so they
are not monotone (Appendix~\ref{app:deployment},
Section~\ref{sec:hat-instance}).  Causal consistency allows one explanation
for concurrent reads and is monotone under the deployment in which each
participant answers its own reads (Appendix~\ref{app:deployment}).  Read
committed and the other HAT guarantees accumulate facts and are monotone
(Section~\ref{sec:hat-instance}).  Strong eventual consistency asks more
than confluence, a least common refinement that every replica reaches, and
last-writer-wins eventual consistency asks less, converging by discarding
content (Section~\ref{sec:crdt-instance}).  What the traditional definitions
leave implicit, and the framework requires, is the output order: the same
operation history yields a monotone or a non-monotone specification depending
on what an exposed read is taken to promise
(Section~\ref{sec:design-boundary}).  Confluence therefore does not replace the
declared consistency model or application requirement; it supplies a common
test of whether that requirement can be maintained without coordination.

\subsection{Safety is not liveness}

The theorems identify when exposed outputs remain refinement-consistent; they
do not guarantee message delivery, termination, or computability of a common
refinement.  Complete CAP's Availability predicate requires each permitted
output to be immediately exposable without a cross-component wait; it is a
semantic nonblocking condition, not a full liveness model.  A protocol result
must still state appropriate fairness, failure, and cost assumptions.

\section{Related Work}
\label{sec:related}

The CALM conjecture connected logical monotonicity with coordination
freedom~\cite{hellerstein2010declarative,hellerstein2020keeping}, and Ameloot
et al.\ proved it for relational transducers, studying how data placement and
system knowledge change coordination
requirements~\cite{ameloot2013relational,ameloot2015weaker};
Sections~\ref{sec:functional-calm-theorem} and~\ref{sec:query-instance}
relate Functional CALM to that result.  Brewer's conjecture and the
Gilbert--Lynch theorem~\cite{brewer2000towards,gilbert2002cap} are taken up in
Section~\ref{sec:cap-corollary} and Appendix~\ref{app:deployment}.  CRDTs
derive strong eventual consistency from state or operation
algebras~\cite{shapiro2011crdt}, and Keep CALM and CRDT On first proposed
monotonicity as the criterion for safe observations of a
replica~\cite{laddad2022keep}; Section~\ref{sec:crdt-instance} places both in
the model.  Work on consistency semantics likewise distinguishes visibility,
ordering, availability, and
convergence~\cite{burckhardt2014principles,mahajan2011consistency}.
Highly available transactions~\cite{bailis2013hat} and invariant
confluence~\cite{bailis2014coordination} are Sections~\ref{sec:hat-instance}
and~\ref{sec:iconfluence-instance}.

\section{Conclusion}
\label{sec:conclusion}

A specification abstracts execution details away.  Functional CALM asks when
a functional specification remains confluent as input arrives: monotonicity
means no input-sealing commitment is needed.  This generalizes the classic
result from logical fact sets to arbitrary input and output refinement orders.

Complete CALM extends the model to specifications that offer several outputs
for one input.  Modeling output events and commitments reveals Directed Outputs
as the additional requirement for confluence without coordination.  When
Lifted Monotonicity fails, progress requires a commitment and hence
coordination, whether implemented by a mutex, lock, atomic ordering mechanism,
or distributed agreement.  Unlike classical CALM, the model can then verify
whether that coordination is proper: sequential and independently parameterized
composition preserve Lifted Monotonicity, so a coordinating layer that exports
a monotone interface composes consistently with monotone downstream components.
A log authority followed by commitment-free register or key-value-store
evaluation is the basic example; MultiConsensus distributes the authority
without changing the exported interface.  Distributed histories and Complete
CAP specialize the same boundary to participants and partitions.

The Complete CAP Theorem is the partition form of the same equivalence.  It recovers the
classical impossibility when a cut separates incompatible choices and supplies
the positive side when all separated choices have common refinements.  A cut
may prevent agreement on input sealing or separate participants empowered to
make incompatible output choices.  Query monotonicity, CRDT merge,
transactional availability, and invariant confluence then become directly comparable without being identified
with one another.

\appendix
\section{Composition and Proper Coordination}
\label{app:composition}

Specifications rarely stand alone: the output of one component becomes input
to another, and independently configured components may each contribute input
to a pipeline.  This section shows that Lifted Monotonicity is preserved by
both forms of composition.  It then uses that fact to define \emph{Proper
Coordination}: coordination has done its job when its commitments leave a
monotone interface that subsequent components can execute without further
commitment.

\subsection{Sequential composition}

Let
\[
  \Spec_1=(I,\InputOrd,M,\preceq_M,S_1)
  \quad\text{and}\quad
  \Spec_2=(M,\preceq_M,O,\OutputOrd,S_2)
\]
be ordered relational specifications with the same ordered middle domain.  This
is a type constraint on both the carrier $M$ and its order $\preceq_M$: the
output type of $\Spec_1$ is exactly the input type of $\Spec_2$.  Their
\emph{sequential composition} is the projection of their equijoin on $M$,
\begin{equation}
  S_2\circ S_1
  =\pi_{I,O}(S_1\Join_M S_2)
  =\{(i,o):\exists m.\ (i,m)\in S_1\land(m,o)\in S_2\}.
  \label{eq:spec-composition}
\end{equation}
We restrict the composed input domain to inputs with a nonempty fiber, as for
all specifications in this paper.

\begin{lemma}[Composition]
\label{lem:composition}
If $\Spec_1$ and $\Spec_2$ satisfy Lifted Monotonicity, then the ordered
specification with table $S_2\circ S_1$ satisfies Lifted Monotonicity.
\end{lemma}

\begin{proof}
Use form~(3) of Proposition~\ref{prop:lifted-monotonicity-decomposition}.
Take finitely many rows $(i_r,o_r)$ of $S_2\circ S_1$ whose inputs have a
common refinement $j$.  For each row choose a join witness $m_r$ such that
$(i_r,m_r)\in S_1$ and $(m_r,o_r)\in S_2$.  Lifted Monotonicity of $\Spec_1$
supplies $m\in S_1(j)$ refining every $m_r$.  Thus $m$ is a common refinement
of the inputs of the rows $(m_r,o_r)$ in $S_2$.  Lifted Monotonicity of
$\Spec_2$ supplies $u\in S_2(m)$ refining every $o_r$.  The witness $m$ puts
$(j,u)$ in $S_2\circ S_1$, which is the required common refinement.
\end{proof}

Relational composition is associative, so Lemma~\ref{lem:composition} extends
inductively to any finite pipeline.  Functional composition is its
singleton-fiber case.

\begin{corollary}[Functional composition]
\label{cor:functional-composition}
If $f:(I,\InputOrd)\to(M,\preceq_M)$ and
$g:(M,\preceq_M)\to(O,\OutputOrd)$ are monotone, then
$(g\circ f)(i)=g(f(i))$ is monotone.
\end{corollary}

\begin{proof}
The graph tables of $f$ and $g$ satisfy Lifted Monotonicity, and their
composition is the graph table of $g\circ f$.  Apply
Lemma~\ref{lem:composition}.
\end{proof}

\subsection{Composition with independent inputs}

Two components may also have separate configuration or environment inputs.  Let
\begin{align*}
  \Spec_F&=\bigl(I\times A,\preceq_I\times\preceq_A,
                  B,\preceq_B,F\bigr),\\
  \Spec_G&=\bigl(J\times B,\preceq_J\times\preceq_B,
                  C,\preceq_C,G\bigr)
\end{align*}
be ordered relational specifications, with tables
$F(I,A,B)\subseteq(I\times A)\times B$ and
$G(J,B,C)\subseteq(J\times B)\times C$.  The type boundary is the ordered domain
$(B,\preceq_B)$: it is both the output type of $\Spec_F$ and the second input
type of $\Spec_G$, with the same carrier and the same refinement order.  The
shared order is what lets a refinement produced by $\Spec_F$ serve as an input
refinement to $\Spec_G$.

Their \emph{independently parameterized composition} is the global query plan
\begin{align}
  G\star F
  &=\pi_{I,J,A,C}\bigl(F\Join_{B}G\bigr) \notag\\
  &=\{((i,j,a),c):\exists b.\ ((i,a),b)\in F
                         \land ((j,b),c)\in G\},
  \label{eq:parameterized-composition}
\end{align}
with the product order on $I\times J\times A$.  As elsewhere, we retain only
composed inputs with a nonempty output fiber.

The same query can be planned in curried form.  For fixed parameter values,
let
\begin{equation}
  F_i=\pi_{A,B}(\sigma_{I=i}F),
  \qquad
  G_j=\pi_{B,C}(\sigma_{J=j}G).
  \label{eq:curried-fibers}
\end{equation}
The curried plan first forms the cross-product of parameter inputs $I\times J$,
then equijoins the corresponding component fibers on their ordered $B$ column.

\begin{proposition}[Curried equijoin plan]
\label{prop:curried-query-plan}
The global plan in Equation~\ref{eq:parameterized-composition} equals
\begin{equation}
  \bigcup_{(i,j)\in I\times J}
  \left\{((i,j,a),c):
    (a,c)\in\pi_{A,C}\bigl(F_i\Join_B G_j\bigr)\right\}.
  \label{eq:curried-query-plan}
\end{equation}
\end{proposition}

\begin{proof}
A row $((i,j,a),c)$ is produced by the global plan exactly when some $b$
satisfies $(i,a,b)\in F$ and $(j,b,c)\in G$.  By
Equation~\ref{eq:curried-fibers}, these two conditions are equivalent to
$(a,b)\in F_i$ and $(b,c)\in G_j$.  That is exactly the condition that
$(a,c)$ appear in $\pi_{A,C}(F_i\Join_B G_j)$ for the pair $(i,j)$ selected
from $I\times J$.  Thus each plan contains exactly the same rows.
\end{proof}

\begin{lemma}[Independently parameterized composition]
\label{lem:parameterized-composition}
If $\Spec_F$ and $\Spec_G$ satisfy Lifted Monotonicity, then the specification
with table $G\star F$ satisfies Lifted Monotonicity.
\end{lemma}

\begin{proof}
Take finitely many rows $((i_r,j_r,a_r),c_r)$ with common input refinement
$(i,j,a)$, and choose witnesses $b_r$ from
Equation~\ref{eq:parameterized-composition}.  Applied at the common refinement
$(i,a)$, Lifted Monotonicity of $\Spec_F$ supplies $b\in F(i,a)$ refining every
$b_r$.  The inputs $(j_r,b_r)$ of the corresponding rows in $G$ therefore
have common refinement $(j,b)$.  Lifted Monotonicity of $\Spec_G$ supplies
$c\in G(j,b)$ refining every $c_r$.  Hence $((i,j,a),c)$ is a row of
$G\star F$ and is their required common refinement.
\end{proof}

For monotone functions
\begin{align*}
  f&:(I,\preceq_I)\times(A,\preceq_A)\to(B,\preceq_B),\\
  g&:(J,\preceq_J)\times(B,\preceq_B)\to(C,\preceq_C),
\end{align*}
the graph-table instance gives the monotone function
\begin{equation}
  h(i,j,a)=g\bigl(j,f(i,a)\bigr).
  \label{eq:curried-composition}
\end{equation}
Equivalently, curry the components as
\begin{align*}
  f^\sharp&:(I,\preceq_I)
       \to\bigl((A,\preceq_A)\to(B,\preceq_B)\bigr),\\
  g^\sharp&:(J,\preceq_J)
       \to\bigl((B,\preceq_B)\to(C,\preceq_C)\bigr),
\end{align*}
with pointwise orders on the function spaces.  Then
$h^\sharp(i,j)(a)=g^\sharp(j)(f^\sharp(i)(a))$.  Proposition~\ref{prop:curried-query-plan}
shows that this curried rewrite is precisely the relational plan that takes the
cross-product of parameter inputs and equijoins the selected graph fibers on
the typed $B$ column.  Thus monotone components remain monotone when wired
together even when each has its own input.

\subsection{Proper Coordination}

Classical CALM can classify a specification as monotone or non-monotone, but it
cannot represent the commitments made by a coordination mechanism.  The
canonical transition system can, which permits a second question: after
coordination acts, has it removed enough alternatives that the remainder of the
system needs no more coordination?

Suppose a coordination layer applies commitments to a source specification and
exports an ordered relational specification $\Spec_C$.  Its internal
commitments may repeatedly remove alternatives; $\Spec_C$ records only the
interface it presents to downstream components.  For a downstream specification
$\Spec_T$, call the layer \emph{proper coordination for $\Spec_T$} when their
sequential or independently parameterized composition is consistent and its
downstream canonical execution requires no further commitment.

\begin{theorem}[Proper Coordination]
\label{thm:proper-coordination}
If the exported specification $\Spec_C$ and downstream specification
$\Spec_T$ satisfy Lifted Monotonicity, then the coordination layer is proper
for $\Spec_T$, under either sequential or independently parameterized
composition.
\end{theorem}

\begin{proof}
Lemma~\ref{lem:composition} or
Lemma~\ref{lem:parameterized-composition}, respectively, gives Lifted
Monotonicity of the composed specification, so Complete CALM gives Consistency.
The exposability consequence following Theorem~\ref{thm:complete-calm} then
makes every output at every commitment-free reachable state exposable.  The
downstream canonical execution therefore needs no further commitment.
\end{proof}

The result is asymmetric.  The coordination layer's commitments remove rows
from its source specification, so they are non-monotone acts.  Those acts can
nevertheless produce a monotone exported interface.  In this precise sense,
more non-monotonicity can make a non-monotone specification coordination-free
\emph{downstream}; it does not make the original commitments disappear.

\paragraph{A log authority followed by a register or key-value store.}
A single authority node suffices to illustrate the construction.  It receives
command proposals, its prior commitment actions, and their results; this local
history is ordered by prefix.  Its exported output is the committed log, also
ordered by prefix.  Each
commitment may be non-monotone over the still-possible next commands, but every
published log extends the preceding one.  The exported log interface is
therefore monotone.

A deterministic register or key-value-store state machine has its own fixed
configuration input, given the equality order, and consumes the committed log.
Its output is the cumulative execution and response history, ordered by prefix
rather than merely the current mutable value.  Extending the log extends this
history without changing an earlier response, while the equality order permits
no configuration change, so the evaluator is monotone in its product input.
This is the independently parameterized construction of
Lemma~\ref{lem:parameterized-composition}: the authority history and store
configuration are independent inputs, joined through the committed log.  By
Theorem~\ref{thm:proper-coordination}, the composed interface is consistent and
the state-machine evaluation requires no commitment of its own.

Coordination has not vanished: the authority performs it whenever it chooses
the next log entry.  The theorem verifies that this coordination is
\emph{proper}: it localizes every choice to log construction and leaves
downstream evaluation commitment-free.  MultiConsensus replaces the single
authority with distributed agreement on the same growing log.  Because it
exports the same monotone committed-prefix interface, the composition argument
is unchanged; only the implementation of the authority becomes distributed
~\cite{lamport2001paxos}.

\section{Complete CAP under a Deployment}
\label{app:deployment}

Theorem~\ref{thm:complete-cap} (Complete CAP) quantifies over all participants
and inputs.  Whether a commitment is necessary is a question about the specification; whether
it requires agreement across a partition also depends on \emph{deployment}:
which participant may hold which input and select which row.  A participant
that controls an entire choice may make the commitment locally.  This appendix
refines the theorem accordingly.

Return to leader election, with \texttt{server1} and \texttt{server2} both
eligible.  If one participant alone is entitled to name the leader, a
partition changes nothing: the two rows are an incompatible family, but both
belong to that participant, and it selects between them without consulting
anyone.  If instead one participant may name \texttt{server1} and another may
name \texttt{server2}, a partition that separates them lets each select its
row alone, and the two selections have no common refinement when the partition
heals.  The same specification is safe under the first deployment and not
under the second; what differs is which incompatible families a partition can
split between its sides.

\begin{definition}[Deployment; separable course]
\label{def:deployment}
A \emph{deployment} over a participant set $P$ assigns to each participant $p$
a set $A_p\subseteq S$ of rows it may select; $(i,o)\in A_p$ means
that $p$ may hold $i$ as a current input and select $o$ there, on its own
authority.  A partition $\Pi$ of $P$ (Section~\ref{sec:cap-corollary}) divides
the participants into two or more nonempty components.

A finite \emph{course} assigns to each of finitely many participants $p$ an
initial input and an I/O run whose selected rows all lie in $A_p$; the run may
make no selection.  It is \emph{separable under $\Pi$} when either its selected
rows occur in at least two components, or it has exactly one selected row and a
silent participant in another component.  The second case tests whether that
one output survives at the silent participant's current input.
\end{definition}

\begin{definition}[Monotone across partitions]
\label{def:monotone-across-partitions}
Relative to a deployment, $\Spec$ is \emph{monotone across $\Pi$} when, for
every course separable under $\Pi$ and every common refinement $j$ of its
participants' current inputs, the outputs in all selected rows have a common
refinement in $\fiber{j}$.  It is
\emph{monotone across partitions} when it is monotone across every partition of
$P$.
\end{definition}

This is the common-refinement condition of
Proposition~\ref{prop:lifted-monotonicity-decomposition}(3), restricted to
courses a partition can separate.  Monotonicity implies monotonicity across
partitions, since the selected rows of a course form a finite family.  The
converse fails whenever every incompatible family of two or more selections is
confined to one participant's authority.  Two mutually exclusive choices owned
by one participant do not become separable merely because a silent participant
exists in another component: the silent-participant exception applies only to
a single selected row.

\begin{theorem}[Complete CAP under a deployment]
\label{thm:complete-cap-deployment}
Fix a deployment.  The following are equivalent.
\begin{enumerate}
  \item Under every partition $\Pi$ and every order of input arrival within
        each component, the participant I/O runs of every course separable under
        $\Pi$ are confluent at every common refinement $j$ of their current
        inputs: some row at $j$ survives in every remainder table.
  \item $\Spec$ is monotone across partitions.
\end{enumerate}
\end{theorem}

\begin{proof}
(2$\Rightarrow$1.)  Fix $\Pi$ and any separable course.  All rows selected on
participant $p$'s I/O run lie in $A_p$ by definition.  Monotonicity across
$\Pi$ supplies $u\in\fiber{j}$ above every selected output.  Each participant's
fiber at $j$ is $\fiber{j}$ intersected with the outputs above its own
selections, and $u$ belongs to every such set.  Hence some row at $j$ survives
in every state, under every arrival order in each component.

(1$\Rightarrow$2.)  If monotonicity across some $\Pi$ fails, a separable course
and a common refinement $j$ have no output in $\fiber{j}$ above all its selected
rows.  Use the I/O runs assigned by the course; every selected row belongs to
its participant's $A_p$.  Each participant's fiber at $j$ then contains only
outputs above all of its own selections, and no output of $\fiber{j}$ is above
all selections in the course, so no row at $j$ survives in every state.
Avoiding this requires either a wait across the cut or refusing some authorized
row, which implements a narrower deployment or specification.
\end{proof}

The theorem concerns cross-component I/O courses; it does not claim that an
arbitrary commitment within one component preserves confluence with other
components.  Courses whose two or more selections are contained wholly in one
component create no cross-component condition.  If a local commitment affects
rows another component may select, its cross-component consequences must
themselves satisfy the theorem's condition.  Only courses that a partition
separates are tested.
When the deployment lets every participant hold every
row, every family is separable under some partition, monotonicity across
partitions is monotonicity, and the theorem is Theorem~\ref{thm:complete-cap}.
Deployment determines which inputs and choices can occur independently, just
as data placement does in the relational-transducer model.

\subsection{Registers}
\label{app:registers}
Consider two replicas of a register initially holding no value.  Participant
$p$ completes a write of \dog{} while $q$ concurrently completes a write of
\catv.  The replicas exchange both writes, after which a partition separates
them.  Each then serves a local read; both writes complete before either read
begins.

An input is a finite causally closed operation history, ordered by
induced-subhistory extension.  An output is an explanation $(L,\rho)$, where
$L$ is an operation order allowed by the consistency model and $\rho$ maps each
completed read to the write supplying its response.  Refinement extends $L$
without reversing an existing order and extends $\rho$ without changing an
answered read.

For linearizability, $L$ is a total order extending real time
~\cite{herlihy1990linearizability}.  If $p$ returns \catv, its explanation
requires $w_p(x,\dog)<_L w_q(x,\catv)$.  If $q$ returns \dog, its explanation
requires the opposite order.  No total order refines both explanations.  The
partition separates the read owners, recovering the classical CAP impossibility
as the negative side of the Complete CAP theorem
~\cite{gilbert2002cap}.

Under causal consistency, the writes remain concurrent and one explanation can
assign $p$'s read to \catv{} and $q$'s read to \dog{}
~\cite{lamport1978time,ahamad1995causal}.  The responses have a common
refinement.  Two possible answers for the same read remain incompatible, but
only that read's owner selects one; under a deployment in which each
participant holds its own views, no partition separates one local decision
into two independent choices, and the causal register is monotone across
partitions.

\section{Commitment Bases for Two-Phase Locking and Multiversion Timestamp Ordering}
\label{app:cc-bases}

Section~\ref{sec:ambiguity-story} described two-phase locking (2PL) and
multiversion timestamp ordering (MVTO) as two commitment bases for one
specification.  This appendix writes the specification and both bases down.

\paragraph{The specification.}
An input is a finite set $T$ of transactions, each with its operations;
inputs are ordered by inclusion, as transactions arrive.  An output is a pair
$(L,X)$: a set $X\subseteq T$ of aborted transactions and a total order $L$ on
the committed ones, $T\setminus X$, the serialization order.  Outputs are
ordered by extension, $(L,X)\OutputOrd(L',X')$ when $X\subseteq X'$ and $L'$
agrees with $L$ on the domain of $L$: an abort is never undone and an order,
once fixed between two committed transactions, is never reversed.  A row
$(T,(L,X))$ is within spec when $X$ and the domain of $L$ partition $T$.  The
rows $(\{A,B\},([A,B],\varnothing))$ and $(\{A,B\},([B,A],\varnothing))$ of
Figure~\ref{fig:ambiguity-frames}(f) have no common refinement, so the
specification is not monotone, and a system needs commitments.  A
specification that allows no aborts has the same rows with $X=\varnothing$;
we return to it below.

\paragraph{Commitments.}
Each commitment below is a partial function on specification states $(i,R)$ that
retains, at $i$ and at every refinement $k$ of $i$, the rows meeting a
condition, and is applicable when a row at $i$ meets it.  Because refinement
never reverses an order or undoes an abort, no retained row refines a removed
one, so each is a commitment in the sense of
Definition~\ref{def:transition-system} whenever it removes a row.
\begin{itemize}
  \item $\mathsf{order}(A,B)$, for distinct $A,B\in i$: retain the rows in
        which $A\in X$, or $B\in X$, or $A<_L B$.
  \item $\mathsf{commit}(A)$: retain the rows in which $A\notin X$.
  \item $\mathsf{abort}(A)$: retain the rows in which $A\in X$.
  \item $\mathsf{stamp}(A)$, given the set $Z\subseteq i$ of transactions
        stamped before $A$: retain the rows $(k,(L,X))$ in which, for every
        $z\in Z$, $z<_L A$ or one of $z,A$ is in $X$, and for every
        $D\in k\setminus(Z\cup\{A\})$, $A<_L D$ or one of $A,D$ is in $X$.
\end{itemize}
The basis of 2PL is $\mathcal B_{\mathrm{2PL}}=\{\mathsf{order},\mathsf{commit},
\mathsf{abort}\}$ and that of MVTO is
$\mathcal B_{\mathrm{MVTO}}=\{\mathsf{stamp},\mathsf{commit},\mathsf{abort}\}$, each
ranging over all transactions.  A protocol is a policy for applying its basis;
computation decides which commitment to apply, and the commitment is the
irrevocable act.

\paragraph{Two-phase locking.}
When $B$ requests a lock on an item that $A$ holds in a conflicting mode, $B$
waits and the scheduler applies $\mathsf{order}(A,B)$: panel (h) of
Figure~\ref{fig:cc-commitments}.  Nothing is committed about transactions
that have not conflicted; $C$'s position stays open.  When $A$ commits, the
scheduler applies $\mathsf{commit}(A)$ and releases $A$'s locks.  A deadlock is
a cycle of waits, in the simplest case $A$ waiting for $B$ and $B$ for $A$,
which arises when $A$ locked one item ahead of $B$ and $B$ locked another
ahead of $A$; the scheduler has then applied both $\mathsf{order}(A,B)$ and
$\mathsf{order}(B,A)$.  Both are applicable only because the specification
allows aborts: after both, the rows that remain at $i$ are exactly those in
which $A$ or $B$ is aborted, so no row in which both commit survives.  Deadlock
resolution is the choice between them, $\mathsf{abort}(A)$ or
$\mathsf{abort}(B)$, after which the survivor's rows are unconstrained by the
cycle.  Under the specification without aborts, $\mathsf{order}(B,A)$ is not
applicable once $\mathsf{order}(A,B)$ has been made, since it would leave no
row at $i$; the scheduler cannot make the second commitment and $B$ waits
forever.  Whether a system handles deadlock is therefore the choice between
the two specifications, and the abort is a commitment in the basis of the
first.

\paragraph{Multiversion timestamp ordering.}
When $A$ arrives it receives a timestamp larger than every timestamp issued
so far, and the scheduler applies $\mathsf{stamp}(A)$: $A$ is committed to
follow every transaction stamped before it and to precede every transaction
stamped after it, including transactions that have not yet arrived.  Panel (i)
of Figure~\ref{fig:cc-commitments} is $\mathsf{stamp}(B)$ with
$Z=\varnothing$.  Reads never cause a commitment: $A$ reads the version of an
item written by the committed transaction with the largest timestamp below
its own, and if that writer has not yet committed, $A$'s commit waits for it, a
dependency rather than a commitment.  Writes can.  If $A$ writes an item that
some transaction with a larger timestamp has already read, the version $A$
would create should have been visible to that read under the order the stamps
committed; MVTO rejects the write and the scheduler applies
$\mathsf{abort}(A)$.  Our specification records orders and aborts, not read
results, so it does not itself say that the late write is invalid; a
specification whose outputs include read facts, as in
Section~\ref{sec:hat-instance}, would.  When $A$ commits, the scheduler
applies $\mathsf{commit}(A)$.

\paragraph{Comparison.}
The two bases commit different things at different times.  2PL commits a
relative order between two transactions, only when they conflict, and
discovers deadlock as a pair of commitments that leaves only abort rows.  MVTO
commits an absolute position for each transaction on arrival, against every
transaction present or future, and pays for the early commitment with aborts
when execution turns out not to match it.  In both, once every remaining row
at the current input has $A$ committed and in the same position relative to
the other committed transactions, that much of the output is exposable, and
exposing it is an output event, not a further commitment.

\section{Coordination-Free Frontiers}
\label{sec:frontiers}

So far we have taken each interface as given and tested the CALM criteria.  A
designer often faces the inverse question: how much can the interface promise
before coordination becomes unavoidable?  The answer depends on what must stay
fixed.  Here we fix the inputs, visible claims, refinement orders, and---when
partitions matter---the deployment.

We compare interface strength by the behaviors within a specification.  An
interface $T$ is \emph{stronger} than $S$ when every behavior within $T$ is
also within $S$, but not conversely.  The stronger interface rules out more
implementations and gives clients a tighter guarantee.  For example,
linearizability is stronger than causal consistency because it allows fewer
histories.  Thus ``stronger'' corresponds to a smaller set of allowed behaviors.
This is a separate order from output refinement: $o\OutputOrd u$ says that one
particular output $u$ preserves the information already exposed by $o$.

We obtain two frontier results.  The first concerns information arriving over
time: how precisely can an interface answer while preserving every answer it
has already exposed?  The second concerns information arriving independently:
how much cross-node agreement can an interface require without withdrawing any
choice that it still offers locally?

\subsection{Remembering exactly what may remain true}

A small lookup table illustrates both the construction and its possible
compaction.
Suppose a data item initially resides at node $a$ and later moves to $b$.  Let
$o_a$ claim that a lookup starting at $a$ succeeds, and let $o_b$ make the same
claim for a lookup starting at $b$.  The richer output $o_{a\leadsto b}$ records
both that $b$ is the current location and that a lookup from $a$ succeeds by
following its forwarder to $b$.  It therefore preserves both simpler lookup
claims:
        \begin{equation}
  o_a\OutputOrd o_{a\leadsto b},
  \qquad o_b\OutputOrd o_{a\leadsto b}.
  \label{eq:lookup-output-dominance}
        \end{equation}
For $i_0\InputOrd i_1$, the transformation is explicit in
Table~\ref{tab:lookup-lift}.

\begin{table}[t]
  \centering
  \small
  \caption{Remembering every output a lookup relation has allowed so far.
  Dominated outputs can then be dropped without loss of content.}
  \label{tab:lookup-lift}
  \begin{tabular}{@{}c l l l@{}}
    \toprule
    Input & Original fiber $X(i)$ & Remembered $X^\uparrow(i)$
          & Pruned $M(i)$ \\
    \midrule
    $i_0$ & $\{o_a\}$
          & $\{o_a\}$
          & $\{o_a\}$ \\
    $i_1$ & $\{o_b,o_{a\leadsto b}\}$
          & $\{o_a,o_b,o_{a\leadsto b}\}$
          & $\{o_{a\leadsto b}\}$ \\
    \bottomrule
  \end{tabular}
\end{table}

The middle column is the original specification table, grouped into one fiber
per input.  The next column remembers: at each input it collects every
output in the original table at that input or any preceding input.
The last column removes $o_a$ and $o_b$ because the retained
$o_{a\leadsto b}$ refines both.  Nothing they said has been forgotten.  If two
remembered outputs were incomparable, both would have to remain unless another
retained output refined them.

We now state this construction for an arbitrary ordered relational specification
$S\subseteq I\times O$.  Write its original fiber as
        \begin{equation}
  X(i)=S(i)=\{o\in O:(i,o)\in S\}.
  \label{eq:hull-original-fiber}
        \end{equation}
The transformation replaces the output carrier $O$ by $\mathcal P(O)$,
compared under the pointwise lift of Equation~\ref{eq:lifted-output-order}.
Its unpruned output is
        \begin{equation}
  X^\uparrow(i)=\bigcup_{j\InputOrd i}X(j).
  \label{eq:monotone-hull}
        \end{equation}
Equivalently, each original row $(j,o)$ contributes $o$ to the transformed row
at every $i\succeq_I j$.  Literal union remembers all rows; the pointwise lift
captures which outputs they cover.  In particular, one retained output may cover
many remembered rows by refining them.

Call $A:I\to\mathcal P(O)$ a \emph{powerset relaxation} of $X$ when
$X(i)\LiftedOutputOrd A(i)$ at every input: every currently possible output has
a retained refinement.  Such a relaxation is monotone when
$i\InputOrd j$ implies $A(i)\LiftedOutputOrd A(j)$.

\begin{theorem}[Remembered-output frontier]
\label{thm:monotone-hull}
The map $X^\uparrow$ is a monotone powerset relaxation.  Moreover, every monotone
powerset relaxation $A$ covers every output seen so far:
        \begin{equation}
  X^\uparrow(i)\LiftedOutputOrd A(i)
  \qquad\text{for every }i.
  \label{eq:hull-coverage}
        \end{equation}
If $X^\uparrow(i)$ is finite, let $M(i)$ contain its undominated elements.  Then
$M(i)$ and $X^\uparrow(i)$ are equivalent under $\LiftedOutputOrd$, the map $M$
is monotone, and $M(i)$ is the unique smallest subset of $X^\uparrow(i)$ that
covers all of $X^\uparrow(i)$.
\end{theorem}

\begin{proof}
The union includes $X(i)$, so $X^\uparrow$ is a relaxation.  If
$i\InputOrd k$, every predecessor of $i$ is also a predecessor of $k$; hence
$X^\uparrow(i)\subseteq X^\uparrow(k)$, which implies monotonicity under
$\LiftedOutputOrd$.

Now let $A$ be any monotone powerset relaxation and take
$o\in X^\uparrow(i)$.  Some $j\InputOrd i$ has $o\in X(j)$.  Relaxation gives
an $a\in A(j)$ with $o\OutputOrd a$, and monotonicity gives a
$b\in A(i)$ with $a\OutputOrd b$.  Thus $b$ refines $o$, proving
Equation~\ref{eq:hull-coverage}.

For a finite set, every element is below an undominated element.  Therefore
$X^\uparrow(i)\LiftedOutputOrd M(i)$; the reverse direction follows from
$M(i)\subseteq X^\uparrow(i)$.  The same observation proves monotonicity of $M$.
Finally, any subset of $X^\uparrow(i)$ that covers an undominated element must
contain that element itself.  Every covering subset therefore contains $M(i)$,
which proves minimality and uniqueness.
\end{proof}

The theorem's perhaps surprising content is minimality.  Remembering all prior
outputs is an obvious safe construction, but every monotone relaxation must
preserve their content under the output order.  Dominance is the only free pruning available
when representatives must come from the remembered outputs; further pruning
requires introducing some other output in the specification that refines what was removed.

\subsection{Persistent forwarding in search structures}

B-link trees provide a concrete systems instance.  During a node split, a parent
may still direct a search to the old node.  The tree remains searchable because
the old node carries a high key and a right link to the new range; the parent
can be repaired later~\cite{lehman1981efficient}.  In other words, the
implementation preserves an old search starting point even though it is no
longer exact.

We can state the required invariant without committing to one tree algorithm.
Inputs are finite prefixes $h$ of legal restructuring histories.  For a key $k$
and stable search position $p$, put $(k,p)$ in $R(h)$ when the key-directed
search procedure can start at $p$ and follow a finite path to a current
occurrence of $k$.  A restructuring step must satisfy three obligations:
\begin{enumerate}
  \item exposed search positions retain stable identities;
  \item every old key-directed edge is replaced by a key-directed path; and
  \item every old occurrence of $k$ can reach a current occurrence of $k$.
\end{enumerate}
The last two obligations allow paths to change while preserving their meaning.
Deletion or reclamation needs a separate seal or lifetime mechanism because it
can violate them.

\begin{proposition}[Persistent-forwarding monotonicity]
\label{prop:persistent-forwarding}
If the three obligations hold, then $h\InputOrd h'$ implies
$R(h)\subseteq R(h')$.  Positive forward-reachability claims are therefore
monotone, and by Functional CALM the specification is consistent.
\end{proposition}

\begin{proof}
Take a search path valid at $h$.  At $h'$, replace each old edge by the path that
simulates it.  From the old terminal occurrence, follow the preserved path to a
current occurrence.  The concatenated path validates the original search
claim.
\end{proof}

This positive result meets the remembered-output frontier.  For a fixed key in
a split-only migration chain, let $X(g)$ be the exact search certificates at
prefix $g$.  Every historical certificate in $X^\uparrow(h)$ has a refinement
in $R(h)$, namely its current forwarding path:
        \begin{equation}
  X^\uparrow(h)\LiftedOutputOrd R(h).
  \label{eq:forwarding-hull}
        \end{equation}
Theorem~\ref{thm:monotone-hull} says that any monotone relaxation must provide
this coverage.  Current forwarding paths may compact many obsolete
certificates by dominating them, just as in Table~\ref{tab:lookup-lift}.  This is deliberately a
split-only statement.  Full implementations with deletion, merging, or memory
reclamation must prove stronger lifetime invariants or coordinate before old
search positions are reclaimed.

\subsection{Preserving independent local choices}

A second small example captures the cross-node question.  Suppose replicas $p$
and $q$ may each expose configuration 0 or 1.  With no cross-replica constraint,
the four complete outputs are
        \begin{equation}
  (0,0),\quad(0,1),\quad(1,0),\quad(1,1).
  \label{eq:product-config-example}
        \end{equation}
Now strengthen the interface by requiring both replicas to expose the same
configuration.  Only $(0,0)$ and $(1,1)$ remain.  Each replica still appears to
have both local choices, so the strengthening has changed no one-replica
interface.  During a partition, however, $p$ may choose 0 while $q$ chooses 1.
The mixed pair $(0,1)$ is locally legal but globally forbidden, and no output
can preserve both choices.  The new global constraint therefore requires
agreement or sacrifices one of the advertised local choices.

The theorem generalizes this example.  Fix a finite participant set $P$.  At
input $i$, let $V_p(i)$ be the complete views locally available to participant
$p$.  The baseline \emph{product interface} contains every combination of local
views.  A stronger interface may remove combinations.  We call it locally
conservative when it leaves each one-participant interface unchanged and adds
only cross-participant constraints.

For the formal result, assume three local properties:
views can continue when input grows; complete views are maximal under local
refinement; and locally co-occurring claims of one owner have a common local
refinement.  The product interface consists of every tuple in
$\prod_{p\in P}V_p(i)$ and every partial tuple obtained by omitting coordinates.
A \emph{normalized strengthening} $T$ selects some complete product tuples and
contains exactly their partial restrictions.  Local conservativity means that, at
every input, the projection of $T$ onto coordinate $p$ remains all of $V_p(i)$.

\begin{theorem}[Independent-product frontier]
\label{thm:product-frontier}
Suppose each coordinate has one owner, every relevant group of owners can be
separated by a legal partition, and availability permits every local choice.  The product interface is monotone across partitions, so by
Theorem~\ref{thm:complete-cap-deployment} it remains available and consistent
under every partition.  Every proper normalized, locally conservative
strengthening is not monotone across partitions.
\end{theorem}

\begin{proof}
For the product interface, take any family of choices that a partition can
separate.  Claims made by one owner have a common local refinement by assumption;
claims of different owners occupy different coordinates and can simply be put
in the same tuple.  Continue each coordinate at the common refined input.  The
resulting tuple preserves the whole family, as monotonicity across partitions
requires.

Now let $T$ be a proper strengthening.  Some complete product tuple $x$ is
missing from $T$.  Local conservativity says that every coordinate $x_p$ is
still locally available to its owner, perhaps as part of a different tuple in $T$.  A partition can separate those owners, and availability lets each choose
its coordinate.  If their selections had a common $T$-refinement, normalize and
complete it.  Maximality of the coordinates forces the result to be exactly
$x$, the tuple that $T$ forbids.  Hence the separated family has no common refinement in $T$.
\end{proof}

\paragraph{A register frontier.}
The abstract product has a direct consistency interpretation.  For each process
$p$, let $V_p(i)$ contain the register views that are individually explainable
by some legal real-time-respecting execution.  A view records the source write
for $p$'s reads, but it need not order concurrent writes in the same way as
another process.  The product interface allows all combinations of these
individually legal views.  Downward-closed history extension preserves old
views, so this causal-view interface is monotone across partitions when each
read has a unique owner.

Linearizability keeps every one-process behavior but adds one cross-process
requirement: all views must be projections of a single global total order.  In
the execution from Appendix~\ref{app:deployment}, one read forces
$\dog<\catv$ and the other forces $\catv<\dog$.  Each local view is legal alone,
but their pair has no global explanation.  Linearizability therefore removes a
product tuple and crosses the frontier.

The qualification is important.  A system can avoid this obstruction by
removing a local choice, assigning the choice to one authority, restricting
the deployment, or forbidding only combinations that a partition cannot
separate.
The theorem does not rank every consistency model.  It identifies the exact
cost of adding cross-participant constraints while promising to preserve all
local behavior.

\section{Additional Applications}
\label{app:additional-applications}

The examples below show how the same two questions recur in classical
distributed tasks: can each choice survive more input, and can independent
choices survive together?  We isolate those obstructions here.  The
results do not replace model-specific theorems about failures, computability, or
termination.

\subsection{One commitment, then monotone authority}

Agreement protocols illustrate one distributed form of coordination.  Before an
authority is established, several incompatible authority lineages may remain
possible.  Publishing one lineage rules the others out: that is a commitment.
Suppose the commitment fixes both the initial authority and a rule that uniquely
determines every certified successor.  The system can then expose three kinds
of growing evidence: a certified epoch chain $E$, votes or certificates $V$,
and decisions $D$ indexed by epoch and slot.  Define refinement by
        \begin{equation}
  (E,V,D)\OutputOrd(E',V',D')
  \quad\Longleftrightarrow\quad
  E\preceq_{\rm pref}E',\quad V\subseteq V',\quad D\subseteq D'.
  \label{eq:authority-refinement}
        \end{equation}
Protocol safety ensures that a later certificate extends the unique lineage and
preserves prior decisions.  Public authority changes are therefore refinements,
not revisions: votes, certificates, epochs, and decisions all accumulate after
the initial commitment.

This statement does not claim that later certificates are free.  Producing one
may require communication and agreement.  It says something more specific:
later protocol work does not choose among remaining output alternatives or
retract a public result.  If the first commitment did not fix a unique
succession rule, competing next epochs would present another output choice
and require another commitment.

\subsection{Why $k$-set agreement needs finite families}

Consensus forbids two different decision values.  The more general $k$-set
agreement task allows at most $k$ values, which makes pairwise examples
misleading when $k>1$.  Fix $k\geq1$, at least $k+1$ participants, and $k+1$
distinct valid proposals $v_1,\ldots,v_{k+1}$.  Outputs are irrevocable partial
decision maps $m:P\rightharpoonup V$, ordered by extension, with at most $k$
values in their range.

At participant $p_r$'s local proposal input, the decision
$\{p_r\mapsto v_r\}$ is within spec.  The union of all proposal inputs is a common
input refinement.  Each local decision can continue there by itself, and any
family of at most $k$ distinct decisions can coexist.  The family of all $k+1$
cannot: every common refinement would preserve $k+1$ values and violate the
specification.  This is exactly the obstruction detected by Lifted
Monotonicity.  If a partition lets the owners decide independently, the
same family witnesses the negative side of Complete CAP.  Consensus is the
special case $k=1$.

This argument identifies the incompatibility in the specification.  Classical wait-free and
topological impossibility theorems additionally depend on a computation model,
failure assumptions, and progress requirements~\cite{saks2000set}.

\subsection{Membership-sensitive naming}

Tight strong renaming presents a different source of incompatibility.  The input
is the finite participant set $P$, ordered by inclusion.  The common output
universe contains finite partial naming maps; at input $P$, legal outputs are
injective maps
        \begin{equation}
  m:P\longrightarrow\{1,\ldots,|P|\},
  \label{eq:tight-renaming}
        \end{equation}
ordered by map extension.

Now start two processes independently.  At input $\{p\}$, tightness forces the
only name $p\mapsto1$; at input $\{q\}$ it likewise forces $q\mapsto1$.  The
combined input $\{p,q\}$ refines both singleton inputs.  Either assignment can
continue alone by giving the other process name 2, so Relational Monotonicity
is not the problem.  They cannot continue together: an injective map cannot
preserve both assignments to name 1.  Complete CALM fails on this two-row family,
and a deployment that places $p$ and $q$ in different components gives the
corresponding Complete CAP obstruction.

Notice why simply extending one completed naming is not a witness.  If $n$
processes already use names $1$ through $n$, a new process can receive $n+1$
without changing an old assignment.  The obstruction comes from independent
partial memberships making incompatible early choices.  The classical renaming
hierarchy adds model-specific topological and wait-free conclusions
~\cite{herlihy1991waitfree,herlihy1999topological}.

\subsection{What does a snapshot promise?}

The word ``snapshot'' covers interfaces with very different interface strength.
Consider inputs that are finite downward-closed causal histories, ordered by
induced extension.  A modest \emph{cut} interface outputs a finite
downward-closed subset of the available history as a lower bound on what has
happened.  Old cuts remain legal as history grows, and the union of finitely
many cuts remains downward closed.  This interface satisfies Lifted
Monotonicity and Directed Outputs.

That easy positive result should not be mistaken for a conventional snapshot
implementation.  The cut interface promises neither freshness nor completeness;
it could legally return an old cut.  A stronger interface may promise that a
vector or cut is the complete state at a globally finished boundary.  Under
equality of final answers, another relevant event changes the required result.
Functional CALM then says that the boundary must be sealed before the
completeness claim is exposed.

These are safety statements about two declared interfaces.  A distributed
snapshot protocol must also collect a consistent cut and terminate under its
channel and failure assumptions~\cite{chandy1985distributed}.  An atomic
snapshot records values at a chosen linearization point instead.  Classic
wait-free shared-memory implementations demonstrate that total ordering alone
does not prove a need for coordination; the process, memory, placement, and
failure model all matter~\cite{afek1993atomic}.
