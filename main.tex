\begin{abstract}
When does a distributed system inherently require coordination?  CALM, CAP,
CRDTs, Highly Available Transactions, and invariant confluence give related
answers in different mathematical languages.  This fragmentation has allowed
conventional wisdom to drift away from what the literature actually proves.
It also makes intuitive questions spanning these results hard even to state.

We show how to express these results in one small, common model.  A
specification is simply a relation from inputs to allowed outputs, together
with an order saying when one output can safely extend another without
contradiction.  Complete CALM says that participants can independently
expose every allowed output without coordination exactly when the
specification is monotone with respect to this order.  Complete CAP is the
partitioned corollary: for a locally realizable, choice-complete interface
whose partition model includes a full-coverage partition into disconnected
singletons, consistency, availability, and partition tolerance coexist exactly
under the same monotonicity condition.  The shared test also clarifies
questions spanning these previously separate areas; we illustrate it with
examples covering various pairings.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Coordination occurs when one participant must wait for communication from
another before committing to a choice.  That wait adds latency, and it can
destroy availability when the needed communication must cross a network
partition.  Avoiding unneeded coordination is therefore a central goal in
distributed systems, parallel computing, and databases.  This paper asks
about the intrinsic need for coordination: which specifications allow
implementations without coordination, and which force every implementation
to coordinate?

The CALM Conjecture proposed a crisp answer: consistency can be achieved
without coordination exactly when the computation is
monotone~\cite{hellerstein2010declarative}.  The claim was meant to work in
both directions.  Monotonicity should identify designs that can proceed
without coordination, while non-monotonicity should show where coordination
is unavoidable.  The subsequent CALM theorem~\cite{ameloot2013relational} proved
this connection for Datalog programs deployed as formal relational
transducers.  That result is important, but its machine model is narrower
than the systems principle CALM came to represent~\cite{hellerstein2020keeping}.

CAP followed a similar path.  Brewer stated a broad systems
observation~\cite{brewer2000towards}, while Gilbert and Lynch proved an
impossibility result for linearizable registers~\cite{gilbert2002cap}.  The
gap between the broad observation and the narrow theorem led to years of
confusion~\cite{brewer2012cap}.  Related work developed in still other
languages.  CRDTs make replicated state converge by arranging states as a
join-semilattice and making updates inflationary~\cite{shapiro2011crdt}.
Highly Available Transactions (HATs) identify transaction guarantees that
survive partitions~\cite{bailis2013hat}.  Invariant confluence identifies
when independently executed transactions can merge without breaking an
application invariant~\cite{bailis2014coordination}.

These results clearly share an idea, but their different mathematical
languages make cross-cutting questions hard to answer.  Does CALM really
include CAP: are all three CAP properties possible precisely for
specifications with the right monotonicity property?  Are the associative,
commutative, and idempotent merge laws used by CRDTs required for consistent
operation without coordination, or are they simply one reliable but
restrictive approach?  Does convergent
CRDT storage automatically provide a HAT interface?  Do strong eventual
consistency and HAT availability together preserve application invariants?
We can reduce each question---and other cross-cutting questions---to the
same test: \emph{is the exposed specification monotone?}

The specification model has only two ingredients:
\begin{enumerate}
  \item a relation from system inputs to allowed outputs; and
  \item a partial order saying when one output safely extends another
        without contradiction.
\end{enumerate}
Unlike a function, a system specification may allow several outputs for the
same input.  Leader election may allow any one agreed leader, a transaction
system may allow any serializable schedule, and deadlock resolution may abort
any transaction on a cycle.  As a separate matter, the partial order says
which later outputs can extend earlier ones without contradiction.

The paper's central result is \emph{Complete CALM}: an interface can
independently expose every output its specification allows without
coordination exactly when the specification is monotone.  This establishes
monotonicity as the general criterion for coordination freedom at an
exposure-complete interface.  \emph{Complete CAP} is the banner corollary: if
the partition model admits a full-coverage partition into disconnected
singletons, the availability question exposes exactly the independent choices
already tested by Complete CALM.  For a locally realizable, choice-complete
interface, all three CAP properties therefore coexist exactly when the
specification is monotone.  Explicit encodings of CRDTs, HATs, and
invariant confluence then show which input--output relation each discipline
constrains, which common extension it supplies, and where its conclusion
depends on a progress premise or a prescribed merge.

\section{Two Registers, One Lesson}
\label{sec:registers}

A familiar register example shows the main idea without much notation.  The
same execution can be safe under one specification and unsafe under another.
The issue is not whether replicas display different outputs.  The issue is
whether one later allowed output can extend both exposed outputs.

Consider a register replicated at processes $p$ and $q$, initially undefined.
Process $p$ writes \dog, process $q$ concurrently writes \catv, and the
replicas exchange the writes later.  The events carry Lamport's familiar
partial order: local program order, send-to-receive order, and all ordering
implied by those relations~\cite{lamport1978time}.  The writes are concurrent
because neither happens before the other.

Under linearizability, the system must behave as if all operations occurred
in one total order~\cite{herlihy1990linearizability}.  Suppose $p$ has
received $q$'s write and a read returns \catv.  Every total order consistent
with that result places the \dog\ write before the \catv\ write.  At the same
time, $q$ can receive $p$'s write and, using only its local information,
return \dog.  That result requires the opposite write order.  Either result
is allowed by itself, but no single total order explains both.  Once clients
have seen both reads, neither can be withdrawn.  The processes must therefore
agree on a write order before exposing the reads: they must coordinate.

Now replace linearizability with causal consistency~\cite{ahamad1995causal}.
An output is no longer one total order.  It is a collection of per-process
\emph{causal views}.  Each view contains operations and everything that
happens before them.  A read may return any write in its view that no later
causal write replaces; either concurrent write may be chosen.  All views are
parts of one causal order, and combining two causally closed parts creates no
cycle or new ordering requirement.  The two reads can therefore coexist:
$p$'s view explains \catv, $q$'s view explains \dog, and a later view can
contain both without revising either.

The lesson is simple.  The replicas returned different outputs under both
specifications, so difference alone does not force coordination.  Under
causal consistency, neither view extends the other, but a later view extends
both.  Under linearizability, neither total order extends the other, and no
allowed total order extends both.  We call the causal outputs
\emph{compatible} and the linearizable outputs \emph{incompatible}.
Coordination is forced by incompatibility, not by difference.

\section{Specifications, Commitments, and Monotonicity}
\label{sec:model}
We define a specification as nothing more than a mapping from inputs to outputs,
with an ordering on outputs that defines non-contradiction.

Let $I$ be the set of inputs and $O$ the set of outputs visible outside the
system. The types of inputs and outputs may union together various ``API''s.
An input may, for example, identify a query, register instance, replicated
object, or database instance.  Outputs, similarly, may be values, operation
orders, database states, or sets of facts.

\begin{definition}[Specification]
A \emph{specification} is a relation $S\subseteq I\times O$.  For each input
$i$,
\[
  S(i)=\{o\in O:(i,o)\in S\}
\]
is the nonempty set of outputs allowed for input $i$.  Each $S(i)$ is fixed:
receiving other inputs does not change it.  We pair $S$ with a partial order
$\Ord$ on outputs, called the \emph{extension order}.  We read $o\Ord o'$ as
``$o'$ safely extends $o$ without contradiction.''
\end{definition}

Different API inputs may use different output types and extension orders.
Formally, take $O$ to be the disjoint union of tagged domains
$\{i\}\times O_i$, and define the global order only within one tag:
\[
  (i,o)\Ord(i',o')
  \quad\Longleftrightarrow\quad
  i=i'\ \text{and}\ o\Ord_i o'.
\]
We normally suppress the input tag and write $o\Ord o'$ inside one $S(i)$;
write $o\prec o'$ when also $o\ne o'$.  Thus a lattice order for one object,
set inclusion for one query, and equality for an acknowledgment coexist as
one partial order on the disjoint output domain.

The order says which outputs can safely follow which; it does not rank one
output as better or worse than another.  For the linearizable register, a
total operation order extends an earlier one by adding operations without
reordering those already present.  For causal consistency, a view extends an
earlier view by adding operations and causal edges without changing earlier
observations.

\begin{definition}[Commitment]
A \emph{commitment} irrevocably restricts the continuations allowed for the
current execution.  Exposing $o\in S(i)$ creates an \emph{exposure
commitment}: every output $u$ that later resolves the accumulated exposures
for $i$ must satisfy $o\Ord u$.  Thus any pair $(i,u)$ with $o\not\Ord u$ is
unavailable as the resolving output; in particular, every strict predecessor
$(i,o')$ with $o'\prec o$ is ruled out.
\end{definition}

The only commitments we need consider in this paper are exposure
commitments.  A participant may expose $o\in S(i)$ only after receiving $i$,
but receiving an input neither forces an exposure nor rules out any pair.
The lower-bound obligation is the formal sense in which exposure is
irrevocable.  It does not prohibit another participant from exposing an
output incomparable with $o$: neither incomparable output need itself be the
final resolution.  The two exposures can coexist exactly when some later
allowed output extends both.  This distinction is why row removal alone is
not the compatibility test.

For one input $i$, consider participants $p_1,\ldots,p_k$ that each receive
$i$ and independently expose outputs $o_1,\ldots,o_k\in S(i)$.  Their
exposure commitments are compatible exactly when the outputs have a common
extension $u\in S(i)$:
\[
  o_j\Ord u
  \qquad\text{for every }j.
\]
Because $u$ extends every $o_j$, none of the exposure commitments rules out
$(i,u)$.  If no such $u$ exists, at least one participant must wait for
communication before making its exposure commitment.

Complete CALM analyzes an \emph{exposure-complete} interface: absent
coordination, every finite assignment of individually allowed outputs in
$S(i)$ to participants receiving the same $i$ is a declared possible choice.
If two choices are correlated, the encoding must place their cumulative
visible facts in one joint output, as the observer records below do.  An
implementation that suppresses choices implements a narrower relation.

\begin{definition}[Monotonicity]
\label{def:monotone}
A specification $(S,\Ord)$ is \emph{monotone} when, for every input $i$ and
every finite collection $o_1,\ldots,o_k\in S(i)$, there is an output $u$
such that
\[
  u\in S(i)
  \quad\text{and}\quad
  o_j\Ord u
  \qquad\text{for every }j.
  \tag{1}
\]
\end{definition}

Thus $S(i)$ is finitely directed under $\Ord$ for each input $i$.  The finite
condition matters because pairwise common extensions need not yield one
output extending every exposure.  Different inputs remain independent: the
common extension may be different for each input.  This is a finite-prefix
safety criterion: after every finite execution prefix, the exposures so far
must have a common allowed extension.  Requiring one limit output for an
infinite execution would additionally need directed-completeness or a
continuity assumption, which we do not make.

\begin{definition}[Coordination]
\emph{Coordination} is waiting for communication before making an exposure
commitment.  Such waiting is required when participants could otherwise
expose, for the same input, a finite collection of outputs with no common
extension in $S(i)$.
\end{definition}

Communication that does not delay an exposure commitment is not coordination.
In particular, participants may exchange data and extend their outputs after
exposure.

\begin{theorem}[Complete CALM]
\label{thm:calm}
For an exposure-complete interface, participants can safely expose every
allowed output without coordination exactly when the specification
$(S,\Ord)$ is monotone.
\end{theorem}

\begin{proof}
Suppose the specification is monotone.  For any input $i$, Equation~(1) gives
an allowed common extension for every finite collection of outputs exposed
independently for $i$.  The resulting exposure commitments are compatible,
so no participant must wait for another participant's choice before making
its own.

Now suppose the specification is not monotone.  Then some input $i$ has a
finite collection of allowed outputs with no common extension in $S(i)$.
Participants that receive $i$ may expose those outputs independently.  Their
exposure commitments would be incompatible, so preventing that outcome
requires at least one participant to wait for communication before making
its commitment.  That wait is coordination.
\end{proof}

Complete CALM applies to the interface as declared.  If an implementation
suppresses some outputs in $S(i)$, it implements a narrower relation, and
monotonicity must be checked on that relation instead.  The theorem does not
provide an algorithm or guarantee liveness.

\section{Complete CAP}
\label{sec:cap}

CAP asks what happens when a partition removes communication from the critical
path.  Here \emph{consistency} means that, for each input, every finite set of
exposed outputs has a common allowed extension.  \emph{Availability} means that
every required request at a nonfailed component eventually returns without
waiting for a message across the cut; silence for the duration of a partition
does not count.  \emph{Partition tolerance} requires both properties for every
allowed partition.

At the interface under test, $S(i)$ is exactly the set of advertised output
choices.  Two assumptions keep the result honest.  A response policy is
\emph{locally realizable} if, under the stated failure and scheduling
assumptions and ignoring cross-component consistency, every nonfailed
component can eventually discharge each required request using only local or
intra-component steps.  The interface is \emph{choice-complete} if no choice
in $S(i)$ may be suppressed merely to avoid a conflict.

Now admit the strongest partition: every participant is a disconnected
singleton.  We call it \emph{full-coverage} when, for each input $i$, every
finite assignment $o_1,\ldots,o_k\in S(i)$ can be exposed at singleton
components that receive $i$.  Singleton topology alone is not enough; input
placement and the response policy must provide this coverage.

\begin{corollary}[Complete CAP]
\label{thm:cap}
For a locally realizable, choice-complete interface under a partition model
with a full-coverage singleton partition, consistency, availability, and
partition tolerance can coexist exactly when $(S,\Ord)$ is monotone.
\end{corollary}

\begin{proof}
If $(S,\Ord)$ is monotone, Complete CALM lets every choice in $S(i)$ be
exposed without waiting for another participant's choice, and local
realizability supplies the required partition-local progress.  If it is not
monotone, Equation~(1) has a finite incompatible collection.  Full coverage
gives a singleton execution that exposes those choices; availability requires
the requests to return, and choice completeness forbids deleting a choice to
avoid the conflict.  With no common extension, consistency must fail unless
some component waits or suppresses a promised choice.
\end{proof}

Thus CAP is not a separate coordination criterion.  At the strongest
partition, it is CALM with an availability obligation: the same monotonicity
boundary tells us exactly which interfaces can remain both consistent and
responsive.  If a deployment admits only weaker partitions or fewer response
choices, monotonicity remains sufficient but may cease to be necessary; only
collections that can actually straddle a cut need be compatible.

\paragraph{Recovering the register result.}
For a register, group $\mathsf{write}(r,\ell,x,v)$ and
$\mathsf{read}(r,\ell,x)$ calls by execution $r$, and expose their cumulative
visible trace through $\mathsf{observe}_{\mathrm{lin}}(r,x)$.  Its relation is
\[
  S(\mathsf{observe}_{\mathrm{lin}}(r,x))
  =\{h:\text{some total order linearizes $h$}\},
  \qquad
  h\Ord h'\Longleftrightarrow h\preceq_{\mathrm{tr}}h'.
\]
Returning a call response exposes a cumulative observer trace that contains
the call and response; there is no independent response row.  The
linearization is only a witness that the trace is legal.  In the
Gilbert--Lynch execution, one singleton completes a write while another must
answer a read without hearing about it~\cite{gilbert2002cap}.  The resulting
completed-write/stale-read trace has no linearization, so the full-coverage
partition exposes the non-monotone witness.  Causal consistency changes the
observer relation: causally closed local views can be combined without
revising either read.
The corollary therefore recovers classical CAP for linearizable registers and
also explains why weaker consistency models can remain available.

\section{Monotonicity Across the Literature}
\label{sec:instances}

We now put the actual API on each result.  A self-contained response such as an
acknowledgment gets its own row in $S$ only when correctness does not relate it
to another call.  Otherwise a stable $\mathsf{subscribe}$ or
$\mathsf{observe}$ row is the sole semantic output for the execution:
returning a call response exposes an extended trace containing that call and
response.  Per-call response sets are only projections of this row, not
independent inputs whose choices can be multiplied.

Related calls carry an opaque execution identifier $r$.  Semantically, $r$
names a fixed universe $E_r$ of invocations and environment order edges, but
it reveals no future workload.  Observer traces grow by adding facts from
$E_r$ while preserving every response and order edge; write
$h\preceq_{\mathrm{tr}}h'$ for this extension.  A trace may learn a remote or
concurrent event, but cannot invent a call or rewrite an exposed response.
The criterion compares alternatives only when the response policy lets
participants expose them independently.  Otherwise exposure completeness---
or, for Complete CAP, full coverage---is absent, so monotonicity remains
sufficient but the corresponding necessity claim does not apply.  These
conventions are shared by the examples in Table~\ref{tab:instances}.

\subsection{CALM: Show the Evidence}

For a query instance $q$ with finite EDB $D_q$, facts arrive through
$\mathsf{insert}(q,f)$ and answers through $\mathsf{subscribe}(q,Q)$.  The
identifier $q$ names the instance; it does not carry the database.  Inserts
only acknowledge receipt.  A certified subscription pairs each answer with
the facts currently known:
\[
  S(\mathsf{insert}(q,f))=\{\mathsf{Ack}\},\qquad
  S(\mathsf{subscribe}(q,Q))
    =\{\langle J,Q(J)\rangle:J\subseteq D_q\}.
\]
Order these outputs by
\[
  \langle J,A\rangle\Ord\langle K,B\rangle
  \quad\Longleftrightarrow\quad J\subseteq K\ \text{and}\ A\subseteq B.
\]
The evidence $J$ is visible output, not a hidden witness.

If $Q$ is monotone, pooling local evidence $J_1,\ldots,J_k$ yields the common
extension
\[
  \left\langle\bigcup_jJ_j,
  Q\!\left(\bigcup_jJ_j\right)\right\rangle.
\]
If $Q$ is not monotone, choose $J\subseteq K$ with
$Q(J)\nsubseteq Q(K)$ and an instance with $D_q=K$.  The outputs
$\langle J,Q(J)\rangle$ and $\langle K,Q(K)\rangle$ have no common extension.
Thus Equation~(1) is ordinary query monotonicity provided every finite EDB
$D$ has some identifier $q_D$; with a smaller workload, the result is relative
to the represented instances.

The relation permits the pooled answer but does not force more facts or
subscription progress.  Hiding $J$ declares a different output relation.  For
that bare interface, the relational-transducer CALM theorem gives the classic
operational result~\cite{ameloot2013relational}.

\subsection{CRDTs: A Built-In Reconciliation}

A state-based CRDT exposes
\[
  \mathsf{update}(x,a),\qquad
  \mathsf{merge}(x,m),\qquad
  \mathsf{subscribe}(x),
\]
where $x$ names the object, $a$ is an inflationary local update, and $m$ is
the sender's accumulated lattice state~\cite{shapiro2011crdt}.  Receiving
$m$ in state $s$ produces $s\sqcup m$.  No request identifiers are needed in
this relation: each update call is a distinct event, while idempotent join
makes duplicate delivery of the same merge state harmless.  The update
mutator itself need not be idempotent.

Updates and merges acknowledge local completion; subscriptions expose the
legal state lattice $L_x$:
\[
  S(\mathsf{update}(x,a))=S(\mathsf{merge}(x,m))=\{\mathsf{Ack}\},
  \qquad S(\mathsf{subscribe}(x))=L_x.
\]
Acknowledgments use equality, while $s\Ord t$ exactly when $s\sqsubseteq t$.
For states $s_1,\ldots,s_k$, the join
\[
  u=\bigsqcup_{j=1}^{k}s_j
\]
is a legal common extension.  Associativity, commutativity, and idempotence
make it independent of message grouping, order, and duplication.  This is a
safety result: it permits $u$ but does not force state exchange or advance a
stale subscription.

CRDTs provide more structure than Complete CALM requires.  Equation~(1) asks
for some common extension; a semilattice provides a uniform \emph{least} one.
For example, let $S(i)=\{a,b,c,d,\top\}$ with
\[
  a\prec c,\quad a\prec d,\quad b\prec c,\quad b\prec d,\quad
  c\prec\top,\quad d\prec\top,
\]
and no other strict comparisons beyond those implied transitively.  Every
finite set extends to $\top$, but $a$ and $b$ have two incomparable minimal
extensions $c$ and $d$, hence no least extension.  The relation is monotone
without being a join-semilattice.

This argument concerns the state interface.  Exact reads that affect later
updates have their own output relation and monotonicity
test~\cite{lamport1978time,laddad2022keep}.

\subsection{HATs: Separate Safety from Progress}

HATs distinguish what transaction histories are safe from which calls must
finish during a partition~\cite{bailis2013hat}.  The API is
\[
  \mathsf{begin}(r,d,T),\quad
  \mathsf{read}(r,d,T,\ell,x),\quad
  \mathsf{write}(r,d,T,\ell,x,v),\quad
  \mathsf{commit}(r,d,T),\quad
  \mathsf{abort}(r,d,T).
\]
Here $d$ includes the configured initial state, while $r$, $T$, and $\ell$
identify the execution, transaction, and operation; none reveals the future
workload.

For guarantee $G$ and session, contact, and failure assumptions $\Gamma$,
the HAT policy $P_\Gamma$ fixes the response choices advertised during a
partition.  Let $i=\mathsf{observe}_{G,\Gamma}(r,d)$.  Its outputs are the
transaction traces admitted by $G$ that use those choices:
\[
  S(i)=\{h:h\text{ is a $G$-admitted observer trace of $r$ on $d$ whose}
              \text{ responses are advertised by $P_\Gamma$}\},
  \qquad h\Ord h'\Longleftrightarrow h\preceq_{\mathrm{tr}}h'.
\]
For readability, the response set for a call $c$ is the projection
\[
  \operatorname{Resp}_i(c)
  =\{\rho:\text{some }h\in S(i)\text{ records $c$ returning $\rho$}\}.
\]
It is not a separate row: returning $\rho$ exposes such a trace $h$.  Begin,
write, and application-abort calls normally return $\mathsf{Ack}$; reads and
commits return the values and outcomes in the exposed relation.

The same policy supplies progress.  A transaction retaining the contacts
required by $\Gamma$ must receive its promised responses without cross-cut
communication; universal system abort is not an escape.  HAT availability
alone requires completion, not every read value that $G$ considers safe, so
choice completeness applies to the policy-advertised relation above.  If the
local policy cannot realize those responses, availability already fails;
otherwise the common-extension test asks whether their observer traces are
jointly safe.

The ordinary and sticky constructions of Bailis et al. supply locally
realizable policies for their positive cases.  Stronger guarantees can fail:
two partition-local histories may each be serializable while their combined
reads and commits form a cycle.  No serializable trace extends both.  CRDT
state convergence does not repair such an exposed read, so a HAT interface
must pass this test independently of its storage layer.

\subsection{Invariant Confluence: Can Valid States Meet?}

Invariant confluence asks whether two replicas that independently reach valid
states can safely merge~\cite{bailis2014coordination}.  The API is
\[
  \mathsf{apply}(r,x,t),\qquad \mathsf{merge}(r,x,m),\qquad
  \mathsf{subscribe}(x),\qquad \mathsf{observe}_{\Phi}(r,x).
\]
Object $x$ is configured with initial state $D_0$, transactions
$\mathcal T$, invariant $\Phi$, and an associative, commutative, idempotent
merge $\sqcup$.  Assume $\Phi(D_0)$ and include zero-step reachability.
A successful apply or merge returns $\mathsf{Ack}$ by exposing the exact audit
transition described below.  Subscriptions separately expose the reachable
states whose entire derivation remains valid:
\[
  S(\mathsf{subscribe}(x))
  =\{D:D\text{ is reachable from $D_0$ using $\mathcal T$ and merges,}
          \text{ with every intermediate state satisfying $\Phi$}\}.
\]

A stale subscription cannot certify internal safety, so the mandatory audit
observer records each successful transition: apply records $D\to t(D)$ and
merge records $D\to D\sqcup m$.  Thus
\[
  S(\mathsf{observe}_{\Phi}(r,x))
  =\{h:\text{every transition has the prescribed result and every reached}
          \text{ state satisfies $\Phi$}\},
\]
ordered by $\preceq_{\mathrm{tr}}$.  Returning each successful
$\mathsf{Ack}$ exposes the corresponding extension of this trace; it is not
an independent acknowledgment row.  An invalid merge therefore cannot return
$\mathsf{Ack}$ and hide behind stale output.

Subscription states use merge absorption:
\[
  D\Ord E\quad\Longleftrightarrow\quad D\sqcup E=E.
\]
The transaction set is $\Phi$-confluent when the prescribed merge of any two
independently reachable valid states is again in the subscription relation.
Associativity then gives, for every finite collection,
\[
  U=D_1\sqcup\cdots\sqcup D_k\in S(\mathsf{subscribe}(x)),
  \qquad D_j\Ord U\ \text{for every }j.
\]
This common extension is permitted, not forced: no merge message need arrive
and no stale subscription need advance.

A uniqueness constraint gives the standard failure: two valid replicas may
allocate the same value, while their merge violates $\Phi$.  That merge has no
legal audit trace; if no valid subscription state extends both allocations,
coordination is unavoidable.  SEC and HAT availability do not prevent this:
they guarantee convergence and transaction progress, not preservation of an
application invariant after reconciliation.

The converse needs the same coverage qualification as Complete CAP.  The
partition policy must expose every independently reachable pair, and the
interface must require $D\sqcup E$---not some alternative valid state---as
their reconciliation.  Without both assumptions, the common-extension test
may pass although the transaction set is not $\Phi$-confluent; the audit still
rejects any invalid prescribed merge.

\section{From Criterion to Program Checker}
\label{sec:practice}

The next pragmatic step is to turn Complete CALM into a program checker or
compiler test.  Progress can come from both directions: certifying programs
that are monotone by construction and finding concrete counterexamples for
programs that are not.

The positive direction is already visible in existing languages and
frameworks.  Positive Datalog programs are monotone, and monotonicity analyses
in Bloom and Hydro identify programs whose outputs can grow without
coordination~\cite{ameloot2013relational,alvaro2011bloom,hydro}.  State-based
CRDTs obtain the same guarantee by placing replica states in a
join-semilattice and requiring updates to be
inflationary~\cite{shapiro2011crdt}.  Mapping a program into one of these
formalisms---or compiling it through a fragment that the formalism
accepts---provides a certificate of coordination freedom.  These approaches
do not cover every monotone specification, but they establish useful
sufficient conditions automatically.

The negative direction is counterexample generation.  A Complete CALM
counterexample has a precise form: one input $i$ and a finite collection of
outputs $o_1,\ldots,o_k\in S(i)$ that participants can expose independently,
but for which no $u\in S(i)$ extends every $o_j$.  This suggests a
model-checking workflow.  A checker can execute or symbolically explore a
program over candidate inputs, message schedules, and partitions; collect the
outputs that may be exposed for each input; and use a declared $S$ and
$\Ord$ to ask whether each collection has an allowed common extension.  A
counterexample identifies both the input and the incompatible exposures that
force coordination.  Open problems include searching large or infinite input
spaces, choosing useful schedule bounds, and representing $S$ and $\Ord$ so
that the common-extension test is decidable and efficient.

A complementary challenge is extracting the specification to be checked.
Recent work studies using LLMs to translate informal statements into
artifacts for proof assistants such as Lean
4~\cite{gulati2024autoformalization}.  It remains open whether similar tools
can recover this paper's higher-level objects---the relation $S$, the
extension order $\Ord$, and the independently exposable outputs---from
working distributed code.  Such extraction would need a checkable
justification, not merely a plausible generated specification, and would
need to surface ambiguities that require a designer to choose the intended
interface semantics.

\section{Conclusion}

The key lever in this paper is not additional machinery, but less.  Prior
work studies coordination through logical languages such as Datalog,
algebraic structures such as semilattices, and operational formalisms such as
I/O automata.  Those formalisms are valuable, but each brings its own syntax
and proof obligations.  By setting that internal structure aside, a
specification can be reduced to input--output pairs and an order $\Ord$ that
says when one output safely extends another.

At that level, monotonicity becomes a universal semantic condition rather
than a property tied to one language or machine model.  Independently exposed
outputs for the same input must have a common allowed extension.  Datalog
fragments, CRDT merge algebras, transaction guarantees, and consistency
models then become different ways to establish---or violate---that one
condition.  Their differences still matter, but they no longer obscure the
shared coordination boundary.

The proof of Complete CALM is consequently almost direct from the
definitions.  That simplicity is a feature of the abstraction, not a defect
in the result.  Model-specific proofs remain essential for connecting a
programming language, protocol, or failure model to its allowed outputs and
extension order.  Once that connection is made, however, the fundamental
obstruction is simple: independent commitments that have no common allowed
extension.  Exposing this obstruction directly sheds broader light than a
more elaborate proof confined to any one formalism.

This viewpoint changes the first question to ask about a distributed
program.  Rather than beginning with the formal tradition in which the
program was written, begin with what its interface may expose and which of
those exposures can coexist.  That small semantic vocabulary provides a
common basis for comparing systems, locating unavoidable coordination, and
building the program checkers suggested in the previous section.

The same abstraction may apply beyond distributed systems and databases.
Generative AI provides a visible example of an ambiguous specification: one
prompt may admit many acceptable token streams.  Viewing those streams as
allowed outputs, exposing each new token is a commitment.  It restricts the
remaining output to streams that extend the visible prefix and rules out
alternatives that were sensible before the token appeared.

Consider the prompt ``What is the population of the capital of Georgia?''
One answer may give the population of Atlanta, interpreting Georgia as the
U.S. state; another may give the population of Tbilisi, interpreting Georgia
as the country.  Those answers make incompatible semantic commitments.  A
third response---``Did you mean the U.S. state or the country?''---preserves
both interpretations instead of choosing between them.

The relevant cost in this setting is not necessarily communication among
participants.  A premature interpretation may cause the user to correct or
repeat the question, spending additional tokens and interaction rounds; a
clarifying question spends tokens immediately but postpones the semantic
choice.  Generation also makes commitments repeatedly, as each visible token
narrows the remaining possibilities.  This suggests a quantitative extension
of the present theory: beyond asking whether commitment is required, ask how
many rounds of commitment a specification requires, and what cost different
commitment strategies incur.
