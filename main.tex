\title{Complete CALM: A Unified Criterion for Coordination}

\author{Joseph M. Hellerstein}
\affiliation{%
  \institution{UC Berkeley \& Amazon Web Services}
  \city{Berkeley, CA}
  \country{USA}
}

\begin{abstract}
When does a distributed system intrinsically need coordination? CALM, CAP,
CRDTs, Highly Available Transactions, and Invariant Confluence each answer part
of this question, but in different formal models, so their answers are hard to
compare or combine.  We put them on common ground.  We provide a minimalist
relational definition of a specification: a table that includes, for each input,
all outputs a system may produce.  Each column carries its own partial order,
saying when one input \inrel another and when one output \outrel another.  A system is
\emph{consistent} when it is confluent: runs whose inputs have a common
\indesc can always catch up to a common state.  Coordination shows up as an
irrevocable \emph{commitment} to constrain the system by removing one or more
rows from the specification table.  Commitments come in two kinds: they either
\emph{seal} input, deciding that potential future inputs will be ignored, as
when a vote is closed to late ballots; or they \emph{choose} among multiple
allowed outputs, as when a system elects a leader or orders transactions.

When each input has only one output, only sealing arises. \emph{Functional CALM}
generalizes the original CALM Theorem from Datalog queries to any function
between ordered domains: such a specification is consistent exactly when it is
monotone, so that more input never retracts an earlier answer, and then no
output ever needs coordination. \emph{Complete CALM} covers ambiguous
specifications that allow several outputs for the same input, where choice
commitments arise too.  There the test becomes \emph{Lifted Monotonicity}: as
inputs \ingrow, the outputs already emitted can always be \outrelpast to a
single output still allowed.

Commitments are explicit in our model, allowing it to check for \emph{Proper
Coordination}: whether a particular use of coordination provides consistency.  A
totally ordered log and a key-value store are each non-monotone, yet agreeing on
the log order makes the combined system monotone and hence consistent without
changing the store. Finally, we turn Brewer's CAP intuition into a theorem for
any consistency guarantee you can write down: a system can keep every allowed
output available and consistent through a network partition exactly when its
specification passes the same test.  Gilbert and Lynch's CAP Theorem is a
special case of this generalization.
\end{abstract}
