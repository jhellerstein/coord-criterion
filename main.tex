\title{Complete CALM: A Unified Criterion for Coordination}

\author{Joseph M. Hellerstein}
\affiliation{%
  \institution{UC Berkeley \& Amazon Web Services}
  \city{Berkeley, CA}
  \country{USA}
}

\begin{abstract}
When does a concurrent system inherently require coordination?  CALM, CAP,
CRDTs, Highly Available Transactions, and Invariant Confluence explore versions
of this question in different formal models, making their conclusions hard to
compare or reuse.  We give them a common declarative framework.  A
specification is a table pairing each input with the outputs it permits, with
inputs and outputs each ordered by refinement.  A specification is
\emph{consistent} when executions it admits can always be brought to a common
state.  Coordination appears in this model as a \emph{commitment}: an
irrevocable decision that rules out possibilities the input still allows and
that no remaining output stands in for.  A commitment does one of two jobs: it
\emph{seals} input, refusing inputs that could still arrive, as when an
official closes the polls; or it \emph{chooses} among permitted outputs, as when
a system picks a leader or a transaction order.

\emph{Functional CALM} generalizes the original CALM Theorem from Datalog
queries to arbitrary functions between ordered domains, so the familiar
monotonicity test no longer depends on the language used to express the
function: a functional specification is consistent exactly when it is
monotone, and then no output ever requires a commitment.  A function permits
one output per input, so its only commitments are seals.
\emph{Complete CALM} handles \emph{ambiguous} specifications that permit several
outputs for one input, where commitments may also choose.  It proves that such
a specification is consistent exactly when it satisfies \emph{Lifted
Monotonicity}: outputs permitted at inputs with a common refinement must share
a refinement permitted there.  Functional monotonicity is the special case of
this common-refinement test with one output per input.

Representing commitments also lets us verify \emph{Proper Coordination}: whether
a chosen use of coordination is sufficient.  Totally ordered logging and
key-value stores are both non-monotone, yet committing to their shared log order
makes the composed system monotone and consistent.  Finally, Complete CALM
yields a Complete CAP theorem that makes Brewer's intuition precise for any
declared consistency guarantee: a system can keep every output its
specification permits available and consistent through network partitions
exactly when the specification passes the common-refinement test.  Gilbert and
Lynch's register impossibility appears as the special case in which a partition
forces a replica to answer before it can see a conflicting write.
\end{abstract}
